Tools

Every off-the-shelf tool in the stack: why we picked it, what it does for us, how it is configured in this repository, how to operate it, and where it did not fit and we wrote code instead.

Principle

Use proven open-source tools wherever they exist; write code only for product logic (profiles, mini-app registry, partner notifications). Each section below ends with an honest "what we use" list. The summary table at the end (where a tool did not fit) lists every place where we had to write our own code around a tool.

All containers are defined in docker-compose.yml; all host ports are bound to 127.0.0.1 only. Versions below were read from the running stack on 2026-10-25 (docker compose ps). Config files are bind-mounted read-only from infra/; they must be world-readable (644/755) because containers run as other users (see troubleshooting).

Postgres

built one server, five databases.

Why

All durable state is relational (identities, profiles, templates, notifications, staff, audit), and three of our services need transactions, unique constraints and jsonb (user extra, audit details). One mature server is cheaper to run and back up than one database per service container. Isolation is kept at the database/login level instead: no service can read another's data.

How it is configured here

  • docker-compose.yml service postgres: image, volume postgres_data, healthcheck pg_isready, passwords passed as env variables from .env.
  • infra/postgres/init-databases.sh is mounted into /docker-entrypoint-initdb.d/. For each service it runs CREATE ROLE ... LOGIN, CREATE DATABASE ... OWNER ... and REVOKE ALL ON DATABASE ... FROM PUBLIC.
DatabaseLoginUsed bySchema managed by
kratoskratosOry KratosKratos (kratos-migrate one-shot container)

notificationnotif_svcnotification-serviceFlyway, V1__send_log.sql, V2__partner_platform.sql
registryregistry_svcregistry-serviceFlyway, V1__registry.sql
infisicalinfisicalInfisicalInfisical (its own migrations)

The admin login (POSTGRES_USER in .env, currently adera_admin) is only for operators; services never use it.

Gotcha

The init script runs only on the first start of an empty data volume. A database added to the script later (the registry entry was added after the first four) is not created on an existing volume. The script is idempotent only in the "empty volume" sense, so on an existing machine create the role and database by hand with the same three statements, using the matching *_DB_PASSWORD from .env.

How to operate it

# interactive shell as the admin login, in one database
docker compose exec postgres psql -U adera_admin -d users

# one-off read-only query (this is how the data page examples were captured)
docker compose exec -T postgres psql -U adera_admin -d notification -c "select count(*) from send_log"

# list databases and logins
docker compose exec -T postgres psql -U adera_admin -d postgres -Atc "select datname from pg_database where not datistemplate"
docker compose exec -T postgres psql -U adera_admin -d postgres -Atc "select rolname from pg_roles where rolcanlogin"

# backup one database (production: schedule this and copy it off the machine)
docker compose exec -T postgres pg_dump -U adera_admin -d users | gzip > users-$(date +%F).sql.gz

Verified on the running stack: databases kratos, users, notification, infisical, registry; logins kratos, users_svc, notif_svc, infisical, registry_svc plus the admin.

What we use from it

  • Plain SQL tables, jsonb, unique constraints and INSERT ... ON CONFLICT (race-safe profile creation).
  • Per-recipient OTP rate limiting is done in Postgres too: notification-service counts rows of send_log per recipient hash (limits: SMS 5/hour and 10/day, email 10/hour and 20/day by default). It does not use Redis for this.
  • Table-by-table documentation: Data.

Not done yet: Postgres exporter for metrics, automated backups (see not built yet).

Redis

built used by the gateway and by Infisical. Our Java services do not use it.

Why

The gateway needs counters shared between gateway instances for rate limiting, and Infisical needs a Redis for its job queues (BullMQ) and cron locks. Redis is the standard choice for both. Redis 7 gives us ACL users, which lets one container serve several clients with separate credentials.

How it is configured here

  • infra/redis/entrypoint.sh builds the ACL file at container start from environment variables, so no password is committed or baked into an image, then execs redis-server.
  • infra/redis/redis.conf: maxmemory 256mb, maxmemory-policy noeviction, appendonly yes, appendfsync everysec, protected-mode yes.

The resulting ACL (real, from ACL LIST with password hashes removed):

user admin on #<hash masked> ~* &* +@all
user apisix on #<hash masked> ~plugin-limit-count:* resetchannels +@all -@admin -@dangerous
user default off resetchannels -@all
user infisical on #<hash masked> ~* &* +@all -@admin
ACL userWho uses itRightsWhy
defaultnobodydisabled (off)Redis' built-in user has no password by default; leaving it on would make the instance open to any container.
adminoperators, healthcheckeverythingOperations and the compose healthcheck.
apisixAPISIX limit-count pluginonly keys matching plugin-limit-count:*; no admin or dangerous commandsIf the gateway is ever compromised it cannot read Infisical's queues.
infisicalInfisicalall keys, no admin commandsInfisical's BullMQ key names were not verified, so it is not prefix-restricted (a known loose end).
Why noeviction

With an eviction policy Redis silently deletes keys when memory is full. For us that would mean lost Infisical background jobs or reset rate-limit counters, with no error anywhere. With noeviction, a full Redis refuses new writes with an error that shows up in logs. The cost is that memory must be watched; today it uses about 3 MB of 256 MB. The comment in redis.conf notes that our own keys carry TTLs; in practice the only keys we create are the gateway counters, which expire with their time window.

Gotcha

The Redis ACL file format does not allow comment lines, which is why the explanation sits in the shell script rather than in the generated file.

How to operate it

set -a; . ./.env; set +a      # loads the passwords into your shell (do not echo them)
R="docker compose exec -T redis redis-cli --no-auth-warning --user admin --pass $REDIS_ADMIN_PASSWORD"

$R ping
$R ACL LIST                                   # shows hashes, not passwords
$R CONFIG GET maxmemory-policy                # noeviction
$R info memory | grep -E "used_memory_human|maxmemory_human"
$R --scan --pattern 'plugin-limit-count:*'    # gateway rate-limit counters (exist only while a window is active)
$R dbsize

Only scan by pattern; never print values from the Infisical (bull:*, {cron}:*) keys. To reset a client's rate limit during testing, delete that client's counter key (DEL on the exact key found by the scan).

What we use from it

  • APISIX limit-count with policy: redis: counters under plugin-limit-count:*, shared and persistent across gateway restarts.
  • Infisical's queue and cron state.
  • Verified in the poms: none of the three Java services depends on Redis.

RabbitMQ

set up, not yet used

Why

Planned for events between services (for example user.created, device.registered, push fan-out). Chosen over NATS or Kafka for first-class Spring support and enough scale for our size (SETUP.md section 3).

Honest status

No service publishes or consumes messages today: none of the three poms has an AMQP dependency and the broker has zero queues in vhost adera (checked via the management API). The partner notification queue is implemented in Postgres tables with background workers inside notification-service, not in RabbitMQ. The broker is running, scraped by Prometheus and shown on the Grafana overview ("RabbitMQ messages waiting", currently 0), so that it is ready when the first event is added.

How it is configured here

  • docker-compose.yml: rabbitmq (management image, default admin user from RABBITMQ_ADMIN_USER/RABBITMQ_ADMIN_PASSWORD, volume rabbitmq_data) and the one-shot rabbitmq-setup (a curlimages/curl container that runs infra/rabbitmq/setup.sh and exits).
  • infra/rabbitmq/setup.sh is idempotent (HTTP PUTs): vhost adera, users user_svc and notification_svc (passwords USER_SVC_RABBIT_PASSWORD, NOTIFICATION_SVC_RABBIT_PASSWORD), and permissions configure/write/read = ".*" on that vhost.

Verified: vhosts / and adera; users adera_admin (tag administrator), user_svc and notification_svc (no tags, so they cannot use the management UI, AMQP only). Permissions are wide on purpose for now: narrow them to per-service name prefixes once the topology exists. RabbitMQ 4 only allows durable queues (Spring's default).

How to operate it

# UI: http://localhost:15672  (user = RABBITMQ_ADMIN_USER from .env)
set -a; . ./.env; set +a
curl -s -u "$RABBITMQ_ADMIN_USER:$RABBITMQ_ADMIN_PASSWORD" http://127.0.0.1:15672/api/vhosts
curl -s -u "$RABBITMQ_ADMIN_USER:$RABBITMQ_ADMIN_PASSWORD" http://127.0.0.1:15672/api/queues/adera
docker compose exec rabbitmq rabbitmq-diagnostics -q ping
docker compose run --rm rabbitmq-setup     # re-run the idempotent setup after changing a password in .env

Metrics come from the built-in Prometheus endpoint rabbitmq:15692 (job rabbitmq).

What we use from it

Currently only the broker, vhost, users and metrics. Planned events are listed in not built yet.

Mailpit

built development only.

Why

We need to read the one-time codes and notification emails without sending real mail. Mailpit is a fake SMTP server with a web inbox and an HTTP API; it is one small container and everything stays on the machine. It is not needed in production.

How it is configured here

  • docker-compose.yml service mailpit: MP_MAX_MESSAGES=500 (oldest are dropped), MP_DATABASE=/data/mailpit.db on volume mailpit_data (messages survive restarts), healthcheck /mailpit readyz, SMTP 1025, UI and API 8025.
  • notification-service sends to it over SMTP (SMTP_HOST=mailpit, SMTP_PORT=1025) when EMAIL_PROVIDER=mailpit (class MailpitEmailProvider).
  • Infisical also uses it for its own mail (invites, password reset) via SMTP_HOST=mailpit, sender no-reply@adera.local.

How to operate it

open http://localhost:8025                         # inbox UI
curl -s http://127.0.0.1:8025/api/v1/info          # version and message count
curl -s "http://127.0.0.1:8025/api/v1/messages?limit=5"
curl -s -X DELETE http://127.0.0.1:8025/api/v1/messages     # empty the inbox

Tip: for one-time codes you do not need to open the inbox for phone logins at all; SMS in dev mode goes to the console and GET http://127.0.0.1:8085/dev/messages returns recent codes (see operational endpoints).

What we use from it

SMTP sink plus read API for tests and humans. Switching to real email is EMAIL_PROVIDER=resend; see delivery modes.

Infisical

built self-hosted secrets manager, used for API keys only.

Why

Third-party API keys (Twilio, Resend, our partner response-signing key, later Firebase) should have an audit trail, environments (dev, prod), rotation, and should not sit in git or a world-readable file. Infisical is open-source, self-hostable and has a CLI and an HTTP API.

How it is configured here

  • docker-compose.yml service infisical (pinned to v0.167.2; the moving latest-postgres tag was ten months stale and incompatible with the current CLI). It uses the shared Postgres (database infisical) and Redis (ACL user infisical). SITE_URL is http://localhost:8080 (must change for a real server); telemetry is off; SMTP goes to Mailpit.
  • Its own bootstrap keys INFISICAL_ENCRYPTION_KEY and INFISICAL_AUTH_SECRET live in .env. Losing the encryption key makes every stored secret unreadable; keep an off-machine copy.
  • Project Adera, environments dev and prod (prod is empty), folders /infra, /kratos, /gateway, /notification, /user.
  • Machine identity adera-local-dev (Token Auth) provides INFISICAL_TOKEN; it expires 2026-11-23. Use Universal Auth beyond local dev.

Where Infisical did not fit

The usual way is to wrap the process (infisical run -- docker compose up) or inject secrets into containers. The owner did not want every docker compose command wrapped, so container secrets stay in .env, and we wrote a loader in the service: InfisicalEnvironmentPostProcessor (notification-service, registered in META-INF/spring.factories) calls GET /api/v4/secrets?projectId=...&environment=...&secretPath=... with the machine token before the Spring context exists and adds the result as the lowest-priority property source (a real environment variable always wins). It only activates when INFISICAL_TOKEN, INFISICAL_PROJECT_ID and INFISICAL_DOMAIN are set, logs only a count and never a value, and a failure is a warning, not a crash (a dev-mode service does not need the keys; a real provider without its keys fails fast). Only notification-service uses it today. It pins HttpClient to HTTP/1.1 because Java's default h2c upgrade over plain HTTP gets a 400 from Infisical.

How to operate it

# UI: http://localhost:8080  (first-time sign-up creates the admin; invite mail goes to Mailpit)
set -a; . ./.env; set +a
# list names only (never paste values into chat or docs)
infisical secrets --env=dev --path=/notification --projectId "$INFISICAL_PROJECT_ID" --domain "$INFISICAL_DOMAIN"
infisical secrets set RESEND_FROM_NAME="Adera" --env=dev --path=/notification --projectId "$INFISICAL_PROJECT_ID" --domain "$INFISICAL_DOMAIN"
infisical secrets delete OLD_NAME --type shared --env=dev --path=/notification ...   # needs --type shared
# a secret change reaches the service at its next start:
docker compose up -d --force-recreate notification-service

Step-by-step add/rotate guides are in Guides. The CLI reads INFISICAL_TOKEN from the environment.

What we use from it

  • Secret storage and environments, the CLI/UI for editing, the /api/v4/secrets read endpoint from our loader.
  • Not used: dynamic secrets, injection agents, Kubernetes operator, Universal Auth (planned).

Ory Kratos

built identity, one-time-code login, sessions, authenticator-app (TOTP) second factor.

Why

Login, sessions and second factor are security-critical and easy to get wrong. Kratos is headless (no UI we must theme), API-first (native mobile flows return JSON and a session_token) and supports passwordless login by one-time code over email and SMS. Chosen over Keycloak and SuperTokens for those reasons (SETUP.md section 3).

How it is configured here

Files: infra/kratos/kratos.yml, infra/kratos/identity.schema.json; compose services kratos-migrate (one-shot: migrate sql up -e --yes) and kratos (serve --watch-courier). Secrets DSN, SECRETS_COOKIE, SECRETS_CIPHER come from environment, never from the file.

The registration web hook

registration.after.code.hooks[0] posts to http://user-service:8080/internal/kratos/after-registration with response.ignore: true, which makes it non-blocking: a slow or down user-service can never block a sign-up. The body is a base64-encoded Jsonnet template in the YAML; decoded it is:

function(ctx) { identityId: ctx.identity.id, email: std.get(ctx.identity.traits, 'email', null), phone: std.get(ctx.identity.traits, 'phone_number', null) }

So user-service receives {"identityId":"<uuid>","email":"..."|null,"phone":"..."|null} and creates the profile row whose id is the Kratos identity id. The hook must come before session in the list.

The courier (how codes leave Kratos)

courier.delivery_strategy: http sends every message Kratos wants to deliver to our notification-service, which decides how to deliver it. Three request configs, all POST with base64 Jsonnet bodies. Decoded:

ChannelURLDecoded body template
email (default)http://notification-service:8080/internal/kratos/email{ recipient: ctx.recipient, subject: ctx.subject, body: ctx.body, htmlBody: std.get(ctx,'html_body',null), templateType: std.get(ctx,'template_type',null) }
sms (channels[0])http://notification-service:8080/internal/kratos/sms{ to: ctx.recipient, body: ctx.body, templateType: std.get(ctx,'template_type',null) }

Kratos retries a message when our endpoint answers non-2xx; notification-service therefore returns 502 for real delivery failures (so Kratos retries) and 200 for rate-limited or skipped messages (so Kratos does not retry them). kratos is started with --watch-courier so queued messages are sent by the same process.

How to operate it

docker compose exec kratos kratos version                      # v26.2.0
curl -s http://127.0.0.1:4434/admin/health/ready                 # {"status":"ok"} (admin port, localhost only)
# list identities (admin API; ids are the user ids)
curl -s "http://127.0.0.1:4434/admin/identities?page_size=5" | python3 -m json.tool
# apply migrations manually
docker compose run --rm kratos-migrate
docker compose logs -f kratos

Client-facing flows are documented in Kratos flows; the API spec is docs/kratos-openapi-v26.2.0.json. Prometheus scrapes kratos:4434/admin/metrics/prometheus. After editing kratos.yml run docker compose restart kratos.

Lessons: use migrate sql up -e --yes in Kratos 26; add hook: session under registration.after.code or sign-up returns no session_token.

What we use from it

  • Identities and traits, code login (register/login/verify), sessions and whoami, session list/revoke, TOTP enrol and aal2 upgrade, the admin API (used by user-service as a safety net to create a missing profile, and by logout).
Where Kratos did not fit, so we wrote code
  • Native-app logout hook: Kratos has no hook that runs on API logout, so a device's push token could stay behind. We wrote POST /api/v1/me/logout (LogoutController in user-service): it optionally removes the device, then calls Kratos to revoke the session.
  • Message delivery: Kratos' built-in SMS/SMTP options do not cover Twilio or Resend with our safety rules, so the whole courier is replaced by an HTTP receiver (KratosCourierController in notification-service) that adds per-recipient limits, a live-mode allowlist and a send log.
  • Account enumeration: at login Kratos answers "account does not exist" for unknown identifiers but "code sent" for known ones. Not yet fixed; the plan is a single "continue" endpoint in our backend (see security).
  • Phone and email are separate identities: linking a second identifier is a feature we still have to build.
  • Staff roles are not in Kratos: it only proves who the person is (and aal2); roles live in registry-service.

APISIX

built the single front door (port 9080), standalone mode.

Why

Rate limits, CORS, request ids, "is this a valid session?" and tracing are the same for every service, so they belong in one place, not in each Spring app. Chosen over Kong because standalone mode keeps all configuration in git as a YAML file (no etcd, no database).

How it is configured here

  • infra/apisix/config.yaml: deployment.role: data_plane with config_provider: yaml (no admin API, no etcd), listen port 9080, and the plugin allow-list: request-id, cors, prometheus, opentelemetry, limit-count, forward-auth, proxy-rewrite, mocking. This list replaces APISIX's defaults. Prometheus metrics are exported on container port 9091.
  • infra/apisix/apisix.yaml: four upstreams (kratos-public, user-service, registry-service, notification-service), the opentelemetry exporter settings in plugin_metadata, one global rule (request-id, prometheus, opentelemetry with always_on sampling, CORS for http://localhost:3000) and the routes below.
  • Secrets reach the file through ${{ENV_VAR}} substitution (APISIX_REDIS_PASSWORD, USER_GATEWAY_SECRET); the variables are passed in the compose environment block of apisix.

Counters live in Redis (policy: redis); over the limit the gateway answers 429.

What forward-auth does

Before forwarding, APISIX calls the verify URL with the client's Authorization (and Cookie for user routes) plus X-Gateway-Secret. If that returns 2xx, APISIX copies the upstream_headers (X-User-Id; or X-Staff-Id and X-Staff-Role) onto the forwarded request, overwriting any value the client sent; otherwise the verify response is returned to the client. status_on_error: 503 means that if the verify service itself is unreachable the client gets 503, not a misleading 401. Full trust model: communication.

How to operate it

  • Route changes in apisix.yaml hot-reload within about a second. Check with docker compose logs --tail=20 apisix. A syntax error is logged and the old config stays.
  • Changes to config.yaml (plugin list, ports) need docker compose restart apisix.
  • A new ${{VAR}} must exist inside the container: add it to the compose environment block and run docker compose up -d apisix (restart does not re-read compose environment).
  • Metrics: apisix_http_status, apisix_http_latency_bucket via Prometheus job apisix; the route id appears as a label because of prefer_name.
  • Quick smoke test (this one is allowed anywhere): curl -i http://127.0.0.1:9080/kratos/admin/identities must return 403.

What we use from it

Routing, the five plugins we use for traffic (limit-count, forward-auth, proxy-rewrite, cors, request-id), mocking for the blocked admin path, prometheus and opentelemetry for observability.

Lessons and limits
  • An unknown plugin in a global rule drops the whole rule silently (request-id, CORS and metrics vanish together). Always add the plugin to config.yaml first.
  • Avoid YAML anchors and aliases in apisix.yaml (its parser does not handle them), which is why the Redis settings are repeated in every route.
  • Per-IP limits use remote_addr: locally all clients share the Docker bridge IP, and behind a real proxy they would all share the proxy's IP until the real client IP is configured (deployment checklist item 4).
  • CORS allows only http://localhost:3000 and the headers Authorization, Content-Type, X-Request-Id; the dashboard origin must be added for production.

RustFS

built S3-compatible object storage for files.

Why

Files (avatars, mini-app logos, later more) should not live in Postgres or on a service's local disk. An S3-compatible store lets us use the standard AWS SDK now and move to any S3 provider later by changing an endpoint. Our database stores only the file's id; the object key is derived from it. (SETUP.md records the choice but not the alternatives considered.)

How it is configured here

  • docker-compose.yml service rustfs: data on volume rustfs_data, S3 API on 9000, web console on 9001, access/secret keys from .env (RUSTFS_ACCESS_KEY, RUSTFS_SECRET_KEY).
  • Bucket adera-media. There is no setup container: S3AvatarStorage (user-service) and S3ObjectStorage (registry-service) check the bucket at startup and create it if missing.
  • user-service and registry-service read STORAGE_ENDPOINT (http://rustfs:9000, internal), STORAGE_PUBLIC_ENDPOINT (default http://127.0.0.1:9000, the address phones use for signed links, because the host is part of the signature), and STORAGE_BUCKET (default adera-media).

Keys currently in the bucket (real; the two objects are registry test logos):

python3 -I tests/e2e/s3tool.py list
2 objects
  apps/<app-uuid>/logo/<image-uuid>.png
  apps/<app-uuid>/logo/<image-uuid>.png

Layout: avatars/{user id}/{image id}.jpg (user-service), apps/{app id}/logo/{image id}.png (registry-service). More on the data page.

How to operate it

set -a; . ./.env; set +a                      # s3tool needs RUSTFS_ACCESS_KEY / RUSTFS_SECRET_KEY
python3 -I tests/e2e/s3tool.py list              # all objects
python3 -I tests/e2e/s3tool.py list avatars/     # by prefix
python3 -I tests/e2e/s3tool.py delete <key>      # delete (only for cleaning test data)
# web console: http://localhost:9001 (log in with the access/secret key from .env)

s3tool.py is a dependency-free SigV4 client (path-style, region us-east-1).

What we use from it

PUT/GET/DELETE object, list, head/create bucket, and presigned GET URLs (60-minute avatar links). A request without a valid signature gets 403, which the e2e test verifies.

Notes and open items
  • With the AWS SDK v2 use path-style access, requestChecksumCalculation(WHEN_REQUIRED), and presign against the public endpoint.
  • Both services currently use RustFS's admin keys; create a bucket-scoped key before production.
  • Production must expose only the S3 API (not the console) over HTTPS for phones, or proxy image reads through the gateway.

Prometheus, Grafana, Loki, Alloy, Tempo, OTel Collector

built metrics, logs and traces in one Grafana.

Why a full stack: the system is several containers calling each other; "why didn't it arrive?" needs one place to see the request, its logs and its timings. All six tools are the standard open-source set and need no code from us beyond switching exporters on in Spring and APISIX.

Prometheus

  • Why: the standard pull-based metrics store; every tool we run already exposes Prometheus metrics.
  • Config: infra/prometheus/prometheus.yml, 15 s scrape interval, 15-day retention (--storage.tsdb.retention.time=15d in compose), volume prometheus_data. Jobs: prometheus, apisix (apisix:9091/apisix/prometheus/metrics), kratos (kratos:4434/admin/metrics/prometheus), rabbitmq (:15692), otel-collector (:8888 and :8889), loki, tempo, alloy, and our three services at /actuator/prometheus.
  • Operate: UI http://localhost:9090. Verified on 2026-10-25: every job reports up (12 targets, since otel-collector has two). 
    curl -s http://127.0.0.1:9090/api/v1/targets | python3 -c 'import json,sys;[print(t["labels"]["job"],t["health"]) for t in json.load(sys.stdin)["data"]["activeTargets"]]'
curl -s "http://127.0.0.1:9090/api/v1/query?query=sum(rate(apisix_http_status%5B1m%5D))"
  • Use: gateway rate/status/latency, JVM and HTTP metrics of the Java services, RabbitMQ queue depth. Note: the services export metrics by being scraped, not via OTLP; the collector's metrics pipeline (exposed on :8889) currently carries nothing because only traces are sent to it (OTEL_TRACES_ENDPOINT).
  • Not done: Postgres/Redis exporters, alert rules.

Grafana

  • Why: one UI for metrics, logs and traces, with jumps between them (trace to logs).
  • Config: compose service grafana (admin user admin, password GRAFANA_ADMIN_PASSWORD, sign-up disabled, analytics off), host port 3001. Everything is provisioned from files so a fresh start is identical: infra/grafana/provisioning/datasources/{prometheus,loki,tempo}.yml (uids prometheus (default), loki, tempo; Tempo is configured with tracesToLogsV2 to Loki with a +/- 1 minute window), provisioning/dashboards/dashboards.yml (folder Adera, path /var/lib/grafana/dashboards) and infra/grafana/dashboards/adera-overview.json.
  • The "Adera overview" dashboard (uid adera-overview) has six panels:
    PanelTypeQuery
    Services up (1 = yes)statup
    Gateway requests per second, by status codetime seriessum by (code) (rate(apisix_http_status[1m]))
    Gateway p95 latency (ms)time serieshistogram_quantile(0.95, sum by (le) (rate(apisix_http_latency_bucket{type="request"}[5m])))
    Rate-limited requests (429) in the last hourstatsum(increase(apisix_http_status{code="429"}[1h])) or vector(0)
    RabbitMQ messages waitingstatsum(rabbitmq_queue_messages) or vector(0)
    Recent errors in any containerlogs (Loki){service=~".+"} |~ "(?i)(error|fatal|panic|exception)"
  • Operate: open http://localhost:3001, Dashboards, folder Adera; or Explore and pick a data source. Verified: data sources Loki, Prometheus, Tempo exist and the dashboard is provisioned. Dashboards are read-only from the file (:ro mount): edit the JSON in git, not in the UI.

Loki

  • Why: cheap log storage that indexes only labels, queried from the same Grafana.
  • Config: infra/loki/loki.yml: single node, filesystem storage (volume loki_data), TSDB schema v13, retention 168 h (7 days) enforced by the compactor, ingestion_rate_mb: 16 and burst 32 (the default 4 rate-limits the first-start backlog), no auth (internal network only, no host port).
  • Operate: Grafana, Explore, data source Loki. Labels set by Alloy: container and service (the compose service name). 
    {service="notification-service"}
{service="kratos"} |= "error"
{service=~"user-service|registry-service"} |~ "(?i)exception"
  • Use: all application and tool logs. Services log OTP/recipient data masked, never codes (see the send-log tests).

Alloy

  • Why: the log shipper; chosen over Promtail because Promtail is being retired.
  • Config: infra/alloy/config.alloy: discovery.docker lists containers through the Docker socket, discovery.relabel maps the container name to label container and the compose service label to service, loki.source.docker tails them, loki.write pushes to http://loki:3100/loki/api/v1/push. Volume alloy_data remembers read positions.
  • Security note: it mounts /var/run/docker.sock read-only; that still lets it see every container, and is on the production review list.
  • Operate: it has no UI we publish; its own metrics are scraped (job alloy). If logs are missing in Loki, check docker compose logs alloy.

Tempo

  • Why: trace storage that works with the Collector and Grafana without extra indexing infrastructure.
  • Config: infra/tempo/tempo.yml: OTLP receivers (grpc 4317, http 4318, inside the container), single node, local disk (volume tempo_data), block retention 72 h (3 days). Gotchas: ingester.lifecycler.min_ready_duration: 0s and an in-memory ring, otherwise /ready stays 503 on a single node.
  • Operate: Grafana, Explore, data source Tempo (TraceQL): 
    { resource.service.name = "apisix" } && { resource.service.name = "kratos" }   # gateway to Kratos requests
{ resource.service.name = "notification-service" }
  • Use: request traces from APISIX, Kratos, and the three Java services. Sampling is always_on at the gateway and TRACING_SAMPLE_RATE (default 1.0) in Spring: revisit both for production.

OpenTelemetry Collector

  • Why: one stable endpoint for every sender, so services never need to know about Tempo; backends can change without touching services.
  • Config: infra/otel-collector/config.yaml: OTLP receiver (grpc 4317, http 4318, published on localhost for services run from an IDE), batch processor, traces pipeline to tempo:4317 (insecure, internal), metrics pipeline exposed for Prometheus on :8889, collector's own metrics on :8888.
  • Senders: APISIX (exporter address in plugin_metadata of apisix.yaml, not config.yaml), Kratos (tracing.providers.otlp in kratos.yml), Java services via OTEL_TRACES_ENDPOINT=http://otel-collector:4318/v1/traces (management.opentelemetry.tracing.export.otlp.endpoint).
  • Operate: docker compose logs otel-collector; health of its own pipeline is in Prometheus job otel-collector.

How a request shows up across all three signals is described in communication; reading them step by step is in Guides.
