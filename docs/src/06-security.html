Security model

The signing scheme partners use (ADERA-SIG-1) with a worked, runnable example, the pseudonymous ids, the SSRF guard, quotas, allowlists, the secrets policy, and an honest list of what is still weak.

Staff roles

Roles are deliberately few. A higher role includes everything below it. They are checked by the controller on every call (403 insufficient_role).

RoleMay do
VIEWERRead: apps and their detail, capability catalog, keys (public metadata only), reviews, reports, templates, delivery log, usage, /admin/api/v1/me.
ADMINEverything a viewer can, plus: create and edit apps, change status, upload logos, set capabilities, limits, payment settings and allowed addresses, register, generate and revoke keys, moderate reviews and reports, create and edit templates, read the audit log.
SUPER_ADMINEverything an admin can, plus: list, add, change and disable staff, and revive a KILLED app.

Safeguards: a super admin cannot demote or disable themselves (409 cannot_demote_self) and the last active super admin cannot be removed (409 last_super_admin). Disabling a staff member removes their role from Kratos and revokes their sessions.

Partner request signing: ADERA-SIG-1

Why signatures and not API keys

A shared API key can be copied from a log, a screenshot or a leaked config and replayed forever. With a signature the partner's private key never leaves the partner; Adera stores only the public key, so even a full leak of Adera's database cannot be used to impersonate a partner. The signature also covers the method, the path, the time and a hash of the body, so a request cannot be altered or redirected to another endpoint, and old requests stop working after five minutes.

The rules

  • Keys. The partner makes an RSA key pair of 2048 bits or more and gives staff the public key (PEM, -----BEGIN PUBLIC KEY-----). A private key sent by mistake is rejected (400 validation_failed, field publicKeyPem). Each key belongs to one app and one environment: DEV or PROD. A deployment is exactly one environment (ADERA_ENV): it accepts only keys of its own environment and refuses the other with 403 wrong_environment, so use the DEV key against the dev deployment and the PROD key against the prod deployment. Up to 5 active keys per environment, so a new key can be added before an old one is revoked. New key ids look like ak_dev_ or ak_prod_ followed by 24 hex characters; keys created before the rename keep their old ak_test_ / ak_live_ ids (they are opaque).
  • Algorithm. RSASSA-PKCS1-v1_5 with SHA-256 (RS256, Java SHA256withRSA, openssl dgst -sha256 -sign). The signature is base64. We also accept URL-safe base64, with or without padding, because partners' libraries differ.
  • Headers on every request: X-Adera-Key-Id (the id staff gave you), X-Adera-Timestamp (unix seconds; allowed skew 5 minutes either way), X-Adera-Signature (base64 signature of the canonical string).
  • Canonical string, five lines joined with \n, no trailing newline: 
    ADERA-SIG-1
{timestamp}
{METHOD}                      upper case, e.g. POST
{path[?query]}                exactly as sent, e.g. /v1/notifications or /v1/templates?x=1
{base64(sha256(body))}        standard base64 of the raw 32-byte SHA-256 of the exact body bytes;
                              an empty body (GET) is the hash of zero bytes
  • Body bytes matter. Hash the bytes you actually send. If your HTTP library re-serialises the JSON after you signed it, the hash changes and you get 401 invalid_signature. Serialise once, sign that string, send that same string.
  • Address check. The request must come from a server address staff registered for that environment (403 ip_not_allowed). An app starts with an empty list, so nobody can call until an admin adds addresses.

Runnable sketch 1: shell and openssl

Make a key once, send only the public half to staff, then sign each request. (This sketch was run against a throwaway key and the signature was verified with openssl dgst -sha256 -verify.)

# once: your key pair. Keep partner.pem secret; send partner.pub to Adera staff.
openssl genrsa -out partner.pem 2048
openssl rsa -in partner.pem -pubout -out partner.pub

# every request
KEY_ID=ak_prod_0123456789abcdef01234567                       # from staff
BODY='{"externalId":"job-1001","userId":"u_p_3f9c1a7e5b2d4c8a9e0f1b6d7a2c4e58","templateId":"5c0e5d58-6a43-4b1e-9d57-3f1f0f7f1a11","params":{"name":"Abebe"}}'
TS=$(date +%s)
HASH=$(printf '%s' "$BODY" | openssl dgst -sha256 -binary | openssl base64 -A)
CANON=$(printf 'ADERA-SIG-1\n%s\nPOST\n/v1/notifications\n%s' "$TS" "$HASH")
SIG=$(printf '%s' "$CANON" | openssl dgst -sha256 -sign partner.pem | openssl base64 -A)

curl -sS -X POST http://127.0.0.1:9080/v1/notifications \
  -H "X-Adera-Key-Id: $KEY_ID" -H "X-Adera-Timestamp: $TS" -H "X-Adera-Signature: $SIG" \
  -H 'Content-Type: application/json' --data-binary "$BODY"

--data-binary (not -d) keeps the body byte-identical to what you hashed. printf '%s' adds no newline; echo would, and break the hash.

Runnable sketch 2: Python (standard library and the openssl command)

Save as adera_sign.py. DRY_RUN=1 prints the canonical string and headers without sending; FIXED_TS pins the timestamp for testing.

#!/usr/bin/env python3
"""Sign and send one Adera partner request (ADERA-SIG-1). Needs only Python 3 and the openssl command.
Usage: python3 adera_sign.py KEY_ID PRIVATE_KEY.pem METHOD PATH [BODY_JSON_STRING]
Set ADERA_BASE (default http://127.0.0.1:9080) and DRY_RUN=1 to print the headers without sending."""
import base64, hashlib, os, subprocess, sys, time, urllib.error, urllib.request

key_id, key_file, method, path = sys.argv[1:5]
body = sys.argv[5].encode() if len(sys.argv) > 5 else b""
ts = os.environ.get("FIXED_TS") or str(int(time.time()))          # unix seconds, within 5 minutes of our clock

body_hash = base64.b64encode(hashlib.sha256(body).digest()).decode()   # empty body = hash of zero bytes
canonical = "\n".join(["ADERA-SIG-1", ts, method.upper(), path, body_hash])   # no trailing newline
signature = base64.b64encode(subprocess.run(
    ["openssl", "dgst", "-sha256", "-sign", key_file], input=canonical.encode(),
    capture_output=True, check=True).stdout).decode()                  # RSASSA-PKCS1-v1_5 with SHA-256 (RS256)

headers = {"X-Adera-Key-Id": key_id, "X-Adera-Timestamp": ts, "X-Adera-Signature": signature}
if body:
    headers["Content-Type"] = "application/json"

if os.environ.get("DRY_RUN"):
    print(canonical); print("---"); [print(f"{k}: {v}") for k, v in headers.items()]; sys.exit(0)

base = os.environ.get("ADERA_BASE", "http://127.0.0.1:9080")
req = urllib.request.Request(base + path, data=body or None, method=method.upper(), headers=headers)
try:
    r = urllib.request.urlopen(req, timeout=30); status, data, rh = r.status, r.read(), r.headers
except urllib.error.HTTPError as e:
    status, data, rh = e.code, e.read(), e.headers
print(status); print(data.decode())
print("response signature headers:", {k: rh.get(k) for k in ("X-Adera-Key-Id", "X-Adera-Timestamp")})

Our signatures: responses and callbacks

We sign too, so a partner can prove an answer or a callback really came from Adera and was not altered. Our public key is at /.well-known/jwks.json (public, cacheable one hour, standard JWKS with kty, use, alg, kid, n, e).

WhatHeadersCanonical string
Every /v1/* response, errors includedX-Adera-Key-Id (our key id), X-Adera-Timestamp, X-Adera-SignatureADERA-SIG-1-RESPONSE, timestamp, HTTP status, base64(sha256(response body)), base64(sha256(your request's signature string)), joined with \n. Binding to your signature means a response cannot be replayed as the answer to a different request.
Callback (we call you)X-Adera-Event: notification.status, X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature, Idempotency-Key, User-Agent: Adera-Callbacks/1Same as a request, with us as the caller: ADERA-SIG-1, timestamp, POST, the path (and query) of your callback URL, base64(sha256(body)).

To check one, build the canonical string, fetch the JWKS, and verify RS256. Sketch (standard library only; save as verify_adera.py; tested against the signature above):

#!/usr/bin/env python3
"""Check an Adera signature (response or callback) against our published key. Standard library only.
Usage: python3 verify_adera.py JWKS_JSON_FILE TIMESTAMP SIGNATURE_B64 CANONICAL_STRING_FILE"""
import base64, hashlib, json, sys

jwks_file, timestamp, signature_b64, canonical_file = sys.argv[1:5]
jwk = json.load(open(jwks_file))["keys"][0]
b64u = lambda s: int.from_bytes(base64.urlsafe_b64decode(s + "=" * (-len(s) % 4)), "big")
n, e = b64u(jwk["n"]), b64u(jwk["e"])
canonical = open(canonical_file, "rb").read()
signature = int.from_bytes(base64.b64decode(signature_b64), "big")
k = (n.bit_length() + 7) // 8
em = pow(signature, e, n).to_bytes(k, "big")                      # RSA public operation
digest_info = bytes.fromhex("3031300d060960864801650304020105000420") + hashlib.sha256(canonical).digest()
expected = b"\x00\x01" + b"\xff" * (k - len(digest_info) - 3) + b"\x00" + digest_info   # PKCS#1 v1.5 padding, SHA-256
print("signature valid" if em == expected else "SIGNATURE INVALID")
sys.exit(0 if em == expected else 1)
Production note

The sketch checks the exact PKCS#1 v1.5 encoding by hand so it needs no library. In a real partner integration prefer your language's JWT or crypto library and cache the JWKS for up to an hour. De-duplicate callbacks on Idempotency-Key: the same callback can arrive twice.

Dev note

If notification-service could not read its signing key from Infisical at start, it signs with an ephemeral key whose kid looks like ephemeral-ab12cd34 and which changes at every restart. This is allowed only while no real provider is on.

Pseudonymous ids

Partners never see a real Adera user id. Each user has a different id in every app: u_p_ followed by the first 32 hex characters of HMAC-SHA256(ALIAS_HMAC_SECRET, "<userId>:<appId>"). The pair (app, alias) maps back to the user in the table app_user_alias in the users database.

  • Why per app: two partners comparing their data cannot tell they share a user, so a leak at one partner exposes nothing about another or about Adera.
  • Why an HMAC and a table: the HMAC makes the same user and app always give the same alias (minting twice is harmless), and the secret means nobody can compute aliases for a guessed user id. Resolving uses the table, so an alias exists only after it was minted.
  • Minting is internal-only today: POST /internal/aliases with X-Internal-Secret, intended to be called when a user first opens an app. The public side (the frontend bridge and the user's consent) is not built yet, so for now the e2e tests and operators call it directly. See internal API.
  • Anti-probing: deleted, suspended and unknown users all answer 422 user_unreachable to a partner.
  • Synthetic users (DEV only): ids named u_p_test_<anything> are not real people. u_p_test_unreachable is unreachable (422 user_unreachable); u_p_test_muted is muted on every channel (200 SUPPRESSED); for the others delivery is simulated: nothing is sent and the attempt is recorded with provider sandbox. In PROD every u_p_test_* id is refused with 422 synthetic_user_not_allowed. There is no other simulation: in DEV real users are delivered through the dev providers (console SMS, Mailpit, fake push), which is why nothing reaches a real phone or inbox.
  • The secret ALIAS_HMAC_SECRET must never change after aliases are minted: changing it makes new aliases differ from the stored ones.

SSRF guard for callback URLs

The partner chooses the callback address, so a careless server could be tricked into calling our own network (cloud metadata, databases, Kratos admin). UrlGuard allows a callback only if all of these hold:

  • scheme is https (plain http only when PARTNER_ALLOW_PRIVATE_CALLBACKS=true, dev only);
  • no embedded credentials (user:pass@) and a host is present;
  • port is 443 or 8443 (or none);
  • every address the host resolves to is public: not loopback, any-local, link-local (includes 169.254.169.254 cloud metadata), private (10/8, 172.16/12, 192.168/16), multicast, 0.0.0.0/8, carrier-grade NAT 100.64/10, 192.0.0.0/24, TEST-NET-1/2/3, 198.18/15 benchmarking, 240.0.0.0/4 and above, or IPv6 unique-local fc00::/7;
  • redirects are never followed (a public URL cannot bounce us to a private one); connect timeout 5 s, request timeout 8 s.

A refused address fails the callback at once (reason such as address_not_public, port_not_allowed, scheme_not_https, host_not_resolvable) and is not retried. The acceptance step is looser (it checks only that the URL starts with http:// or https:// and is at most 500 characters), so a bad callback URL is not rejected when you send the notification: the failure shows in the staff delivery view (callbacks[].lastError).

Quotas

Staff set four limits per app and per channel (SMS, EMAIL, IN_APP); null is unlimited and 0 is none. Counting uses UTC days.

LimitMeaningError limit value
maxPerUserPerDayMessages to one user todaymax_per_user_per_day
maxPerDayAll messages todaymax_per_day
maxDistinctUsersPerDayDifferent users reached todaymax_distinct_users_per_day
maxTotalLifetime totalmax_total

The check and the insert happen in one transaction with a row lock per app and channel, so concurrent requests cannot overshoot. A refused request uses no quota. Granting a notify capability creates a conservative default limit row (SMS 3 per user per day, 100 per day, 100 distinct users, 1000 lifetime; email 5, 500, 500, 10000; in-app 20, 10000, 10000, unlimited). See the capability catalog.

Allowlists

  • Partner server addresses (per app, per environment): up to 50 IPs or CIDR ranges. A range that matches everything (/0) is refused for PROD. DEV and PROD lists are stored separately and only the deployment's own is used. No DNS names, because names can change under us.
  • Live recipient allowlist NOTIFY_LIVE_ALLOWLIST: when set and a provider is real, only these recipients get real messages. It applies to Kratos codes and to partner messages. Use it for the first real send.
  • App allowed origins: per-app list of web origins for the future frontend bridge (allowedOrigins; format https://host[:port], no path). Stored and validated, not enforced by anything yet.
  • Callback ports: only 443 and 8443.
  • Template links: values a partner fills into a template may not contain links unless the template parameter declares allowLinks.

Protecting personal data

  • Logs and the send log never hold a code or a full number. Recipients are masked (+2519*****20, a***@example.com) and rate limits use a SHA-256 hash of the recipient.
  • Staff delivery views never show message values (they can hold personal data); only status, channel, reason and attempts.
  • Avatars and logos are re-encoded. The server decodes, centre-crops to a square, resizes to at most 512 px and writes a fresh JPEG, which drops EXIF location and camera data and neutralises odd files. Size and pixel limits guard against decompression bombs. Files are stored under random ids and served only by signed, expiring URLs (the bucket is not public).
  • Kratos identities hold only email and phone_number traits; everything else lives in user-service.
  • Muting: a user can mute SMS, email or in-app per app; the partner is not told (the request is answered 200 SUPPRESSED).

Secrets policy

  • Container secrets and trust secrets live in .env (gitignored, mode 600). Third-party API keys and our partner signing key live in Infisical and are read at start by notification-service. See Setup: secrets for the full split.
  • Nothing secret is committed, baked into an image, or printed in these documents. .env.example lists names only.
  • Back up INFISICAL_ENCRYPTION_KEY and INFISICAL_AUTH_SECRET off the machine. The CLI token expires 2026-11-23.
  • Rotate any key that was ever pasted into a chat or a file outside Infisical. The unrelated docs/ride_flow-credentials.env (another project) holds live keys that Adera does not use.
  • The Java services never log a secret value (the Infisical loader logs only the count of secrets and failure messages).

Known limitations

From SETUP.md section 12, checked against the code, plus items found while writing these documents.

Security and behaviour

  • Account enumeration at login. Kratos answers "account does not exist" for unknown identifiers but "code sent" for known ones. Plan: a single "continue" endpoint in our backend that always says "code sent".
  • Phone and email are separate identities. Linking a second identifier (and merging two profile rows) is a feature still to build.
  • Unauthenticated internal hooks. user-service /internal/kratos/after-registration and notification-service /internal/kratos/sms|email check no secret. They are reachable only inside the compose network (and on localhost dev ports). Worst case: an empty profile row, or a message triggered from inside. A shared-secret header is the next step.
  • Account deletion is not implemented (a store requirement). It must delete the Kratos identity, anonymise the profile, remove avatar files and device tokens.
  • Avatar formats. JPEG, PNG, GIF and BMP only; iPhone HEIC and WebP are not decoded by the JDK, so the app should convert to JPEG first.
  • Admin storage keys. user-service and registry-service use RustFS's admin keys. Create a bucket-scoped key before production.
  • No malware or NSFW scanning of avatars and logos (re-encoding removes active content, not inappropriate images).
  • Per-IP limits. They can block real users behind shared mobile-carrier addresses, and locally all clients share one Docker IP. Behind a proxy the real client IP must be configured, otherwise all users share one counter and partner address checks see the proxy.
  • Real sending is built but largely untested. Twilio and Resend adapters are unit-tested against mocked HTTP and real-mode start-up was verified, but no real SMS has been confirmed delivered end to end by the final code (an earlier real email did arrive; SMS to Ethiopia failed with Twilio error 21612 from the US sender). Resend uses a borrowed account and sender until a domain is verified. The first real send must use the allowlist.
  • Firebase push is a fake until a service account exists; the Firebase code has not been run against Firebase.
  • RabbitMQ permissions are wide (.*) for both service users, to be narrowed once real queues exist.

Found while documenting (not fixed)

  • Replay window. A captured signed partner request can be replayed for up to 5 minutes (no nonce). The effect is limited: POST /v1/notifications is idempotent by externalId (a replay returns 200 replayed), reads are harmless.
  • Callback DNS check and connect are separate lookups. UrlGuard resolves the host, then the HTTP client resolves it again to connect, so a hostile DNS server could answer differently the second time (DNS rebinding). Not tested as exploitable; pinning the resolved address would close it.
  • Silent fallback to an ephemeral signing key if Infisical is unreachable at start (dev mode only, but easy to miss; see Setup).
  • Callback URL validation at accept time is weaker than at send time (see the SSRF section).
  • No data retention jobs. send_log, notifications, attempts, callbacks, usage_daily and audit_event grow without limit.
  • Staff identities created by the admin API skip the registration hook, so they have no app_user row until they first call /api/v1/me.
  • Kratos admin (4434) and RustFS (9000, 9001) are published on localhost; anyone with local shell access can use them. Fine for dev, not for a shared server.
