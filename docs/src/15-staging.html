15. Staging server

The shared staging deployment at 157.245.133.250: what runs there, the addresses the frontend team uses, where to read SMS and email codes, how a push deploys, how to roll back and how to reach the internal tools. It runs exactly the laptop setup (DEV mode, console SMS, Mailpit email, fake push): nothing real is ever sent. Set up 2026-11-05 with a copy of the laptop's data taken that day.

HTTP only

No domain and no HTTPS yet, so passwords, codes and session tokens travel unencrypted. Use demo data only. HTTPS is the next step once a domain is chosen (a reverse proxy in front of ports 9080 and 8090).

Native apps call the gateway directly. A browser app on another origin is refused by CORS: the gateway only allows http://localhost:3000, which still works for a frontend developer running a dev server on their own machine.

2. Getting codes as a frontend developer

Registration, verification, password reset and staff sign-in all send a code. On staging nothing reaches a phone or a real mailbox:

  • SMS (phone verification, phone password reset): open http://157.245.133.250:8091/, type the phone number in international form (+2519...) and press Show. The page refreshes every 10 seconds. From a script: curl -u <inbox login> 'http://157.245.133.250:8091/messages?to=%2B251900000001'.
  • Email (email verification, email recovery, staff sign-in codes): open Mailpit on http://157.245.133.250:8025/. The same messages also show on the SMS page.
  • The SMS list is kept in memory: it empties when notification-service restarts (every deploy). Mailpit keeps its mail.
  • Both pages sit behind one shared login, because anyone who reads them could take over any account on staging. Do not share it outside the team.

3. Data

On 2026-11-05 the laptop's Docker volumes were copied as they were (stack stopped first, so the copy is consistent): every Postgres database (Kratos identities and sessions, users, registry, notification, Infisical), the RustFS files (logos, avatars), Mailpit, Grafana and Redis. Row counts were compared table by table after the copy (section 9). So staging has the same apps, demo users (with the passwords in section 13), staff, reviews, reports, consents, templates, notifications and audit history as the laptop had. From then on the two are separate: nothing syncs.

Staff: admin@adera.local (SUPER_ADMIN) keeps the owner's authenticator. The demo staff accounts (demo-admin-1, demo-viewer-1, ...) were enrolled by scripts whose authenticator secrets were not kept; to use one, reset its authenticator (section 7) or create a temporary account with tests/e2e/tempstaff.py on the server.

4. How a change gets to staging (CI/CD)

Workflow: .github/workflows/ci.yml (GitHub Actions on OnTheWayHomeWard/super_adera).

Push toWhat runs
master or a pull requestTests only: mvn verify for notification-service, user-service and registry-service (Testcontainers starts Postgres), backoffice npm test and npm run build, and the docs link check.
stagingThe same tests, then five images built and pushed to GHCR (ghcr.io/onthewayhomeward/adera-{notification-service,user-service,registry-service,backoffice,edge}, tags staging and the commit sha), then the deploy job: SSH to the server as deploy and run deploy/staging/deploy.sh <sha>, which checks the commit out, pulls the images, runs docker compose up -d, restarts the gateway and checks the health of every service. The job fails if a health check fails.

To deploy what is on master:

git push origin master:staging

A documentation change deploys the same way: the docs are baked into the edge image. Everything else (Postgres, Kratos, APISIX, Grafana and the rest) is a public image pinned in docker-compose.yml; to change one, change the tag and push.

GitHub secrets used by the deploy job: STAGING_HOST, STAGING_SSH_KEY (a key made only for this, accepted only for the deploy user) and STAGING_KNOWN_HOSTS (the server's host key). Images are pulled with the job's own short-lived token.

5. Rolling back

Every image is also tagged with its commit sha. Either push the older commit to staging:

git push --force-with-lease origin <good-sha>:staging

or, on the server, run the previous images without CI:

ssh deploy@157.245.133.250
cd /opt/adera
ADERA_IMAGE_TAG=<good-sha> docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d
docker compose -f docker-compose.yml -f docker-compose.staging.yml restart apisix

Database migrations (Flyway) only go forward: an older service refuses to start against a newer schema. A rollback across a migration needs a database restore (section 7).

6. The server

  • DigitalOcean droplet, 4 vCPU, 8 GB RAM, 160 GB disk, 4 GB swap, Ubuntu, Docker Engine with the compose plugin, automatic security updates.
  • Firewall (ufw): only 22, 9080, 8090, 8025, 8091 and 9000 are open from outside (plus the Docker networks to the host, for test callback receivers). Every other container port is bound to 127.0.0.1 exactly as on a laptop.
  • Code in /opt/adera (a checkout of the staging branch, owned by deploy); the tracked .env is the laptop's. Not in git, only on the server: deploy/staging/htpasswd (the inbox login), deploy/staging/CREDENTIALS.md, and the seeding script's partner keys in tests/e2e/.seed-keys/.
  • Logins: root (the owner's SSH key, host alias bellme-adera-staging) and deploy (the CI key and the owner's key).

The compose files

The server runs docker-compose.yml plus docker-compose.staging.yml. The override takes our four images from GHCR, adds the edge container (nginx: docs on 8090, Mailpit on 8025 and SMS on 8091 behind basic auth), publishes the gateway, the edge ports and the object store on the public address, and points Kratos' public URL and the signed image links at 157.245.133.250.

For the deploy user, COMPOSE_FILE is set in ~/.bashrc, so plain docker compose in /opt/adera uses both files. As root, use the alias:

cd /opt/adera
alias dc='docker compose -f docker-compose.yml -f docker-compose.staging.yml'
dc ps
dc logs -f --tail 100 notification-service
dc restart user-service && dc restart apisix

7. Internal tools (SSH tunnel)

Grafana, Prometheus, Infisical, RabbitMQ, the RustFS console, Postgres, Redis, Kratos' admin API and the services' own ports are not public. Open them with a tunnel and use the laptop addresses:

ssh -N bellme-adera-staging \
  -L 3001:127.0.0.1:3001 -L 9090:127.0.0.1:9090 -L 8080:127.0.0.1:8080 \
  -L 15672:127.0.0.1:15672 -L 9001:127.0.0.1:9001 -L 5432:127.0.0.1:5432

Then Grafana is http://127.0.0.1:3001, Prometheus :9090, Infisical :8080, RabbitMQ :15672, RustFS console :9001, Postgres 127.0.0.1:5432. Stop the laptop stack first, or pick other local ports, because the laptop uses the same ones. The backoffice's System page links to these laptop addresses, so they work once the tunnel is open.

Backups and resets

# database dump (all databases) to the server's disk
dc exec -T postgres pg_dumpall -U adera_admin | gzip > /opt/adera-backup-$(date +%F).sql.gz

# reset a staff member's authenticator (Kratos admin API, from the server)
curl -X DELETE http://127.0.0.1:4434/admin/identities/<identity-id>/credentials/totp

There is no automatic backup yet; it belongs to the production checklist (section 2).

8. What the frontend team needs

  • Base URL http://157.245.133.250:9080 everywhere the guides say http://127.0.0.1:9080. Kratos flow URLs (ui.action) already carry the staging address.
  • Demo users and their passwords: section 13, part 2a. They can sign in at once (all verified).
  • Guides: sign-in and account, catalog, notifications, permissions and the bridge, partner API, banners.
  • Testing the super app's bridge: Bridge Lab, a test mini app with a step-by-step checklist and live logs (runs on the laptop for now; staging needs an https address first).
  • New accounts: register normally, then take the code from the SMS page or Mailpit.
  • Gateway limits apply per IP. A whole team behind one office address shares them (for example 10 sign-ins per minute).
