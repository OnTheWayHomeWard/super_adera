Endpoint reference

Every endpoint of every service, grouped by who calls it: 94 documented endpoint entries in six groups (the partner group has 4 endpoints plus one worked example). Each one has its purpose, who may call it, the headers it needs, every parameter, a real request and response captured from the running stack, and every error.

How to read the reference

  • Base URL. $BASE is the gateway, http://127.0.0.1:9080 in development. Clients use only this address. Where a service path differs from the client path, the page shows an "Internal path".
  • Real examples. Each response was captured from the dev stack through the gateway (console SMS, Mailpit; nothing real was sent). Tokens, keys, codes and personal data are masked or replaced by placeholders ($TOKEN, $KEY_ID, $APP). Identifiers belong to throw-away data that was deleted.
  • Click an endpoint to expand it. The filter box on each page searches methods, paths and words; "Expand all" opens everything (and printing opens all).
  • Error shape. Our services answer {"error":"<code>"}, often with "fields":{...}. Framework errors (bad path id, unknown route, wrong method, wrong content type, unreadable body) use it too since 2026-10-26: invalid_request, not_found, method_not_allowed, unsupported_media_type, not_acceptable, internal_error. Gateway-level answers (429, forward-auth 401) are not JSON. All error codes: error-code index.
  • Unknown JSON fields are rejected by the write endpoints of registry-service, notification-service's partner and admin API and user-service (validation_failed, unknown field). Absent field means unchanged, null means clear.

The mechanics (what the gateway adds, why a client cannot forge identity headers) are in the trust model. The route table is in Gateway routes at a glance.

What the gateway itself can answer

  • 429 when a limit above is exceeded (an HTML page, with X-RateLimit-* headers). Back off and retry after the reset time.
  • 401 with an empty body from forward-auth on user routes (missing, invalid or expired session). Staff routes answer 401 or 403 with a JSON body from registry-service.
  • 503 when the verification service or Kratos is down (not 401: your token may be fine).
  • 403 {"error":"forbidden"} for anything under /kratos/admin/.
  • 404 (APISIX default) for any path with no route, including every /internal/** path.
  • Every response carries X-Request-Id; use it when reporting a problem (find it in logs and traces).

Things worth knowing

  • Staff and partner endpoints were captured with a super admin session and a throw-away app; the user endpoints with throw-away users.
  • The partner callback (a request Adera sends) is documented on the partner page.
  • Endpoints that exist in code but are deliberately not exposed through the gateway are all under /internal (group d) and the actuator and dev endpoints (group f). The gateway exposes no route for them.
