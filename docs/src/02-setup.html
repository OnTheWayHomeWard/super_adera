Setup and running

How to start the whole platform on one machine, where each secret lives, how to switch between dev and real message delivery, how to run the tests, and what has gone wrong before.

Why one project per service

Each microservice has its own pom.xml and Dockerfile and shares no build with the others, so one can be rebuilt, tested and later moved to its own repository without touching the rest. A shared library will only be extracted when real shared code exists (today Cidrs exists in both registry-service and notification-service as a copy).

The working tree is not under git at the time of this writing (the folder has no .git). The state described here is the working tree as of 2026-10-25.

Secrets: .env versus Infisical

There is no secret value in any documentation page or in docker-compose.yml. Secrets live in exactly two places, split by who reads them.

KindWhereVariable namesWhy there
Container secrets.env (read by docker compose and passed to containers as environment)POSTGRES_PASSWORD, KRATOS_DB_PASSWORD, USER_DB_PASSWORD, NOTIFICATION_DB_PASSWORD, REGISTRY_DB_PASSWORD, INFISICAL_DB_PASSWORD, REDIS_ADMIN_PASSWORD, INFISICAL_REDIS_PASSWORD, APISIX_REDIS_PASSWORD, RABBITMQ_ADMIN_PASSWORD, USER_SVC_RABBIT_PASSWORD, NOTIFICATION_SVC_RABBIT_PASSWORD, KRATOS_SECRETS_COOKIE, KRATOS_SECRETS_CIPHER, GRAFANA_ADMIN_PASSWORD, RUSTFS_ACCESS_KEY, RUSTFS_SECRET_KEYThese are needed to start the databases and tools themselves. Infisical lives on Postgres and Redis, so it cannot hold the secrets that start Postgres and Redis.

Infisical's own bootstrap.envINFISICAL_ENCRYPTION_KEY, INFISICAL_AUTH_SECRETInfisical needs them before it can serve anything. Back both up off this machine. Losing the encryption key makes every stored secret unreadable.

Delivery mode switches (not secret).envSMS_PROVIDER, EMAIL_PROVIDER, NOTIFY_DEV_ENDPOINTS, NOTIFY_LIVE_ALLOWLIST, FCM_PROVIDER, PARTNER_ALLOW_PRIVATE_CALLBACKSSwitching mode is one edit and one command (see below).
Staff bootstrap, storage address.envBOOTSTRAP_SUPER_ADMIN_EMAIL, ADERA_ENV (dev or prod; which environment this deployment is), ADMIN_REQUIRE_AAL2 (optional), STORAGE_PUBLIC_ENDPOINT (optional)Plain configuration.
Third-party API keysInfisical, project Adera, environment dev, folder /notificationTWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_MESSAGING_SERVICE_SID, TWILIO_PHONE_NUMBER, RESEND_API_KEY, RESEND_FROM_EMAIL, RESEND_FROM_NAME, PARTNER_SIGNING_KEY_ID, PARTNER_SIGNING_PRIVATE_KEY_B64. Still to add: FIREBASE_SERVICE_ACCOUNT_B64Only notification-service needs them, and only when a real provider is on. They are loaded at service start by our own code (notification-service), not injected by compose. This keeps real provider keys out of .env, the images and git, and lets you rotate one without editing files.

Verified on 2026-10-25: the dev environment has secrets only in /notification (the nine names above, no Firebase key yet). The folders /infra, /kratos, /gateway and /user exist but hold nothing. The prod environment is empty.

Start-up race

The notification-service makes one attempt (5-second timeout) to read Infisical when it starts and carries on if that fails. If Infisical is slow or down at that moment you get a log line Could not load secrets from Infisical (/notification), and the service silently runs with no signing key (it creates an ephemeral key, which changes at every restart) and with no Twilio/Resend keys. In dev mode that is harmless; with a real provider the service refuses to start instead. This was seen once while these docs were being written (a restart while Infisical was still slow; the JWKS kid then looked like ephemeral-xxxxxxxx); a later restart loaded all nine secrets and the persistent key. Fix: start Infisical first, then docker compose up -d notification-service again. See the troubleshooting list.

How to read, add and rotate an Infisical secret is a step-by-step guide: Guides: Infisical.

Running with docker compose

# from the repository root
docker compose up -d            # build (first time) and start everything
docker compose ps               # long-running services should be Up; postgres/redis/rabbitmq/mailpit show (healthy)
docker compose logs -f kratos   # follow one service
docker compose logs --since 10m notification-service
docker compose up -d notification-service   # re-create ONE service after editing .env or its compose block
docker compose build user-service && docker compose up -d user-service   # after changing Java code
docker compose restart apisix   # re-read a bind-mounted config (apisix.yaml hot-reloads on its own in about a second)
docker compose stop             # pause everything: containers stay, data survives
docker compose start            # start the stopped containers again (same containers, same data, no rebuild)
docker compose stop mailpit     # or one service only; docker compose start mailpit brings it back
docker compose down             # stop, keep volumes (data survives)
docker compose down -v          # stop AND DELETE all data (databases, Redis, files, Infisical content). Be sure.
Good to know
  • docker compose restart does not re-read the environment: block or .env. After adding or changing a variable, use docker compose up -d <service>.
  • Two one-shot containers run at start and then exit; this is normal: kratos-migrate (database migrations) and rabbitmq-setup (vhost and users).
  • The Postgres init script (infra/postgres/init-databases.sh) runs only on the first start of an empty data volume. Adding a new database later (as was done for registry) needs a manual CREATE ROLE / CREATE DATABASE on the running server.
  • Start order is declared with depends_on: Kratos waits for its migration and for notification-service; user-service and registry-service wait for Postgres, RustFS and Kratos; APISIX waits for Redis and Kratos. Nothing waits for Infisical (see the warning above).

Dev versus real delivery

Kratos always hands its messages to notification-service. The service, not Kratos, decides from .env whether anything leaves the machine. The defaults are the safe dev values, and the compose file applies them if the variable is absent (${SMS_PROVIDER:-console} and so on).

Setting in .envDev (what is running now)RealWhat it does
ADERA_ENVdev (default)prodThe one environment this deployment is (DEV or PROD). Passed to registry-service and notification-service; anything else stops them starting. Keys and allowed IPs of the other environment are stored but refused here (403 wrong_environment). Switch with docker compose up -d registry-service notification-service.
SMS_PROVIDERconsoletwilioConsole: writes the SMS (and its code) to the service log and the dev store; nothing is sent. Twilio: real SMS, costs money. Needs the four TWILIO_* secrets in Infisical.
EMAIL_PROVIDERmailpitresendMailpit: SMTP to the local inbox at :8025. Resend: real email. Needs RESEND_API_KEY, RESEND_FROM_EMAIL, RESEND_FROM_NAME in Infisical.
NOTIFY_DEV_ENDPOINTStruefalseExposes GET/DELETE /dev/messages, which return one-time codes. The service refuses to start with this true while a real SMS or email provider is on.
NOTIFY_LIVE_ALLOWLISTempty (ignored)a comma-separated list of numbers and addresses, or emptyWhen non-empty and a provider is real, real sends go only to these recipients; others are suppressed. Use it for the first real test.
FCM_PROVIDERfakefirebasePush provider for in-app notifications. firebase needs FIREBASE_SERVICE_ACCOUNT_B64 in Infisical (not yet added).
PARTNER_ALLOW_PRIVATE_CALLBACKStrue in this dev .env (e2e tests only)falseLets partner callbacks go to http and private addresses. The service refuses to start with this true while any real provider (SMS, email or push) is on. The compose default is false.

The channels switch independently. After editing .env:

docker compose up -d notification-service
docker compose logs --since 1m notification-service | grep -E "NOTIFICATION MODE|PARTNER PLATFORM|Infisical"
NOTIFICATION MODE: sms=console (dev, nothing leaves the machine), email=mailpit (dev, nothing leaves the machine), allowlist=off, devEndpoints=true
PARTNER PLATFORM: push=fcm-fake (dev), workers=true, privateCallbacks=true

The real-mode start was verified once with a throwaway instance (it loaded the Twilio and Resend secrets and printed sms=twilio (REAL), email=resend (REAL) without sending). The first real send must use the allowlist. The full checklist is Guides: switching to real delivery.

Why so many guards

A mistake here costs money (SMS) or exposes one-time codes (the dev endpoint), so the dangerous combinations are impossible to start rather than merely discouraged: dev endpoints with real providers, private callbacks with real providers, a real provider without a persistent signing key.

Rate limit

The gateway allows 10 Kratos "submit" calls per minute per IP, shared by everything on this machine. If you run two scripts at once, or run one twice quickly, you will see 429. Wait a minute.

Going to a server (deferred checklist)

Copying the folder and running docker compose up -d starts the containers but is not production-ready. Do these first (from SETUP.md section 12, restated):

  1. Infisical starts empty on a new server (its data is in the Postgres volume). Restore the infisical database (it works with the same .env keys) or recreate project, secrets and token by hand, then update INFISICAL_TOKEN and INFISICAL_PROJECT_ID.
  2. Public HTTPS in front of the gateway only (for example Caddy: api.<domain> to APISIX :9080). Everything else stays on 127.0.0.1; use SSH tunnels.
  3. Replace hard-coded localhost URLs: Kratos serve.public.base_url (otherwise phones get 127.0.0.1 flow URLs), Infisical SITE_URL, the APISIX CORS origin.
  4. Real client IP in APISIX behind the proxy. Without it, the per-IP limits apply to all users combined, and partner allowed-address checks (which use X-Client-IP from the gateway) see the proxy's address.
  5. Set the delivery mode: SMS_PROVIDER=twilio, EMAIL_PROVIDER=resend, NOTIFY_DEV_ENDPOINTS=false, empty NOTIFY_LIVE_ALLOWLIST, PARTNER_ALLOW_PRIVATE_CALLBACKS=false. Mailpit is not needed.
  6. Backups of Postgres and an off-machine copy of INFISICAL_ENCRYPTION_KEY and INFISICAL_AUTH_SECRET.
  7. Private git repository (secrets are gitignored) and copy .env separately and privately.
  8. Revisit trace sampling (always_on), the Grafana admin password and the Alloy Docker-socket mount.
  9. RustFS must be reachable by phones over HTTPS for avatars and logos: set STORAGE_PUBLIC_ENDPOINT to its public address (the signature covers the host). Only the S3 API, not the console on 9001.
  10. Create a bucket-scoped RustFS access key instead of the admin keys (user-service and registry-service use the admin keys today) and keep the console private.
  11. Give notification-service a persistent partner signing key in Infisical and make sure Infisical is reachable at its start.
  12. Open issue: Twilio to Ethiopia (+251) failed with error 21612 from the US sender; a local route or another channel is needed.

Also not done (production hardening): TLS everywhere, trace sampling, Postgres and Redis exporters, narrower RabbitMQ permissions, Universal Auth for Infisical, separate Postgres/Redis for Infisical, rotating any key that was ever pasted into a chat.

Troubleshooting and lessons learned

Each of these cost time once. Symptom first.

SymptomCause and fix
A container cannot read its mounted config, or exits at startBind-mounted config files must be world-readable (644/755); containers run as other users.
Kratos: migration error at startIn Kratos 26 use kratos migrate sql up -e --yes (as kratos-migrate does). To get a session_token right after sign-up add hook: session under registration.after.code.
Redis refuses to startACL files cannot contain comment lines. infra/redis/entrypoint.sh writes the file from env for that reason.
Gateway has no CORS headers, no request id and no metrics, with no errorAn unknown plugin in a global rule drops the whole rule silently. The plugin list in apisix/config.yaml replaces APISIX's defaults; add a plugin there (and restart) before using it in apisix.yaml.
No traces from the gatewayAPISIX 3.x reads OpenTelemetry exporter settings from plugin_metadata in apisix.yaml, not from config.yaml.
A new ${{ENV}} in apisix.yaml is emptyThe variable must exist in the container: docker compose up -d apisix (restart is not enough). Also avoid YAML anchors and aliases in that file.
Tempo /ready stays 503Single node: set ingester.lifecycler.min_ready_duration: 0s (done).
Loki drops the first burst of logsRaise ingestion_rate_mb (done: 16).
Infisical CLI or API incompatibilitiesPin the image (latest-postgres was ten months stale). infisical secrets delete needs --type shared for shared secrets.
Java service gets HTTP 400 from InfisicalPin Java's HttpClient to HTTP/1.1; the default h2c upgrade over plain HTTP is rejected.
A Spring start-up component logs nothingEnvironmentPostProcessors run before logging exists; use DeferredLogFactory.
Service reports DOWN because SMTP is downSpring's mail health indicator is disabled on purpose (management.health.mail.enabled=false).
Docker build is slow or fails on JavaBuild with maven:3.9-eclipse-temurin-21, run on eclipse-temurin:21-jre as a non-root user (the Dockerfiles do). On the host use JAVA_HOME=/usr/lib/jvm/java-21-openjdk; the default JDK is 26.
Spring Boot 4 test code does not compileMockMultipartHttpServletRequestBuilder no longer extends MockHttpServletRequestBuilder (use AbstractMockHttpServletRequestBuilder<T>); @MockitoBean lives in org.springframework.test.context.bean.override.mockito; Jackson is tools.jackson.* (v3).
Signed avatar or logo URL gives 403The host is part of the S3 signature. Sign with the public endpoint (STORAGE_PUBLIC_ENDPOINT), use path-style addressing and requestChecksumCalculation(WHEN_REQUIRED) with the AWS SDK against RustFS.
Sign-up works even though user-service is downBy design: the Kratos web_hook has response.ignore: true (non-blocking). The profile is created on the first GET /api/v1/me instead.
Changed a variable but the service still uses the old valuedocker compose restart does not re-read the environment. Use docker compose up -d <service>.
Python IncompleteRead on a 413 responseThe server closes the connection right after the status line; catch it and use e.partial.
429 in testsPer-IP gateway limits (10 Kratos submits per minute). Wait a minute; locally every client shares one Docker IP.
A partner call is refused with ip_not_allowed right after you changed the allowed addressesnotification-service caches app configuration for about 15 seconds. Wait, then retry (partner.py sleeps 16 s).
Staff login stops at mfa_requiredThe session is aal1. Do the authenticator step (see Guides: staff login). Kratos does not accept the same TOTP code twice, so wait for the next 30-second window.
Notification-service logs Could not load secrets from InfisicalInfisical was not ready or reachable. Check curl http://127.0.0.1:8080/api/status, then docker compose up -d notification-service.
