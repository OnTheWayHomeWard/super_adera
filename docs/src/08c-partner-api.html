8c. Partner API

How a mini app's server sends notifications to Adera users and reads the result: four signed endpoints, the signed callback Adera sends back, the statuses, and every error.

How the partner API works

  • Base URL: $BASE = http://127.0.0.1:9080 in development; the real address will be the public API host.
  • Setup by staff first (staff API): the app is created, granted notify.sms / notify.email / notify.inapp, given limits, your server addresses for the environment (DEV and PROD can both be filled in), your public key and its approved templates. You receive a key id and template ids. Guide: register a mini app.
  • Signing: sign every request with your private key (ADERA-SIG-1, RS256). Full rules, a worked example and runnable shell and Python code are in Security. In these examples $KEY_ID, $TS and $SIG are the three header values that code produces.
  • User ids: you address a user by their pseudonymous id for your app (u_p_...), never by phone or email. You never choose the channel: the template kind and the user's data decide.
  • Environments: every deployment is exactly one environment, DEV or PROD (ADERA_ENV). Use the DEV key against the dev deployment and the PROD key against the prod deployment; a key of the other environment gets 403 wrong_environment. DEV works for any app that is not killed; PROD only while the app status is LIVE. There is no separate simulated sandbox: the dev deployment's providers (console SMS, Mailpit, fake push) are the sandbox. Only users named u_p_test_<anything> are synthetic and simulated in DEV (nothing sent; u_p_test_unreachable is 422 user_unreachable, u_p_test_muted is 200 SUPPRESSED); in PROD they are refused with 422 synthetic_user_not_allowed.
  • Idempotency: externalId is your own unique id for the message. The same request again returns 200 with "replayed": true; the same id with different content is 409 external_id_reused. Safe to retry after a timeout.
  • Delivery is asynchronous. 202 QUEUED means accepted; the final result arrives by callback (or poll the status endpoint).
  • Error shape: {"error":"<code>"} plus details (fields, limit, capability).

Caches

Adera caches key and app configuration for about 15 seconds. After staff change allowed addresses, capabilities, app status or revoke a key, expect up to 15 seconds before the partner API reflects it.

Purpose

Asks Adera to reach one user with one of your approved templates. Adera validates the request synchronously (signature, address, template, values, user, channel, quota) and stores it as QUEUED; a background worker delivers it and reports the result by callback.

Channel choice (you never name it): an IN_APP template goes to the user's inbox plus a push (needs notify.inapp). A DIRECT template goes by SMS if the user has a phone number and your app has notify.sms; otherwise by email if the user has an email and your app has notify.email.

Why a user can be silently suppressed: if the user muted your app for that channel the answer is 200 with status SUPPRESSED and reason recipient_opted_out, not an error, so you cannot learn which users muted you in a way that identifies them as an error pattern.

How to use it

  • Fields: notificationId, externalId, status, channel, reason (when present), environment, createdAt, expiresAt, completedAt (when final), attempts.
  • Statuses: QUEUED, PROCESSING, RETRYING (not final); SENT, FAILED, UNREACHABLE, SUPPRESSED, EXPIRED (final). See glossary.

The callback Adera sends you

If you gave a callbackUrl, Adera POSTs one signed status report to it when the notification reaches a final status. This is an endpoint you provide. 1 callback(s) were captured with a local receiver during the test run; the one below is real (the signature is shortened).

  • Request: POST to your URL, Content-Type: application/json, User-Agent: Adera-Callbacks/1.
  • Headers: X-Adera-Event: notification.status, X-Adera-Key-Id (Adera's key id), X-Adera-Timestamp, X-Adera-Signature, Idempotency-Key (unique per callback, repeated on retries: de-duplicate on it).
  • Verify the signature with the key at /.well-known/jwks.json: the canonical string is ADERA-SIG-1, timestamp, POST, the path (and query) of your URL, base64(sha256(body)) joined with newlines. Code: Security.
  • Body fields: event (always notification.status), notificationId, externalId, status, channel, reason (null when none), environment, at (ISO-8601).
  • Answer: any 2xx within 8 seconds. Anything else (or no answer) is retried after 1 minute, doubling up to 6 hours, 8 attempts in all (about a day), then given up.
  • URL rules: https only, port 443 or 8443, no embedded credentials, every address the host resolves to must be public; redirects are not followed. A refused URL fails at once without retry (see SSRF guard).
  • Reports are sent for final statuses only (SENT, FAILED, UNREACHABLE, SUPPRESSED, EXPIRED), not for QUEUED or RETRYING.

Notification statuses

StatusFinal?Meaning
QUEUEDnoAccepted, waiting for the delivery worker (checked every second).
PROCESSINGnoA worker holds it (a 60-second claim; an abandoned claim is picked up again).
RETRYINGnoA temporary failure; next attempt after 30 s doubling up to 1 hour, at most 8 attempts, until ttlSeconds passes.
SENTyesHanded to the provider (SMS, email) or stored in the inbox with push attempted. For a synthetic u_p_test_* user in DEV: simulated success (nothing sent).
FAILEDyesPermanent provider refusal (bad number or address, rejected sender: provider 4xx except 408/429) or the maximum attempts were used.
UNREACHABLEyesThe user was deleted or suspended meanwhile, or has no phone / no email for the chosen channel.
SUPPRESSEDyesThe user muted your app (recipient_opted_out), or the live allowlist excluded the recipient (not_allowlisted). Not an error.
EXPIREDyesThe deadline (ttlSeconds) passed before it could be delivered.

Retries: delivery backoff is 30 s, 1 m, 2 m, 4 m ... capped at 1 hour with plus or minus 10% jitter. Permanent errors are never retried. A "delivered" status means the provider accepted it; Adera does not track handset delivery receipts.
