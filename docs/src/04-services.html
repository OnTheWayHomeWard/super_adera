4. Services

The three Spring Boot services we wrote ourselves. Everything else in the platform is an off-the-shelf tool (see Tools); these services hold only product logic.

Why three small services

Each service owns one database and one job, and nothing else can read that database (see Postgres). They are independent Maven projects (no shared parent build, no shared library): a shared library is only worth extracting once real shared code exists. The cost is a little repeated code, for example the same Cidrs helper and the same gateway-trust filter pattern appear in more than one service. That is accepted on purpose.

Inside the compose network every service listens on 8080; the host ports above exist only for development and are bound to 127.0.0.1. Production traffic enters through the gateway only (trust model).

What all three share

  • Stack: Spring Boot 4.1.2 (parent spring-boot-starter-parent), Java 21, Maven, Spring MVC, Spring Data JPA + Flyway (ddl-auto: validate: the schema is changed only by migrations), Actuator, Micrometer Prometheus registry, OpenTelemetry starter, Bean Validation.
  • Error shape: JSON {"error": "<code>", ...details}. Codes are machine-readable and stable; full index in Reference.
  • Trust filters: each service has a servlet filter that checks constant-time (MessageDigest.isEqual) shared secrets by path. An empty secret disables its check; this is for local development only (registry-service logs a warning at start).
  • Observability: management.endpoints.web.exposure.include = health,info,prometheus. Traces go by OTLP/HTTP to OTEL_TRACES_ENDPOINT (compose sets http://otel-collector:4318/v1/traces), sampling probability TRACING_SAMPLE_RATE (default 1.0: every request, fine for dev, lower it in production). Prometheus scrapes /actuator/prometheus of each service (jobs notification-service, user-service, registry-service in infra/prometheus/prometheus.yml). We did not write any custom metrics: only the Spring/JVM/HTTP ones.
  • Clock: a single Clock.systemUTC() bean so tests can fix time.
  • Prototype RestClient.Builder bean: each client customises its own copy (base URL), so clients never share a builder (a Spring Boot 4 gotcha we hit).
  • Docker image: multi-stage. Build stage maven:3.9-eclipse-temurin-21 (mvn -B -q -DskipTests package), run stage eclipse-temurin:21-jre as non-root user app (uid 10001), java -XX:MaxRAMPercentage=75 -jar /app/app.jar, port 8080. No secrets are baked in.

Building and testing (any service)

This machine's default JDK is 26, so always pin Java 21 for Maven:

cd services/<service>
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk
./mvnw -q test                 # unit + integration tests (integration tests need Docker for Testcontainers)
./mvnw -q -DskipTests package  # builds target/<service>-0.0.1-SNAPSHOT.jar

# the container image (what compose runs):
cd ../..
docker compose build <service>
docker compose up -d <service>

notification-service

our code built Port 8085 (dev), database notification, services/notification-service. Java package root app.adera.notification.

Responsibilities

  1. Kratos courier. Kratos is configured with the HTTP courier strategy: every login/registration code it would send goes to POST /internal/kratos/sms or /internal/kratos/email. This service rate-limits per recipient, optionally applies a live allowlist, calls the selected provider (console or Twilio for SMS, Mailpit or Resend for email) and writes a send_log row with no code and no full recipient.
  2. Partner notification platform. Mini-app backends call /v1/* with RSA-signed requests. The service verifies the signature and the caller's address, resolves the user's pseudonymous id through user-service, enforces templates and quotas, queues the notification, delivers it in background workers (SMS, email, in-app + push) with retry, and sends signed callbacks.
  3. In-app inbox. The bell-menu data for a signed-in user (/api/v1/me/notifications).
  4. Staff visibility. Template management and the delivery log/usage numbers under /admin/api/v1/notification/*.
  5. Our signing key. Signs every /v1 response and every callback; publishes the public half at /.well-known/jwks.json.

Not authenticated

/internal/kratos/* (courier) and /dev/messages have no authentication of their own: GatewayTrustFilter only covers /admin/api/** and /api/**, and PartnerAuthFilter only /v1/**. They are safe only because the gateway does not route them and the port is bound to 127.0.0.1. A shared-secret header is on the to-do list (not built yet). /actuator/* is also open inside the network.

DeliveryService.deliver re-checks the user at delivery time (phone, email and mute may have changed): in DEV the synthetic users (u_p_test_*) are marked SENT without sending (attempt provider sandbox; real users go through the dev providers like any message); unreachable user, no phone/email, muted, or not on the live allowlist end terminally as UNREACHABLE or SUPPRESSED; in-app notifications always write the inbox row first (idempotent per notification), then push to each active token; push is best effort.

Startup safety checks

  • ProviderSafetyCheck: NOTIFY_DEV_ENDPOINTS=true together with a real SMS or email provider aborts startup (dev endpoints would expose one-time codes). On ready it logs NOTIFICATION MODE: sms=... email=... allowlist=... devEndpoints=... at WARN.
  • PartnerSafetyCheck: PARTNER_ALLOW_PRIVATE_CALLBACKS=true together with any real provider (SMS, email or push) aborts startup. On ready it logs PARTNER PLATFORM: push=... workers=... privateCallbacks=....
  • SigningKeyHolder: no PARTNER_SIGNING_PRIVATE_KEY_B64 with a real SMS/email provider aborts startup; otherwise an ephemeral key ephemeral-xxxxxxxx is generated and a warning is logged (partners cannot rely on it across restarts).
  • Real providers fail fast with a clear message when credentials are missing (Twilio account SID/token and a messaging service SID or number; Resend key and sender; Firebase credentials).

Infisical loader

InfisicalEnvironmentPostProcessor runs before the Spring context exists. If INFISICAL_TOKEN, INFISICAL_PROJECT_ID and INFISICAL_DOMAIN are set, it calls GET {domain}/api/v4/secrets?projectId=...&environment={INFISICAL_ENV, default dev}&secretPath={INFISICAL_PATH, default /notification}&expandSecretReferences=true (5 s timeout, HTTP/1.1 pinned because the default h2c upgrade makes Infisical answer 400) and adds every returned secret as the lowest-priority property source named infisical. A real environment variable therefore always wins, which makes local overrides easy. A failure is logged (message only, never the token) but not fatal: dev providers still start; a real provider then fails fast naming the missing key. Because it runs before logging exists it uses DeferredLogFactory, or its messages would be lost.

Keys currently present in Infisical dev /notification (names only, checked 2026-10-25): PARTNER_SIGNING_KEY_ID, PARTNER_SIGNING_PRIVATE_KEY_B64, RESEND_API_KEY, RESEND_FROM_EMAIL, RESEND_FROM_NAME, TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_MESSAGING_SERVICE_SID, TWILIO_PHONE_NUMBER. FIREBASE_SERVICE_ACCOUNT_B64 is not there yet. The other folders (/, /infra, /kratos, /gateway, /user) were empty. Only notification-service has this loader; user-service and registry-service read their secrets from environment variables set by compose from .env.

user-service

our code built Port 8086 (dev), database users, services/user-service. Package root app.adera.user.

Responsibilities

  1. The user record. Kratos owns identity, login and sessions; this service owns everything else about the person, keyed by the Kratos identity id (user id = Kratos identity id). Profile, language/market/timezone, optional location, free-form extra JSON, verification tier and status.
  2. Avatars. Decode, centre-crop, resize (at most 512 px), flatten transparency, re-encode as JPEG, store in RustFS, hand out 60-minute signed links.
  3. Devices and push tokens. One row per app installation with an FCM token.
  4. Gateway session check. /internal/auth/verify turns Kratos' whoami into the X-User-Id header the gateway forwards.
  5. Kratos registration webhook. Creates the profile row when an identity is created.
  6. Logout. One call removes the push token and revokes the Kratos session (Kratos has no native-app logout hook).
  7. Pseudonymous aliases and mute preferences. A different u_p_... id per user per app; per-app mute switches. Internal API for notification-service.

registry-service

our code built Port 8087 (dev), database registry, services/registry-service. Package root app.adera.registry.

Responsibilities

  1. The mini-app registry. Each mini app: identity, localized name/description, logo, brand colour, categories, markets, publisher and support contacts, entry URL, allowed origins, status (DRAFT, LIVE, PAUSED, KILLED), priority, ratings.
  2. What an app may do. Capabilities (granted/denied/suspended per app), payment settings, per-channel notification limits, per-environment allowed server addresses.
  3. Partner keys. Register a partner's PUBLIC RSA key (or generate a pair once, for DEV work); revoke; at most 5 active keys per environment (DEV and PROD are counted separately; new key ids are ak_dev_... / ak_prod_...).
  4. Staff. Roles VIEWER, ADMIN, SUPER_ADMIN. The role lives in Kratos metadata_public.role (writable only through the admin API) and is mirrored in table staff for listing and status. The first super admin is bootstrapped from BOOTSTRAP_SUPER_ADMIN_EMAIL.
  5. Staff gate for the gateway. /internal/staff/verify: valid session, active staff, aal2 (authenticator app done) gives X-Staff-Id and X-Staff-Role.
  6. Catalog for users. LIVE apps with permissions, anonymous reviews and ratings, "report this app".
  7. Moderation and audit. Hide reviews, work through reports, append-only audit of every staff change.
  8. Internal API for notification-service: partner key lookup and app context.

Notes and rough edges seen while documenting
