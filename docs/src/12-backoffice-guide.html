12. Backoffice guide (staff operator's manual)

How to do your job in the Adera backoffice, step by step: sign in, manage a mini app from creation to LIVE, answer "why didn't my notification arrive?", handle reports, look after users and colleagues. It describes what the dashboard does today, written from the code (backoffice/src and the three services' controllers), not from plans. For the API calls behind each screen see 11. Backoffice and 8b. Staff API.

How this page is organised

1 Roles, 2 Signing in (with troubleshooting), 3 Screen by screen (all nine sections: login, dashboard, mini apps with every tab, moderation, users, notifications, staff, audit log, system), 4 A mini app from zero to LIVE (one end-to-end tutorial), 5 "Why didn't my notification arrive?", 6 Recipes, 7 What the backoffice cannot do yet. Section 3.5 is the users manual and 3.7 the staff-management manual.

Conventions

Addresses are the development stack: dashboard http://127.0.0.1:9080/backoffice/, Mailpit (the dev inbox) http://127.0.0.1:8025. Example values (adera-fix, 203.0.113.10, support@adera-fix.example) are made up; 203.0.113.0/24 is a range reserved for documentation. No screenshots are included: the folder backoffice/tests/ui/out was empty when this was written, so screens are described in words.

1. Who this is for, and what each role can do

2. Signing in

Staff need two proofs: a one-time code sent to your email, and a code from an authenticator app (this is the "second factor"). Until both are done the admin API answers 403 mfa_required. The page has a three-step indicator: Email, Emailed code, Authenticator.

2.1 First time ever on this account

  1. Open http://127.0.0.1:9080/backoffice/. Any address in the dashboard sends you to /backoffice/login and the page title "Staff sign-in".
  2. Email step. Type your work email in "Work email" and press Send me a code. The address is lower-cased for you. If the field is empty or not an email the form says so. The account must already be a staff member (see 2.5 and 3.7).
    • If Kratos does not know the address, the page shows "This account does not exist or has not setup sign in with code." and nothing is sent (checked against the running stack: no email was produced).
  3. Emailed code step. The page says "We sent a 6-digit code to ... It is valid for 5 minutes." In the development stack nothing real is sent: a blue box "Development stack" links to Mailpit. Open http://127.0.0.1:8025; the newest message is from "Adera" with the subject Use code NNNNNN to log in. Type the six digits (the box accepts digits only) and press Continue. A wrong or expired code shows Kratos' own message; Use another email starts over. (In a real environment the same email arrives in your inbox and the blue box is not shown, because BACKOFFICE_DEV_HINTS is false.)
  4. Authenticator setup step (only when this account has no authenticator yet). The page says "First time here: set up an authenticator app" and shows:
    • a QR code: in your phone's authenticator app choose "scan a QR code";
    • the Secret as text with a copy button, for apps or password managers where you type or paste it ("enter a setup key", account name anything, type "time based");
    • a Setup link (otpauth://totp/...) with a copy button, for password managers that import links.
    Any app that supports standard TOTP (time-based, 6 digits, 30 seconds) works: Google Authenticator, Microsoft Authenticator, Authy, Aegis, 2FAS, 1Password, Bitwarden. The secret is private: anyone who has it can generate your codes. Do not paste it into chat or tickets.
  5. Type the 6-digit code the app shows now into "Code from the authenticator app" and press Confirm and sign in. If the account is still not at the second level the page asks for the next code ("The authenticator app is set up. Enter the next code it shows (the same code cannot be used twice)."): wait for the app's number to change and enter the new one.
  6. You land on the Dashboard. The top bar shows your email and a role tag (Viewer (read only), Admin, Super admin) and Sign out.

2.2 Every later login

  1. Email, then the emailed code, exactly as above.
  2. The page now asks "Enter the 6-digit code from your authenticator app for ...". Type the current code and press Sign in. Use another account goes back to the start.

Kratos refuses an authenticator code it has already accepted. If you sign out and in again within the same 30-second window, wait for the next code. If you reload the page between the emailed code and the authenticator step, the page resumes at the authenticator step ("Resuming sign-in...").

2.3 Signing out

Press Sign out (top right). The session is revoked at Kratos and the tab's stored copy is deleted; you return to the login page. Closing the tab also ends your access, because the session token is kept only in that tab's sessionStorage, never in localStorage and never in a cookie. A new tab, even in the same browser, needs a new sign-in. Reloading the same tab keeps you signed in.

2.5 The first (bootstrap) super admin

A fresh install has nobody who can add staff, so registry-service creates the first SUPER_ADMIN at start from the environment variable BOOTSTRAP_SUPER_ADMIN_EMAIL, but only when no active super admin exists. Look for the value in the repository-root .env (it is also the address tests/e2e/*.py sign in with; this page does not print it). The account is a normal Kratos identity: sign in with that email as in 2.1, and enrol your authenticator. On the Staff screen it carries the gold tag "bootstrap super admin". After you have added real super admins you can promote and demote freely; the only rule is that the last active super admin cannot be removed (see 3.7). Changing the variable later does not create a second bootstrap account while an active super admin exists.

2.6 Troubleshooting sign-in

Troubleshooting

(1) "It asks for an authenticator code but never showed me a QR code." That account already has an authenticator enrolled, so the page goes straight to "Enter the 6-digit code from your authenticator app". The usual cause on a dev machine is that the end-to-end script tests/e2e/staff.py (or npm run smoke, or a script run with ADERA_STAFF_EMAIL set to your address; partner.py, admin_users.py and seed_demo.py use a temporary account by default) signed in first and enrolled its own authenticator; staff.py keeps that secret in tests/e2e/.staff-totp-<email>.json (gitignored, mode 0600; treat it as a secret). You do not have that secret in your phone. The fix is to remove the enrolled authenticator, so the next sign-in shows the QR code again. This is a Kratos admin API call on the machine that runs the stack (port 4434 is published on 127.0.0.1 only and the gateway blocks /kratos/admin); the dashboard has no button for it (the Staff screen has no such action, so a SUPER_ADMIN cannot do it from the UI today):

# 1. find the identity id of the account (replace the address with the account's email)
curl -s -G --data-urlencode "credentials_identifier=you@example.com" \
  http://127.0.0.1:4434/admin/identities | python3 -c 'import json,sys;[print(i["id"], sorted(i["credentials"])) for i in json.load(sys.stdin)]'
# prints for example:  0b648e27-....  ['code', 'totp']        (totp in the list = an authenticator is enrolled)

# 2. delete only the authenticator credential (the account, its role and the email-code login stay)
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE http://127.0.0.1:4434/admin/identities/<id>/credentials/totp   # 204 = done

Then sign in again: after the emailed code you get the QR code and enrol your own authenticator. If the e2e scripts used that account before, delete tests/e2e/.staff-totp-<email>.json too, otherwise they will try the old secret. See also the note below about keeping tests and people on separate accounts. Anyone who can reach port 4434 can do this to any account, which is why it is local-only.

(2) "No one-time code arrived." Check, in this order: the email address (an unknown address shows the "account does not exist" message instead); Mailpit in dev (the code is the newest message to that address; real mode: spam folder); and the per-recipient email limit in notification-service. Every message Kratos asks to send passes through a per-recipient limit of 10 emails per hour and 20 per day (LIMIT_EMAIL_PER_HOUR, LIMIT_EMAIL_PER_DAY; defaults in application.yml, not overridden in docker-compose.yml). Beyond that the message is recorded as suppressed (rate_limited) and no email is produced, but the page still says "We sent a 6-digit code". Wait for the hour to pass.

(3) "Too many sign-in attempts from this address (the limit is 10 per minute)" / HTTP 429. The gateway allows 10 login-step submits per minute per IP address. One sign-in uses three or four submits (send code, check code, enrol or authenticator code), and everyone behind the same office address shares the counter. Wait a minute. Do not run npm run smoke or the Python e2e scripts at the same time as people sign in.

(4) Lost or replaced phone. There is no self-service recovery. Another SUPER_ADMIN cannot reset it from the dashboard either (no such button). Someone with access to the Kratos admin port must run the two commands in (1) for your account; then enrol the new phone. To be safe, keep at least two super admins and enrol the same account on a second device (scan the QR code on both phones during setup: the secret cannot be shown again later).

(5) Other messages. "This sign-in attempt expired. Start again." (the flow lasts 10 minutes); "The sign-in session is no longer valid. Start again."; "The server could not be reached. Check your connection and that the gateway is running."

E2E scripts and your own account

The bootstrap super admin has a person's authenticator app enrolled, so the e2e scripts never sign in as it. partner.py, admin_users.py and seed_demo.py create a temporary staff account with tests/e2e/tempstaff.py (a random tempstaff-xxxx@adera.local address, role ADMIN, authenticator enrolled by the helper) and remove it when they finish, even if they fail: the Kratos identity, the staff row, the secret file tests/e2e/.staff-totp-<email>.json and the email rows in send_log. The helper refuses to run unless the dev endpoint (/dev/messages) answers.

  1. python3 -I tests/e2e/tempstaff.py creates and removes one account as a self-test (--role SUPER_ADMIN for another role; clean removes leftovers of an interrupted run).
  2. To use a real account instead, set ADERA_STAFF_EMAIL: the script reads the emailed code from the dev endpoint and asks for the authenticator code (or takes it from ADERA_TOTP); nothing is created or deleted.
  3. staff.py still accepts an email on the command line: python3 -I tests/e2e/staff.py test-viewer@example.test logs that account in and prints the result of /admin/api/v1/me. npm run smoke and the Playwright walkthrough use STAFF_EMAIL (or the bootstrap value in .env for the smoke test).

3. Screen by screen

The left menu has eight entries: Dashboard, Mini apps, Moderation, Users, Notifications, Staff, Audit log, System (Login is the ninth screen, shown when you are signed out). Every table row shows times in your browser's local time to the second; hover a time to see the exact stored value (UTC). Destructive actions ask "are you sure?" first and keep the dialog open if the server refuses, showing the reason inside it. Server errors appear in a red box with the plain-language message and, below it, "HTTP status · code". Validation errors (validation_failed) also put one message next to each offending field.

Under every screen, "Audited" says what is written to the append-only audit log (section 3.8): who, role, action, target, details, IP and time.

For: proving who you are. Full steps, authenticator apps and troubleshooting are in section 2. Fields: Work email; 6-digit code; Code from the authenticator app (first time) or Authenticator code (later). Buttons: Send me a code, Continue, Use another email, Confirm and sign in, Start over, Sign in, Use another account. Tab General

For: the logo and every descriptive field. Logo: Upload logo / Replace logo / Remove logo (confirmation: "An app without a logo cannot go LIVE."). The server accepts up to 2 MiB, decodes the image, scales it to at most 512 px and stores a PNG. Checks you can see: "The logo is larger than 2 MiB.", "Use a PNG, JPEG or WebP image.", server: "not a supported image (use PNG, JPEG, GIF or BMP)", "could not read the image, it may be corrupt", "image dimensions are too large", 413 file_too_large.

Known mismatch

The file picker and the browser check allow WebP, but the server does not accept WebP (it accepts JPEG, PNG, GIF, BMP, and the picker filters GIF and BMP out). Use PNG or JPEG. A WebP file passes the browser check and is then refused by the server with "not a supported image".

Then read-only facts (rating, created, updated, display name, logo image id) and the same form as New app, where the slug is fixed. Only fields you changed are sent, so the audit log shows exactly what changed; if nothing changed the form says "Nothing was changed." and after saving a green "Saved: name, supportEmail" appears. Audited: app.update (details: the list of field names), app.logo (new image id), app.logo.remove. Worked example: open adera-fix, tab General, Upload logo, choose adera-fix-logo.png (square, under 2 MiB); the logo appears and the amber "No logo yet" note disappears.

Tab Notification limits

For: keeping cost and spam under control, per channel (SMS, EMAIL, IN_APP). Four numbers per channel, all counted in UTC days except the lifetime total: Max per user per day (messages to one user), Max per day (messages from this app), Max distinct users per day (different people reached), Max total (lifetime on that channel, per environment). The table shows each as a number, "unlimited" or "0 (none allowed)", and "Configured: yes / no limits set". Edit opens a dialog with, for each number, Unlimited or Limit to and a whole number. Server: "must be a whole number >= 0, or null for unlimited".

Empty (null) versus 0
  • Unlimited (empty, null): no cap on that measure. Example: Max total unlimited means the app can send forever; Max per day unlimited means no daily cap.
  • 0: nothing is allowed. A 0 in any of the four numbers makes every send on that channel fail with 429 quota_exceeded (naming the limit, e.g. max_per_day), because the first message already exceeds a limit of zero. Use it to switch a channel off without touching capabilities. Example: SMS Max per day 0 stops SMS today; set it back to 100 to resume.
  • A channel with no limits set at all ("no limits set") is treated as unlimited. This only happens if the capability was never granted through the dashboard; granting it creates the defaults above.
  • Example: maxPerUserPerDay 3, maxPerDay 100, maxDistinctUsersPerDay 100, maxTotal unlimited: one person gets at most 3 SMS a day, 100 SMS go out per day in total to at most 100 different people, and there is no lifetime cap. The 4th SMS to the same user that day is refused with quota_exceeded / max_per_user_per_day.

A refused request uses no quota. Limits are per environment for the counters (Usage tab) but one set of limits applies to both DEV and PROD.

Audited: limit.set (channel and the new values). Worked example: row SMS, Edit; Max per user per day: Limit to 2; Max per day: Limit to 200; Max distinct users per day: Limit to 200; Max total: Unlimited; Save limits; the SMS row now reads 2 / 200 / 200 / unlimited.

Tab Environments and IPs

For: the partner's server addresses. A partner's call is accepted only if it comes from a registered address for this deployment's environment, so a stolen key is useless from anywhere else. Two editable cards, DEV (the dev deployment; works for any app that is not KILLED) and PROD (the prod deployment; only while the app status is LIVE; the range 0.0.0.0/0 that matches everything is refused for PROD). You can fill in both, but a deployment is exactly one environment (ADERA_ENV): the card of the environment this deployment runs is tagged ACTIVE on this deployment, the other stored, not used here with a note that it applies on the other deployment. A new app starts with an empty list in both: nothing can call yet (yellow note "Empty: no server can call in this environment."). Enter one address or CIDR range per line (or comma separated), IPv4 or IPv6, at most 50; Save addresses. The list shown afterwards is what the server stored: a single address is stored as /32 (IPv6 /128) and duplicates are dropped. Errors: "'999.1.1.1' is not a valid IP address or range", "must be a list (max 50) of IPs or ranges", "a range that matches every address (/0) is not allowed for PROD". Audited: environment.set (environment, the stored list). Worked example: DEV card: 203.0.113.10; PROD card: 203.0.113.10 and 198.51.100.0/24; Save each card. Tab Partner keys

For: how the partner proves who they are. They sign each request with a private key that only they hold; you store the matching public key. The table lists every key: Key id (ak_dev_... or ak_prod_..., older keys ak_test_... / ak_live_..., which the partner sends in X-Adera-Key-Id), Environment (with an "active here" or "not active here" tag), Algorithm, Fingerprint (SHA-256 of the key, to check you have the right one), Label, Status (ACTIVE or REVOKED), Expires, Created, Revoked. A key past its expiry stops working even though it is still listed ACTIVE. At most 5 active keys per environment (409 too_many_active_keys: "This environment already has the maximum of 5 active keys. Revoke one first."), which is what makes rotation possible.

  • Register a public key (preferred): choose Environment (DEV or PROD; the active one is the environment this deployment runs, and for the other you get a warning notice), an optional Label ("partner backend 2026"), an optional expiry (must be in the future: "must be in the future"), and paste the PEM. The PEM must begin with -----BEGIN PUBLIC KEY----- and be an RSA key of 2048 bits or more. A private key is refused with "that is a PRIVATE key. Never send it..."; other messages: "must be a PEM public key starting with -----BEGIN PUBLIC KEY-----", "RSA key must be at least 2048 bits", "not a valid RSA public key".
  • Generate a key pair: the server makes an RSA 3072-bit pair, stores the public half and shows the private key once in a dialog that cannot be closed until you tick "I have saved the private key somewhere safe." It has Copy and Download .pem buttons (file name like adera-1a2b3c4d-dev-ak_dev_...pem). Choosing PROD shows a red warning: a private key that passes through this screen is exposed to whoever is looking. Use this only for DEV, and send the key to the partner over a secure channel, never plain email or chat.
  • Revoke (on an ACTIVE row, with confirmation): "The partner's requests signed with this key are refused immediately. This cannot be undone." Their calls then fail with 401 key_revoked_or_expired.

How a partner makes a key pair (they do this on their own machine, with OpenSSL 1.1 or newer):

openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out partner-private.pem   # KEEP SECRET, never send, never paste into the backoffice
openssl rsa -in partner-private.pem -pubout -out partner-public.pem                    # this one is safe to share
head -1 partner-public.pem                                                             # must print: -----BEGIN PUBLIC KEY-----

(These commands were run to check the output headers; OpenSSL 3.6.5.) Paste the contents of partner-public.pem (the whole block, BEGIN and END lines included, which you can get with cat partner-public.pem) into "Public key (PEM)". The file partner-private.pem (header -----BEGIN PRIVATE KEY-----) never leaves the partner's server; openssl genrsa also works. How the partner then signs requests is in Security: signing and 8c.

Audited: key.register (target type partner_key, target = the key id; details: app id, environment, fingerprint) and key.revoke. Because the target is the key id, these events do not appear in the app's own "Audit" tab (which filters on the app id); find them in the Audit log with Action key. or Target type partner_key. Worked example (rotation): the partner sends partner-public.pem; Register a public key; Environment LIVE, Label fix backend 2027, paste, Register; the new row appears with a fresh key id. The partner switches its servers to the new id; when the old key shows no traffic, Revoke it.

3.7 Staff (add, change role, deactivate)

For: deciding who may sign in and with what power. SUPER_ADMIN only (others see "Staff management is for super admins."). Adding a colleague

  1. Press Add staff member. Enter their work Email (validated: "Not a valid email address", server "must be a valid email address") and pick a Role (default VIEWER, so a mistake is safe). Add.
  2. What happens: if the address has never signed in, an identity is created for it in Kratos with the role stored as admin-only metadata (a user cannot edit it through any self-service flow). If the address already has an account (for example it is also a customer), that account is granted the role. If it is already staff, its role is set and it is re-activated; the call is idempotent. No email is sent to them: tell them yourself.
  3. How the new person logs in the first time: they open the dashboard address, type their email, read the emailed code, enter it; the page then shows the QR code and secret for the authenticator (section 2.1); they enter the first code and are in, with the role you chose. Their second sign-in asks for the authenticator code only.
Add on an existing member

Adding an address that is already staff changes that person's role and re-activates them, and it obeys the same protections as Change role (below): you cannot demote or disable yourself (cannot_demote_self) and the last SUPER_ADMIN cannot be demoted (last_super_admin). Fixed 2026-10-26; before that this path skipped both checks.

Changing a role

Change role, pick the new role, Save role (disabled until you pick a different one). Takes effect at once for new requests (the server reads the role on each call). Deactivate (confirm: "Their dashboard sessions are revoked and they can no longer sign in"): the status becomes DISABLED, the role is removed from their Kratos account and all their sessions are revoked, so their next click shows "Your session ended" and signing in again gives "not an active staff member". Their authenticator stays enrolled. Reactivate restores the stored role and lets them sign in again.

Protection against locking everyone out

  • Cannot lower or disable yourself while you are an active super admin: 409 cannot_demote_self "You cannot lower or disable your own account. Ask another super admin."
  • Cannot remove the last active super admin (demote or deactivate): 409 last_super_admin "This is the last active super admin. Add or promote another one first."

Audited: staff.create (email, role) and staff.update (role, status); target type staff, target = the person's identity id. 4. Tutorial: a mini app from zero to LIVE (and how to stop it)

This is the whole lifecycle as one story. You are an ADMIN onboarding Adera Fix (slug adera-fix), a partner that wants to send "your job was accepted" messages by SMS and in the app. Sign in first (section 2). Each step names the screen from section 3 for the full field list.

  1. Create the app. Mini apps, New app, fill the form as in 3.3 (slug adera-fix, name Adera Fix, support email support@adera-fix.example, market ET), Create app. Status DRAFT: the partner can use only DEV.
  2. Logo. Tab General, Upload logo, a square PNG or JPEG under 2 MiB. (Not WebP, see the mismatch note in 3.3.) The amber "No logo yet" note disappears.
  3. Support email. If you skipped it in step 1: tab General, field "Support email" support@adera-fix.example, Save changes ("Saved: supportEmail"). The blue note at the top now says "Ready for LIVE" in green.
  4. Capabilities. Tab Capabilities. Row notify.sms: Change, GRANTED, Save. Row notify.inapp: the same. Skip notify.email unless the partner needs email. Without notify.sms a DIRECT message cannot go by SMS: it falls back to email when the user has an email and notify.email is granted, otherwise the partner gets 403 capability_not_granted. No reason text is needed for notify.*. If the partner also needs, say, the user's city, grant location.coarse with a reason such as To show technicians near you (users will read it).
  5. Notification limits. Tab Notification limits. Granting created defaults; look at them and tune. For SMS, which costs money: Edit, Max per user per day 2, Max per day 200, Max distinct users per day 200, Max total 5000, Save limits. Remember empty (Unlimited) = no cap and 0 = nothing allowed (3.3 explains with examples). Check IN_APP too (default 20 per user per day, 10000 per day).
  6. Allowed server IPs. Tab Environments and IPs. Ask the partner for the public IP addresses their servers call from (outbound). DEV card: 203.0.113.10, Save addresses. PROD card: the production addresses, for example 203.0.113.10 and 198.51.100.0/24, Save addresses. Both lists start empty and nothing can call until you fill them.

Later, register the PROD key the same way with Environment PROD and the partner's own public key.
  8. Create a template. To retire a template without deleting it: Deactivate. To make it temporary set "Expires".
  9. Let the partner test on the dev deployment. With the DEV key (the dev deployment only accepts DEV keys: 403 wrong_environment otherwise) and a DEV address the partner sends to the synthetic users named u_p_test_anything (u_p_test_unreachable and u_p_test_muted exercise those paths). Nothing real is sent in DEV (the dev providers are console SMS and Mailpit; for the synthetic users delivery is simulated: QUEUED then SENT with provider sandbox; in PROD they are refused with 422 synthetic_user_not_allowed). How to call: 8c and Guide: send a notification. You watch it in tab Notification log (Environment DEV).
  10. Go LIVE. The checklist: logo, support email, a PROD key, PROD addresses, a granted notify.* capability, at least one active template. Only the first two are enforced by the dashboard. Press the status button LIVE and confirm. If something is missing the dialog already warned and the server answers "Not ready for LIVE: missing a logo and a support email." (it names whichever is missing). On success the tag turns LIVE (green), the app is visible to users, and PROD calls are accepted.
  11. Watch it. Tab Notification log, Environment LIVE: new rows appear as the partner sends. Tab Usage (LIVE): today's sent count against Max per day, users reached against Max distinct users, lifetime against Max total. Dashboard: "Notifications, last 24 hours". When a row is FAILED or SUPPRESSED, open it and read the "Why did this not arrive?" box (section 5).
  12. Pause or kill. Different tools for different problems:
    • PAUSED (any ADMIN, reversible): the app disappears from the catalogue and the partner's PROD calls get 403 app_paused; DEV still works. Use for "stop for an hour while we talk".
    • KILLED (emergency): everything is refused immediately, DEV too (403 app_killed). Only a SUPER_ADMIN can bring it back (status buttons, confirm).
    • To stop only one channel without hiding the app: set that channel's limits to 0 (Notification limits) or change notify.sms to SUSPENDED (Capabilities); the partner then gets quota_exceeded (limits at 0) or capability_not_granted (suspended; note a DIRECT message may fall back to email if notify.email is granted and the user has an email). To stop one message type: Deactivate the template.
    • Compromised key: Revoke it on tab Partner keys (calls with it fail at once with key_revoked_or_expired) and register a new one.
    Every one of these steps except template changes is in the audit log (3.8).

5. "Why didn't my notification arrive?"

Start in the app's tab Notification log (or the global Notifications screen). Find the row by the partner's External id, open details, read the coloured box, then use the tables below.

No row at all?

A request that is refused before it is accepted leaves no trace in the log: bad signature, address not allowed, app not active, unknown or inactive template, invalid values, unknown or unreachable user, quota exceeded (user_unreachable is answered immediately for unknown, suspended and deleted users). Those are returned to the partner as an error code in the HTTP answer. Ask the partner for the exact code and look it up on System, "Partner-facing codes" or Reference: error codes. If the app was PAUSED or KILLED at that moment, that is the answer. Exception: a user who muted the app is accepted and logged as SUPPRESSED.

Status glossary

StatusMeaningWhat to do
QUEUEDAccepted and waiting for the delivery worker (it polls every second).Normally gone within seconds. If rows stay QUEUED, check System: notification-service may be down.
PROCESSINGA worker is sending it right now.Wait. If stuck for minutes, tell engineering.
RETRYINGAn attempt failed for a temporary reason (provider timeout, 5xx, rate limit, our own dependency down). It is retried with growing waits: 30 s, 1 min, 2 min, 4 min... at most 1 hour apart, up to 8 attempts, and only until the message expires.Read "Next attempt" and the last attempt's error code. Nothing to do unless it never recovers.
SENTHanded to the provider (SMS, email) or stored in the user's inbox with push attempted. Adera does not track handset delivery receipts, so SENT is not proof the phone showed it. For the synthetic u_p_test_* users in DEV nothing is really sent (provider sandbox); in this dev stack SMS goes to the console log (provider console), email to Mailpit and push to a fake (fcm-fake).If the user says it did not arrive: check the user's mute preferences and phone/email on the user page, the provider's own log, and whether the user is a synthetic u_p_test_* one (simulated in DEV).
FAILEDPermanent failure (the provider said the request itself is wrong, such as a bad number or rejected sender, error codes like twilio_http_400) or all 8 attempts failed (max_attempts:...). Never retried.Read the error code in the attempts table; fix the cause (for example the user's number) and have the partner send a new message with a new externalId.
UNREACHABLENo way to reach the person: the account was deleted or suspended (user_unreachable) or there is no phone (no_phone) or email (no_email) on file.Look the user up (3.5). Reactivate if suspended by mistake.
SUPPRESSEDDeliberately not sent: the user muted this app's channel (recipient_opted_out, set in the app window's menu) or, with a real provider and an allowlist active, the recipient is not on it (not_allowlisted).Check the user's "Mute preferences per app". An allowlist is an operations setting (NOTIFY_LIVE_ALLOWLIST).
EXPIREDIt kept failing until its deadline passed (the partner's ttlSeconds, default 24 hours, between 60 seconds and 7 days).Same as FAILED: find the recurring error in the attempts table.

Reading the attempts and callbacks tables

  • Attempts: one row per try with Channel, Provider (sandbox, console, twilio, mailpit, resend, fcm-fake, fcm), Outcome and Error code. Outcomes: OK (provider accepted), TRANSIENT (temporary failure, will retry), PERMANENT (will not retry), SKIPPED (not tried: not_allowlisted, or no_devices for push when the user has no registered phone). "No attempt was made" means the decision came before any provider was called (for example UNREACHABLE or SUPPRESSED).
  • For IN_APP messages the inbox entry is the reliable part: it is stored first, and the message is marked SENT even if there is no device to push to or push is only the fake provider. Push error codes push_unavailable (temporary) and token_unregistered (dead token, retired) refer to the optional push.
  • Callbacks are the partner's webhook calls telling them the final status (only when they sent a callbackUrl). Status PENDING (waiting for the next try), PROCESSING, DELIVERED (the partner answered 2xx) or FAILED (gave up after 8 tries over about a day, 1 minute doubling up to 6 hours). If the callback is not DELIVERED, the partner's server is the problem, not the notification; the last HTTP status and last error say what their server answered.

A quick checklist

  1. Is there a row? No: get the error code from the partner (see the box above).
  2. Environment DEV? Then the dev providers (console, Mailpit) were used, and for synthetic u_p_test_* users nothing was sent by design.
  3. Status and reason: use the tables above.
  4. Muted or unreachable? Open the user (3.5): status, phone and email, "Mute preferences per app".
  5. Still unclear? System page: is notification-service UP? Is the provider mode what you expect (dev: SMS to the console log, email to Mailpit)?

6. Common workflows (recipes)

6.1 Onboard a new partner app

  1. Mini apps, New app (3.3).
  2. General: logo and support email.
  3. Capabilities: grant the notify.* you agreed.
  4. Notification limits: set sensible numbers.
  5. Environments and IPs: partner's server addresses for DEV and PROD.
  6. Partner keys: register their DEV public key; send them the key id.
  7. Templates: create the messages.
  8. Partner tests on the dev deployment.
  9. Register their PROD key; set status LIVE.
  10. Watch Notification log and Usage for the first day. (Details: section 4.)

6.2 Rotate a partner key

  1. The partner generates a new pair (3.3 commands) and sends the new partner-public.pem.
  2. Partner keys, Register a public key, same environment, a label with the year, paste, Register. (An environment can hold 5 active keys, so both work during the changeover; if you already have 5, revoke the oldest unused one first.)
  3. Give the partner the new key id; they switch their servers.
  4. When the partner confirms the switch (and the Notification log keeps showing normal traffic), Revoke the old key (confirm). Its calls now fail with 401 key_revoked_or_expired.
  5. Check Audit log, Action key., for the register and revoke entries.

6.3 Temporarily stop an app's notifications

  1. Whole app (LIVE traffic stops, app hidden from users): status PAUSED; later LIVE (or DRAFT). Emergency: KILLED (SUPER_ADMIN to undo).
  2. One channel only: Notification limits, set that channel's four numbers to 0 (or "Max per day" 0, which is enough); later restore them. Or Capabilities, change notify.sms to SUSPENDED with a reason such as "investigating complaints", later GRANTED again.
  3. One message type: Templates, Deactivate.
  4. Tell the partner which error code to expect (app_paused, quota_exceeded, capability_not_granted, template_inactive).

6.4 Investigate a user complaint ("I didn't get the code or message", "I can't use the app")

  1. Users, search the phone or email they gave (or their user id). Open the user.
  2. Status: SUSPENDED or DELETED explains a blocked app (403 account_suspended or account_deleted). ADMIN and above: the "Audit for this user" card shows who changed it and why.
  3. "Mute preferences per app": a muted channel for that app explains SUPPRESSED messages. Check phone and email exist (masked is fine for a VIEWER).
  4. Find the app (Mini apps), tab Notification log, filter Status or Channel, look for the time of the complaint, open details (section 5).
  5. For sign-in problems use section 2.6 (limits, Mailpit, allowlist). Do not change the account without a reason; every status change needs one and is audited.

6.5 Moderate a report

  1. Moderation, Reports tab (OPEN by default).
  2. Read Reason and Details; click the app link for context (its Reports and Reviews tabs).
  3. Act on the app if needed (status PAUSED or KILLED, or contact the partner via the support email).
  4. Return and press Resolve (acted on) or Dismiss (no action). Reopen if it comes back.
  5. For an abusive review: Reviews tab, Hide (confirm); the rating is recalculated.

6.6 Add a colleague

  1. Staff (SUPER_ADMIN), Add staff member, their work email and the lowest role that suffices (VIEWER by default).
  2. Tell them to open /backoffice/ and sign in with that email: emailed code, then QR code and first authenticator code.
  3. Check the row is ACTIVE.
  4. Change role later with Change role; never re-add an existing member to change a role.
  5. Make sure at least two people are SUPER_ADMIN.

7. What the backoffice cannot do yet

Each item below was checked against the code on 2026-10-25.

Server-side paging and search of mini appsThe list returns everything at once (at most 200 apps when no status filter is chosen) and the search box filters in the browser.
Payments are not enforcedThe Payment tab stores currencies, holds and amount limits, and pay.request can be granted, but no payment feature exists and nothing reads these settings.
No user hard-delete or erasure"Mark deleted" is a final status. It blocks the account and partner delivery but erases no data and does not remove the Kratos identity. Staff also cannot edit a user's profile (name, phone, email) or undo a deletion.
