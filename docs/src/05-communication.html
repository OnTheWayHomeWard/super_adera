How everything communicates

The request paths one by one, as diagrams and numbered steps: login, registration, a signed-in user's request, a staff request, a partner notification (accept, deliver, call back), the inbox and push, and observability. Then the trust model that makes these paths safe.

Reading the diagrams

Each diagram is a time line from top to bottom. Solid arrows are requests; dashed arrows are answers. Blue boxes are our services, grey boxes are tools, green is storage, amber is outside providers. Numbers in the diagram match the numbered steps under it. Paths are as the code and infra/apisix/apisix.yaml define them; everything here was cross-checked against the running stack in the endpoint pages.

One rule behind all of it

Services never trust a caller because of where it is. They trust a request because it carries a secret only the gateway (or another of our services) knows, and they take the user's or staff member's identity only from headers the gateway wrote after checking the session. Details in the trust model.

1. User login with a one-time code (email or phone)

  1. The app starts a native login flow: GET /kratos/self-service/login/api. The gateway strips /kratos and forwards to Kratos. Limit: 120 per minute per IP (route kratos-public). Kratos answers with a flow id and the form fields it expects.
  2. Nothing else happens at the gateway for this step; it is a plain proxy with a rate limit, a request id and a trace span.
  3. The app posts {"method":"code","identifier":"+2519..."} to /kratos/self-service/login?flow=ID. This is a POST under /kratos/self-service/*, so the strict limit applies: 10 per minute per IP (route kratos-self-service-submit; counters in Redis). That limit is the first line of protection against SMS-cost abuse.
  4. Kratos looks the identifier up. If an identity exists it creates a 6-digit code (valid 5 minutes, selfservice.methods.code.config.lifespan) and queues a courier message. If no identity exists, Kratos answers that the account does not exist (known account-enumeration weakness; see known limitations).
  5. Kratos runs with --watch-courier and courier.delivery_strategy: http. It posts the message to http://notification-service:8080/internal/kratos/sms (phone) or /internal/kratos/email (email). The request body is built by a small Jsonnet snippet inside kratos.yml (decoded on the Kratos page).
  6. NotificationDispatcher applies, in order: the per-recipient limit (5 per hour and 10 per day for SMS, 10 and 20 for email, counted from the send log by a SHA-256 hash of the recipient), then the live allowlist (real providers only), then the provider (console or Twilio for SMS, Mailpit or Resend for email), then writes a send_log row with a masked recipient and no code. A rate-limited or allowlist-skipped message still returns 200 (status suppressed or skipped), on purpose, because Kratos retries any non-2xx and a retry would defeat the limit. A provider failure returns 502, so Kratos keeps the message and retries.
  7. The user types the code; the app posts the same body plus "code" to the same login?flow=ID URL (again counted in the 10 per minute).
  8. Kratos verifies the code and returns 200 with a session_token (valid 30 days, session.lifespan: 720h). The app sends it as Authorization: Bearer ... from then on.

Registration is the same shape with /self-service/registration/api and traits.phone_number or traits.email; after the code is verified Kratos also creates the identity and runs the hooks below. Dev mode: the "provider" is the console (log plus GET /dev/messages) or Mailpit, so the code can be read by tests and by you.

Full request and response examples: Kratos flows.

2. Registration webhook: the profile row

  1. After a successful sign-up Kratos runs the web_hook configured under selfservice.flows.registration.after.code.hooks (before the session hook). It posts {"identityId":..., "email":..., "phone":...} to http://user-service:8080/internal/kratos/after-registration. The body comes from a Jsonnet function in kratos.yml.
  2. user-service inserts the profile row (app_user) with the Kratos identity id as the primary key, using INSERT ... ON CONFLICT DO NOTHING so a repeated or racing call is harmless.
  3. The hook is response.ignore: true: Kratos does not wait for, or care about, the answer. A user-service outage therefore never blocks a sign-up.
Why a safety net exists

Because the hook is fire-and-forget, a lost call would leave a user with no profile. The first GET /api/v1/me creates the row from Kratos' admin API if it is missing (race-safe). Staff identities created through the Kratos admin API by POST /admin/api/v1/staff do not run registration hooks at all, so they also get their profile row lazily, if they ever call /api/v1/me.

No authentication on this hook

/internal/kratos/after-registration (and notification-service's /internal/kratos/*) check no secret, because Kratos' hook configuration is static and would have to carry it in kratos.yml. They are not routed by the gateway and only reachable inside the compose network (and on localhost ports 8085 and 8086 in dev). Worst case: someone inside the network creates an empty profile for an id, or triggers a message. Adding a shared-secret header is on the to-do list.

3. Authenticated user request (forward-auth, X-User-Id)

  1. The app calls, for example, GET /api/v1/me with Authorization: Bearer $TOKEN. The gateway route is me (limit 300 per minute per IP) and has the forward-auth plugin.
  2. forward-auth makes a side request to user-service /internal/auth/verify, forwarding the client's Authorization and Cookie headers and adding X-Gateway-Secret. user-service's GatewayAuthFilter rejects the call with 401 if that secret is wrong.
  3. user-service asks Kratos GET /sessions/whoami with the same credentials. Kratos' own answer carries the identity in the body, not in headers, which is why this small translator exists.
  4. Kratos answers with the session; user-service reads active and identity.id. A 401/403 from Kratos means "invalid session". A Kratos outage or 5xx becomes 503, not 401, so an outage is not mistaken for a bad token.
  5. user-service answers 200 with the header X-User-Id: <identity id> (or 401). On a non-200 the gateway returns that answer to the client and never contacts the upstream. If the verify call itself fails the gateway answers 503 (status_on_error: 503).
  6. The gateway forwards the original request to the upstream, setting X-User-Id from step 5 (replacing anything the client sent, tested by journey.py) and setting X-Gateway-Secret via proxy-rewrite. The service requires both: without the secret or without a valid UUID X-User-Id it answers 401.
  7. The upstream answers; the gateway relays it. This same forward-auth is used on /api/v1/apps* (served by registry-service) and /api/v1/me/notifications* (served by notification-service); only the upstream differs. The user id is always the Kratos identity id.

4. Staff request (X-Staff-Id, X-Staff-Role, aal2)

  1. The dashboard calls /admin/api/v1/... with the staff member's session token. Routes admin-api (and the more specific admin-notification for /admin/api/v1/notification/*) use forward-auth to registry-service.
  2. The gateway calls registry-service /internal/staff/verify with only the Authorization header plus X-Gateway-Secret.
  3. registry-service asks Kratos whoami. If the identity has an authenticator app enrolled but this session has not completed that step, Kratos itself answers 403; registry-service reports it as 403 mfa_required.
  4. Kratos returns the session, including identity.metadata_public.role and authenticator_assurance_level.
  5. registry-service decides: is there an ACTIVE row in its staff table with a valid role (otherwise 403 not_staff), and, because ADMIN_REQUIRE_AAL2 is true, is the session aal2 (otherwise 403 mfa_required)? Aal2 means the person proved both the emailed code and the authenticator-app code.
  6. On success it answers 200 with X-Staff-Id and X-Staff-Role. The gateway sets both on the forwarded request, plus X-Gateway-Secret, plus X-Client-IP: $remote_addr (used in the audit log).
  7. The controller enforces the role per endpoint (VIEWER reads, ADMIN changes, SUPER_ADMIN manages staff and revives killed apps) and writes every change to the audit log.
  8. JSON answer. The same path is used for the notification admin API (templates, delivery log, usage), which notification-service serves behind the same gateway checks.
Why the role lives in Kratos too

The role is stored in the Kratos identity's metadata_public.role (only the Kratos admin API can write it; no self-service flow lets a user edit it) and mirrored in registry-service's staff table for listing, status and audit. registry-service checks both: the Kratos session must carry a known role and the local row must be ACTIVE, so disabling a person in the table cuts access at once even though their session is still valid in Kratos (disabling also revokes their sessions).

5. Partner notification request

A partner is a mini app's own server. It has no Adera login. It proves who it is by an RSA signature over each request, and we prove who we are by signing the answer and every callback. The signing rules are in Security: ADERA-SIG-1.

5a. Accepting the request (synchronous)

  1. The partner POSTs /v1/notifications with X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature. Gateway route partner-api: limit 600 per minute per IP, no forward-auth.
  2. The gateway sets X-Gateway-Secret and X-Client-IP: $remote_addr (overwriting any client value) and forwards to notification-service. The service believes X-Client-IP only when the secret matches.
  3. PartnerAuthFilter reads the body (max 64 KB, else 413 request_too_large), checks the three headers (401 missing_signature), the timestamp (401 invalid_timestamp or stale_timestamp, allowed skew 5 minutes), then asks registry-service for the public key (GET /internal/partner-keys/{keyId}, 401 unknown_key or key_revoked_or_expired) and the app context (GET /internal/apps/{appId}/context; the environment is always this deployment's ADERA_ENV). Both calls carry X-Internal-Secret and are cached for 15 seconds.
  4. It rebuilds the canonical string from the request as received and verifies the RS256 signature (401 invalid_signature). Then: does the key belong to this deployment's environment (a DEV key on a PROD deployment or the reverse is 403 wrong_environment), is the app usable here (DEV works for any app that is not killed; PROD only when the app status is LIVE; else 403 app_<status>), and is the caller's address inside this environment's allowed list (403 ip_not_allowed)?
  5. NotificationAcceptor validates the body, checks idempotency by externalId (same request again: 200 replayed:true; different request: 409 external_id_reused), loads the template (must belong to the app, active and within its validity window), checks the values against the template's declared params (length, control characters, no links unless allowed), and resolves the pseudonymous id: user-service GET /internal/aliases/resolve then GET /internal/users/{id}/delivery-context (phone, email, language, push tokens, mute switches). A deleted, suspended or unknown user is always 422 user_unreachable so partners cannot probe for accounts.
  6. It chooses the channel itself (the partner never does): an IN_APP template goes to inbox plus push (needs notify.inapp); a DIRECT template goes by SMS if the user has a phone and the app has notify.sms, else email if the user has an email and the app has notify.email. A muted channel is stored as SUPPRESSED (answered 200). Otherwise in one database transaction it reserves quota (usage_daily, usage_total, serialised with a row lock; over a limit gives 429 quota_exceeded with the limit name, and nothing is stored) and inserts the notification as QUEUED. This table is the queue.
  7. 202 with {"status":"QUEUED", ...}. ResponseSigningFilter adds X-Adera-Key-Id, X-Adera-Timestamp and X-Adera-Signature, computed with our key over the response and bound to the request signature it answers.

5b. Delivery and callback (asynchronous)

  1. DeliveryWorker runs every second. In one SQL statement it claims up to 20 due rows (QUEUED or RETRYING whose time has come, or PROCESSING whose 60-second lock expired) using FOR UPDATE SKIP LOCKED, so several service instances can run without sending twice and a crashed worker's claim simply expires.
  2. DeliveryService re-reads the user (their phone, mute or status may have changed), renders the template in the user's language, and for a synthetic user (u_p_test_*, DEV only) just records an attempt with provider sandbox and marks SENT; everyone else goes through the real pipeline with the dev providers (console SMS, Mailpit, fake push).
  3. It sends through the channel chosen at acceptance (Twilio or console, Resend or Mailpit, FCM or fake). With real providers and an allowlist set, other recipients are SUPPRESSED (not_allowlisted).
  4. It records a row in notification_attempt and sets the final or next status: SENT; FAILED (permanent provider error such as a bad number); UNREACHABLE (user deleted or suspended, no phone or email); SUPPRESSED; EXPIRED (kept trying until the deadline); otherwise RETRYING with backoff 30 s doubling up to 1 hour, at most 8 attempts, with plus or minus 10% jitter. When a status is final and the partner gave a callbackUrl, a signed report is queued in callback.
  5. CallbackWorker runs every 2 seconds and claims due callbacks the same way.
  6. It POSTs {"event":"notification.status", ...} to the partner. UrlGuard first refuses anything that is not https on port 443 or 8443 with a host whose every resolved address is public (SSRF guard); redirects are never followed. Headers: X-Adera-Event, X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature (our key, same canonical form as a request) and Idempotency-Key.
  7. A 2xx marks the callback DELIVERED. Anything else retries on the schedule 1 m, 2 m, 4 m, 8 m, 16 m, 32 m, 1 h, 2 h, then every 4 h, for 24 hours after the callback was queued (at most 15 attempts; a partner's Retry-After may lengthen a wait; never sooner than 30 s); a refused address fails at once.

The partner can also poll GET /v1/notifications/{externalId}, and staff can see every attempt and callback at GET /admin/api/v1/notification/notifications/{id}.

Why a Postgres table and not RabbitMQ

The notification table with SKIP LOCKED gives durable, restart-safe, multi-instance queueing with no extra moving part, and the "queue" rows are also the delivery record staff need. RabbitMQ is installed and ready for events between services, but nothing uses it yet.

6. Inbox and push

  1. For an IN_APP notification the worker asks user-service for the user's delivery context, including the list of active FCM tokens.
  2. It writes the inbox_item row first. This is the reliable part: the user sees it whenever they open the app.
  3. Then it pushes to every active token through the FCM provider (fake in dev: nothing leaves the machine; firebase when a service account exists). Push is best effort on top of the inbox row.
  4. If Firebase says a token is unregistered, notification-service calls user-service POST /internal/devices/deactivate so the token is not tried again; other failures are recorded as transient. The notification is then marked SENT.
  5. The app reads its bell menu at GET /api/v1/me/notifications (same forward-auth as step 3; the route is served by notification-service), with /unread-count, PUT /{id}/read and PUT /read-all. Users mute a channel per app at /api/v1/me/apps/{appId}/preferences.

7. Observability flow (traces, metrics, logs)

  1. Traces. APISIX (OpenTelemetry plugin, settings in plugin_metadata, sampler always_on in dev) and Kratos (tracing.provider: otel) send OTLP/HTTP spans to otel-collector:4318. The Java services send theirs to OTEL_TRACES_ENDPOINT (also the collector); the gateway's trace context header lets one trace span gateway, Kratos and our services.
  2. The collector batches and forwards traces to tempo:4317 (3-day retention).
  3. Metrics. Prometheus scrapes every 15 seconds: APISIX :9091/apisix/prometheus/metrics, Kratos admin port /admin/metrics/prometheus, RabbitMQ :15692, the three Spring services at /actuator/prometheus, Loki, Tempo, Alloy and the collector's own metrics (:8888). (Metrics are scraped, not pushed; the collector's :8889 exporter is empty because no service sends metrics over OTLP, so Prometheus no longer scrapes it.)
  4. Logs. Every container writes to stdout; Alloy reads them through the Docker socket, labels them with container and service, and pushes them to Loki (7-day retention). Not drawn above for space: Alloy to Loki.
  5. Grafana has three provisioned data sources (Prometheus, Loki, Tempo; a trace links to the logs of the same minute). Dashboard: Adera overview. How to use it: Guides.

Trust model: who may call what

Four headers carry trust. Three are written by the gateway after it has checked something, one by our services among themselves.

  • Header overwriting. Because APISIX sets these headers, a client cannot forge X-User-Id or X-Staff-Role. If the client sends its own, the gateway's value replaces it. This is verified by journey.py ("forged X-User-Id overridden").
  • Bypassing the gateway. The service ports 8085, 8086 and 8087 are published on localhost for development. Calling them directly without the gateway secret gives 401. This is also tested ("bypassing the gateway rejected").
  • Constant-time comparison. All secret checks use MessageDigest.isEqual.
  • Internal-only routes. /internal/** is never routed by the gateway: a request to /internal/... on port 9080 finds no route (404). /kratos/admin/* is explicitly mocked as 403 {"error":"forbidden"} so Kratos' admin API is unreachable from outside.
  • An empty secret disables its check. In every service, an unset GATEWAY_SECRET or INTERNAL_API_SECRET turns that check off (a warning is logged at start in registry-service). This exists for local development only; never run a deployment with an empty secret.
  • Known gaps. /internal/kratos/after-registration and /internal/kratos/sms|email have no authentication (compose network only). Both Java services that write to RustFS use its admin keys. See known limitations.
