Data

Where every piece of information lives: five Postgres databases, one object-storage bucket, and a Redis that our own services do not use. For each table: the columns, why it exists, who writes and reads it, and a real example row from the dev stack.

How the examples were made

Examples were read from the running dev stack on 2026-10-25 with read-only SELECTs. Personal data is masked (phones +2519******07, emails a***@adera.local). Secrets, password hashes, one-time codes, session tokens, TOTP secrets, HMAC keys and key material were never selected; where a column would hold one it is shown as <masked>.

The dev database is mostly empty on purpose: the e2e scripts (tests/e2e/*.py) delete everything they create. Tables with no rows show an example labelled illustrative example. These are made-up rows that follow the real constraints; nothing was written to the real data to produce them.

Who owns what

One Postgres server, one database per service, and one login per database (created by infra/postgres/init-databases.sh; public access is revoked). A service can only see its own database. If it needs data from another service it calls that service's internal API (see internal API).

Why one database per service

It keeps the services independent: user-service can be changed, restored or moved without touching registry or notification data, and a bug or leaked password in one service cannot read another service's tables. The cost is that there are no cross-database foreign keys. Ids that point across services (for example notification.app_id pointing at registry.mini_app.id) are plain UUIDs, checked by code, not by the database.

One id for a person: Kratos id = user id

Kratos creates the identity and gives it a UUID. user-service uses that same UUID as the primary key of app_user (no second id, no mapping table). Staff work the same way: the Kratos identity id is the primary key of registry.staff.

Why

Every request through the gateway is authenticated by a Kratos session. The gateway turns it into X-User-Id (the identity id), and that value can be used directly as the key of the user's row. No lookup is needed and nothing can drift out of sync.

Real proof from the dev stack, using the staff member (the only identity that exists right now). The same UUID appears in Kratos and in the registry:

SELECT id, schema_id, state FROM identities;

--------------------------------------+-----------+--------

-- db registry
SELECT identity_id, role, status FROM staff;
             identity_id              |    role     | status
--------------------------------------+-------------+--------

For an ordinary end user the same equality holds between kratos.identities.id and users.app_user.id. The dev users database is empty right now (the e2e cleanup removed the test users, and the staff member was created through Kratos' admin API, which does not fire the registration hook, so it has no profile). illustrative example of the pair for a phone sign-up:

The row is created by Kratos' registration web hook (/internal/kratos/after-registration), or on first GET /api/v1/me if the hook was lost (see communication).

Database kratos (Ory Kratos)

This schema belongs to Kratos. We never write to it with SQL: services talk to Kratos through its public and admin HTTP APIs. It is documented here so you know what is stored about a login and where, and so you can inspect it when something goes wrong. Kratos creates 26 tables (migrations applied by the kratos-migrate container); the ones that matter to us:

Never query these columns casually

identity_credentials.config (TOTP secret, code settings), sessions.token and logout_token, identity_login_codes.code, identity_registration_codes.code, courier_messages.body (contains the one-time code) and selfservice_*_flows.ui / csrf_token are credentials or hold credentials. Select named columns only. They were not read for this page.

sessions and session_devices

Purpose: one row per logged-in device. Why: the session token the app sends as Authorization: Bearer maps to a row here; deleting the row (or active = false) is how logout works. aal says how strongly the session was authenticated: aal1 = one factor (emailed or texted code), aal2 = plus authenticator app. The staff API requires aal2. Written by: Kratos on login/registration/logout. Read by: Kratos for every whoami (called by user-service and registry-service for gateway forward-auth).

app_user_alias

Purpose: the pseudonymous id a partner sees for a user. Why: partners must not learn our user ids, and the same person must look different in every mini app so two partners cannot join their data. The alias is u_p_ + the first 32 hex characters of HMAC-SHA256(ALIAS_HMAC_SECRET, userId:appId). The HMAC cannot be reversed, so this table is the only way back from an alias to a user (resolution is by table lookup). Minted when the user first opens/uses that app. Written and read by: user-service (AliasService), called by registry/notification-service through internal endpoints.

Database notification (notification-service)

Schema: V1__send_log.sql (login codes) V2__partner_platform.sql (partner platform) and V3__environments_dev_prod.sql (renames TEST/LIVE to DEV/PROD in notification, usage_daily, usage_total and queued callback payloads; adds the CHECK constraints). Two different jobs share this database: (1) the Kratos courier path, which logs every OTP delivery in send_log; (2) the partner platform, which has templates, notifications, attempts, inbox, callbacks and usage counters. Only send_log has rows in the dev stack; the others show illustrative example rows.

send_log

Purpose: one row per delivery attempt of a Kratos message (login/registration code by SMS or email). Why: (a) answer "did the code go out?" without storing the code, (b) rate limiting. Rate limits are counted from this table (recipient + channel + recent time), not in Redis, so they survive restarts and need no extra moving part. It never stores the message body (it contains the one-time code) or the full recipient: only a masked form for humans and a SHA-256 hash for lookups. Written and read by: notification-service (NotificationDispatcher, SendLogRepository).

notification

Purpose: one row per partner request, and the work queue for delivery. Why: a row means "accepted"; background workers pick due rows, deliver, retry on temporary failure and finally set a status. A database queue (instead of RabbitMQ) was chosen because the volume is low, it is transactional with the idempotency check and inbox write, and RabbitMQ is set up but not used yet (see RabbitMQ). Written by: notification-service (NotificationAcceptor, NotificationStore, DeliveryWorker). Read by: the same, plus the partner status endpoint and the staff delivery log.

ColumnTypeMeaning and why
iduuid PKOur notification id (notificationId in callbacks).
app_id, environmentuuid, varchar(5)Which app, and the environment of the deployment that took the request (DEV or PROD; CHECK (environment IN ('DEV','PROD'))). Rows from before the rename were migrated in place (TEST to DEV, LIVE to PROD).
external_idvarchar(100)Partner's own unique id. UNIQUE (app_id, environment, external_id) makes the API idempotent.
request_hashvarchar(64)Hash of the request: same externalId + same hash = replay (200), different = 409 external_id_reused.

Redis keys

Redis (redis:7-alpine, ACL users, noeviction, 256 MB) is used by two clients only: APISIX (rate-limit counters) and Infisical (queues and caches). None of our three Java services connects to Redis: their rate limits and queues are in Postgres (send_log, notification). Keys were listed by pattern with SCAN as the admin user (498 keys, 100 with a TTL at the time of reading).

PatternWriterWhat and how long
plugin-limit-count:v1:/routes/<route id>:<hash>:<client ip>APISIX limit-count (user apisix, whose ACL allows only ~plugin-limit-count:*)String counter of requests in the current window. TTL = the window (60 s). Example: plugin-limit-count:v1:/routes/kratos-self-service-submit:129764580:172.18.0.1 value 1, ttl 44 s. When the counter passes the route limit the gateway answers 429. Client IP is the Docker gateway address locally, so all clients share one counter in dev.
bull:* (about 120 keys)Infisical (BullMQ job queues)Queue metadata, stalled-job checks (TTL about 20 s). Must never be evicted, which is why Redis is noeviction.
{cron}:run:*, {cron}:last:*, {cron}:slot:*, {cron}:pendingInfisical schedulerScheduled-job bookkeeping (hundreds of small hashes).
secret-manager:*, secret-etag:*, project-permission-data:*, kms-project-sm-material:*, identity-*, worker-heartbeat:*, infisical-admin-cfgInfisicalCaches for secret reads, permissions, token verdicts; short TTLs (minutes). These can contain cached secret material in encrypted form (not inspected).

noeviction
Why noeviction

With an eviction policy Redis would silently delete keys when memory is full. For Infisical's job queues that means lost jobs. With noeviction Redis refuses writes instead, which is a loud, visible failure. The APISIX keys all carry a TTL so they cannot fill memory on their own. See Redis.
