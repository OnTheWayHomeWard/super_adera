8b. Staff / dashboard admin API

Everything the staff dashboard calls: mini-app management, capabilities, limits, allowed server addresses, partner keys, reviews and reports, audit, staff accounts, notification templates and the delivery log. 38 endpoints, captured live (the six added for the backoffice are in Dashboard counts and registered users; filters were added to the audit log, notification list and reports).

How staff calls work

  • Base URL: $BASE = http://127.0.0.1:9080 in development. All paths start with /admin/api/v1.
  • Who: an active staff member with an aal2 Kratos session: the emailed one-time code and an authenticator-app code. Get the token with the staff login guide and the Kratos flows. Send it as Authorization: Bearer $TOKEN.
  • What the gateway does: forward-auth to registry-service /internal/staff/verify, then it sets X-Staff-Id and X-Staff-Role and forwards. Clients never send those headers (a client-sent value is overwritten). See the staff request path.
  • Roles: VIEWER reads; ADMIN changes things; SUPER_ADMIN manages staff and revives killed apps. The role is read from the live Kratos session on every call, so a role change applies at once with no new login. A too-low role gets 403 insufficient_role.
  • Routing: /admin/api/v1/notification/* is served by notification-service (route admin-notification); everything else under /admin/api/v1 by registry-service (route admin-api). Both use the same staff check and the same 300 per minute limit.
  • Bodies are JSON (Content-Type: application/json) except the logo upload (multipart). Unknown fields are rejected with 400 validation_failed on every write, so a typo never silently does nothing. Absent field = unchanged, null = clear (where the field is optional).
  • Every change is audited (actor, role, IP, target) and can be read at GET /audit.
  • Error shape: {"error":"<code>"}, plus "fields":{"<field>":"<message>"} for validation (every problem is reported at once) or details such as missing. Notification-service endpoints use the same shape.

The examples assume:

BASE=http://127.0.0.1:9080
TOKEN=...   # aal2 staff session token (never commit or share it)
APP=...     # a mini app id (UUID)

Who am I

GET/admin/api/v1/meWho am I, as the dashboard sees me
Audience
Adera staff (the dashboard)
Client path
/admin/api/v1/me through the gateway
Internal path
same path on registry-service :8080 (the gateway does not rewrite it)
Auth
Authorization: Bearer $TOKEN, a Kratos session token of an aal2 staff session. The gateway checks it and adds X-Staff-Id, X-Staff-Role, X-Gateway-Secret. Minimum role: VIEWER.
Rate limit
300 per 60 s per client IP (gateway route admin-api)
Implemented in
services/registry-service/src/main/java/app/adera/registry/auth/../staff/StaffController.java

Purpose

Returns the staff member's id (the Kratos identity id) and role. The dashboard calls this after login to show who is signed in and to decide which buttons to show. It is also the cheapest way to test that a token is aal2.

Request parameters

None.

Example request

curl -sS -i -X GET "$BASE/admin/api/v1/me" \
  -H "Authorization: Bearer $TOKEN"

Example response

HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: 8c52977b-a694-4dc3-b716-014dd2a5c1f6

{
  "id": "0b648e27-181c-4650-87d7-441a5f07fb00",
  "role": "SUPER_ADMIN"
}

Errors

StatuserrorWhen it happens
200-OK, any active staff role.
401unauthorizedNo Authorization header, or an invalid, expired or revoked session token. Returned by the gateway's forward-auth (from registry-service).
403mfa_requiredThe session is only aal1 (emailed code only), or Kratos refuses it because an authenticator app is enrolled but not used in this session. Do the authenticator step.
403not_staffA valid session, but the person is not an ACTIVE staff member (customers get this).

Real error responses

Without a token:
HTTP 401  {"error": "unauthorized"}
aal1 token:
HTTP 403  {"error": "mfa_required"}
After the staff member was disabled (a valid session is no longer enough):
HTTP 401  {"error": "unauthorized"}

How to use it

  • Call it once after login and cache the role in the dashboard; every call re-checks it anyway.
  • mfa_required here means: send the user to the authenticator-app step, then retry.
GET/admin/api/v1/systemWhich environment is this deployment (DEV or PROD)?
Audience
Adera staff (the dashboard)
Client path
/admin/api/v1/system through the gateway
Internal path
same path on registry-service :8080 (the gateway does not rewrite it)
Auth
Authorization: Bearer $TOKEN, a Kratos session token of an aal2 staff session. The gateway checks it and adds X-Staff-Id, X-Staff-Role, X-Gateway-Secret. Minimum role: VIEWER.
Rate limit
300 per 60 s per client IP (gateway route admin-api)
Implemented in
services/registry-service/src/main/java/app/adera/registry/dashboard/SystemController.java

Purpose

Returns the environment this deployment runs, from the ADERA_ENV setting. A deployment is exactly one environment; staff can store allowed addresses and keys for both DEV and PROD, but only the one reported here is active. The dashboard uses it to mark the active environment on the Environments and Keys tabs and as the default of the Usage tab. Routed by the existing admin-api wildcard route, so the gateway needed no change.

Request parameters

None.

Example request

curl -sS -i -X GET "$BASE/admin/api/v1/system" \
  -H "Authorization: Bearer $TOKEN"

Example response

HTTP/1.1 200 OK
Content-Type: application/json

{
  "environment": "DEV"
}

Illustrative: added with the DEV/PROD change; the value is PROD on a prod deployment.

Errors

StatuserrorWhen it happens
200-OK, any active staff role.
401unauthorizedNo or invalid session token (from the gateway's forward-auth).
403mfa_required / not_staffSame rules as /me.
