16. Banners

Promotional banners in the super app: a picture with a title, shown in one of four places, that opens a mini app, a super-app screen or a web page when tapped. Staff manage them in the backoffice; the super app reads the ones that are showing right now with one public call.

Status

built 2026-11-21 Built as designed below, in eight commits (design, table and rules, staff API, images, public API and gateway route, backoffice, seed and e2e, these samples). The examples are real answers from the running dev stack. The frontend guide is docs/guides/app-banners/; every staff endpoint with real requests and answers is in 8b. Staff API, Banners.

1. Summary

  • Where they live: registry-service (it owns the catalog, the image storage, staff roles and the audit log). One new table, banner (migration V9__banners.sql).
  • Who manages them: staff in the backoffice, new menu item Banners. VIEWER reads; ADMIN and SUPER_ADMIN create, change, publish, pause and delete. Every change is written to the audit log.
  • Who reads them: the super app, through the gateway, without signing in (banners can be shown on the home screen before login): GET /api/v1/banners. Only banners that are showing right now are returned.
  • One switch, no clock job: staff set only DRAFT, PUBLISHED or PAUSED. Whether a published banner is showing is computed at read time from its start and end time and from its linked app. Nothing is ever written when a banner starts or ends.

3. Status and visibility

Staff set one switch. The rest is computed every time someone reads, from the clock:

shown  =  status = PUBLISHED
      AND starts_at <= now
      AND (ends_at IS NULL OR now < ends_at)
      AND (no linked app OR the linked app is LIVE)
Stored statusTimesComputed state (backoffice label)Shown to users?
DRAFTanyDRAFT (Draft)no
PAUSEDanyPAUSED (Paused)no
PUBLISHEDnow < startsAtSCHEDULED (Scheduled)no, it appears by itself at startsAt
PUBLISHEDinside the windowLIVE (Live)yes, if the linked app (if any) is LIVE
PUBLISHEDendsAt <= nowENDED (Ended)no, it disappears by itself at endsAt

The admin answers carry both state and visible. They differ in one case only: state = LIVE but the linked app is not LIVE (paused, killed or still a draft), so visible = false; the backoffice says so next to the badge. When the app goes LIVE again, the banner is back without anyone touching it.

Publishing needs an image. DRAFT or PAUSED to PUBLISHED without an uploaded image answers 409 not_ready_to_publish with {"missing": "image"}, the same way an app cannot go LIVE without a logo. Any other change between the three values is allowed. Editing a published banner is allowed and takes effect at once (the public answer may be cached for up to 60 seconds).

4. Action types

actionTypeWhat a tap doestargetLinked app
MINI_APPOpens the linked mini app through the normal launch (consent and launch token as for any launch), at the route target.A path starting with /, such as /promo/first-ride (no // at the start, no spaces), or empty/null for the app's home.required

EXTERNALOpens a web page (in the system browser or an in-app browser tab, not in a mini-app WebView).Required: an https:// URL whose host is on the allow-list BANNER_EXTERNAL_DOMAINS (the domain itself or any subdomain of it). No user name or password in the URL.optional
NONENothing: an image only.Must be empty (null).optional

Why the allow-list: a banner is shown to every user with Adera's name on it. A typo or a compromised staff account must not be able to send everyone to a phishing page, so external links can only go to domains the operators configured.

The allow-list is checked when a banner is saved. Removing a domain from the list later does not hide banners already saved with it (see decisions).

5. Images

Uploaded with POST /admin/api/v1/banners/{id}/image (multipart field file), with the same checks as an app logo: the content is decoded (the file name and declared type are not trusted), only PNG, JPEG, GIF and BMP are accepted, dimension limits guard against decompression bombs, and re-encoding drops metadata. Up to 4 MiB (BANNER_MAX_BYTES).

The server stores three sizes in RustFS, each with its longest side at most:

NameLongest sideUse it for
small480 pxThumbnails, lists, small phones
medium960 pxMost phones at full width
large1600 pxTablets and wide screens

An image is never made larger: a 600 px wide upload gives a 480 px small and 600 px medium and large. Each size is JPEG (photos are much smaller as JPEG than as PNG; transparency is flattened onto white). Keys: banners/{banner id}/{image id}/{size}.jpg. Replacing the image writes a new image id and deletes the old files. Answers carry a signed link per size, valid for STORAGE_PRESIGN_MINUTES (60), plus its width and height so the client can reserve the space before the picture loads.

8. Backoffice

  • Menu item Banners (all roles). Tabs Live / Scheduled / Draft / Paused / Ended / All (the computed state), filters for placement and category, columns: thumbnail, title, placement, category, linked app, start, end, priority, state badge (with a note when the linked app is not LIVE).
  • New banner and edit: title and subtitle in English, Amharic and Afaan Oromoo, placement, category, linked app (picker), action type with a target field that changes with it (route for a mini app, adera:// link, https URL with the allowed domains listed, nothing for NONE), start and end date-time pickers, priority, image upload (resized on the server), and a preview of how the banner looks in the chosen placement.
  • Publish, Pause, Back to draft buttons, and Delete behind a confirmation.
  • A VIEWER sees the same screens read-only: no create, save, upload, status or delete buttons.

10. Audit

Every write is in the audit log in the same transaction as the change: banner.create, banner.update, banner.image, banner.status, banner.reorder, banner.delete. Reads are not audited.

12. Decisions

  • No login for the public list. The home screen shows banners before sign-in. The route still goes only through the gateway (shared secret), with the normal rate limit. (The app catalog, by contrast, needs a signed-in user.)
  • No "ended" status and no scheduled job. Start and end are only compared with the clock when reading. Nothing can be late or forgotten, and an ended banner can be extended by editing endsAt.
  • Titles in three languages like app names, English required.
  • Priority: higher first. Reorder sets priorities 10 apart so one banner can later be slotted between two others by hand.
  • Images are JPEG (photos are several times smaller than PNG); transparency is flattened onto white.
  • The new-banner form starts at the current minute, so publishing shows the banner at once (rounding up made it "Scheduled" for up to a minute; found in the browser walk-through).
  • Allow-list checked on save only. Re-checking every banner on every read would hide banners silently; operators who remove a domain should pause the banners that use it.
  • The linked app must exist when saving, in any status, so a banner can be prepared for an app that is not LIVE yet; it shows once the app is LIVE.
