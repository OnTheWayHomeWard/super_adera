8e. Kratos self-service flows

The sign-up, login, session and authenticator-app calls the app makes to Ory Kratos through the gateway. They are Kratos' own API (we wrote no code for them); this page documents how Adera configured and uses them. 13 endpoint blocks.

Why Kratos, and what this means for the app

Passwordless login with email or SMS codes, sessions and TOTP are solved problems; building them ourselves would add risk and no product value. Kratos is "headless": it returns a flow object that describes the form, and the Flutter app renders its own UI from it. Our code only (a) sends the codes (notification-service is Kratos' courier), (b) creates the profile after sign-up (webhook to user-service) and (c) turns a session token into X-User-Id for the gateway.

Examples captured 2026-10-25 through $GATEWAY/kratos in dev mode with throwaway users (phone numbers masked, deleted afterwards). $TOKEN is the session_token.

How a native flow works

  1. Create the flow with a GET (.../registration/api or .../login/api). You receive an object with id, state, expires_at and ui (action, method, nodes, messages).
  2. Submit with a POST to ui.action (JSON body; field names are the node names). Kratos answers the next state of the flow.
  3. Read the answer by state, not only by HTTP status. In API flows a step that needs more input is answered with 400 and the updated flow (state: sent_email after the code was sent; the error texts are in node or ui messages). A finished flow is 200 with session_token and session.
StateMeaning
choose_methodNothing submitted yet, or the last submit was rejected before a code was sent (unknown account, invalid number).
sent_emailA code was sent (the name says email, but it is used for SMS as well). Next: submit with code.
passed_challengeThe challenge was passed but something else stopped the flow (for example "account exists already" at registration).
show_form / successSettings flow: form shown / changes saved.

Sessions and assurance levels

aal1 = one factor (the emailed/SMS code). aal2 = a second factor (authenticator app) was also completed. Customers are always aal1. Staff must reach aal2 (ADMIN_REQUIRE_AAL2=true) before the gateway lets them into /admin/api/v1. Because Kratos is configured with the default whoami behaviour (highest_available), an aal1 session of an identity that has an authenticator app gets 403 session_aal2_required from whoami; registry-service reports that as 403 mfa_required and user-service treats it as invalid (401).

Walkthrough: sign up with a phone, then call the API

export GATEWAY=http://127.0.0.1:9080
PHONE=+2519XXXXXXXX            # a number you control; in dev nothing is really sent

FLOW=$(curl -s $GATEWAY/kratos/self-service/registration/api | python3 -c 'import sys,json; print(json.load(sys.stdin)["id"])')
curl -s -X POST "$GATEWAY/kratos/self-service/registration?flow=$FLOW" \
  -H 'Content-Type: application/json' \
  -d "{\"method\":\"code\",\"traits.phone_number\":\"$PHONE\"}" >/dev/null     # 400 sent_email is expected

# dev mode only: read the code from notification-service
curl -s "http://127.0.0.1:8085/dev/messages?to=$(python3 -c "import urllib.parse,sys; print(urllib.parse.quote('$PHONE'))")"
CODE=123456                    # copy the 6 digits from the body above

TOKEN=$(curl -s -X POST "$GATEWAY/kratos/self-service/registration?flow=$FLOW" \
  -H 'Content-Type: application/json' \
  -d "{\"method\":\"code\",\"traits.phone_number\":\"$PHONE\",\"code\":\"$CODE\"}" \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["session_token"])')

curl -s "$GATEWAY/api/v1/me" -H "Authorization: Bearer $TOKEN"

Login of an existing user is the same with /login/api, /login?flow= and "identifier" instead of "traits.phone_number". See also the guides.

Purpose

Used twice per sign-up. Step 1: send the identifier; Kratos answers 400 with state: sent_email (this 400 is the normal "now ask for the code" answer in Kratos' API flow, not a failure) and asks our notification-service to send the code (SMS or email). Step 2: send the same identifier plus code; on success Kratos creates the identity and returns 200 with the session_token. Right after creation Kratos calls our registration webhook (user-service creates the profile row; non-blocking) and issues the session, because hook: session is configured.

How to use it

  • Anti-enumeration at registration: sending a phone that already has an account still answers "a code has been sent"; the "account exists" error appears only after the code is entered, so a stranger cannot probe which numbers are registered. Login behaves differently (see below).
  • The session returned is aal1 (code method completed). Store session_token securely (Keychain/Keystore); it lives 30 days (session.lifespan: 720h).
  • Dev mode: the code is not delivered; read it from GET http://127.0.0.1:8085/dev/messages?to=<phone> (8f) or from Mailpit.
  • Right after step 2, user-service has the profile row (webhook), so GET /api/v1/me works immediately.

Calling the aal2 flow with a session that is already aal2 (e.g. right after enrolling)

curl -s "$GATEWAY/kratos/self-service/login/api?aal=aal2&refresh=false" \
  -H "X-Session-Token: $TOKEN"

Kratos answers 400 with error.id = session_already_available ("you are already logged in"). Log in again (aal1) before upgrading, or skip the upgrade: a session that enrolled TOTP is already aal2. Observed during testing; the 400 body is Kratos' standard error JSON.

How to use it

  • The login flow asks for identifier (labelled "ID"): it can be an email address or an E.164 phone number.
  • Flow ids are single-use per attempt chain: after a successful login the same flow cannot be reused (a second submit gives message 4010002 "Could not find a strategy to log you in with").

How to use it

  • Kratos does not accept the same TOTP code twice, so scripts must wait for the next 30-second window between enrolment and the next code (tests/e2e/staff.py does).
  • The role of a staff member is not part of this flow: it is metadata_public.role set by registry-service.
