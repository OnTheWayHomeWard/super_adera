8e. Kratos self-service flows

The sign-up, verification, sign-in, forgot-password, change-password and session calls the super app makes to Ory Kratos through the gateway, plus our two small public endpoints around them (phone password reset, code pre-flight). Kratos' calls are Kratos' own API; this page documents how Adera configured and uses them. Captured live on 2026-10-26.

What changed (2026-10-26)

End users no longer sign in with one-time codes. They register with a phone (email optional) and a password (at least 6 characters, nothing else), verify the address with a code sent by SMS or email, then sign in with identifier and password. Forgot password works by code: email through Kratos' recovery flow, phone through our /public/v1/password-reset/* endpoints (Kratos recovery only accepts an email address). Dashboard staff are unchanged: emailed code, then authenticator app (8b). The two kinds of people live in two Kratos identity schemas: user (app users, the default) and default (staff, created through the admin API).

Kratos is "headless": it returns a flow object that describes the form and the app renders its own UI. Our code (a) sends the codes (notification-service is Kratos' courier: SMS and email endpoints unchanged), (b) creates the profile after sign-up (Kratos web_hook to user-service on the password registration method), (c) the phone reset and the code pre-flight.

Examples captured 2026-10-26 through $GATEWAY/kratos in dev mode with throwaway users (deleted afterwards; session tokens shortened). $TOKEN is the session_token.

How a native flow works

  1. Create the flow with a GET (.../registration/api, .../login/api, .../recovery/api, .../settings/api). You receive id, state, expires_at and ui (action, method, nodes, messages).
  2. Submit with a POST to ui.action (JSON; field names are node names).
  3. Read the answer by state and message ids, not only by HTTP status. A finished sign-in is 200 with session_token; rejected input is 400 with the flow and messages; some "try again" answers (wrong verification or recovery code) are 200 with an error message; a refused sign-in for an unverified address is 403 with error.id.

The whole user journey (call sequence)

  1. GET /kratos/self-service/registration/api then POST .../registration?flow=ID with {"method":"password","password":...,"traits.phone_number":...} (optional traits.email). Answer: identity (unverified) and continue_with[0].flow = a verification flow whose code was already sent to verifiable_address. No session yet.
  2. POST .../verification?flow=VID with {"method":"code","code":"123456"} until state is passed_challenge.
  3. GET .../login/api then POST .../login?flow=ID with {"method":"password","identifier":...,"password":...}. Answer: session_token (30 days). Use Authorization: Bearer $TOKEN on /api/v1/me etc.
  4. Forgot password: by email GET .../recovery/api, POST .../recovery?flow=ID (email, then code) gives a privileged token and a settings flow; by phone POST /public/v1/password-reset/start then /finish.
  5. Change password: GET .../settings/api with the session, POST .../settings?flow=ID with {"method":"password","password":...}.

Sessions and assurance levels

aal1 = one factor (an app user's password, or a staff member's emailed code). aal2 = a second factor (authenticator app) was also completed. Customers are always aal1. Staff must reach aal2 (ADMIN_REQUIRE_AAL2=true) before the gateway lets them into /admin/api/v1. Because Kratos is configured with the default whoami behaviour (highest_available), an aal1 session of an identity that has an authenticator app gets 403 session_aal2_required from whoami; registry-service reports that as 403 mfa_required and user-service treats it as invalid (401).

Walkthrough: sign up, verify, sign in, call the API

export GATEWAY=http://127.0.0.1:9080
PHONE=+2519XXXXXXXX            # a number you control; in dev nothing is really sent
j() { python3 -c "import sys,json; print(json.load(sys.stdin)$1)"; }
H='Content-Type: application/json'

# 1. register (no session comes back; a verification code is sent)
FLOW=$(curl -s $GATEWAY/kratos/self-service/registration/api | j '["id"]')
VFLOW=$(curl -s -X POST "$GATEWAY/kratos/self-service/registration?flow=$FLOW" -H "$H" \
  -d "{\"method\":\"password\",\"password\":\"tadesse\",\"traits.phone_number\":\"$PHONE\"}" | j '["continue_with"][0]["flow"]["id"]')

# 2. dev mode only: read the code from notification-service, then verify
curl -s "http://127.0.0.1:8085/dev/messages?to=$(python3 -c "import urllib.parse; print(urllib.parse.quote('$PHONE'))")"
CODE=123456                    # copy the 6 digits from the body above
curl -s -X POST "$GATEWAY/kratos/self-service/verification?flow=$VFLOW" -H "$H" -d "{\"method\":\"code\",\"code\":\"$CODE\"}"   # state passed_challenge

# 3. sign in with the password
LFLOW=$(curl -s $GATEWAY/kratos/self-service/login/api | j '["id"]')
TOKEN=$(curl -s -X POST "$GATEWAY/kratos/self-service/login?flow=$LFLOW" -H "$H" \
  -d "{\"method\":\"password\",\"identifier\":\"$PHONE\",\"password\":\"tadesse\"}" | j '["session_token"]')

curl -s "$GATEWAY/api/v1/me" -H "Authorization: Bearer $TOKEN"

The seeded demo users can sign in the same way (sample data). The same sequence is automated in tests/e2e/journey.py (63 checks). See also the guides.

Enumeration and brute-force summary

QuestionAnswer (checked live)
Can the login screen tell whether a phone/email has an account?No: unknown and wrong password give the same status, message 4000006 and flow shape.
Recovery by email, phone reset, verification of unknown addresses?No: the same 200/202 answer, and nothing is sent for an unknown address (notify_unknown_recipients: false).
Registration?Yes, it leaks: an existing identifier gives message 4000007. Mitigation: 5 registration submits a minute per IP. Not closable with Kratos configuration.
Account lockout after wrong passwords?None. Kratos has no lockout.
What limits password guessing?Gateway only: 10 tries/min per IP, 10 tries per 15 min per identifier, 6-character minimum. Side effect: someone can exhaust a victim's per-identifier budget (a 15-minute denial of sign-in attempts). IPs are keyed on the address the gateway sees: behind a proxy they need a real-IP setting (deferred, SETUP section 12).
What limits code abuse (SMS cost)?Registration 5/min per IP, recovery 5/min per IP + 5 per 15 min per email, reset start 5/min per IP + 5 per 15 min per phone, per-recipient SMS 5/hour and 10/day (silent drop, see the pre-flight check), 5 wrong tries per reset code.

Enumeration warning (honest)

Registering an identifier that already has an account answers 400 with message 4000007 "An account with the same identifier (email, phone, username, ...) exists already." (checked live 2026-10-26). So registration does reveal whether a phone or email is registered. Kratos offers no switch for this. The only brake is the gateway limit of 5 registration submits a minute per IP. The login, recovery and phone-reset answers do not reveal it (below).

Which address must be verified

Login is refused with session_verified_address_required when the address used to sign in is not verified, even if the account's other address is. A refused login returns a verification flow (and sends a code) for the address Kratos picks (details.continue_with[0].flow.verifiable_address, not always the one typed). Verify what the flow names, sign in again, repeat if needed.

Brute-force protection (honest)

Kratos has no account lockout. The only guards are the gateway limits (10 tries a minute per IP, 10 tries per 15 minutes per identifier, so rotating IPs does not help against one account, but an attacker can still lock a victim out of login attempts for up to 15 minutes by burning the per-identifier budget) and the 6-character minimum. IP limits use the client address seen by the gateway; behind a proxy they need a real-IP setting (deferred production work).

Purpose

Kratos' API cannot tell the client that a code was dropped by the per-recipient limit (SMS 5/hour, 10/day; email 10/hour, 20/day), so a screen would say "we sent a code" although nothing was delivered. Call this before registration, before a resend (sign-in that is refused as unverified), and before starting recovery by email.
