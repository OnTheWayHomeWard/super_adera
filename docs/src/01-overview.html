Overview

Adera is the backend of a community super app: people sign in with a phone number or email, and third-party "mini apps" can reach them through Adera in a controlled, consent-based way. This page says what exists today, what does not, and how the pieces fit.

What Adera is

The Adera app (a Flutter mobile app, not part of this repository) talks to one backend through one front door, the API gateway on port 9080. The backend does three jobs today:

  1. Identity and login. Email-or-phone login with a one-time code, no passwords, 30-day sessions. This is done by Ory Kratos, an off-the-shelf identity server. We wrote only the pieces around it: the SMS/email delivery (notification-service) and the profile that Kratos does not hold (user-service).
  2. The user's own data. Profile, optional location, free-form extra JSON, avatar picture, and the phone's push (FCM) tokens: user-service.
  3. The mini-app platform. Staff register a mini app, grant it capabilities (what it may ask for), set limits, register the partner's public key and approve message templates (registry-service plus an admin API in notification-service). The partner's server then sends notifications to users with signed requests; Adera delivers them by SMS, email, or in-app inbox plus push, and reports the result by a signed callback.
Principle

Use proven open-source tools; write code only where the product logic is ours. Login, sessions, TOTP, rate limiting, secrets, metrics, logs and traces are all tools we configure, not code we wrote. Our three Java services contain only what is specific to Adera: the profile record, pseudonymous per-app ids, the mini-app registry and its rules, partner request signing, template approval, quotas, retries and callbacks. Where a tool did not fit, we say so on the tools page.

Architecture

Everything the apps call goes through the gateway. Behind it, three Java services (blue) hold our product logic; the rest are tools. The numbered request paths are drawn one by one in How everything communicates.

Legend. Blue boxes are our code. Grey boxes are off-the-shelf tools. Green boxes are data stores. Amber is outside providers. Light blue are callers. Dashed arrows are secondary or unused paths. Not drawn, to stay readable: the Kratos registration webhook to user-service, the service-to-service calls (notification-service to registry-service and user-service), and registry-service writing logos to RustFS. All are in section 5.
