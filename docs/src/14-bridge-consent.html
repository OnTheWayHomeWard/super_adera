14. Mini app bridge and user consent (design proposal)

How a mini app gets data about a user and from the device, how the user decides what it may have, and how we stop it from taking more. Nothing on this page is built yet. It is a proposal to discuss; every endpoint and table below is a suggestion, and the sample requests and responses are illustrations of the intended shape, not output from the running stack. Written 2026-11-04 on top of what exists today (apps, granted capabilities, pseudonymous ids, signed partner API, notification limits, mute preferences).

Proposal

Status: for discussion. Section 11 lists the decisions I need from you before building.

1. The short answer

  • The manifest is our registry, not a file the mini app hosts. A mini app must not describe its own powers. The list of capabilities an app may ever ask for is what staff granted in the backoffice (user.basic, location.fine, ...). We add a purpose sentence per capability, written by the partner and approved by staff, so the user is told why.
  • The backend decides, always. The super app's bridge (the JavaScript the mini app calls) checks locally only to give quick feedback. A mini app is third-party code inside a WebView, so the bridge cannot be trusted as a gate. Every data request ends in a backend check, and the backend does not look at what the bridge said.
  • Three gates, in this order: (1) did Adera grant this capability to this app, and is the app LIVE? (2) did this user say yes to this capability for this app, and is it still yes? (3) is the request for exactly what that capability covers? Fail any gate and nothing is returned.
  • Consent is stored per user, per app, per capability, with a history, so "allowed" is something we can prove and the user can change at any time.
  • Yes, we need endpoints for the menu toggles. A permissions sheet in every mini app's top menu needs read, change and revoke endpoints (section 6).
  • Location is different. We never hold the user's live position. It is read from the phone, so it needs the phone's own permission as well as ours. The backend records consent and the super app hands the reading to the mini app (section 3).

2. The three gates

GateQuestionWho knowsFails with
1. GrantedIs the capability granted to the app, and is the app LIVE (not DRAFT, PAUSED or KILLED)?registry-service (exists today)403 capability_not_granted or 403 app_not_live
2. ConsentedDid this user allow it, and not revoke it since? Is the user ACTIVE?user-service (new table)403 consent_required or 403 consent_revoked
3. In scopeIs the thing asked for covered by the capability? (location.coarse gives a city, never coordinates; user.contact never gives the address.)The data endpoint itself403 outside_capability

Gate 1 is checked on every call, so pausing or killing an app, or removing a capability in the backoffice, takes effect immediately. The 15-second revoked-key cache we already accepted is the only delay.

3. Two kinds of data, two paths

KindExamplesHeld byHow the mini app gets it
Server-helduser.basic (the pseudonymous id), user.full_name, user.contact, user.addressuser-servicePath A or B below
Device-heldlocation.coarse, location.fineThe phoneThe bridge asks the phone; the backend only checks and records consent
Action, no datanotify.sms, notify.email, notify.inapp, pay.requestnotification-service, payments laterThe mini app backend calls the partner API; the gate is applied there

Path A: through the bridge (the mini app's frontend asks)

The mini app calls adera.getProfile(). The super app calls the backend with the user's session, the backend runs the three gates and returns the data, and the super app passes it into the page. The data lands in the mini app's browser code. Fine for low-risk fields (a first name to say "Hi Hana"). Quick to build, but anything in the page can be copied by the partner's scripts or by a bad ad or library the partner loaded.

Path B: through the mini app's backend (recommended for identifying data)

The super app opens the mini app with a short-lived launch token (section 4). The mini app's backend verifies the token and then calls Adera with a signed request (the signing scheme partners already use) to read what the user consented to. Data never travels through the browser, it is logged on our side per call, and the partner's keys, rate limits and environment checks all apply.

Recommendation: support both behind the same three gates. Use Path B for user.full_name, user.contact and user.address. Allow Path A only for user.basic and for device data.

Location

The phone asks the user for its own location permission the first time (the system dialog). Our consent is a separate yes. The bridge only gives a reading if both are yes, and returns denied without telling the mini app which of the two said no. If the mini app's backend needs the position, the mini app frontend sends it; we do not store positions on our servers.

4. Launching a mini app: the launch token

Opening a mini app creates a short session. The super app asks the backend for a launch token and loads the mini app URL (the one registered in the backoffice) with the token. The token is a signed JWT using the same Adera signing key as callbacks; partners already fetch the public key at /.well-known/jwks.json.

POST /api/v1/me/apps/demo-ride/launch
Authorization: Bearer <user session>

200
{
  "launchToken": "eyJhbGciOiJSUzI1NiIsImtpZCI6...",
  "expiresInSeconds": 300,
  "url": "https://ride.example.com/app?launch=eyJhbGciOi...",
  "consents": [
    {"capability": "user.basic",     "state": "GRANTED"},
    {"capability": "location.fine",  "state": "NOT_ASKED"}
  ]
}

Decoded token (claims): iss Adera, aud the app's id, sub the pseudonymous id u_p_... (never the real user id), env dev or prod, scopes the capabilities the user allowed at this moment, exp five minutes ahead. The mini app backend uses it to know who is calling, then calls Adera with its own signed requests for the data. Scopes in the token are only a hint for the mini app: Adera re-checks consent on every data call, so a revoked permission stops working even with a live token.

5. Consent: what we store

New tables in user-service (it owns users and the per-app pseudonymous ids):

TableColumnsNotes
app_consentuser id, app id, capability, state (GRANTED, DENIED), decided at, decided on screen (first-launch or menu), app version askedOne current row per user, app and capability. Absence means NOT_ASKED.
consent_eventuser id, app id, capability, from state, to state, at, sourceAppend only. This is the proof that the user agreed and when.

The consent screen shows only capabilities the app is granted (gate 1). If staff later grant a new capability, the user is asked again at next launch, and nothing is shared meanwhile. If staff remove one, the consent row stays but is inert, and the permissions sheet no longer lists it.

Per-capability text lives in the registry next to the grant: purpose (one sentence, shown to the user), and required true or false. Staff review the text with the grant, so a partner cannot show "to improve your experience" for a location request.

7. Scenario: Demo Ride, start to finish

  1. Admin grants Demo Ride user.basic, user.full_name, location.fine and notify.sms, and approves a purpose sentence for each. The app goes LIVE.
  2. Hana taps Demo Ride in the super app. The app calls GET /permissions and shows the dialog. Hana allows name and location, denies SMS. The phone's own location dialog follows and she allows it.
  3. The super app calls POST /launch and opens the mini app with the launch token. Scopes: basic, name, location.
  4. The mini app frontend calls adera.getLocation(). The bridge checks the phone permission, the backend confirms consent, and the position goes to the page.
  5. The mini app backend verifies the token and calls GET /profile. It receives the alias and the name.
  6. The mini app backend sends the driver code by SMS through the partner API. Gate 2 says notify.sms is DENIED, so the message is refused with 403 consent_required and no SMS leaves. The mini app falls back to in-app (notify.inapp) if it was granted and allowed.
  7. Later Hana opens the top menu of Demo Ride, sees the sheet "Your name: on, Location: on, SMS: off", turns location off. The next getLocation() returns denied. She turns SMS on, and the next SMS goes through.
  8. Hana taps "Disconnect". Everything becomes DENIED, the mini app is sent a user.disconnected callback (section 8), and the next /profile returns 403.

8. Notifications, revocation and callbacks

  • Consent for notify.* joins the existing mute preferences. Today a user can mute an app's notifications (stored in user-service) and the app's own notify limits come from the registry. I suggest one idea: the notify consent is the mute switch. Denied means muted. That removes a second place where the user would have to say the same thing. Existing mutes would be converted to DENIED on migration.
  • Revoke is immediate. The gate reads the consent row on each call. There is no cached "allowed".
  • Tell the partner. When consent changes, we send a signed callback (the retry-for-24-hours mechanism already exists): user.consent_changed with the alias, the capability and the new state, and user.disconnected on disconnect. A partner that kept the user's name is expected to delete it on user.disconnected. We can require this in the partner terms, but we cannot enforce it technically once the data has left.
  • Suspended or deleted users fail gate 2 for everything.

9. What this does and does not protect

ThreatHandled by
A mini app calls the bridge for data it was not grantedGate 1 in the backend; the bridge's own check is only a courtesy
A mini app asks for data the user said no toGate 2, on every call
A mini app asks for more than a capability coversGate 3: each capability has a fixed set of fields
The mini app page loads a different site and the bridge talks to itThe bridge is injected only for the registered URL's origin; it checks the origin on every message
A stolen launch tokenFive-minute life, tied to one app and one pseudonymous id; data calls need the partner's private key as well
A partner keeps data after the user withdrew consentNot preventable by us. Callbacks, terms and audit only
A partner reads data and shares it with a third partyNot preventable by us. Same as above

10. Suggested build order

  1. Registry: purpose and required per granted capability, with backoffice fields and audit.
  2. user-service: app_consent, consent_event, the permissions, consent and list endpoints. Tests, docs, a screen in the backoffice for counts.
  3. notify.* gate in the notification path, and mute converted to consent.
  4. Launch token and the partner /profile endpoint (Path B).
  5. Callbacks user.consent_changed and user.disconnected.
  6. The JavaScript bridge specification for the super app team: method list, message format, origin rule, error codes. Written last, because it is only a thin layer over steps 1 to 5.

Each step is a separate commit with tests and its documentation, as with the bug fixes.

11. Decisions I need from you

  1. Path A, B or both? I recommend both, with identifying data only on B.
  2. Fine-grained consent or one yes per app? I propose per capability (the toggles you described). One yes per app is simpler but cannot support "share name but not location".
  3. Required capabilities: may the app mark some as required so the super app refuses to open without them? I suggest yes.
  4. Merge mute with notify consent? I suggest yes (section 8).
  5. Does consent expire? For example ask again after 12 months. I suggest no for now.
  6. Is the pseudonymous id enough for user.basic, or should the mini app be able to link users across two of its own apps? I suggest one id per user and app, as today.
  7. Payments: pay.request needs its own confirmation each time (a per-payment prompt) and not a stored yes. Agreed?
