14. Mini app bridge and user consent (agreed design)

How a mini app gets data about a user and from the device, how the user decides what it may have, and how we stop it from taking more. Permissions are asked at the moment of need, one at a time, like Android, not all at launch. Design agreed on 2026-11-04; implementation starts from this page. Every endpoint and sample below is the intended shape; once a step is built, its real requests and responses replace the illustrations (marked as such on each step).

Status

Agreed, build in progress (section 10 lists the steps and which are built). Decisions taken are in section 11. Built so far: step 1 (purpose per capability) and step 2 (the consent endpoints in user-service).

1. The short answer

  • The manifest is our registry, not a file the mini app hosts. A mini app must not describe its own powers. The capabilities an app may ever ask for are the ones staff granted in the backoffice (user.basic, location.fine, ...). We add a purpose sentence per capability, written by the partner and approved by staff, so the user is told why. The mini app cannot change that text.
  • Ask at the moment of need, one permission at a time. Opening a mini app shows no dialog. When the mini app first needs location, it asks for location, the super app shows our approved text, and the user answers. A granted answer is remembered; a denied one is remembered too and limits how often the app may ask again (section 5).
  • The backend decides, always. The super app's bridge (the JavaScript the mini app calls) only drives the dialog. A mini app is third-party code inside a WebView, so the bridge cannot be the gate. Every data request ends in a backend check that ignores what the bridge said.
  • Three gates, in this order: (1) did Adera grant this capability to this app, and is the app LIVE? (2) did this user say yes to this capability for this app, and is it still yes? (3) is the request for exactly what that capability covers? Fail any gate and nothing is returned.
  • The mini app decides what a "no" means. It can show "we cannot continue without your location", the reason, and an Allow button that asks again, or open the permission settings once asking is blocked. The server does not know which permissions an app cannot live without.
  • The menu sheet always works. Every mini app's top menu lists its permissions with a switch each; that is the only way to undo a block (section 5).
  • Location is different. We never hold the live position. It is read from the phone, so it needs the phone's own permission as well as ours. The backend records consent and the super app hands the reading to the mini app (section 3).

2. The three gates

GateQuestionWho knowsFails with
1. GrantedIs the capability granted to the app, and is the app LIVE (not DRAFT, PAUSED or KILLED)?registry-service (exists today)403 capability_not_granted or 403 app_not_live
2. ConsentedDid this user allow it, and not revoke it since? Is the user ACTIVE?user-service (new table)403 consent_required (body says the state: NOT_ASKED, DENIED, BLOCKED)
3. In scopeIs the thing asked for covered by the capability? (location.coarse gives a city, never coordinates; user.contact never gives the address.)The data endpoint itself403 outside_capability

Gate 1 is checked on every call, so pausing or killing an app, or removing a capability in the backoffice, takes effect immediately. The 15-second revoked-key cache we already accepted is the only delay.

3. Two kinds of data, two paths

KindExamplesHeld byHow the mini app gets it
Server-helduser.basic (the pseudonymous id), user.full_name, user.contact, user.addressuser-servicePath A or B below
Device-heldlocation.coarse, location.fineThe phoneThe bridge asks the phone; the backend only checks and records consent
Action, no datanotify.sms, notify.email, notify.inapp, pay.requestnotification-service, payments laterThe mini app backend calls the partner API; the gate is applied there

Path A: through the bridge (the mini app's frontend asks)

The mini app calls adera.getProfile(). The super app calls the backend with the user's session, the backend runs the three gates and returns the data, and the super app passes it into the page. The data lands in the mini app's browser code. Fine for low-risk fields (a first name to say "Hi Hana"). Quick to build, but anything in the page can be copied by the partner's scripts or by a bad ad or library the partner loaded.

Path B: through the mini app's backend (recommended for identifying data)

The super app opens the mini app with a short-lived launch token (section 4). The mini app's backend verifies the token and then calls Adera with a signed request (the signing scheme partners already use) to read what the user consented to. Data never travels through the browser, it is logged on our side per call, and the partner's keys, rate limits and environment checks all apply.

Recommendation: support both behind the same three gates. Use Path B for user.full_name, user.contact and user.address. Allow Path A only for user.basic and for device data.

Location

The phone asks the user for its own location permission the first time (the system dialog). Our consent is a separate yes. The bridge only gives a reading if both are yes, and otherwise returns denied or blocked without telling the mini app which of the two said no. If the mini app's backend needs the position, the mini app frontend sends it; we do not store positions on our servers.

4. Launching a mini app: the launch token

Opening a mini app creates a short session. The super app asks the backend for a launch token and loads the mini app URL (the one registered in the backoffice) with the token. The token is a signed JWT using the same Adera signing key as callbacks; partners already fetch the public key at /.well-known/jwks.json.

POST /api/v1/me/apps/demo-ride/launch
Authorization: Bearer <user session>

200
{
  "launchToken": "eyJhbGciOiJSUzI1NiIsImtpZCI6...",
  "expiresInSeconds": 300,
  "url": "https://ride.example.com/app?launch=eyJhbGciOi...",
  "consents": [
    {"capability": "user.basic",     "state": "GRANTED"},
    {"capability": "location.fine",  "state": "NOT_ASKED"}   (a state only; no dialog is shown at launch)
  ]
}

Decoded token (claims): iss Adera, aud the app's id, sub the pseudonymous id u_p_... (never the real user id), env dev or prod, scopes the capabilities the user allowed at this moment, exp five minutes ahead. The mini app backend uses it to know who is calling, then calls Adera with its own signed requests for the data. Scopes in the token are only a hint for the mini app: Adera re-checks consent on every data call, so a revoked permission stops working even with a live token.

5. Permission states and what we store

Each (user, app, capability) is in one of four states:

StateMeaningA request from the mini app
NOT_ASKEDNever asked (also: no row)Shows the dialog
GRANTEDThe user said yesReturns granted with no dialog
DENIEDThe user said no onceShows the dialog one more time (the mini app should explain why first)
BLOCKEDThe user said no twice in a rowReturns blocked with no dialog. Only the menu switch can change it

Rules: answering yes in the dialog sets GRANTED and the denial count to 0. The first no sets DENIED (count 1); the second no sets BLOCKED (count 2). A switch in the menu always works: switching on sets GRANTED, count 0; switching off sets DENIED, count 0, so the mini app may ask again later. A capability not granted to the app by staff never gets a dialog: the request returns not_available at once. There is no timer that unblocks; only the menu does.

The server enforces this, not the bridge: a dialog is only allowed after the server has issued a one-time prompt for it (section 6), and an answer without a prompt is refused unless it comes from the menu.

New tables in user-service (it owns users and the per-app pseudonymous ids):

TableColumnsNotes
app_consentuser id, app id, capability, state, denial count, decided at, source (dialog or menu), prompt id and prompt expiry (while a dialog is open)One current row per user, app and capability. No row means NOT_ASKED.
consent_eventuser id, app id, capability, from state, to state, at, sourceAppend only. Proof that the user agreed and when.

The menu sheet lists only capabilities that are currently granted to the app (gate 1). If staff remove a capability its row stays but is inert and no longer listed. If staff grant a new one, nothing happens until the mini app asks for it.

Built (step 1): the purpose sentence, as it works today

The text was already stored next to the grant under the name reason; it is now called purpose everywhere (database column renamed by migration V7__capability_purpose.sql; the old request field name reason is still accepted as an alias). It is one sentence per language (en, am, om), at most 160 characters, one line, no link, and required in English (10 characters or more) for the capabilities whose catalog entry says purposeRequired: true. Decision: a grant without a purpose is allowed for the other capabilities (user.basic, notify.*); the dialog then shows the catalog's default sentence (defaultPurpose), so no dialog is ever empty. Each capability also has a catalog label (the dialog headline), returned by GET /admin/api/v1/capabilities and in the public catalog permissions. Other services read label, purpose and default from registry-service in the permissions field of GET /internal/apps/{appId}/context (only GRANTED capabilities are listed there).

6. Endpoints

All user endpoints use the existing gateway route for signed-in users. They live under /me/apps/{app}, so they do not collide with the public catalog's /apps/{app}/permissions (what an app is allowed to use, visible to anyone). {app} is the id or slug.

EndpointPurposeCalled by
GET /api/v1/me/apps/{app}/permissions builtEvery capability granted to the app with label, purpose and this user's state. Menu sheet and getPermissionSuper app
POST /api/v1/me/apps/{app}/permissions/{capability}/request builtThe mini app asked. Returns the state and, only if a dialog is allowed, a one-time prompt with the approved textSuper app, from requestPermission
PUT /api/v1/me/apps/{app}/permissions/{capability}/answer builtThe dialog answer, with the prompt id from the previous callSuper app
PUT /api/v1/me/apps/{app}/permissions/{capability} builtThe menu switch: sets GRANTED or DENIED, resets the count, unblocksSuper app, menu sheet

GET /api/v1/me/permissions builtSettings screen: every app that holds at least one permission, with what it can seeSuper app
POST /api/v1/me/apps/{app}/launchLaunch token (section 4)Super app
GET /v1/users/{alias}/profile (partner API)Only the fields the user allowed, nothing elseMini app backend, signed
GET /admin/api/v1/apps/{id}/permissionsBackoffice: per capability, counts of granted, denied and blocked users (counts only, no list)Staff

7. Scenario: Demo Ride, start to finish

  1. Admin grants Demo Ride user.basic, user.full_name, location.fine and notify.sms, approves a purpose sentence for each, and the app goes LIVE.
  2. Hana taps Demo Ride. No dialog appears. The super app calls POST /launch and opens the mini app with the launch token.
  3. Hana taps "Find a ride". The mini app calls adera.requestPermission("location.fine"). The super app shows "Demo Ride would like your precise location. Find a driver near you." Hana taps Allow. The phone's own location dialog follows and she allows it. The mini app gets granted and getLocation() returns a position.
  4. The mini app backend verifies the token and calls GET /profile. Name was never requested, so it returns only the alias and "granted": ["user.basic"]. (user.basic is the pseudonymous id and needs no dialog on its own; see section 11.)
  5. At the end of the trip the mini app wants to text the driver's code. It calls requestPermission("notify.sms"). Hana taps Deny. The mini app gets denied, shows "We can send the code in the app instead", and uses notify.inapp (asking for that permission the same way if needed). Had it sent the SMS anyway, the partner API would have answered 403 consent_required and no SMS would leave.
  6. The mini app later asks for notify.sms again, with an explanation screen first. Hana denies again. The state is now BLOCKED.
  7. Next day the mini app tries once more and gets blocked without any dialog. It shows "Text messages are switched off" and a button that calls adera.openPermissionSettings(). Hana turns SMS on in the sheet, and the next SMS goes through.
  8. Hana opens the top menu and turns location off. The next getLocation() returns denied, and the mini app shows "We cannot continue without your location" and an Allow button that asks again.
  9. Hana taps "Disconnect". Everything becomes DENIED, the mini app receives a user.disconnected callback (section 8), and the next /profile returns 403.

8. Notifications, revocation and callbacks

  • Consent for notify.* joins the existing mute preferences. Today a user can mute an app's notifications (stored in user-service) and the app's own notify limits come from the registry. I suggest one idea: the notify consent is the mute switch. Denied means muted. That removes a second place where the user would have to say the same thing. Existing mutes would be converted to DENIED on migration.
  • Revoke is immediate. The gate reads the consent row on each call. There is no cached "allowed".
  • Tell the partner. When consent changes, we send a signed callback (the retry-for-24-hours mechanism already exists): user.consent_changed with the alias, the capability and the new state, and user.disconnected on disconnect. A partner that kept the user's name is expected to delete it on user.disconnected. We can require this in the partner terms, but we cannot enforce it technically once the data has left.
  • Suspended or deleted users fail gate 2 for everything.

9. What this does and does not protect

ThreatHandled by
A mini app calls the bridge for data it was not grantedGate 1 in the backend; the bridge's own check is only a courtesy
A mini app asks for data the user said no toGate 2, on every call
A mini app asks for more than a capability coversGate 3: each capability has a fixed set of fields
The mini app page loads a different site and the bridge talks to itThe bridge is injected only for the registered URL's origin; it checks the origin on every message
A stolen launch tokenFive-minute life, tied to one app and one pseudonymous id; data calls need the partner's private key as well
A partner keeps data after the user withdrew consentNot preventable by us. Callbacks, terms and audit only
A partner reads data and shares it with a third partyNot preventable by us. Same as above

10. Build order

  1. Built 2026-11-04. Registry: purpose per granted capability, with backoffice field and audit.
  2. Built 2026-11-04. user-service: app_consent, consent_event, the request, answer, menu, list and disconnect endpoints with the state rules of section 5. Tests, docs.
  3. Backoffice: counts per capability on the app page.
  4. notify.* gate in the notification path, and mute converted to consent.
  5. Launch token and the partner /profile endpoint.
  6. Callbacks user.consent_changed and user.disconnected.
  7. The bridge specification for the super app team: method list, message format, origin rule, error codes. Written last, because it is a thin layer over steps 1 to 6.

Each step is a separate commit with tests and its documentation, as with the bug fixes. When a step is built, its sample requests and responses on this page are replaced by real ones captured from the running stack.

11. Decisions taken (2026-11-04)

  1. Ask at the moment of need, never all at launch. One permission per request; there is no batch request.
  2. Two denials block. After the second no the dialog is not shown again; the mini app can only point the user to the permission settings.
  3. Only the menu unblocks. No timer. The menu switch also resets the denial count.
  4. No required flag. The mini app decides what to do when a permission is refused.
  5. Per-capability consent (not one yes per app).
  6. Notification consent replaces mute (mute becomes DENIED on migration).
  7. Identifying data goes through the mini app's backend with a signed request; the browser path is only for user.basic and device data.

Still open, with my default: does consent expire? (default: no.) Does pay.request need a confirmation on every payment rather than a stored yes? (default: yes; designed when payments are built.) Does user.basic, the pseudonymous id, need a dialog? (default: no, the id is not personal data and the mini app needs it to identify the user at all; it is granted without asking.)

12. Decisions taken while building (where this page was silent)

The wording and numbers above won everywhere the code allowed it. Where the page said nothing, this is what was chosen (each is easy to change):

  • Step 1. The existing per-capability reason already was the purpose text (per language, required in English for sensitive capabilities, shown to users), so it was renamed purpose instead of adding a second field; reason stays accepted as an input alias. New rules: at most 160 characters, one line, no link. A grant without a purpose is allowed where the catalog does not require one, and the dialog then shows the catalog's default sentence.
  • Step 2, app state. A DRAFT or unknown app answers 404 not_found (users never see drafts); a PAUSED or KILLED app answers 403 app_not_live (the page's gate 1 wording). Disconnect is allowed for any existing non-draft app, also paused, so a user can always leave.
  • Step 2, errors. 409 prompt_invalid (no ticket, wrong ticket, used, or tied to another user, app or capability), 409 prompt_expired, 403 capability_not_granted for answer and menu on a capability staff did not grant, 409 use_disconnect for switching user.basic off, 403 account_suspended / account_deleted for a user who is not ACTIVE. All use the {"error": code} shape; validation uses validation_failed with fields.
  • Step 2, user.basic. Reported GRANTED without a row while granted to the app (open decision default). Disconnect stores DENIED for it too (so the next profile call can be refused); it is switched on again by the menu or, from step 5, by opening the app. It cannot be refused in a dialog or switched off alone.
  • Step 2, shapes. The list endpoint returns a JSON array. Each item also carries denialCount, canAskAgain (a dialog would be shown on the next request) and decidedAt. The settings overview lists an app only while the user has at least one GRANTED permission there; only permissions that are still granted by staff are shown. The answer to Disconnect is {"disconnected": true, "changed": [...]}.
  • Step 2, ticket. pr_ plus 24 random hex characters, valid 5 minutes, single use, replaced by the next request. Never-asked permissions stay NOT_ASKED after Disconnect; a BLOCKED one becomes DENIED with count 0 (the page says "everything to DENIED, count 0").
  • Step 2, rate limit. 30 per minute per address for the dialog request route, matched in the gateway by a regular expression on the path (APISIX does not match a wildcard in the middle of a path); everything else under /api/v1/me keeps 300 per minute.
