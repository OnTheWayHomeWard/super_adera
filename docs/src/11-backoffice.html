11. Backoffice (staff dashboard)

A plain, detailed React dashboard for Adera staff: mini apps, moderation, users, notifications, staff, audit log and system health. Built with Refine and Ant Design (default theme). It lives in backoffice/, is served by the gateway at http://127.0.0.1:9080/backoffice/ and talks only to the staff API (8b) and the Kratos flows (8e).

Operator's manual

This page is the technical overview (screens, API calls, configuration, tests). For step-by-step instructions written for staff (signing in, every field, a mini app from zero to LIVE, "why didn't my notification arrive?", recipes) read 12. Backoffice guide.

What it is

  • Static files only. A node build produces HTML, JavaScript and CSS; nginx serves them. There is no backend of its own, no database and no secrets in the files. Everything shown comes from the staff-protected API.
  • Same origin. The page, the admin API (/admin/api/v1) and Kratos (/kratos) are all behind the gateway at port 9080, so there is no CORS to configure.
  • The server is the authority. The role-aware UI only hides or disables what the server would refuse (VIEWER read-only, ADMIN writes, SUPER_ADMIN manages staff). Every refusal the server still sends is shown in plain words.
  • Session handling. The aal2 session token is kept in memory and in sessionStorage (gone when the tab closes; never localStorage) and sent as Authorization: Bearer. A 401 sends you to the login page with a message; 403 mfa_required goes to the authenticator step; 403 not_staff signs you out and says the account is not an active staff member.

Run it

docker compose up -d --build backoffice apisix   # production-like, then open http://127.0.0.1:9080/backoffice/
cd backoffice && npm install && npm run dev       # hot reload at http://localhost:5173/backoffice/ (proxies /admin, /kratos to the gateway)
npm run build                                       # type-check and build dist/
npm test                                            # unit tests
npm run smoke                                       # live API smoke test against the running stack
bash tests/ui/run.sh                                # browser walk-through (Playwright in a throw-away container)

Details are in backoffice/README.md.

Login

  1. Enter the staff email. The dashboard starts a Kratos native login flow and submits the email; Kratos sends a 6-digit code (valid 5 minutes) through notification-service. In the dev stack the email goes to Mailpit (http://127.0.0.1:8025) and the page says so while dev hints are on.
  2. Enter the code. First time for this account: scan the QR code (or type the secret, or open the otpauth:// link) in an authenticator app and enter the first code to enrol. After that: authenticator code only.
  3. The result is an aal2 token. The top bar shows your email and role; Sign out revokes the session at Kratos and clears the tab's storage.

Only active staff can use the dashboard: a signed-in account that is not an active staff member gets 403 not_staff on every admin call and the dashboard signs it out with that message. The first super admin is created from BOOTSTRAP_SUPER_ADMIN_EMAIL when no super admin exists (flagged on the Staff screen).

Gateway rule

The gateway allows 10 login-step submits per minute per IP (429), and Kratos refuses an authenticator code it has already accepted, so a second sign-in within the same 30-second window must wait for the next code. The page explains both. Native flows have no cookies, so the gateway removes the Origin header from POST /kratos/self-service/*: Kratos otherwise refuses a native flow submitted by a browser's fetch() ("The HTTP Request Header included the Origin key").

Roles

RoleCan do
VIEWERRead everything the dashboard shows. Users: email and phone masked, no gender, date of birth or extra values. No audit log. No writes (buttons hidden or disabled; the server answers 403 insufficient_role if tried).
ADMINEverything a viewer can, plus all changes to apps, capabilities, limits, addresses, keys, payment settings, templates, moderation and user status; reads the audit log and unmasked user data.
SUPER_ADMINEverything an admin can, plus staff management and reviving a KILLED app.

Screens and the API calls they make

Paths are relative to /admin/api/v1 unless they start with /kratos or /backoffice. Errors are always the shape {"error": code, ...}; validation errors carry fields, which the forms show next to the inputs. Destructive actions (status changes, key revoke, user suspend or delete, staff deactivate, logo removal) ask for confirmation.

Configuration

Nothing is baked into the image. At start the container writes /backoffice/config.json from environment variables (set in docker-compose.yml, override in the repo-root .env). The file is public: no secrets.

Tests

  • Unit (Vitest): session handling (memory plus sessionStorage), API client error mapping (401, 403 mfa_required and not_staff, 429, validation fields, 204), Kratos flow handling, role gating, form payloads.
  • Live smoke (npm run smoke, backoffice/tests/live/): the dashboard's own API client against the running stack with a real staff session: login, apps, keys, templates, VIEWER masking, staff, audit filters, health probes.
  • Browser walk-through (bash backoffice/tests/ui/run.sh): Playwright in a throw-away container clicks through login, every app tab, moderation, users, notifications, staff, audit, system, sign-out and session expiry, saving screenshots.
  • Backend: user-service AdminUsersTests and MaskingTest; registry-service BackofficeApiTests and TrustAndBootstrapTests; gateway checks in tests/e2e/admin_users.py.

Notes and limits

  • The app list returns all apps at once and the search box filters them in the browser; fine for hundreds of apps, to be paged server-side later.
  • Payment settings are stored but payments are not built yet.
  • Staff accounts are created by email; a new staff member signs in with the emailed code and enrols an authenticator on first use.
  • Audit rows are never deleted by the dashboard; suspended or deleted users are refused at the gateway, and cannot receive notifications (delivery context reachable: false).
