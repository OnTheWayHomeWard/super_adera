Environment variables

Where a variable is set: .env = repo-root .env (gitignored; compose reads it); compose = fixed in docker-compose.yml; Infisical = project Adera, environment dev, folder shown; default = the value in the service's application.yml. "Secret" means the value must never be printed or committed. Service-specific property names and meanings are in Services.

Lessons that apply to every row: docker compose restart does not re-read compose environment; after changing .env or compose use docker compose up -d <service>. See troubleshooting.

Variables used by the e2e scripts

tests/e2e/*.py read .env themselves (for example RustFS keys for s3tool.py) and keep a per-staff TOTP state file in tests/e2e/.staff-totp-<email>.json (gitignored, mode 0600; it is a secret, do not share it). Scripts that need staff use a temporary account from tests/e2e/tempstaff.py (removed afterwards), never the bootstrap account; ADERA_STAFF_EMAIL selects a real account instead.

Capability catalog and default limits

Capabilities are what staff may allow a mini app to ask for (Capability enum in registry-service; list at GET /admin/api/v1/capabilities). Granting is the admin gate; the per-user consent gate arrives with the frontend bridge (not built). Each app-capability pair has a state GRANTED, DENIED or SUSPENDED. A capability marked reason required cannot be granted without an English reason of at least 10 characters, which is shown to users verbatim in the consent sheet.

Only the three notify.* capabilities are enforced by code today (notification-service). The others are stored and shown in the public catalog as permissions but nothing consumes them yet (the frontend bridge and payments are not built).

Default notification limits

When notify.* is GRANTED and the app has no limit row for that channel yet, registry-service inserts these defaults (AppConfigService.defaultLimit). Staff change them per app with PUT /admin/api/v1/apps/{id}/notification-limits/{channel}. null means unlimited, 0 means none. Counting is per UTC day (the lifetime total is never reset). An app can hold limits for a channel without the capability, but delivery still requires the capability.

Environments

A deployment is exactly one environment, set by ADERA_ENV=dev|prod (default dev); the dev deployment is DEV, the prod deployment is PROD, and they never co-exist. Staff can store allowed addresses and register keys for both, but only the one that matches the deployment is active: a key of the other environment is refused with 403 wrong_environment. DEV: works for any app that is not KILLED; the dev providers (console SMS, Mailpit, fake push) are the sandbox, and the synthetic users u_p_test_* (u_p_test_unreachable, u_p_test_muted) are simulated, nothing sent. PROD: the app status must be LIVE; synthetic users are refused (422 synthetic_user_not_allowed). Each environment has its own keys, allowed addresses and usage counters. This is separate from the app status above.

Partner key states

StateMeaning
ACTIVEStored status. Usable unless expires_at has passed.
(expired)Not a stored status: ACTIVE with a past expires_at. Calls fail with key_revoked_or_expired.
REVOKEDRevoked by staff (revoked_at set). Irreversible; register a new key. Calls fail with key_revoked_or_expired within about 15 s.

Key ids look like ak_dev_<24 hex> / ak_prod_<24 hex> (keys made before the rename keep ak_test_ / ak_live_); the algorithm is RS256; at most 5 ACTIVE keys per app and environment.

Error-code index

Application errors are {"error": "<code>", ...details}. This index was built from the exception handlers and every throw site in the three services. Statuses returned by the gateway itself (429, 403 for blocked admin, 503 from forward-auth) and by Kratos are listed at the end. Examples with real bodies are in the endpoint reference.

ip_not_allowed403Caller address not inside the app's allowed CIDRs for this environment (new apps start with an empty list, so nothing can call).
capability_not_granted (with capability)403Template needs a channel whose notify.* capability is not GRANTED.
validation_failed (with fields)400Unknown field; bad externalId, userId, templateId, params, data, callbackUrl, ttlSeconds.
invalid_request400Body is not a JSON object.
not_found404GET /v1/notifications/{externalId} with an unknown id (for this app and environment).
template_not_found404Template id unknown or belongs to another app.
external_id_reused409Same externalId with a different request (the request hash differs). The same request again is a 200 replay.
wrong_environment403The key belongs to the other environment than this deployment (DEV key on a PROD deployment or the reverse); checked after the signature verifies. The registry's internal context endpoint gives the same code when asked for the other environment.
synthetic_user_not_allowed422A u_p_test_* user on a PROD deployment (synthetic users exist in DEV only).
user_unreachable422Alias unknown, user deleted or suspended, or no usable channel (all look the same on purpose).
template_inactive, template_not_yet_valid, template_expired422Template switched off, before validFrom, or past expiresAt.
param_invalid (with fields)422Value not declared, missing required, too long, control characters, link-like text where links are not allowed, or wrong type.

Not errors: 202 QUEUED accepted; 200 with "replayed": true; 200 with status SUPPRESSED (the user muted the app, not revealed as an error).

Doc vs code: docs/PARTNER_API.md does not list invalid_timestamp, unknown_app, request_too_large, template_not_yet_valid, the exact 403 codes app_draft|app_paused|app_killed (it says "app not active in this environment"), or template_not_found (it says "404 template not yours / unknown").

Glossary of terms

aal1 / aal2
Kratos "authenticator assurance level". aal1 = one factor (an emailed or texted code). aal2 = a second factor too (authenticator-app code, TOTP). Staff need aal2.
Alias (pseudonymous id)
u_p_<32 hex>: the id a partner sees for a user. Different for every app, derived with HMAC from a server secret, resolvable only through our table. See Security.
Allowed addresses / CIDR
The server IPs or ranges (per environment, DEV or PROD) a partner may call from. A request from elsewhere is ip_not_allowed.
APISIX
The API gateway; the app's only entry point (port 9080).
Audit event
An append-only record of a staff change in registry.audit_event.
Callback
A signed HTTP POST from us to the partner's callbackUrl when a notification reaches a final status.
Capability
A permission staff can grant an app (read user name, send SMS, ...). See the catalog above.
Courier (Kratos)
Kratos' component that sends messages. Here it posts to notification-service instead of sending itself.
Delivery context
What notification-service learns from user-service about one user for one app: reachable?, language, phone, email, push tokens, mute switches.
Dev mode / real mode
Dev: SMS to the console log, email to Mailpit, fake push, dev endpoints on. Real: Twilio, Resend, Firebase. See delivery modes.
externalId
The partner's own unique id for a notification: idempotency key and lookup reference.
Forward-auth
An APISIX plugin that asks another service "may this request pass?" before forwarding. The answer's headers (X-User-Id, X-Staff-Id, X-Staff-Role) are copied onto the forwarded request.
Gateway secret (X-Gateway-Secret)
Shared secret proving a request came through APISIX. Services reject /api and /admin/api calls without it.
Idempotency-Key (callback)
The callback row id, sent as a header so the partner can de-duplicate retries.
Infisical
Self-hosted secrets manager holding API keys (Twilio, Resend, our signing key).
Internal secret (X-Internal-Secret)
Shared secret for service-to-service calls (/internal/**). The gateway never routes those paths.
JWKS
JSON Web Key Set at /.well-known/jwks.json: our public signing key, so partners can verify responses and callbacks.
Kratos identity id = user id
The Ory Kratos identity UUID is used as the user id everywhere (user-service app_user.id, staff identity_id).
Mini app
A partner service shown inside the Adera super app, registered in registry-service.
Mute
A user's per-app choice to stop in-app, SMS or email messages. Partners are never told; the notification is simply SUPPRESSED.
RS256 / ADERA-SIG-1
RSA signature with SHA-256 over our canonical string. The signing scheme for partner requests, responses and callbacks.
Environment (DEV / PROD)
What a deployment is (ADERA_ENV); keys and allowed addresses are stored per environment but only the deployment's own is active. See environments above.
Session token
The Kratos session token the native app sends as Authorization: Bearer ...; valid 30 days.
SSRF guard
UrlGuard: stops a partner-supplied callback URL from reaching our internal network.
Template
An admin-approved message with declared values; partners cannot send free text.
TOTP
Time-based one-time password from an authenticator app (6 digits, 30 s window). Kratos refuses to accept the same code twice.
Verification tier
How strongly a user is verified: CONTACT, ID, PROVIDER.
Webhook (registration)
Kratos' non-blocking call to user-service after sign-up, creating the profile row.
