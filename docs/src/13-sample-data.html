13. Sample data (test scenarios for the DEV stack)

A script that fills the DEV stack with realistic data so the team can try every screen and flow: users in every account state, reviews and reports in every state, apps in every status, partner keys, templates and notifications in every state that the real system can produce. Everything goes through the real APIs (users through the gateway as real signed-in users, staff through the admin API, partners with signed requests), so every row is validated and audited. Script: tests/e2e/seed_scenarios.py. Written 2026-10-25 from the code, which wins over the other pages.

DEV only

The script refuses to run unless notification-service's /dev/messages endpoint answers. Nothing real is sent: SMS goes to the console log, email to Mailpit, push to the fake provider. It never uses the bootstrap staff account: it creates temporary staff accounts with tests/e2e/tempstaff.py and removes them at exit.

2. Run and remove

python3 -I tests/e2e/seed_scenarios.py              # create or complete (safe to repeat, about 9 minutes the first time, 3 later)
python3 -I tests/e2e/seed_scenarios.py --check      # read-only verification (masking, roles, counts)
python3 -I tests/e2e/seed_scenarios.py --remove     # delete everything it created, nothing else
python3 -I tests/e2e/seed_scenarios.py --no-outage  # skip the Mailpit stop (see below)
  • Run it from the repository root, after tests/e2e/seed_demo.py. It keeps ids in tests/e2e/.seed-scenarios-state.json (gitignored) but decides from the servers' own data, so a lost state file does not duplicate users, apps, templates or staff.
  • It is slow because the gateway allows 10 sign-up/login submits a minute per address. It paces itself and waits out 429 answers.
  • Mailpit is stopped for about 40 seconds, and started again even if the script fails, to make email delivery fail for real: that produces RETRYING and EXPIRED.
  • --remove uses the Kratos admin API for identities and SQL for the rest, because the platform has no delete for users, apps, templates, notifications, reviews, reports or audit rows. It also deletes avatar and logo files, the fake addresses' one-time-code log rows, recomputes the ratings of the older apps with the service's own formula, and resets their allowed addresses. The five older apps stay.
  • After a removal and a new run the counts were identical (same checks, 306 passed).

4. Scenarios that could not be produced

ScenarioWhy
Notification status FAILEDPermanent failures exist only for Twilio and Resend HTTP 4xx errors (not used in DEV). Temporary errors retry eight times over hours, so FAILED would take a day of Mailpit downtime.
A RETRYING row that staysThe status lasts 30 to 120 seconds. The script shows it live, and the row ends SENT once Mailpit is back.
Callback FAILED by exhausted retriesEight attempts over about a day. One callback is FAILED at once (invalid_url); two are PENDING and will become FAILED by themselves.
app_draft, app_pausedIn DEV every app except KILLED may call. Only PROD refuses those states.
Reports against reviewsThe API takes reports against apps only.
Notes on a reportThe API takes a status only (OPEN, REVIEWED, DISMISSED); there is no note field.
A user addressA profile has no postal address (capability user.address exists, nothing stores one).

5. Issues found

Found while generating the flows. None was fixed (only the script is mine).

#IssueReproduce
1Bug (fixed 2026-10-26). A staff member who never signed in could not be deactivated: 503. registry-service treats Kratos' 404 "no sessions" on DELETE /admin/identities/{id}/sessions as "Kratos unavailable" (StaffService.update via KratosClient.revokeSessions). The row stays ACTIVE.SUPER_ADMIN: POST /admin/api/v1/staff {email, role VIEWER}, then PATCH /staff/{id} {"status":"DISABLED"} gives 503. After one email sign-in of that account it works. (user-service ignores the same 404.)
2Fixed 2026-10-26: a reopened report used to keep handledBy and handledAt; they are now cleared on reopen (a migration also cleared the two seeded OPEN rows that still had them).PATCH /reports/{id} REVIEWED, then OPEN; read it back: both null.
3A second report by the same user against the same app is silently dropped while the first is OPEN, even with another reason or details. The user is told "received".u02: report food SPAM, then SCAM with new details: same report id, reason still SPAM.
4Report handling has no notes and no "resolved" status; the word in the manual ("Resolve") is REVIEWED in the API, and RESOLVED is refused (400).PATCH /reports/{id} {"status":"RESOLVED"}.
5Reports and reviews only work for LIVE apps. Once an app is PAUSED or KILLED its reviews stay but the author gets 404 on my-review (cannot read or delete it), and nobody can report the app.u01 reviewed demo-paused; the app is PAUSED: GET and DELETE /api/v1/apps/demo-paused/my-review, POST .../report give 404.
6By design (admins hide reviews explicitly): reviews of a SUSPENDED or DELETED user stay public and count toward the rating until staff hide them by hand.u12 (DELETED) has a visible review of demo-food; the catalog count 10 includes it.
7PUT /api/v1/me/apps/{appId}/preferences accepts any UUID: preferences are stored for apps that do not exist.PUT with a random UUID returns 200 and a row is created.
8Partner callbackUrl was only checked for a prefix (fixed 2026-10-26: the shape is now checked when the request arrives and a bad one answers 400 validation_failed). An address with credentials (http://user@host/) or, in PROD, plain http://, gets 202 and the callback later fails (invalid_url, scheme_not_https). The validation message says "must be an https URL" while http is accepted.Send with callbackUrl "http://user@127.0.0.1:9/hook": 202; the notification detail shows a FAILED callback with last error invalid_url.
9There is no public way to mint a pseudonymous id (the "when the user opens the app" step is not built); the capability user.address has no data behind it.The seed uses the internal endpoint POST /internal/aliases.
10User search does not find the local phone format: 0900000004 finds nothing for +251900000004 (251 900 000 004 and the last digits work).Users, search "0900000004".
11UI: the dashboard panel "Apps not ready for LIVE" lists a DRAFT app whose "Missing" cell says "nothing: ready".Dashboard with demo-flights as DRAFT.
12UI: on the user detail at 1440 px the Profile table is clipped at the card edge (the phone number is cut).Users, open u01 as SUPER_ADMIN.
13UI: a notification detail still shows "Next attempt" after completion, shows the app as a bare UUID, and "Status reason" is "-" for SENT after retries.Notifications, open seed-food-email-retried.
14UI: staff who no longer exist in the registry show as a short id in the audit log and "Recent staff activity" (every audit row of this seeding, since its temporary accounts are removed).Audit log.
15The partner status check GET /v1/notifications/{id} shows PROCESSING while a provider call hangs; with Mailpit stopped, the first attempt took over 15 seconds to fail (the cause was not investigated). A slow provider can hold worker slots.Stop Mailpit, send an EMAIL notification, watch the status.
16When a limit is exhausted, max_total is reported even if per-user or per-day limits are also hit (checks run in a fixed order); partners cannot tell which others apply.demo-quota SMS after the 5th message: any user gets max_total.
17The browser console shows one 400 and one 403 during staff sign-in (every role). They come from the sign-in steps, not from the data screens.Open the dashboard with developer tools, sign in.
18Operational: sign-up and login are limited to 10 submits a minute per address, so seeding 15 users takes minutes; one-time-code limits are per recipient (SMS 5/hour). Re-running --remove clears the fake addresses' log rows so a recreation is not blocked.Run the script.
