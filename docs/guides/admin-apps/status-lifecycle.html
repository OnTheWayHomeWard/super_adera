Status lifecycle

DRAFT, LIVE, PAUSED, KILLED: the rules for changing them and what each one does to users, partners and notifications.

Overview

Every app has one status. The status is the master switch: it decides whether users can find the app, whether the partner's servers may call Adera, and therefore whether notifications can be sent. There are four statuses and one endpoint to change them.

Why this existsYou need a switch that works in minutes without deleting anything: to hold an unfinished app back (DRAFT), to publish it (LIVE), to stop it temporarily during an incident (PAUSED), and to shut it down for good when it is abusive or compromised (KILLED). Reviving a KILLED app is reserved for the owner level because it was killed for a serious reason.

What each status means

StatusMeaningUsers (catalog)Partner calls, DEV deploymentPartner calls, PROD deployment
DRAFTNew or not yet approved. The starting status.Not listed. Detail by slug or id answers 404 not_found.Allowed, so the partner can build and test.Refused: 403 app_draft.
LIVEPublished. The only status users can see.Listed in GET /api/v1/apps and openable; reviews and reports accepted.Allowed.Allowed.
PAUSEDTemporarily off: incident, investigation, the partner asked, a pending fix.Disappears from the catalog (404 on detail, reviews and report).Allowed (testing continues).Refused: 403 app_paused.
KILLEDShut down: abuse, fraud, compromised keys, contract ended.Disappears from the catalog.Refused: 403 app_killed.Refused: 403 app_killed.

The rule behind the partner columns: in the DEV deployment an app is usable unless it is KILLED, so partners can integrate before going live; in the PROD deployment it is usable only while it is LIVE. (A deployment is exactly one environment, see Environments and IPs; this dev stack runs DEV, so the PROD column comes from the code and its tests, not from a live capture.)

  • The client learns about a status change only the next time it fetches the catalog. Fetch it when the super app opens and whenever the user returns to the mini-app list; treat a 404 on an app the user had as "no longer available".
  • Status does not touch the partner's own website. A user who already has the page open can keep using it; PAUSED and KILLED remove the app from Adera's catalog and stop its calls to Adera, they do not take down the partner's server.
  • Existing reviews are kept while an app is not LIVE and come back with it; the average rating is unchanged.

What notifications do

  • New sends are refused as in the table (the same 403 app_... on every partner endpoint, including status lookups and the template list).
  • Already accepted messages (QUEUED or RETRYING) are not cancelled by a status change: the delivery worker does not look at the app status again, so they are still delivered or finish retrying, and their callbacks are still sent. This is how the code works (there is no status check in the delivery path). They cannot be cancelled from the API: normally they are delivered within seconds, and messages in RETRYING keep trying until they expire (24 hours by default). If the problem is the wording, edit the template text: delivery uses the template's current words.
  • In-app inbox entries already created stay in the users' inboxes.
  • Keys, capabilities, limits, addresses and templates are untouched by a status change; they are simply not used while the app is not usable.
Delay

The notification service remembers an app's answer for about 15 seconds. After you pause or kill an app, partner calls can still be accepted for up to 15 seconds. The same applies when you set an app back to LIVE: the partner may still see the old refusal for up to 15 seconds.

Transition rules

There is no required order: any status can be set from any status, with exactly three rules.

RuleDetails
1. Leaving KILLED needs SUPER_ADMINAny change from KILLED to DRAFT, LIVE or PAUSED by an ADMIN is refused with 403 only_super_admin_can_revive_killed_app. Setting KILLED on an app that is already KILLED is allowed for an ADMIN (it just records another event).
2. LIVE needs a logo and a support emailEvery time the status is set to LIVE (from DRAFT, from PAUSED, even LIVE to LIVE) the server checks the app has a logo and a supportEmail; otherwise 409 not_ready_for_live and fields.missing says which (logo, supportEmail or logo,supportEmail). The check runs only when the status is set: removing the logo later from an app that is already LIVE does not take it offline, but you cannot set it LIVE again until the logo is back.
3. Only the four names are validAny other value, or a missing status, is 400 validation_failed.

Pause or kill? Which one to use

SituationUseWhy
Incident under investigation, partner outage, a bug that sends wrong messagesPAUSEDReversible by any ADMIN as soon as it is fixed; nothing else about the app changes.
The partner asks to be taken offline for maintenancePAUSEDSame.
Abuse, fraud, a leaked private key that you cannot rotate in time, a terminated contractKILLEDOnly a SUPER_ADMIN can bring it back, so a second pair of eyes decides.
An app that was approved by mistake and must be hidden againDRAFTHidden from users, still testable in DEV, and an ADMIN can publish it again later.

Endpoint

Who may call
ADMIN or SUPER_ADMIN; leaving KILLED: SUPER_ADMIN only
Auth

Rate limit
300 requests per minute per client IP at the gateway (HTTP 429 beyond that)

Purpose. Sets the app's status. When to use it. To publish an app (LIVE), stop it temporarily (PAUSED), shut it down (KILLED), return it to draft (DRAFT), or revive a killed one (SUPER_ADMIN).

Request body

FieldTypeRequiredMeaning
statusstringyesDRAFT, LIVE, PAUSED or KILLED. Any letter case is accepted (live works).
curl -sS -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/status" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
  "status": "LIVE"
}'

Reviving a KILLED app (SUPER_ADMIN)

Exactly the same call, made with a SUPER_ADMIN token. Real sequence from the test: killed by an ADMIN (200), ADMIN revive refused (403), a second KILLED by the ADMIN accepted (200, no-op), SUPER_ADMIN revive to PAUSED accepted:

ADMIN  -> KILLED again:
HTTP 200 (status KILLED)

SUPER_ADMIN -> PAUSED:
HTTP 200 (status PAUSED)

Good practice: revive to PAUSED first, check keys, capabilities and addresses (the reason it was killed may still be there), then set LIVE with a second call.

Effects, audit, side effects

  • Audit: app.status with meta {"from": "PAUSED", "to": "LIVE"} (also written when the status does not actually change). Real event below.
  • Takes effect at once in the user catalog; partner calls follow within about 15 seconds (see the delay note above).
  • Not reversible only in the sense that leaving KILLED needs a SUPER_ADMIN; every other change is undone by setting the previous status.
  • No notification is sent to the partner or to users by Adera; tell the partner yourself (their support email is on the app).

Scenario

A partner reports that their backend is sending the wrong template to thousands of users. You set the app to PAUSED (one call), tell the partner, wait for their fix, check the notification log, and set it LIVE again. If instead you discover their private key leaked, you set KILLED, and a super admin revives it only after a new key is registered and the old one revoked. Step by step: see the runbooks.

Backoffice: the app page shows Status: with a one-line help text and, for an ADMIN, Change to: buttons for the other three statuses. Each button opens a confirmation ("Set ... to PAUSED?") that repeats what the status does; PAUSED and KILLED are shown as dangerous actions. Banners say what is missing for LIVE ("To go LIVE this app still needs logo and supportEmail") or that the app is ready. For a KILLED app the buttons are disabled for an ADMIN with the tag "Only a super admin can revive a KILLED app".
