Capabilities

What a mini app may ask for: the catalog, granting, denying and suspending, the purpose sentence, and what each capability does.

Overview

A capability is one thing a mini app is allowed to ask for: a piece of user data, a kind of location, the right to send SMS, the right to ask for a payment. By default an app has none. Staff grant them one by one, and can deny or suspend them again. The capabilities that are granted are what the user sees on the app's detail page ("this app can ..." with the purpose sentence you approved), and the text of the permission dialog the user answers when the app asks for it, and, for the three notify.* capabilities, what the notification service enforces on every partner call.

Why this existsLeast privilege: a partner gets only what its product needs, each grant is a deliberate, audited decision, and any sensitive grant must come with a plain-language purpose sentence that is shown to users in the permission dialog. Suspending is the quick brake when a partner misuses one capability but the rest of the app should keep working.

Be clear with partners

Only the notify.* capabilities change what the platform does today. user.*, location.* and pay.request are recorded, audited and shown to users, but no service checks them yet because the in-app bridge and the payment feature are not built. Grant them anyway when the product needs them, so that the consent text users see is already right when the bridge ships.

States and purposes

StateMeaningEffect today
GRANTEDThe app may use it.Counts for the notification checks; listed to users in the catalog with its label, description and purpose.
DENIEDReviewed and refused (or never approved).Not usable; not shown to users. The purpose you write is kept for staff.
SUSPENDEDWas granted, switched off for now (misuse, investigation).Not usable; not shown to users. Switch back with GRANTED.
  • A capability that has never been set is simply not granted (default deny). There is no "delete": set DENIED.
  • DENIED and SUSPENDED behave the same for the platform; the difference is the story you tell staff and the audit trail.
  • The purpose (formerly called "reason"; the old field name is still accepted in requests) is ONE plain sentence, an object like {"en": "To show technicians near you.", "am": "..."} (en, am, om). When you GRANT a capability whose purposeRequired is true (user.full_name, user.contact, user.address, location.coarse, location.fine, pay.request) English purpose of at least 10 characters is required; Amharic and Oromo are optional but recommended. Write it for the user ("Find a driver near you."), not for engineers: it is shown verbatim in the permission dialog. Rules checked on every language: at most 160 characters, one line, no link (no http:, www., mailto:, ://). There is no automatic check that it is a single sentence beyond these limits; that is the reviewer's job.
  • A purpose is optional for the other capabilities (user.basic, notify.*) and for DENIED or SUSPENDED. A grant without a purpose is allowed there: the dialog then shows the catalog's default text for the capability (see defaultPurpose in the catalog below), so no dialog is ever empty. Every change of a purpose is on the audit log with the old and the new text.

Side effect: default notification limits

Granting notify.sms, notify.email or notify.inapp also creates that channel's notification limits with conservative defaults, but only if the app has no limits for that channel yet (existing limits are never touched, and suspending or denying never removes them). An admin raises them per app later (see Notification limits).

Purpose. Sets the state of one capability for one app, and (when granting) the purpose sentence users will read. The call replaces that capability's state and purpose; it is an upsert, not a patch. When to use it. To approve what a partner asked for, to refuse it, or to suspend a capability during a misuse investigation.

appIdpathUUIDyesThe app.
capabilitypathstringyesA key from the catalog, e.g. location.coarse.

purposebodyobjectrequired when granting a capability that needs oneOne sentence per language (en, am, om); en at least 10 characters when required; each at most 160 characters, one line, no link. reason is accepted as the old name (not together with purpose).
(anything else)body--Any other body field is refused with unknown field.

Effects, audit, gotchas

  • Audit: capability.set, meta {"capability": "notify.sms", "state": "SUSPENDED", "purpose": {}, "previousState": "GRANTED", "previousPurpose": {}} plus the new and previous purpose text, so the audit tab shows exactly what users were told and what it replaced).
  • Takes effect in the notification service within about 15 seconds. After you suspend notify.sms, new DIRECT sends are not made by SMS (see the next section).
  • Messages already accepted keep their channel; they are not re-routed when a capability changes later.
  • To remove a grant, set DENIED (or SUSPENDED if it should come back).
  • The purpose of a GRANTED capability is shown to users verbatim: re-read it before saving. Changing it later is another PUT with the same state and a new purpose.

Scenario

A home-services partner asks for city-level location. You grant location.coarse with "To show technicians near you" and the Amharic text. Users who open the app's details now see that line. Later you find the partner sends too many SMS: you suspend notify.sms only, and tell them to use in-app messages until you re-grant it.

How the notify.* capabilities act on partner sends

The partner never chooses a channel. The template kind and the user's contact details decide, and the capabilities gate each channel:

Template kindChannel chosenNeeds
IN_APPIN_APP (inbox entry plus push to the user's devices)notify.inapp GRANTED, else 403 capability_not_granted (with capability: notify.inapp).
DIRECTSMS if the user has a phone and notify.sms is granted; otherwise EMAIL if the user has an email and notify.email is grantedAt least one of the two matching capabilities. If the user's reachable contact needs a capability that is not granted: 403 capability_not_granted; if no contact fits: 422 user_unreachable.

Real partner-side results from the test (the DIRECT template to a test user who has both a phone and an email):

notify.sms SUSPENDED, notify.email GRANTED -> falls back to email:
HTTP 202  channel: EMAIL

both SUSPENDED:
HTTP 403  {"error": "capability_not_granted", "capability": "notify.sms"}

both GRANTED again -> SMS:
HTTP 202  channel: SMS

So suspending SMS alone can quietly move a partner's traffic to email; suspend both channels if you want the DIRECT sends to stop.

Not built yet

  • Enforcement of user.*, location.* and pay.request (the per-user consent is stored by user-service since 2026-11-04: users answer one permission at a time in the super app; the partner profile endpoint and the bridge arrive in later steps and this page is updated as each lands).
  • A separate history view of a capability's old purposes (the audit tab of the app shows each change with the old and new text).
  • Adding new capability keys without a code change.
