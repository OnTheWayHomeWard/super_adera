Roles and access

How staff sign in for API use, the three roles, and who may do what.

Overview

Every call in this guide is made by a staff member. A staff member proves who they are twice (an emailed one-time code and an authenticator-app code), and then has one of three roles. This page explains how to get a working token for API use, what each role may do on mini apps, and what you see when something is missing.

Why this existsMini apps decide what partners may send to real people and what data they may see. Two proofs of identity plus three simple roles keep that power with a few people, and every change is written to the audit log with the actor's name, role and IP address.

Staff sign-in for API use

Staff accounts use the same identity service as end users (Kratos, reached through the gateway at $GATEWAY/kratos/...), but with a second step. The result is a session token. You send it as Authorization: Bearer $TOKEN on every admin call. The gateway asks the registry service on every request whether the token belongs to an active staff member at aal2, and passes the staff id and role on to the service that handles the call. A person who is not staff, or whose account was disabled, gets 403 not_staff or 401 unauthorized.

StepWhat happensResult
1. Email codeYou ask for a one-time code for your staff email address and submit it.A session at aal1. The admin API still answers 403 mfa_required.
2. Authenticator app (first time only)You enrol an authenticator app (TOTP) on the aal1 session. This needs a recent login (the identity service wants a "privileged session", at most 15 minutes old).Right after enrolment the session is already aal2.
3. Authenticator app (every later login)After the emailed code you upgrade the session with the current 6-digit code from the app.A session at aal2: the admin API works.

Facts that matter when you script this:

  • The emailed code is valid for 5 minutes; a login flow lives 10 minutes. A session lasts 30 days, but each new login needs both proofs again.
  • The gateway allows only 10 login-code submissions per minute per client IP, and the notification service limits one-time-code emails to about 10 per hour per address. Log in once and reuse the token; do not log in per request.
  • An authenticator code can be used only once: if you need two logins in the same 30-second window, wait for the next code.
  • In the dev stack nothing is emailed: the code is shown at http://127.0.0.1:8085/dev/messages (and in the Mailpit inbox at http://127.0.0.1:8025). On a real deployment it arrives by email.
  • Only a SUPER_ADMIN can make someone staff (POST /admin/api/v1/staff with an email and a role). The very first super admin is created from the BOOTSTRAP_SUPER_ADMIN_EMAIL setting when the registry service starts.

Every later login: after step 1 (emailed code) upgrade the session with the authenticator code. Note the X-Session-Token header (not Authorization) on these two calls:

F2=$(curl -sS "$GATEWAY/kratos/self-service/login/api?aal=aal2&refresh=false" -H "X-Session-Token: $TOKEN_AAL1" | jq -r .id)
curl -sS -X POST "$GATEWAY/kratos/self-service/login?flow=$F2" \
  -H "X-Session-Token: $TOKEN_AAL1" -H "Content-Type: application/json" \
  -d '{"method": "totp", "totp_code": "123456"}'
# the answer contains the new "session_token": that is $TOKEN for the admin API
HTTP 200  (trimmed)

{
  "session_token": "<SESSION_TOKEN>",
  "session": {
    "authenticator_assurance_level": "aal2",
    "authentication_methods": [
      "code",
      "totp"
    ]
  }
}

Test the token:

curl -sS "$GATEWAY/admin/api/v1/me" -H "Authorization: Bearer $TOKEN"
Watch out

Never use another person's account for scripts, and never put a session token or an authenticator secret into a repository. For tests, the repository ships a helper (tests/e2e/tempstaff.py) that creates a temporary staff account in the dev stack and deletes it again. There are no API keys or service accounts for staff: automation needs a real staff session.

Roles

RoleWhat it is forCan do on mini apps
VIEWERRead-only access: support, partners' account managers, auditors of the product (not of the audit log).Read everything about apps, keys (fingerprints only), templates, usage, the notification log, reviews and reports. Cannot change anything. Cannot read the audit log.
ADMINRuns the platform day to day.Everything a VIEWER can, plus every change on apps, keys, limits, addresses, templates, payment settings, moderation, and the audit log. Can set any status, but cannot move an app out of KILLED.
SUPER_ADMINThe owner and the people the owner trusts most.Everything an ADMIN can, plus reviving a KILLED app and managing staff (add, change role, disable).

A higher role includes everything below it. The server decides on every request; the backoffice only hides or greys out what the server would refuse. If you force a forbidden call anyway the answer is 403 insufficient_role.

Note

Apps, keys, templates and the notification log carry no personal data of end users, so a VIEWER sees them in full. (Masking of phone numbers and emails applies to the Users screens, which are not part of this guide.)

StatuserrorMeaningWhat to do
401unauthorizedNo token, an unknown or expired session, or the staff member was disabled.Sign in again. If it keeps failing for a known good account, ask a SUPER_ADMIN whether it was disabled.
403mfa_requiredThe session is aal1: the authenticator step is missing.Do step 2 or 3 above and retry with the new token.
403not_staffThe person signed in, but is not an active staff member (or has no role).A SUPER_ADMIN adds them as staff.
403insufficient_roleThe role is too low for this action.Ask someone with the needed role; see the matrix.
403only_super_admin_can_revive_killed_appAn ADMIN tried to move an app out of KILLED.A SUPER_ADMIN does it.
429(gateway body)More than 300 admin requests per minute from one IP.Slow down; the body comes from the gateway, not from the API.
503identity_service_unavailable or a gateway 503The identity service or the registry could not be reached while checking the token.Retry in a moment; check the System page for service health.

Purpose. Returns the staff member's id and role as the API sees them. When to use it. Right after login, to show who is signed in, to decide which buttons to show, and as the cheapest check that a token really is aal2.

Request

No parameters.

curl -sS -X GET "$GATEWAY/admin/api/v1/me" \
  -H "Authorization: Bearer $TOKEN"

Response

HTTP 200 OK

{
  "role": "ADMIN",
  "id": "0e5171f6-687c-4312-9212-971e28305d8d"
}

Errors

StatuserrorWhen it happensWhat to do
401unauthorizedNo token or an invalid one.Sign in again.
403mfa_requiredaal1 token.Finish the authenticator step.
403not_staffNot an active staff member.Ask a SUPER_ADMIN.

How to use the result

  • Cache the role in the client; the server re-checks it on every call anyway, so a stale cache can only make a button appear that is then refused.
  • The id is the staff id used as the actorId in audit events and as the actor audit filter.
