Environments and allowed IPs

DEV and PROD, ADERA_ENV, and the list of server addresses a partner may call from.

Overview

Two ideas decide whether a partner's server may call Adera: which environment this deployment is, and from which addresses the call comes.

Why this existsA partner's backend is a server with a fixed place on the internet. Allowing only its registered addresses means a stolen key is useless from anywhere else, and keeping DEV and PROD apart means a test key can never send real SMS and a production key never reaches the test system.

DEV and PROD, and ADERA_ENV

  • A deployment of Adera is exactly one environment, set by ADERA_ENV=dev or ADERA_ENV=prod (in the .env file, passed to the registry service and the notification service; both must agree). Any other value stops the service from starting; a mismatch between the two services is logged and partner calls answer 503 service_unavailable.
  • The dev deployment is DEV, the production deployment is PROD, and they never run together. They are separate deployments.
  • Staff can store addresses and register keys for both environments on either deployment, but only the one that matches the deployment is active: the other is stored and ignored. A key of the other environment is refused with 403 wrong_environment.
  • Usage counters, limits in effect and stored notifications always use the deployment's environment.
  • App status rules differ by environment (see Status lifecycle): DEV works for any app that is not KILLED, PROD only while the app is LIVE.
  • Every new app starts with both environments present and empty address lists: nothing can call until you add addresses.
  • DEV is not an isolated simulator: it runs with the development providers (SMS printed to a console, email into a local inbox, fake push), so real users in DEV are "delivered" through those. Test users whose id starts with u_p_test_ are simulated in DEV and refused in PROD.

Allowed server addresses

For each app and environment there is one list of IPs or CIDR ranges. The partner's calls to /v1/* are accepted only when the caller's address is in the list for the deployment's environment (403 ip_not_allowed otherwise).

RuleDetails
Accepted formsAn IPv4 or IPv6 address (203.0.113.10), or a range in CIDR form (198.51.100.0/24, 2001:db8::/32). Hostnames are not accepted and no DNS lookup is ever done.
NormalisationA single address becomes a /32 (IPv4) or /128 (IPv6) range. IPv6 is written in full: 2001:db8::/32 is stored as 2001:db8:0:0:0:0:0:0/32. Duplicates are removed (the order you sent is kept).
SizeAt most 50 entries per environment. The list may be empty (then nothing can call).
The all-addresses range/0 (for example 0.0.0.0/0) is refused for PROD. It is accepted for DEV, where it means "any server"; avoid it unless you are testing from changing addresses.
Replace, not addThe PUT replaces the whole list. To add one address, send the current list plus the new one.
FamiliesAn IPv4 range never matches an IPv6 caller and the reverse.
Which address countsThe address the gateway sees the partner's request coming from (the gateway forwards it as X-Client-IP, trusted only with the gateway secret). If Adera sits behind a load balancer or CDN, give the platform team the address the gateway really sees. On the dev stack, calls from the host machine arrive as the Docker bridge address (172.18.0.1 in the capture below).
Order of checksFor a partner call the checks run in this order: timestamp, key exists, key usable, signature, key's environment, app usable (status), then the address. So a partner who gets ip_not_allowed has a valid key and signature; only the address is wrong.

Purpose. Sets the list of allowed server addresses of one app for one environment. When to use it. During onboarding (give the partner's production server IPs), when the partner moves hosting, or to remove an address that should no longer call.

Path and body

NameWhereTypeRequiredMeaning

curl -sS -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/environments/PROD" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
  "allowedCidrs": [
    "203.0.113.10",
    "198.51.100.0/24",
    "2001:db8::/32",
    "203.0.113.10/32"
  ]
}'

What the partner sees

Before an address is registered, and after the dev stack's address was added (the call was made from this machine; the first refusal is the first call, the second answer comes after the 15-second delay described below):

before:
HTTP 403  {"error": "ip_not_allowed"}

PUT DEV allowedCidrs ["172.18.0.1"] ->
HTTP 200  {"environment": "DEV", "allowedCidrs": ["172.18.0.1/32"]}

after (~15 s later):
HTTP 202  {"notificationId": "dda14451-2d22-43a9-8cf4-2c62b3afb1c2", "externalId": "doc-order-1001", "status": "QUEUED", "channel": "IN_APP", "environment": "DEV", "createdAt": "2026-10-26T11:05:53.746186Z", "expiresAt": "2026-10-27T11:05:53.745969Z"}

Allowing any address in DEV (accepted; not allowed for PROD):

HTTP 200  {"environment": "DEV", "allowedCidrs": ["0.0.0.0/0"]}

Effects, audit

  • Audit: environment.set, meta {"environment": "PROD", "allowedCidrs": [the stored list]}.
  • The notification service remembers an app's addresses for about 15 seconds, so a new address may need up to 15 seconds to start working, and a removed one up to 15 seconds to stop. Tell the partner to retry after a quarter of a minute rather than assuming the change failed.
  • The other environment's list is unaffected. Reversible: send the previous list.

Scenario

A partner moves its servers. You add the new address next to the old one (send both), wait for the partner to confirm traffic from the new host, then send the list with only the new address. Never send an empty list to the active environment unless you want to cut the partner off.

Reading the lists

The lists are part of GET /admin/api/v1/apps/{appId} (environments: one row per environment with allowedCidrs). There is no separate GET.

[
  {
    "environment": "DEV",
    "allowedCidrs": []
  },
  {
    "environment": "PROD",
    "allowedCidrs": []
  }
]

That is a fresh app: both lists empty.
