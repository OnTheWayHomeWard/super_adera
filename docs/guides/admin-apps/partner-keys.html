Partner keys

Register a partner's public key, generate a sandbox pair, list and revoke keys.

Overview

A partner proves who it is by signing every request to the partner API with a private key that only the partner holds. Adera stores the matching public key. A registered key has an id (ak_dev_... or ak_prod_...), belongs to one app and one environment, and can expire or be revoked.

Why this existsWith a public key on our side there is no shared secret that can leak from Adera's database: stealing our data does not let anyone impersonate a partner. And because the partner signs the whole request (method, path, time and a hash of the body), a captured request cannot be changed or replayed later.

Rules

RuleDetails
AlgorithmRSA, signatures RS256 (RSASSA-PKCS1-v1_5 with SHA-256). Keys shorter than 2048 bits are refused. Other key types (EC, Ed25519) are not accepted.
FormatA PEM public key that starts with -----BEGIN PUBLIC KEY----- (the format openssl rsa -pubout produces). The older BEGIN RSA PUBLIC KEY format and certificates are refused. A PEM that contains PRIVATE KEY is refused with a message telling the partner to keep it.
Key idGenerated by Adera: ak_ + environment (dev or prod) + 24 random hex characters. The partner sends it in the header X-Adera-Key-Id. It is an identifier, not a secret. (Keys that existed before the DEV/PROD rename may still be called ak_test_... or ak_live_....)
FingerprintSHA-256 of the DER form of the public key, as 64 hex characters. Use it to confirm with the partner that the key you registered is the key they hold.
EnvironmentEvery key belongs to DEV or PROD. Only keys of the deployment's environment work there (403 wrong_environment otherwise). Up to 5 active keys per app and environment (409 too_many_active_keys); an expired key that was not revoked still counts.
StatusACTIVE or REVOKED. A key is usable only if it is ACTIVE and not past its expiresAt. An expired key still shows as ACTIVE in the list; compare expiresAt with the clock.
ImmutableA key cannot be edited (label and expiry too) or un-revoked. To change anything, register a new key and revoke the old one.
SecretsAdera never stores a private key. The only exception is the one-time response of generate, which is not stored either.

How a partner makes a key pair

# private key: stays on the partner's server, never sent to Adera
openssl genrsa -out partner-private.pem 3072
chmod 600 partner-private.pem

# public key: this is what is registered
openssl rsa -in partner-private.pem -pubout -out partner-public.pem
cat partner-public.pem

# fingerprint, to compare with the one Adera shows after registration
openssl rsa -pubin -in partner-public.pem -outform DER | sha256sum

2048 bits is the minimum; 3072 is a good default. The partner e-mails or uploads only partner-public.pem.

The three z_key_... examples above are, in order: a key in the old BEGIN RSA PUBLIC KEY format (made with openssl rsa -RSAPublicKey_out), an elliptic-curve key, and a 1024-bit RSA key.

Effects, audit

  • The key works for the partner within about 15 seconds. Audit: key.register, target type partner_key, target id the key id, meta {"appId", "environment", "fingerprint"}.
  • To find the audit events of an app's keys, filter the audit log by appId=<app id> (every entry now records its app; the App's Audit tab uses it too), or by targetType=partner_key / the key id.
  • Reversible: revoke the key.

Scenario

A partner sends partner-public.pem. You register it for PROD with an expiry one year out and a label naming the partner's system, read the fingerprint back to them, and then wait for their first signed call.

What the partner sees

Calls signed with a revoked or expired key are refused. The notification service remembers a key for about 15 seconds (an accepted trade-off, not a bug), so the refusal may start up to 15 seconds after the revoke (the backoffice says "immediately"; in practice it is within a quarter of a minute):

revoked key, 16 s after the revoke:
HTTP 401  {"error": "key_revoked_or_expired"}

expired key:
HTTP 401  {"error": "key_revoked_or_expired"}

Effects, audit

  • Audit: key.revoke (target type partner_key, target id the key id, meta {"appId"}). Not reversible: register a new key instead.
  • Messages the partner already had accepted are not affected; only new calls are refused.

Checking that a key works (what the partner does)

The signing rule, in short (the partner guide has the full description): the partner sends three headers, X-Adera-Key-Id, X-Adera-Timestamp (Unix seconds, at most 5 minutes off) and X-Adera-Signature = base64 of the RS256 signature over this text, with newlines between the lines:

ADERA-SIG-1
<timestamp>
<METHOD>
<path and query, e.g. /v1/notifications>
<base64 of the SHA-256 of the request body>

A partner (or you, holding the partner's private key) can test a freshly registered key with plain shell tools, here a harmless status lookup that answers 404 not_found when the signature, key, environment and address are all accepted:

KEY_ID=ak_dev_...            # from the register response
TS=$(date +%s)
HASH=$(printf '' | openssl dgst -sha256 -binary | base64)          # empty body for a GET
SIG=$(printf 'ADERA-SIG-1\n%s\n%s\n%s\n%s' "$TS" GET /v1/notifications/does-not-exist "$HASH" |
      openssl dgst -sha256 -sign partner-private.pem | base64 -w0)
curl -sS "$GATEWAY/v1/notifications/does-not-exist" \
  -H "X-Adera-Key-Id: $KEY_ID" -H "X-Adera-Timestamp: $TS" -H "X-Adera-Signature: $SIG"

Run as written against the dev stack, with a freshly registered key, this printed (the 404 is the success signal: the signature, key, environment and address were all accepted, and only the notification does not exist). The fingerprint the API returned was also identical to openssl rsa -pubin -in partner-public.pem -outform DER | sha256sum:

{"error":"not_found"}
HTTP 404

Partner-side refusals, and which admin action fixes them, are listed on the Errors page.
