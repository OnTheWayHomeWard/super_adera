Admin: managing mini apps

Operate every mini app from the API, with the backoffice equivalent named for each action.

This guide is for the owner and for Adera's admins and developers who run mini apps (the partner services listed inside the Adera super app). It documents every staff action on a mini app, API first: the calls under /admin/api/v1, and, for each one, the screen or tab of the backoffice (the staff dashboard) that does the same thing. Only staff can create or configure mini apps; partners and users never call these endpoints.

Start here

  • New to the staff API? Read Roles and access first (how to get a token, what each role may do).
  • Setting up a partner? Follow the first runbook in Runbooks: it uses every other page in order.
  • Something is on fire? Runbooks has "pause an app in an incident" and "kill an app" at the top of its list.
  • A partner says a message did not arrive? Why did it not arrive?

Base URL (examples)$GATEWAY = the API gateway, for example http://127.0.0.1:9080 on the dev stack. Every path in this guide is called through it, exactly as written.
Backoffice$GATEWAY/backoffice/, served from the same origin as the API. Every API action below names the screen or tab that does the same thing.

RolesVIEWER (read), ADMIN (change things), SUPER_ADMIN (also staff management and reviving a killed app).

EnvironmentThe deployment runs in exactly one environment, ADERA_ENV=dev or prod. See Environments and IPs.

Conventions

Error shape

Every error is JSON with an error code (lowercase, with underscores). Validation errors add a fields object with one message per bad field. Some conflicts add details in fields too (for example which items are missing). The code is stable; the message text can change.

HTTP 400  {
    "error": "validation_failed",
    "fields": {
      "bogus": "unknown field",
      "slug": "required: 2-40 chars, lowercase letters, digits and dashes (e.g. adera-fix)",
      "name": "required (at least an English name)",
      "brandColor": "must look like #0F9D58",
      "markets": "must be a non-empty list of ET, US",
      "website": "must be an https:// URL",
      "priority": "must be a whole number from 0 to 100000 (lower is shown first)"
    }
  }
StatusMeaning in this API
400validation_failed (read fields), or invalid_request (the body is not JSON, or a path id is not a UUID).
401unauthorized: no token, or a token the identity service does not accept.
403mfa_required (aal1 session), not_staff (valid session but not an active staff member), insufficient_role, only_super_admin_can_revive_killed_app.
404not_found: the app, key, template, notification, review or report does not exist.
409A rule of the current state, for example slug_taken, not_ready_for_live, too_many_active_keys, template_code_taken.
413file_too_large: the logo upload is over the limit.
429The gateway rate limit (see above).

The complete list with what to do about each is on the Errors page.

Pagination and totals

  • GET /admin/api/v1/audit and GET /admin/api/v1/notification/notifications: limit (default 50, at most 200) and offset (default 0).
  • GET /admin/api/v1/reviews, /reports and /apps/{id}/reviews: page (0-based, default 0) and size (default 50, at most 100).
  • The lists that can be long (/audit, /reviews, /reports, /notification/notifications) return the number of matching rows in the response header X-Total-Count; the body is a plain JSON array, newest first.
  • GET /admin/api/v1/apps is not paged: without a status filter it returns at most 200 apps, ordered by priority then slug.

Ids, timestamps, languages

  • Apps, templates, notifications, reviews, reports and staff are identified by UUIDs. An app also has a permanent slug (the admin API uses the UUID in paths; the user-facing catalog accepts either).
  • Partner key ids look like ak_dev_c8fefc24c0f9748b9e8f81c2 (ak_prod_... for PROD). They are identifiers, not secrets.
  • Timestamps are ISO-8601 in UTC (2026-10-26T11:05:20.456350281Z); request fields that take a time accept the same format, e.g. 2027-01-01T00:00:00Z.
  • Languages: en (English, required wherever text is required), am (Amharic), om (Afaan Oromoo). Texts are objects like {"en": "...", "am": "..."}.
  • Money amounts are in minor units (cents or santim): 1000 means 10.00.

Glossary

TermMeaning
Super appThe Adera app that end users install.
Mini appA partner service listed inside the super app. In the API it is an app.
PartnerThe company behind a mini app. Its servers call Adera's partner API to send notifications.
SlugThe short permanent name of an app (adera-fix). Used in links; cannot be changed.
StatusDRAFT, LIVE, PAUSED or KILLED: whether users can see the app and whether partners may call.
CapabilityOne kind of data or service an app may ask for (user.basic, notify.sms, ...). Admin grants, denies or suspends it.
EnvironmentDEV or PROD. A deployment is exactly one of them (ADERA_ENV); keys and allowed addresses are stored per environment.
Allowed server addressesThe IPs or CIDR ranges a partner's servers may call from (per app, per environment).
Partner keyAn RSA public key registered for an app. The partner signs every request with the private half, which only they hold.
TemplateA message the partner is allowed to send (words in en/am/om plus declared values). Partners cannot send free text.
ChannelHow a notification reaches a user: SMS, EMAIL or IN_APP (inbox plus push).
Notification limitsPer app and channel quotas: per user per day, per day, distinct users per day, lifetime total.
aal1 / aal2Session assurance levels: aal1 = emailed code only, aal2 = emailed code plus authenticator app. The admin API needs aal2.
Audit eventA row in the audit log written for each change: who, role, action, target, details, IP, time.
BackofficeThe staff web dashboard. It calls the same API.
