Notification limits

Per-channel quotas for a mini app: the four limits, null versus 0, the defaults and how they act.

Overview

Each app has notification limits per channel (SMS, EMAIL, IN_APP). They cap how many messages a partner can send, how many different users it can reach, and how often one user can be messaged. The notification service checks them atomically on every send; a message over a limit is refused with 429 quota_exceeded and nothing is stored or billed.

Why this existsSMS costs money and every channel can be abused (spamming users, a bug that loops). Limits make the worst case bounded and predictable: conservative defaults when a channel is granted, and an admin who raises them when the partner has shown it needs more.

The four limits

FieldCountsWindowTypical use
maxPerUserPerDayMessages to one user from this app on this channelPer UTC dayStops one user being flooded.
maxPerDayAll messages from this app on this channelPer UTC dayDaily spend or volume ceiling.
maxDistinctUsersPerDayDifferent users reached from this app on this channelPer UTC dayStops mass-blasting the whole user base.
maxTotalAll messages ever sent on this channel (lifetime)Forever, until you raise itPilot budget: "1000 SMS and then ask us".

null versus 0 (important)

ValueMeaning
null (or the field left out of the request)Unlimited for that limit.
0None allowed: the first message already exceeds the limit. Use it to switch a channel off without touching the capability.
a positive whole numberThat many; the next one is refused.
Watch out

The PUT replaces all four limits at once. A field you leave out becomes null = unlimited, not "unchanged". Always send all four fields, copying the current values from GET /admin/api/v1/apps/{appId} (notificationLimits) and changing only the one you mean to change. In the real example below only maxPerDay was sent for EMAIL: the other three became unlimited.

What is counted

  • Every message the partner API accepts counts once, when it is accepted (status QUEUED), whatever happens to it afterwards (sent, failed, retried). A message that later fails is not given back.
  • Not counted: requests refused for any reason (validation, quota, template problems, unknown user), repeats of the same externalId (they replay the first answer), and messages to users who muted the app (they end SUPPRESSED at the door).
  • The day is the UTC day, so daily limits reset at 00:00 UTC (03:00 in Ethiopia).
  • Usage is counted per app, per environment and per channel; the limit values are the same in DEV and PROD. The lifetime total therefore starts at zero when you go to PROD.
  • Counting is serialised per app and channel, so parallel requests cannot overshoot a limit.

Defaults

There are no defaults at app creation. A channel gets limits when you grant its capability (notify.sms, notify.email, notify.inapp), only if none exist yet:

ChannelmaxPerUserPerDaymaxPerDaymaxDistinctUsersPerDaymaxTotal
SMS31001001000
EMAIL550050010000
IN_APP201000010000null (unlimited)

If a channel has no limits row at all (possible only for an app configured by other means), the notification service applies no limits to it; setting the limits row once fixes that.

Raise the SMS limits of a pilot partner:

curl -sS -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/notification-limits/sms" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
  "maxPerUserPerDay": 5,
  "maxPerDay": 500,
  "maxDistinctUsersPerDay": 300,
  "maxTotal": 5000
}'

Reading the current limits and usage

The current rows are the notificationLimits part of GET /admin/api/v1/apps/{appId}. How much of them is used right now is GET /admin/api/v1/notification/usage (Notification log and usage); the backoffice Usage tab shows both side by side as meters.

What the partner sees

A real refusal after setting maxPerUserPerDay to 1 for IN_APP and sending to the same test user twice, and after setting maxPerDay to 0:

second message to the same user today:
HTTP 429  {"error": "quota_exceeded", "limit": "max_per_user_per_day", "channel": "IN_APP"}

maxPerDay = 0:
HTTP 429  {"error": "quota_exceeded", "limit": "max_per_day", "channel": "IN_APP"}

limit names the limit that stopped it (max_per_user_per_day, max_per_day, max_distinct_users_per_day or max_total) and channel the channel. The partner should not retry immediately: a daily limit clears at 00:00 UTC, a lifetime limit needs you to raise it.

Effects, audit

  • Audit: limit.set, meta {"channel": "SMS", "maxPerUserPerDay": 2, "maxPerDay": null, "maxDistinctUsersPerDay": null, "maxTotal": 500} (real fields, the new values; null = unlimited. Entries written before 2026-10-26 had one text instead; a migration converted them. The old values are not recorded, so note them before you change).
  • The notification service picks up the change within about 15 seconds.
  • Lowering a limit below today's usage simply blocks further sends today; nothing already accepted is removed.

Scenario

A pilot partner used 950 of its 1000 lifetime SMS and asks to continue. You read the usage, agree on 20,000, and send the PUT with all four fields (copying the other three), changing maxTotal. You check the next day's usage meter.

Not built yet

  • Different limits for DEV and PROD, or per template category (the backoffice hint "PROMOTIONAL may be limited more strictly later" is a plan, not a feature).
  • Alerts when an app reaches a limit (use the usage view).
  • Per-limit "change one field" calls: the PUT always writes all four.
