Runbooks

Seven end-to-end procedures: onboard, pause, kill, rotate a key, raise a quota, add an IP, retire a template.

Before you start

Each runbook gives the API calls (shell, with curl) and names the backoffice screen that does the same. All of them assume a staff token at aal2 (sign-in) with the role named in the runbook. Define these once in your shell:

export GATEWAY=http://127.0.0.1:9080          # your gateway
export TOKEN=...                              # aal2 staff session token (a secret: never paste it into chat or a ticket)
api() { curl -sS -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" "$@"; }
export APP_ID=...                             # from: api "$GATEWAY/admin/api/v1/apps" | jq '.[] | {id, slug, status}'
Note

Examples were run on the dev stack with a throwaway app. Two timing facts apply everywhere: the notification service remembers an app's status, addresses, capabilities, limits and keys for about 15 seconds, so a change reaches partner calls within a quarter of a minute; and each deployment keeps its own data, so doing something "in production" means calling the production gateway with a production staff token.

The runbooks: 1. Onboard a new mini app, 2. Pause an app in an incident, 3. Kill an app, 4. Rotate a partner key, 5. Raise a quota, 6. Add an allowed IP, 7. Retire a template.

1. Onboard a new mini app

When: a partner has been approved. Role: ADMIN. You need from the partner: names (English at least) and description, a logo (PNG, ideally square 512 px), a support email, publisher name, entry URL, the public IPs of their servers, a public key (they make it, see Partner keys), the messages they want to send (wording in English and Amharic), the capabilities they need and why. Backoffice: Mini apps > New mini app, then the tabs of the app in this order.

  1. Create the app (starts as DRAFT, invisible to users):
    api -X POST "$GATEWAY/admin/api/v1/apps" -d '{
  "slug": "adera-fix",
  "name": {"en": "Adera Fix", "am": "አደራ ፊክስ"},
  "description": {"en": "Find a trusted technician near you."},
  "brandColor": "#0F9D58", "categories": ["home"], "markets": ["ET"],
  "publisherName": "Fix PLC", "supportEmail": "support@fix.example",
  "entryUrl": "https://app.fix.example/start", "priority": 100
}' | tee /tmp/app.json | jq '{id, slug, status}'
export APP_ID=$(jq -r .id /tmp/app.json)
  2. Upload the logo (a LIVE requirement; call curl directly so it sets the multipart header, see the Logo page): curl -sS -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/logo" -H "Authorization: Bearer $TOKEN" -F file=@logo.png.
  3. Grant capabilities one by one. Sensitive ones need a reason users will read; the notify ones create default limits:
    api -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/capabilities/user.basic" -d '{"state": "GRANTED"}' >/dev/null
api -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/capabilities/location.coarse" \
  -d '{"state": "GRANTED", "reason": {"en": "To show technicians near you.", "am": "በአቅራቢያዎ ያሉ ባለሙያዎችን ለማሳየት።"}}' >/dev/null
api -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/capabilities/notify.inapp" -d '{"state": "GRANTED"}' >/dev/null
  4. Check the notification limits that appeared and adjust if the agreement says otherwise (see Notification limits): api "$GATEWAY/admin/api/v1/apps/$APP_ID" | jq .notificationLimits.
  5. Payment settings, only if the partner takes payments (policy only today): see Payment settings.
  6. Register the partner's DEV public key and the DEV addresses (they can start building at once; DEV works for every status except KILLED):
    jq -Rs '{environment: "DEV", publicKeyPem: ., label: "fix backend (dev)", expiresAt: "2027-06-30T00:00:00Z"}' partner-dev-public.pem |
  api -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/keys" -d @- | jq '{keyId, fingerprint, status}'
api -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/environments/DEV" -d '{"allowedCidrs": ["203.0.113.10"]}'
  7. Create the templates with the agreed wording and give the partner the returned ids (see Templates).
  8. Partner tests in DEV with the synthetic users u_p_test_* (nothing real is sent; u_p_test_muted and u_p_test_unreachable exercise the other outcomes). Watch their messages in the log: api "$GATEWAY/admin/api/v1/notification/notifications?appId=$APP_ID&limit=10". If they get ip_not_allowed, see runbook 6.
  9. Production: against the production deployment repeat steps 1 to 5 and 7 as they are, and in step 6 register the partner's PROD key (the partner makes a separate production key pair; use register, not generate) and the PROD addresses. Review the limits (step 4) again for production.
  10. Check readiness: api "$GATEWAY/admin/api/v1/dashboard" | jq .draftApps shows missingForLive (it must be empty), then publish: api -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/status" -d '{"status":"LIVE"}'. A 409 not_ready_for_live tells you what is missing.
  11. Verify as a user: GET /api/v1/apps/adera-fix with an ordinary user session shows the app with its permissions and reasons; and the audit log has the whole story: api "$GATEWAY/admin/api/v1/audit?target=$APP_ID&limit=50".

Undo: set the status back to DRAFT (hidden from users); there is no delete. Keys can be revoked and templates deactivated.

2. Pause an app in an incident

When: a partner's backend misbehaves (wrong or duplicate messages, a security scare), the partner asks, or users report a broken app. Role: ADMIN. Backoffice: the app's page header, Change to: PAUSED. Pausing is reversible by any ADMIN; if it is serious use runbook 3.

  1. Pause: api -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/status" -d '{"status":"PAUSED"}' | jq .status. The app disappears from the user catalog at once; partner calls to the production deployment are refused (403 app_paused) within about 15 seconds. (In the DEV deployment PAUSED still allows calls, so the partner's test traffic continues.)
  2. Know what is already queued. Pausing does not cancel messages already accepted, and there is no way to cancel them from the API. Normally the queue drains within seconds; messages in RETRYING keep retrying until they expire (24 hours by default). Check: api "$GATEWAY/admin/api/v1/notification/notifications?appId=$APP_ID&status=queued" and ...status=retrying. If the wording is the problem, edit the template text to something neutral (delivery uses the template's current words, so the queued messages then say the new text); deactivating the template only stops new sends (runbook 7).
  3. Tell the partner (their contact is the app's supportEmail) what you saw and when you paused.
  4. Investigate: the notification log and detail (Notification log), the app's audit trail, reports (GET /admin/api/v1/reports?appId=$APP_ID&status=open).
  5. Resume once the partner confirms the fix: status: LIVE (needs the logo and support email, still there unless someone removed them). Watch the log for a few minutes: counts of FAILED and the volume per hour (GET .../notification/stats?appId=$APP_ID).

Check: a call with the partner's key now returns app_paused on production; the catalog no longer lists the app. Undo: step 5.

3. Kill an app

When: abuse, fraud, a compromised key you cannot rotate quickly, the contract ended. Role: ADMIN to kill; only a SUPER_ADMIN can revive. Backoffice: Change to: KILLED (confirmation says "This stops all of the partner's API calls immediately").

  1. Kill: api -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/status" -d '{"status":"KILLED"}'. All partner calls, in DEV and PROD, are refused (403 app_killed) within about 15 seconds; the app leaves the catalog.
  2. Cut access fully (defence in depth, and so a later revive does not silently restore everything): revoke every key (GET .../keys, then DELETE .../keys/{keyId} for each ACTIVE one), suspend the notify capabilities (PUT .../capabilities/notify.sms with {"state":"SUSPENDED"}, and email, in-app), and deactivate the templates (this stops new sends; messages already accepted are still delivered, and cannot be cancelled from the API).
  3. Moderate what users saw: hide abusive reviews (PATCH /admin/api/v1/reviews/{id} with HIDDEN) and close the reports (PATCH /admin/api/v1/reports/{id} with REVIEWED).
  4. Record why in your incident ticket (the audit log keeps who and when, not why); tell the partner and, if users were affected, support.

Reviving (SUPER_ADMIN): only after the reason is gone. Revive to PAUSED first: api -X POST ... -d '{"status":"PAUSED"}' with a SUPER_ADMIN token (an ADMIN gets 403 only_super_admin_can_revive_killed_app). Then register a new key (the old ones stay revoked), re-grant only the capabilities that are justified, re-activate the needed templates, check addresses, and finally set LIVE.

4. Rotate a partner key

When: on a schedule (before a key's expiresAt), when a person who knew the private key leaves, or after a suspected leak. Role: ADMIN. Backoffice: App > Partner keys. The method is overlap: the new key works next to the old one, so there is no outage. The platform does not show when a key was last used, so you confirm the switch with the partner.

  1. The partner generates a new key pair (how) and sends the new public key only.
  2. Register it with an expiry: jq -Rs '{environment:"PROD", publicKeyPem:., label:"fix backend 2027", expiresAt:"2028-06-30T00:00:00Z"}' new-public.pem | api -X POST "$GATEWAY/admin/api/v1/apps/$APP_ID/keys" -d @-. Read the fingerprint back to the partner and note the new keyId. There can be at most 5 active keys per environment; revoke old unused ones first if you hit too_many_active_keys.
  3. The partner deploys the new private key and the new key id (X-Adera-Key-Id) and sends a test request (or a harmless status lookup, see Checking that a key works). Wait at least 15 seconds after registering before the first call.
  4. Confirm with the partner that all their servers now use the new key and look at the log for fresh SENT messages after the switch.
  5. Revoke the old key: api -X DELETE "$GATEWAY/admin/api/v1/apps/$APP_ID/keys/$OLD_KEY_ID". Within about 15 seconds calls signed with it get 401 key_revoked_or_expired. Revoking is permanent.
  6. Verify: api "$GATEWAY/admin/api/v1/apps/$APP_ID/keys" shows the old key REVOKED and the new one ACTIVE; audit has key.register and key.revoke (filter targetType=partner_key).

Emergency (leaked key): reverse the order: revoke first (stops the attacker within about 15 seconds, and the partner too), then register the new key and let the partner switch. Expect failing partner calls until they do.

5. Raise a quota

When: a partner reports 429 quota_exceeded and the business agrees they may send more. Role: ADMIN. Backoffice: App > Notification limits (Edit) and App > Usage.

  1. Find which limit it was: ask for the error body ({"error":"quota_exceeded","limit":"max_per_day","channel":"SMS"}); the limit field names it.
  2. Read the usage and the current limits: api "$GATEWAY/admin/api/v1/notification/usage?appId=$APP_ID" and api "$GATEWAY/admin/api/v1/apps/$APP_ID" | jq .notificationLimits. Check that the traffic is legitimate (the log, and whether one user is getting many messages).
  3. Decide the new numbers. Fields you leave out keep their value (the PUT merges since 2026-10-26), so you may send only what changes, for example {"maxTotal": 50000}; sending all four still works: 
    api -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/notification-limits/SMS" \
  -d '{"maxPerUserPerDay": 5, "maxPerDay": 2000, "maxDistinctUsersPerDay": 1500, "maxTotal": 50000}'
    (null means unlimited, a missing field means unchanged; 0 means none.)
  4. Verify: the response echoes the saved row; the app detail shows it; the partner retries after about 15 seconds. A daily limit that was already reached today is now measured against the new number, so sending can resume at once.
  5. Record the old and new values in your ticket (the audit event stores only the new ones) and, for SMS, tell finance that the monthly ceiling just moved.

Undo: PUT the previous values.

6. Add an allowed IP

When: the partner added a server or changed hosting and gets 403 ip_not_allowed. Role: ADMIN. Backoffice: App > Environments and IPs.

  1. Confirm the cause: ip_not_allowed is only returned after the key and signature were accepted, so the key is fine. Ask the partner for the public address their server calls from (the address Adera's gateway sees, not an internal one).
  2. Read the current list (the PUT replaces it): api "$GATEWAY/admin/api/v1/apps/$APP_ID" | jq '.environments'.
  3. Write the list with the new address added: 
    api -X PUT "$GATEWAY/admin/api/v1/apps/$APP_ID/environments/PROD" \
  -d '{"allowedCidrs": ["203.0.113.10/32", "198.51.100.77"]}'
  4. The answer shows the stored list (a bare address becomes /32). Wait about 15 seconds, then the partner retries; a call that previously failed now gets 202. Do not conclude that the change failed before that.
  5. Later, when the old server is gone, PUT the list again without its address. Use the right environment: on the production deployment the PROD list is the active one; the DEV list is stored but unused there.

Undo: PUT the previous list. Never use /0 ranges for PROD (refused anyway).

7. Retire a template

When: a campaign ended, the wording is wrong or outdated, a template is being replaced. Role: ADMIN. Backoffice: App > Templates > Deactivate (or Edit to set Expires). There is no delete.

  1. Find it: api "$GATEWAY/admin/api/v1/notification/templates?appId=$APP_ID" | jq '.[] | {id, code, active, usableNow, version}'.
  2. If it is being replaced, create the new template first (new code), give its id to the partner, and let them switch before you retire the old one.
  3. Switch it off (reversible): api -X PATCH "$GATEWAY/admin/api/v1/notification/templates/$TEMPLATE_ID" -d '{"active": false}'. For a planned end instead, set expiresAt to the end date; to end it right now you can also set expiresAt to a past time.
  4. Check: the response shows usableNow: false and unusableReason: template_inactive (or template_expired). Partner sends with that template id get 422 template_inactive from then on. Messages already accepted but not yet delivered are not cancelled; they are delivered using the template's current words (see Templates).
  5. Keep a record: template changes are not in the audit log, so write down who retired what and when.

Undo: {"active": true} (and clear or move expiresAt with null or a future date).
