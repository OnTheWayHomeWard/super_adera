Create, edit and list apps

Create an app, read it, change it, and find apps by status.

Overview

An app record is who the mini app is (names, description, logo, colours, publisher, contact), where it lives (entry URL, allowed origins) and how it is listed (categories, markets, priority). Everything else about an app (status, capabilities, limits, addresses, keys, templates, payment settings) has its own page. This page covers creating an app, reading it, editing it, and the two small helpers that summarise the whole catalog.

Why this existsThe catalog entry is what users see before they open a mini app, so the data has to be complete and trustworthy: a real support contact, a logo, the publisher's name. Creating an app is deliberately cheap (a new app starts as DRAFT and is invisible to users); it becomes visible only when an admin sets it LIVE.

Fields of an app

The same fields are used to create an app (POST) and to change one (PATCH). On create, slug and name are required; everything else is optional. Unknown fields are rejected (unknown field), so a typo never silently does nothing.

FieldTypeRequiredRules and defaultWhy it exists
slugstringcreate only2 to 40 characters: lowercase letters, digits and dashes; must start and end with a letter or digit (adera-fix is fine, -fix, Fix and fix_it are not). Permanent: changing it later is refused. Must be unique (409 slug_taken).Short stable name used in links and in the user catalog (/api/v1/apps/adera-fix).
nameobject of stringscreateKeys en, am, om. en is required. Each text at most 100 characters; empty texts are dropped.The title users see, in their language (English is the fallback).
descriptionobject of stringsnoSame keys. Each text at most 1000 characters. Default: empty object.The short description in the catalog.
brandColorstring or nullno#RRGGBB hex (stored upper-case). null clears it.Accent colour for the app's tile and header.
categorieslist of stringsnoUp to 10 items, each lowercase, starts with a letter, 2 to 31 characters of letters, digits, _, - (e.g. home, travel). Default: empty.Lets the client group and filter the catalog.
marketslist of stringsnoNon-empty list of ET, US (case is normalised, duplicates removed). Default: ["ET"].Which markets the app is offered in; the user catalog can be filtered by ?market=.
publisherNamestring or nullnoAt most 150 characters.Who runs the app, as shown to users.
publisherLegalNamestring or nullnoAt most 200 characters.The registered company name, for the details page.
supportEmailstring or nullnoA valid email address (trimmed, lower-cased). Required before the app can go LIVE.Where users and staff reach the publisher.
supportPhonestring or nullnoAt most 30 characters, free text (not validated as a phone number).Optional phone contact.
websitestring or nullnohttps:// URL without spaces. See the known issue below about very long URLs.The publisher's website.
entryUrlstring or nullnohttps:// URL, or http://localhost... / http://127.0.0.1... for development. At most 500 characters.The page the super app opens when a user taps the mini app.
allowedOriginslist of stringsnoUp to 10 origins like https://app.example.com: scheme, host and optional port, no path and no trailing slash. Default: empty.Origins that may talk to the super app's bridge. Stored and shown to staff; nothing enforces it yet (see Not built yet).
priorityintegernoWhole number 0 to 100000. Lower is listed first. Default 100.Order in the catalog (then by slug).
extraobjectnoAny JSON object up to 16384 bytes. On update it is merged key by key (see PATCH rules).Free-form settings and notes that do not deserve a column (contact person, tier, region).

Read-only fields in every response: id, logoImageId, logoUrl (a temporary signed link, see Logo), status, ratingAvg, ratingCount (computed from visible reviews), createdAt, updatedAt. The contact fields are returned grouped as publisher (name, legalName, supportEmail, supportPhone, website) even though they are written as flat fields.

Note

The backoffice form (Mini apps > New mini app, and App > General) has one input per field with the same limits, and shows the server's messages next to the field when it refuses.

Effects, side effects, audit

  • Creates the app row, and two environment rows (DEV and PROD) with empty address lists.
  • Audit: app.create (target type mini_app, target id the app id, meta {"slug": ...}).
  • Nothing is visible to users and no partner can call yet. Reversible? There is no delete: set the status to KILLED to retire an app; the slug stays taken.

Scenario

A food-delivery company signs the partnership. You create doc-food with its names in English and Amharic, publisher name, support email and entry URL. It stays DRAFT while you add the logo, capabilities, keys and addresses.

How to use the result

  • Use id in every other admin path. The slug is for humans.
  • To find apps that cannot go live yet use GET /admin/api/v1/dashboard (below): it lists drafts with what is missing.
  • There is no text search in the API; the backoffice list filters and sorts in the browser.

Gotchas

  • The admin API takes the UUID only; the slug works in the user catalog, not here.
  • logoUrl is a signed link that expires (default 60 minutes). Do not store it; fetch it again when you need it.
PATCH/admin/api/v1/apps/{appId}Edit an app (partial update)
Who may call
ADMIN or SUPER_ADMIN
Auth
Staff session Bearer token at assurance level aal2 (Authorization: Bearer $TOKEN)
Rate limit
300 requests per minute per client IP at the gateway (HTTP 429 beyond that)
Backoffice
App > General (the edit form)
Audit name
app.update (meta: names of the changed fields)
Reversible
Yes: send the old value again (no history of old values)

Purpose. Changes some fields of an app and leaves the rest alone. When to use it. To fix a typo, add a translation, set the support email so the app can go LIVE, change the order in the catalog, or store a note in extra.

PATCH semantics (read this)

SituationWhat happens
A field is absentUnchanged.
A text field is null (brandColor, publisherName, publisherLegalName, supportEmail, supportPhone, website, entryUrl)Cleared. For publisherName, publisherLegalName and supportPhone an empty or blank string clears it too; for the others (email, URLs, colour) an empty string is a validation error, send null.
name or description is sentThe whole object is replaced, not merged: sending {"am": "..."} for name is refused because en is required; sending a description without om removes the Oromo text. Always send every language you want to keep.
categories, markets, allowedOrigins are sentThe whole list is replaced.
extra is sentMerged key by key: keys you send are set, keys you do not send stay, and a key sent as null is removed. (The backoffice Extra data box does the same.)
slug is sentAlways refused: the slug is permanent and cannot be changed.
An unknown field is sentRefused with unknown field. Nothing is changed when any field is invalid (the update is all or nothing).

Request example

Change the description, move the app up the list and edit extra: set tier, add region, remove contactPerson.

curl -sS -X PATCH "$GATEWAY/admin/api/v1/apps/$APP_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
  "description": {
    "en": "Updated description."
  },
  "priority": 10,
  "extra": {
    "tier": "gold",
    "contactPerson": null,
    "region": "addis"
  }
}'

Clearing a field

curl -sS -X PATCH "$GATEWAY/admin/api/v1/apps/$APP_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
  "supportEmail": null,
  "website": null
}'

This removes the support email and the website; the app can no longer go LIVE until a support email is set again. The response is the full app (publisher.supportEmail and publisher.website are null).

Effects, audit

  • Audit: app.update, meta {"fields": [the names of the fields in the request]} (the values are not logged; compare with the response, or keep your own change ticket).
  • Takes effect immediately for the catalog that users see (if the app is LIVE). There is no versioning of an app record: the audit log tells you who changed which fields and when, not the old values.
  • Changing supportEmail or the logo of a LIVE app does not change its status. Clearing the support email of a LIVE app does not take it offline; the readiness check runs only when the status is set.

Not built yet

  • Deleting an app (use status KILLED).
  • Changing a slug.
  • Free-text search or paging on the app list (it returns at most 200 apps).
  • allowedOrigins is stored and returned to staff but is not used by any service yet; it is meant for the future in-app bridge that opens the mini app's page.
  • A history of old values of an app record.
