Dashboard, system and health

The read-only summary endpoints behind the backoffice home and System pages, and how to read them.

Overview

The backoffice Dashboard home page is built from four read-only calls, each loading (and failing) on its own: /dashboard (apps, reports, reviews, staff counts), /users/stats, /notification/stats, and the newest rows of the notification, report and audit lists. The System screen adds /system and live health probes. All of them are open to every staff role; counts contain no personal data.

Why it exists

To answer in ten seconds: is anything on fire (open reports, failing deliveries, a dead service) and is there work waiting (draft apps that cannot go live yet, reports to review). The numbers are real counts from the databases, never estimates. The figures in the examples were captured on a shared dev stack, so other people's test data is included.

Home counts

GET/admin/api/v1/dashboardCounts of apps, reports, reviews and staff, and draft apps not ready for LIVE
Why
One call for the numbers on the home page: how many mini apps in each status, how much moderation is waiting, how many staff exist, and which draft apps still lack something before they can go LIVE.
Auth
Staff aal2 Bearer, any role
Rate limit
300/min/IP
Backoffice
Dashboard: panels Mini apps by status, Moderation, Apps not ready for LIVE

Request

No parameters.

curl -sS "$GATEWAY/admin/api/v1/dashboard" -H "Authorization: Bearer $TOKEN"

Response 200

HTTP/1.1 200 OK

{
  "apps": {
    "DRAFT": 2,
    "LIVE": 6,
    "PAUSED": 2,
    "KILLED": 1,
    "total": 11
  },
  "reports": {
    "open": 8,
    "total": 12
  },
  "reviews": {
    "total": 16,
    "hidden": 2,
    "last7Days": 16
  },
  "staff": {
    "active": 9,
    "disabled": 1
  },
  "draftApps": [
    {
      "id": "3180f7cd-fdd9-425c-b609-fe00232f9438",
      "slug": "demo-flights",
      "name": {
        "am": "በረራዎች",
        "en": "Flights"
      },
      "missingForLive": []
    }
  ]
}
FieldMeaning
apps.DRAFT / LIVE / PAUSED / KILLEDNumber of mini apps in each status (always all four keys, zero when none). apps.total is their sum.
reports.open, reports.totalReports whose status is OPEN, and all reports ever filed. open is the work queue.
reviews.total, reviews.hidden, reviews.last7DaysAll reviews, those currently HIDDEN by staff, and those created in the last 7 days (by creation time, edits do not count).
staff.active, staff.disabledStaff rows by status. Includes every account in the staff table (also colleagues who never signed in).
draftApps[]Up to 10 DRAFT apps, newest first: id, slug, name (per-language object) and missingForLive. The list holds logo and/or supportEmail, the two things a DRAFT app needs before it can go LIVE; an empty list means the app is ready and only needs the status change.

Errors

Only the sign-in errors (401, 403 mfa_required, 403 not_staff). It never answers insufficient_role.

Use in a client

Show reports.open prominently (red when above zero) and link it to the reports list with status=OPEN. The numbers are computed on each call; poll no faster than every 30 seconds.

User and notification statistics

GET/admin/api/v1/users/statsRegistered-user counts by status
Why
Know how many customers exist, how many are suspended or deleted, and the sign-up pace.
Served by
user-service (route admin-users)
Auth
Staff aal2 Bearer, any role
Backoffice
Dashboard: panel Users

Request

curl -sS "$GATEWAY/admin/api/v1/users/stats" -H "Authorization: Bearer $TOKEN"

Response 200

HTTP/1.1 200 OK

{
  "total": 16,
  "active": 14,
  "suspended": 1,
  "deleted": 1,
  "createdLast7Days": 16
}

createdLast7Days counts profiles created in the last 7 days regardless of their current status. Note that /users/stats is matched before the /users/{id} pattern, so the word stats is never treated as a user id.

Errors

Sign-in errors only.

GET/admin/api/v1/notification/statsDelivery counts across all apps (or one)
Why
Spot delivery trouble: a rising share of FAILED, UNREACHABLE or EXPIRED in the last 24 hours means a provider or a partner problem.
Served by
notification-service (route admin-notification)
Auth
Staff aal2 Bearer, any role
Backoffice
Dashboard panel Notifications; the Notifications screen header

Request

QueryTypeRequiredMeaning
appIduuidnoRestrict the counts to one mini app. A value that is not a uuid answers 400 invalid_request-style errors (see Errors).
curl -sS "$GATEWAY/admin/api/v1/notification/stats" -H "Authorization: Bearer $TOKEN"

Response 200

HTTP/1.1 200 OK

{
  "total": 55,
  "last24h": {
    "total": 55,
    "byStatus": {
      "EXPIRED": 1,
      "SENT": 45,
      "SUPPRESSED": 7,
      "UNREACHABLE": 2
    }
  },
  "byStatus": {
    "EXPIRED": 1,
    "SENT": 45,
    "SUPPRESSED": 7,
    "UNREACHABLE": 2
  },
  "byChannel": {
    "EMAIL": 8,
    "IN_APP": 18,
    "SMS": 29
  }
}

total and byStatus/byChannel cover all time; last24h covers the last 24 hours (total is the sum of its byStatus). Only statuses that occur appear as keys. The meaning of each status is in the notification visibility page.

Errors

Sign-in errors; a malformed appId is rejected before any query (see the notification visibility page for the exact body).

System: environment, health and links

GET/admin/api/v1/systemWhich environment this deployment is (DEV or PROD)
Why
A deployment runs in exactly one environment (setting ADERA_ENV). Keys and allowed server addresses of the other environment can be stored but are not used here. The backoffice shows a DEV or PROD tag so nobody mistakes a test stack for production.
Auth
Staff aal2 Bearer, any role
Backoffice
System page, first paragraph; environment tag in the header

Request

curl -sS "$GATEWAY/admin/api/v1/system" -H "Authorization: Bearer $TOKEN"

Response 200

HTTP/1.1 200 OK

{
  "environment": "DEV"
}

Errors

Sign-in errors only.

Not built yet

There is no endpoint that returns build version or uptime. Use the health probes below, Grafana and Prometheus.

Health probes

GET/backoffice/api/health/{service}Is this service up? (the System page's table)
Why
The services' own health endpoints are not reachable from outside the Docker network. The backoffice web server proxies a fixed list of probes so staff can check them from the System page.
Auth
Staff aal2 Bearer, any role (same forward-auth as the admin API; the path is not under /admin/api/v1)
Rate limit
120/min/IP
Backoffice
System: Service health (refreshes every 30 seconds, button Check now)

Request

{service} is one of: registry, user, notification, kratos, prometheus, grafana, loki, mailpit, infisical. GET only; any other name answers a plain nginx 404.

curl -sS "$GATEWAY/backoffice/api/health/registry" -H "Authorization: Bearer $TOKEN"

Response 200 (examples)

HTTP/1.1 200 OK

{
  "groups": [
    "liveness",
    "readiness"
  ],
  "status": "UP"
}
HTTP/1.1 200 OK

{
  "status": "ok"
}
HTTP/1.1 200 OK

{
  "database": "ok",
  "version": "13.0.2",
  "commit": "3fcdbc5a"
}

The body is whatever the service answers, so its shape differs per service (Prometheus and Loki answer plain text). The status code is passed through: anything other than 200 means the service is down or not ready. The page marks a service UP when it answered 200 and, if there is a status field, it reads UP, ok or ready.

Errors

401 unauthorized without a staff token (verified), 404 for an unknown name (verified, an HTML page from nginx), and a gateway or proxy error status when the service itself is down (the page shows DOWN). Probes time out after 3 seconds.

serviceWhat it isChecks

The gateway itself is up if the call reached this point.

Tool links on the System page

The System page lists links to the tools around the platform: Grafana (dashboards), Prometheus (metrics), Mailpit (dev inbox), Infisical (secrets), RabbitMQ management and the RustFS console. They are not an API: the backoffice reads them from its static config.json (written when its container starts from BACKOFFICE_* settings); a link that is not configured is not shown. In the dev stack they point to 127.0.0.1 ports (Grafana 3001, Prometheus 9090, Mailpit 8025, Infisical 8080, RabbitMQ 15672, RustFS console 9001). The same page also lists the Capability catalog (GET /capabilities), a glossary of staff error codes and of partner-facing error codes.

How to read the home page

You seeIt meansDo this
Open reports above zeroUsers reported a mini app and nobody has handled it.Work through them: see Moderation: reports.
Hidden reviews growingStaff have hidden many reviews.Check the audit log for who and why (review.moderate).
Apps not ready for LIVE lists logo or supportEmailA draft app cannot go LIVE yet.Ask the app owner or fill the missing field in the app detail.
Suspended users above zeroSomeone was suspended and not reactivated.Open Users with status SUSPENDED and confirm each is intentional.
Notifications: many UNREACHABLEPartners are sending to deleted, suspended or unknown users, or to users without a phone or email.Open the Notifications log and read the reasons.
Notifications: FAILED or EXPIRED in the last 24 hoursA provider problem, or an unreachable provider in DEV (for example Mailpit down).Check Service health on the System page, then the delivery attempts of one notification.
A service shows DOWNIts health probe did not answer 200.Look at its logs in Loki or docker compose logs <service>.

Errors

These endpoints have no business errors of their own. Sign-in errors are described on the roles page; see also the error codes page.
