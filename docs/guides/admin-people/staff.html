Staff management

SUPER_ADMIN only: list, add, change role, deactivate and reactivate staff, how a new colleague signs in for the first time, the safety rules, and the bootstrap super admin.

Overview

Staff are the people who can sign in to the admin API and the backoffice. Only a SUPER_ADMIN manages them: list, add by email and role, change role, deactivate and reactivate. In the backoffice this is the screen Staff (menu entry visible to super admins only). The role lives in the person's Kratos identity (metadata_public.role), the staff table in registry-service mirrors it for listing, status and audit; the API keeps both in step.

Why a separate staff list

Customers and staff share one identity system (Kratos). The staff table says who is allowed to act as staff. Being in Kratos is not enough: not_staff is answered to everybody who is not an ACTIVE row with a role.

Add a colleague

POST/admin/api/v1/staffMake an email address a staff member with a role
Why
Give a colleague access. The person need not have signed in before: the identity is created if it does not exist.
Auth
Staff aal2 Bearer, role SUPER_ADMIN
Audit action
staff.create (first time) or staff.update (the address already had a staff row), target type staff
Reversible
Yes: deactivate (see below). The row is never deleted.
Backoffice
Staff > Add staff member (default role VIEWER)

Body

FieldTypeRequiredConstraintsWhy it exists
emailstringyesA valid email address (name@domain.tld, name up to 64 characters); trimmed and lower-cased.Their sign-in address: the emailed code goes here.
rolestringyesVIEWER, ADMIN or SUPER_ADMIN (any case)Their access level.

Unknown extra fields are ignored on this endpoint (unlike PATCH).

Request

curl -sS -X POST "$GATEWAY/admin/api/v1/staff" \
  -H "Authorization: Bearer $SUPER_TOKEN" -H "Content-Type: application/json" \
  -d '{"email":"tempstaff-doc72fbf@adera.local","role":"VIEWER"}'

Response 200

HTTP/1.1 200 OK

  "email": "tempstaff-doc72fbf@adera.local",
  "role": "VIEWER",

  "createdAt": "2026-10-26T10:59:38.576319028Z",

The answer is the staff record (status code 200, not 201).

What happens

  • If Kratos already has an identity with that email (somebody who signed in before, or a customer who registered with that email), the role is granted on that identity. Otherwise a new Kratos identity is created, active, with the role. The staff row is inserted ACTIVE with createdBy = you.
  • Calling it again for an address that is already staff is idempotent: it changes the role to the one you give, sets the status back to ACTIVE and writes staff.update (verified: the second call with ADMIN for an upper-cased address returned the same id with role ADMIN, and the person's next call already had admin rights).
  • Nothing is emailed to the new person. Tell them yourself where to sign in.

Gotcha

Granting a role by email to an address that belongs to an ordinary customer turns that customer's account into a staff account (the same identity). Use a work address that is not a customer.

How the new person signs in the first time

Verified end to end with a throwaway account:

  1. You add the address (above). The person has no authenticator yet.
  2. They request an emailed code and enter it (the sign-in flow on the roles page, or the backoffice Login screen). The session is aal1. Calling the admin API now answers 403 mfa_required.
  3. They enrol an authenticator app on that session (backoffice: the page shows a QR code and the secret). Right after enrolment the same session is aal2 and the admin API works with the role you gave.

Before the authenticator step

{
  "error": "mfa_required"
}

After enrolling

HTTP/1.1 200 OK

{
  "role": "VIEWER",
  "id": "d553ee53-d4b3-4650-93bf-5ed098e244e7"

Their second and later sign-ins ask for the emailed code and then the authenticator code. If they lose the authenticator see the lost-authenticator runbook.

Change role, deactivate, reactivate

PATCH/admin/api/v1/staff/{identityId}Change a staff member's role and/or status
Why
Promote or demote a colleague; cut off a person who left (deactivate) or give access back (reactivate).
Auth
Staff aal2 Bearer, role SUPER_ADMIN
Audit action
staff.update (target type staff, meta {role, status} = the values after the change)
Reversible
Yes
Backoffice
Staff: Change role (disabled until you pick a different role), Deactivate / Reactivate (with confirmation)

Path

identityId: the id from the staff list.

Body

FieldTypeRequiredConstraintsWhy it exists
rolestringnoVIEWER, ADMIN, SUPER_ADMINNew role.
statusstringnoACTIVE or DISABLEDDeactivate or reactivate.

Send either or both; an absent field stays unchanged. Any other field: 400 validation_failed with "<field>": "unknown field". All problems are reported at once.

Effects (all verified)

ActionWhat changes for the colleague
Change roleApplies to their next call, no new sign-in: a viewer promoted to ADMIN could read GET /audit immediately; demoted back, the same token got 403 insufficient_role.
Deactivate (DISABLED)The role is removed from their Kratos identity and all their sessions are revoked: the next call with the old token answers 401 unauthorized. They can still pass the emailed code and the authenticator step (the authenticator stays enrolled), but the admin API then answers 403 not_staff. Their stored role is kept.
ReactivateStatus back to ACTIVE and the stored role is written to Kratos again. They must sign in again (sessions were revoked); a session created while they were disabled works again at once (verified).

Protections

RuleHow it worksVerified
No self-demotionA super admin cannot change their own role away from SUPER_ADMIN or set themselves DISABLED: 409 cannot_demote_self. Setting your own role to SUPER_ADMIN again is accepted (a no-op that still writes an audit row).Live: both refusals and the no-op.
Never zero super adminsRemoving SUPER_ADMIN or activity from the last active super admin is refused with 409 last_super_admin. In practice the self rule already covers this: the caller must itself be an active super admin and cannot target itself, so at least two active super admins exist whenever the rule is evaluated. It remains as a second safety net (for example if the Kratos role and the staff row ever disagree).From code only: it cannot be provoked through the API in a healthy system, and the guide did not touch the bootstrap account.
Roles cannot be edited by usersmetadata_public.role in Kratos can only be written with the Kratos admin API, never through a self-service flow.Design (Kratos identity schema).
Staff are never deletedThere is no delete: DISABLED is the removed state. The audit log keeps their id (the actor email shows as null once the staff row is gone, for example for temporary accounts deleted by test scripts).Code.
Keep two super admins

If the only super admin loses the authenticator, nobody can add staff or recover through the API. Keep at least two, on different phones. The bootstrap recovery below is the fallback.

The bootstrap super admin

A fresh install has nobody who can add staff. At start-up registry-service reads the environment variable BOOTSTRAP_SUPER_ADMIN_EMAIL (in the repository .env, and as a deployment setting in production) and, only when no active super admin exists, makes that address a SUPER_ADMIN (creating the Kratos identity if needed). It retries in the background for about a minute because Kratos may still be starting, and logs Created the first super admin from BOOTSTRAP_SUPER_ADMIN_EMAIL. The person then signs in with that address and enrols an authenticator, exactly as in the first sign-in above. In the staff list this person has bootstrap: true.

How to change it afterwards

  1. Add your real people as SUPER_ADMIN through the Staff screen (or POST /staff) while you can still sign in.
  2. Optionally deactivate the old bootstrap account (it is a normal account).
  3. Change BOOTSTRAP_SUPER_ADMIN_EMAIL to an address you control (or leave it blank to disable bootstrapping) and restart registry-service for it to be read. The new value has no effect while any active super admin exists; it only matters for recovery. The bootstrap tag in the staff list simply follows whichever address the variable holds.
Recovery when every super admin is gone

If all super admins are disabled or lost, set BOOTSTRAP_SUPER_ADMIN_EMAIL to an address you control and restart registry-service. Because no active super admin exists, it grants that address SUPER_ADMIN (and re-activates it if the address already had a disabled staff row). Sign in with that address, enrol the authenticator, then add the others. Do this only on the machine that runs the stack; it is not an API.

Worked scenarios

  • Add a colleague, remove a colleague and recover from a lost authenticator: see the runbooks page for step by step procedures.
  • Promote a viewer to admin for a week: PATCH role: ADMIN; change it back afterwards. Both moves are in the audit log (staff.update).

Not built yet

  • No "reset authenticator" button or API: it needs the Kratos admin API on the server (runbook).
  • No invitation email: nothing is sent when a colleague is added.
  • No delete of staff rows, no list filtering or paging, no last-sign-in time.
  • No change of a staff member's email address.
