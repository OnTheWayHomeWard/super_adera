Registered users

List, search and inspect registered users, see what a viewer is allowed to see, and suspend, reactivate or delete an account with the exact effects on sign-in, partner delivery and reviews.

Overview

Registered users are Adera's customers (the people who sign up in the app with a phone number or email). Staff see them in the backoffice screen Users (list with search, and a detail page per user). This is how support finds a person, and how an admin stops an abusive account. The endpoints are served by user-service through the gateway route admin-users; all three need an aal2 staff session. VIEWER reads masked data; ADMIN and SUPER_ADMIN see full contact details and may change a user's status.

Why status changes exist

Staff need a fast, reversible way to stop an account that abuses the platform (spam reviews, scam messages) without deleting evidence. SUSPENDED is the reversible stop; DELETED is final and is for accounts that must be closed for good. Every change needs a written reason and is audited.

Use in a client

Debounce the search box. Show masked values as received (never try to un-mask). Keep the id of the chosen row: it is the key for the detail page, the status change and the audit filter target=<id>. Sizes above 100 silently become 100 (verified: size=1000&page=-4 answered page 0, size 100).

What search matches

The q text is matched against the stored values. A VIEWER only matches name and user id: phone and email are masked for them, so they are not searched (a VIEWER search for a full phone or email finds nothing, changed 2026-10-26). ADMIN and SUPER_ADMIN match everything below:

  • A 36-character UUID that parses: exact match on the user id, nothing else.
  • Anything else: case-insensitive contains match on email, phone (+251... form), first name, last name, or first last together. % and _ in the text are matched literally. Example: q=doc-tmp finds a user called "Doc-tmp Tester".
  • Phone typed loosely: when the text contains only digits and the separators space, +, (, ), -, and at least 3 digits, the digits are also matched against the digits of every stored phone. q=93012 114 finds +251993012114 (verified).
  • Terms are not split into words: q=Tester Doc finds nothing, q=Doc-tmp Tester does.

Verified examples (ADMIN): q=+251993012114 (exact phone), q=93012%20114 (spaced digits) and q=<uuid> each returned total: 1.

Use in a client

Render masked: true as a banner. Treat extra as arbitrary JSON written by the user and the apps (do not trust or execute it).

Every field of the detail response

FieldMeaning
idThe user's id (the Kratos identity id).
email, phoneContact details. Either can be null (a user signs up with one of them). Masked for VIEWER.
firstName, lastNameNames as the user entered them; may be null.
statusACTIVE, SUSPENDED or DELETED.
marketET or US: which market the user belongs to (decides which apps they see).

verificationTierHow far the user is verified (CONTACT = a confirmed phone or email).

timezoneIANA timezone, for example Africa/Addis_Ababa.
avatarImageIdId of the profile picture, or null. The picture itself is not exposed here.

termsAcceptedVersion, termsAcceptedAtWhich terms version the user accepted and when (null if never).
deletedAtSet when the status became DELETED.
extra / extraKeysFree-form JSON (preferences the user and apps store). For VIEWER extra is null and extraKeys lists the key names.
devices{active, total, platforms}: how many phones are registered for push (active means a usable push token) and on which platforms. Tokens are never shown.
aliasCountIn how many mini apps this user has a pseudonymous id (apps the user opened). The ids are never shown: partners know the user only by that id.
mutePreferences[]Per app the user muted: appId, muteInApp, muteSms, muteEmail, updatedAt. Empty means nothing is muted. A muted channel makes partner notifications end as SUPPRESSED (recipient_opted_out).
maskedTrue when the caller is a VIEWER.

The list response contains the first block only (id, email, phone, names, status, market, language, verificationTier, createdAt, lastSeenAt).

Suspend, reactivate or delete

POST/admin/api/v1/users/{id}/statusChange a user's status: ACTIVE, SUSPENDED or DELETED
Why
Stop an abusive account (suspend), give it back after an appeal (reactivate), or close it for good (delete).
Auth
Staff aal2 Bearer, role ADMIN or SUPER_ADMIN (VIEWER: 403 insufficient_role, checked first)
Header
Content-Type: application/json
Rate limit
300/min/IP
Audit action
user.status (target type app_user)
Reversible
SUSPENDED to ACTIVE: yes. DELETED: no (final)
Backoffice
User detail, card Account status: buttons Suspend, Reactivate, Mark deleted (each asks for a reason in a confirmation box)

Body

FieldTypeRequiredConstraintsWhy it exists
statusstringyesACTIVE, SUSPENDED, DELETED (any case)The new status.
reasonstringrequired for SUSPENDED and DELETED, optional for ACTIVE3 to 500 characters after trimming (a longer text is rejected for any status)Kept in the audit log: the answer to "why was this person suspended?" months later.

Unknown fields are rejected: 400 validation_failed with "<field>": "unknown field".

curl -sS -X POST "$GATEWAY/admin/api/v1/users/$USER_ID/status" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \

Request: reactivate

curl -sS -X POST "$GATEWAY/admin/api/v1/users/$USER_ID/status" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"ACTIVE","reason":"doc-tmp: appeal accepted"}'

Answers 200 with the detail (status: ACTIVE).

Request: delete

curl -sS -X POST "$GATEWAY/admin/api/v1/users/$USER_ID/status" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"DELETED","reason":"doc-tmp: account closed at owner request"}'

Answers 200 with status: DELETED and deletedAt set.

Idempotency

Asking for the status the user already has returns 200 with the detail and changes and audits nothing (verified with ACTIVE on an active user, and with DELETED on a deleted user: the second call is a no-op, not an error). Only a different status on a deleted user answers 409 user_deleted.

Deleted is not erased

"Mark deleted" blocks the account forever but does not remove personal data or the Kratos identity. There is no endpoint for erasure; see Not built yet. Never promise a customer that their data was erased on the strength of this action.

Worked scenarios

  • An abusive reviewer: find the review in Moderation, copy the userId, open the user, suspend with a reason that names the review id, then hide the review (suspending does not hide it). See the abusive-user runbook.
  • Appeal accepted: Users, filter SUSPENDED, open the user, Reactivate with a note. The user keeps the account; the next call works with a new sign-in (or the same session if it was created after the suspension).
  • Support asks "is this number registered?": search the digits; a VIEWER gets a masked row and the status, which is enough to answer.

Errors on this page

Sign-in errors (401, 403 mfa_required, 403 not_staff) apply to every call. The business errors are listed with each endpoint; the full table is on the error codes page.

Not built yet

  • No endpoint to erase a user's data or remove the Kratos identity (do it by hand with the Kratos admin API and SQL, as the repository's journey script does for test users).
  • No bulk status change, no CSV export, no user notes or tags, no way to edit a user's profile from the dashboard.
  • No staff-visible history of logins; the audit log records only staff changes.
