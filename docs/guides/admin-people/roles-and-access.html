Staff sign-in, roles and permissions

How staff authenticate for the admin API (aal1 versus aal2), what the three roles can do, and a verified permission matrix for every admin endpoint.

Overview

Every staff call goes through the gateway. Before it reaches a service the gateway asks registry-service (which asks Kratos) whether the caller is an active staff member with a valid session that completed the authenticator-app step. The gateway then forwards the request with the caller's id and role, and each endpoint decides whether that role is enough. This page covers the sign-in, the three roles, and the full permission matrix for every admin endpoint.

Why two steps

The admin API can suspend customers, hide reviews, change who may send SMS and add other admins. A stolen emailed code must not be enough on its own, so a staff session only works after the authenticator-app code was also entered. Kratos names that level aal2; a session with only the emailed code is aal1.

Staff authentication for API use

Staff sign in with passwordless email codes plus an authenticator app (TOTP). There are no passwords. The sign-in is a Kratos native (API) flow under $GATEWAY/kratos. The backoffice screen Login performs the same steps for people; a script does them like this:

  1. Emailed code. GET /kratos/self-service/login/api returns a flow id. POST /kratos/self-service/login?flow=<id> with {"method":"code","identifier":"you@company.com"} emails a 6-digit code (valid 5 minutes). POST again with the same body plus "code":"123456" to receive session_token. That session is aal1.
  2. First time only: enrol the authenticator. With the aal1 token (Authorization: Bearer ...) call GET /kratos/self-service/settings/api. The flow's node totp_secret_key holds the secret (the backoffice also draws it as a QR code). Add it to an authenticator app, then POST /kratos/self-service/settings?flow=<id> with {"method":"totp","totp_code":"<6 digits>"}. Right after enrolment the same session is already aal2. Settings changes need a session younger than 15 minutes.
  3. Every later sign-in: upgrade to aal2. After the emailed code call GET /kratos/self-service/login/api?aal=aal2&refresh=false with header X-Session-Token: <aal1 token>, then POST /kratos/self-service/login?flow=<id> with {"method":"totp","totp_code":"<6 digits>"} and the same header. The response carries the aal2 session_token.
  4. Call the admin API with Authorization: Bearer $TOKEN (the aal2 token). There is no separate staff API key.

The Kratos request and response bodies are Kratos' own; the Python helper tests/e2e/staff.py in the repository is a working reference (email_login, enrol_totp, upgrade_to_aal2). Kratos refuses an authenticator code it has already accepted, so wait for the next 30-second window before reusing the app. Gateway limits: 10 login-step submits per minute per IP (everyone behind one office address shares it), 300 admin calls per minute per IP. In DEV the emailed code is readable at the Mailpit inbox (http://127.0.0.1:8025) or the dev endpoint /dev/messages of notification-service; nothing real is sent.

Order of checks

A deactivated colleague who still has an authenticator enrolled gets mfa_required at aal1 and not_staff only after the authenticator step (verified). Do not read mfa_required as proof that the account is still staff.

Session handling

  • Lifetime. A Kratos session lasts 720 hours (30 days) after sign-in (session.lifespan in infra/kratos/kratos.yml). The token is the Kratos session token; the backoffice keeps it in the browser tab.
  • The role is read on every call. It lives in the Kratos identity (metadata_public.role), which only the Kratos admin API can write (a user cannot edit it through any self-service flow). A role change therefore applies to the very next request, with no new sign-in. The staff row (status ACTIVE or DISABLED) is read on every call too.
  • Deactivation revokes every session of that person immediately: their next call answers 401 (verified in the Staff runbook).
  • Sign-out. Kratos native logout: DELETE /kratos/self-service/logout/api with {"session_token":"$TOKEN"}. Afterwards the token answers 401.
  • Sign-ins are not audited. The audit log records changes made through the admin API, not logins or logouts.
  • Lost authenticator. There is no self-service recovery and no dashboard button; see the lost-authenticator runbook.

The three roles

RoleIntended forCan
VIEWERSupport and read-only colleaguesRead everything the dashboard shows except the audit log and the staff list. Personal data of users is masked. Cannot change anything.
ADMINOperators who run mini apps and moderationEverything a viewer can, plus see full user contact data, read the audit log, and make changes: create and edit apps, keys, limits, templates, moderate reviews and reports, suspend/reactivate/delete users.
SUPER_ADMINThe owner and a few trusted peopleEverything an admin can, plus manage staff (list, add, change role, deactivate) and move a KILLED app back to another status.

Higher ranks include everything below. Keep at least two super admins so that losing one authenticator does not lock you out (see the runbooks).

What a refused call looks like

curl -sS -i -X POST "$GATEWAY/admin/api/v1/users/$USER_ID/status" \
  -H "Authorization: Bearer $VIEWER_TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"SUSPENDED","reason":"doc test"}'
HTTP/1.1 403 Forbidden

{
  "error": "insufficient_role"
}

The same 403 insufficient_role answers GET /audit, GET /staff, POST /staff, PATCH /reviews/{id} and PATCH /reports/{id} for a viewer (all verified). The role is checked before the request body is validated, so a viewer never learns about field errors.

Masking rules for VIEWER

Applied by user-service to every user response (list and detail). The response says so: "masked": true on the detail. A viewer sees:

FieldADMIN / SUPER_ADMINVIEWER
emailfull valuefirst letter, ***@, first letter of the domain, *** and the last domain part: d***@e***.com. Very short or malformed values become ***.
phonefull E.164 valuecountry part and last four digits: +251*****0015 (for +1 numbers the first two characters are kept).
gender, dateOfBirthvaluesnull
extra (free-form JSON)the objectnull, and extraKeys lists only the key names
names, status, market, language, tier, timezone, location summary, devices, aliasCount, mute preferencesvaluesvalues (not masked)
Search sees the full value

A viewer can still search by a full phone number or email: the search runs on the real data and returns the masked row. That lets a viewer confirm that a given phone is registered. This is how the dashboard is built today (listed in Known issues).

Reviews and reports show the author's user id (not masked) to every role; the id alone does not reveal contact data. The notification log never contains message values, user ids or aliases for any role.

Request

No parameters, no body.

curl -sS "$GATEWAY/admin/api/v1/me" -H "Authorization: Bearer $TOKEN"

Response 200

HTTP/1.1 200 OK

{
  "role": "VIEWER",
  "id": "8834038d-18f3-4777-8f44-3aa6e641f2d9"
}

id is the Kratos identity id (the same id used as actorId in the audit log and id in the staff list). role is the current role.

Errors

401 unauthorized, 403 mfa_required, 403 not_staff as in the table above.

Use in a client

Call it once after sign-in. Treat mfa_required as the cue to show the authenticator step, not_staff as the cue to sign out. Re-call it when a request answers insufficient_role, in case the role changed.

What the gateway adds to your request

After the staff check the gateway sets X-Staff-Id and X-Staff-Role on the forwarded request, together with a shared secret and the client IP (X-Client-IP), and overwrites any value a client sent. Services refuse requests that did not come through the gateway. You never send these headers yourself. The audit log records the staff id, the role at that moment and the client IP of each change.
