Runbooks

Step-by-step procedures for the situations operators meet: an abusive user, a report about an app, adding and removing colleagues, a missing SMS, a lost authenticator and auditing a change.

Each runbook says when to use it, the steps with the exact calls, how to check the result and how to undo it. Calls assume the variables on the overview page. Ids come from the answers of the earlier steps.

Runbook: handle an abusive user

When: a user posts abusive or spam reviews, or several reports point to one person. Role: ADMIN. Backoffice: Moderation, then Users.

  1. Find the evidence. GET /reviews?appId=$APP_ID (or GET /reports?status=OPEN); copy the userId and the review or report id.
  2. Look at the account. GET /users/$USER_ID: status, market, how long registered, devices. If it is already SUSPENDED or DELETED, stop.
  3. Suspend with a reason that cites the evidence. POST /users/$USER_ID/status {"status":"SUSPENDED","reason":"abusive review <reviewId>, report <reportId>"}. Effect: their sessions are revoked, every user API call answers 403 account_suspended, partners get user_unreachable for them.
  4. Hide the abusive content (suspending does not): PATCH /reviews/$REVIEW_ID {"status":"HIDDEN"} for each review. There is no filter by author, so list the reviews of the apps they used and match userId.
  5. Close the reports about them: PATCH /reports/$REPORT_ID {"status":"REVIEWED"}.
  6. Check with GET /audit?target=$USER_ID (the user.status entry with your reason) and GET /users/$USER_ID (status SUSPENDED).
  7. Decide delete or not. Suspension is enough for most cases. Use DELETED only when the account must be closed for good: it cannot be undone, and it does not erase data.

Undo: reactivate with {"status":"ACTIVE","reason":"appeal accepted"} and restore wrongly hidden reviews with {"status":"VISIBLE"}. Verified with a throwaway user (see the Registered users page): suspend, user refused with account_suspended, reactivate, user works again.

Runbook: handle a report about an app

When: the Dashboard shows open reports. Role: ADMIN to act, any role to read. Backoffice: Moderation > Reports.

  1. List the queue. GET /reports?status=OPEN. Group by appSlug and reason: several reports with the same reason against one app mean a real problem.
  2. Read the app. GET /apps/$APP_ID: status, support email and publisher, allowed origins, rating. Read the user's details text (untrusted).
  3. Check delivery if the reason is BROKEN or SCAM by message. GET /notification/notifications?appId=$APP_ID&limit=20 shows whether the app is sending and how it ends (statuses, reasons).
  4. Contact the publisher at the app's support email when the problem might be on their side. Give them the reason and time, never the reporter's identity.
  5. Act on the app if needed: pause (POST /apps/$APP_ID/status {"status":"PAUSED"}) while investigating, or kill it for good (KILLED; only a super admin can bring it back). See the mini-app administration guide.
  6. Close the report. PATCH /reports/$REPORT_ID with REVIEWED (you acted or confirmed the problem) or DISMISSED (no action needed). Repeat for each report on the same issue.
  7. Check: GET /reports?appId=$APP_ID&status=OPEN is empty; GET /audit?target=$APP_ID shows any status change and GET /audit?targetType=app_report&limit=5 the report decisions.

Undo: reports can be reopened (OPEN) at any time; an app can be set LIVE again unless it was KILLED.

Runbook: add a colleague

When: a new person needs dashboard or API access. Role: SUPER_ADMIN. Backoffice: Staff > Add staff member.

  1. Choose the lowest role that works: VIEWER for read-only support, ADMIN for operators, SUPER_ADMIN only for the owner and one backup.
  2. Add them.
    curl -sS -X POST "$GATEWAY/admin/api/v1/staff" \
  -H "Authorization: Bearer $SUPER_TOKEN" -H "Content-Type: application/json" \
  -d '{"email":"new.person@company.com","role":"VIEWER"}'
    The answer has their id and status: ACTIVE. Nothing is emailed to them.
  3. Tell them how to sign in. They open the backoffice ($GATEWAY/backoffice/), enter the address, type the emailed code, then scan the QR code with an authenticator app and type the first code. The next sign-ins ask for the emailed code and the authenticator code. Until they enrol, the admin API answers them 403 mfa_required.
  4. Check. GET /staff lists them ACTIVE; GET /audit?target=<their id> shows staff.create. After their first sign-in they can call GET /me and see their role.
  5. If they cannot get a code: check the address spelling (the code goes to that exact address); in production check the email provider; the notification service limits one-time-code emails per address (10 per hour, 20 per day by default).

Undo: deactivate them (next runbook). Verified end to end with a throwaway account on the dev stack.

Runbook: remove a colleague

When: someone leaves or should lose access. Role: SUPER_ADMIN. Backoffice: Staff > Deactivate. Do it at once, not at the end of the notice period.

  1. If they are a super admin, confirm another active super admin exists (GET /staff).
  2. Deactivate.
    curl -sS -X PATCH "$GATEWAY/admin/api/v1/staff/$STAFF_ID" \
  -H "Authorization: Bearer $SUPER_TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"DISABLED"}'
    Their role is removed and every session is revoked immediately: their next call with the old token answers 401; signing in again ends in 403 not_staff (verified).
  3. Review what they did. GET /audit?actor=$STAFF_ID&limit=200. Look for role grants, key registrations and capability changes you need to reverse.
  4. Rotate what they could see. Partner keys generated by the platform show the private key once to the person who generated it: if they generated keys, revoke and re-issue them in the app administration. Remove them from the other tools (Grafana, Infisical, RabbitMQ, the server) separately; those are not controlled by this API.
  5. Check. GET /staff shows status: DISABLED; the dashboard's staff.disabled counter went up.

Undo: {"status":"ACTIVE"} restores their stored role. Rows are never deleted, so the audit log keeps showing who they were.

Runbook: investigate "user says they got no SMS"

When: a user or a partner reports a missing SMS. Role: any (the user lookup shows masked data to a viewer). First ask which SMS: the sign-in code sent by Adera itself, or a message from a mini app.

A. A message from a mini app

  1. Find the user. GET /users?q=<digits of the phone>. Check status (SUSPENDED or DELETED means the partner gets user_unreachable and nothing is sent), phone (null means no SMS channel), and in the detail mutePreferences: muteSms: true for that app means the SMS was suppressed on purpose.
  2. Find the notification. Ask the partner for the externalId and roughly when. GET /notification/notifications?appId=$APP_ID&channel=SMS&from=...&to=...; the partner's externalId identifies it (the log has no recipient filter by design).
  3. Read the detail. GET /notification/notifications/$ID: status and reason (glossary on the Notification visibility page):
    • SUPPRESSED + recipient_opted_out: the user muted the app. Explain how to unmute (three-dot menu in the app window).
    • SUPPRESSED + not_allowlisted: the deployment only delivers to an allowlist (live safety net).
    • UNREACHABLE + user_unreachable / no_phone: account deleted or suspended, or no phone number.
    • FAILED / EXPIRED: read attemptLog (provider and error code, for example a bad number or an unreachable provider).
    • SENT: the provider accepted it. Delivery to the handset is not tracked: check the number, signal and the carrier.
  4. If there is no notification at all, the partner's request was refused: ask for the HTTP answer they got (user_unreachable, capability_not_granted if the app has no notify.sms, quota_exceeded when a limit was reached; see GET /notification/usage?appId=...).
  5. Check delivery health. System page: notification-service UP; Dashboard: share of FAILED or EXPIRED in the last 24 hours.

B. The Adera sign-in code

Sign-in codes are sent by notification-service on behalf of Kratos. A person who asked for too many codes is shown "try again in N minutes" by the backoffice login page (it calls POST /public/v1/login-codes/check first); the limits are SMS 5 per hour / 10 per day and email 10 per hour / 20 per day per address, and a rejected or dropped code is SUPPRESSED rate_limited in the send log. They are not partner notifications, so they do not appear in the admin API. Look at the user first (GET /users?q=...): a SUSPENDED or DELETED account still receives codes (Kratos does not know the status) but cannot use the API. Then check the send log on the server (it stores only a hash and a masked recipient):

docker compose exec -T postgres psql -U adera_admin -d notification -c \
  "select created_at, channel, status, error_code, provider from send_log \
   where channel='SMS' and recipient_hash = encode(sha256('+251911234567'::bytea),'hex') \
   order by created_at desc limit 10"
send_log status / error_codeMeaning
SENTHanded to the provider (in DEV the console provider only logs it; read it at http://127.0.0.1:8085/dev/messages).
SUPPRESSED / rate_limitedThe per-recipient limit was reached (defaults: SMS 5 per hour and 10 per day per number; email 10 per hour and 20 per day per address). Tell the user to wait; do not raise the limits to fix a single person.
SKIPPED / not_allowlistedA live allowlist is active and the number is not on it.
FAILED / <code>The provider refused (for example an invalid number or a route that does not serve the country). See the provider's dashboard.

Also remember the gateway limit of 10 sign-in submits per minute per IP: users on one shared network can hit 429 before any SMS is sent.

Runbook: recover from a lost authenticator

When: a staff member lost or replaced the phone with the authenticator app, or the account shows an authenticator prompt but no QR code (the account has an authenticator someone else enrolled). Who: someone with access to the Kratos admin API. This is not an admin API call and has no dashboard button; a SUPER_ADMIN cannot do it from the Staff screen.

Check who is asking

Resetting an authenticator removes the second factor of that account. Confirm the requester's identity out of band (a call, in person) before you do it. Anyone who can reach the Kratos admin port can do this to any account, which is why that port is never exposed through the gateway.

Dev machine (Kratos admin API on 127.0.0.1:4434)

  1. Find the account (credentials lists the sign-in methods; totp means an authenticator is enrolled):
    curl -s -G --data-urlencode "credentials_identifier=person@company.com" \
  http://127.0.0.1:4434/admin/identities \
  | python3 -c 'import json,sys;[print(i["id"], sorted(i["credentials"])) for i in json.load(sys.stdin)]'
    <identity id>  ['code', 'totp']

    (verified on a throwaway staff account: before the reset the credentials were ['code', 'totp'], afterwards ['code'].)

  2. Delete only the authenticator credential (the account, its role and the emailed-code sign-in stay):
    curl -s -o /dev/null -w '%{http_code}\n' -X DELETE \
  http://127.0.0.1:4434/admin/identities/<id>/credentials/totp
    204
  3. Revoke their existing sessions. Deleting the credential does not end sessions that are already at aal2: the old token kept answering 200 on GET /me after the reset (verified). If the phone was lost or stolen, revoke them:
    curl -s -o /dev/null -w '%{http_code}\n' -X DELETE \
  http://127.0.0.1:4434/admin/identities/<id>/sessions
    204

    After that the old token answered 401 unauthorized (verified).

  4. The person signs in again. After the emailed code the admin API answers 403 mfa_required (verified); the backoffice shows the QR code again. They scan it with the new phone and enter the first code; the session is then aal2 and GET /me answers 200 with their role (verified).
  5. Tell them to enrol on two devices (scan the QR code on both phones during setup): the secret cannot be shown again later.
  6. If it was a test account that scripts enrolled, delete its secret file tests/e2e/.staff-totp-<address>.json too, otherwise scripts try the old secret.

Production

  • The Kratos admin API must not be published. Run the same three calls from inside the private network (a shell in the Kratos or registry container, or a port-forward you close afterwards), using the admin URL of that environment instead of 127.0.0.1:4434.
  • There is no self-service recovery (recovery flows are not enabled) and there is no dashboard action: every reset is an operator action, so keep the operator list short and note each reset in your own ticket (it is not in the audit log).
  • If every super admin is locked out and no other admin can sign in: reset the authenticator of one super admin as above, or set BOOTSTRAP_SUPER_ADMIN_EMAIL to an address you control and restart registry-service (it only acts when no active super admin exists; see Staff management).
  • Prevention: keep at least two super admins; enrol each authenticator on two devices; store the recovery procedure where the owner can find it.

Runbook: audit a change

When: "who changed this?" or a periodic review. Role: ADMIN or SUPER_ADMIN (the audit log is closed to viewers). Backoffice: Audit log, or the Audit tab of an app, or the Audit card of a user.

  1. Identify what changed and its id: app id, user id, review id, key id (ak_...) or staff id.
  2. Ask the log about that id. GET /audit?target=$ID. For one kind of change add action= with a prefix (app.status, capability., key., user.).
  3. Read each event: actorEmail and actorRole (who and with which power), at (when, UTC), ip (from where), meta (what: from/to for statuses, reason for user changes, fields for app edits, capability/state for permissions).
  4. Widen if needed: everything one person did in a period: GET /audit?actor=$STAFF_ID&from=2026-10-20T00:00:00Z&to=2026-10-27T00:00:00Z&limit=200, paging with offset until you have X-Total-Count rows.
  5. If nothing is found, remember what is not audited (sign-ins, reads, direct database or Kratos admin changes) and look in the service logs (Loki) instead.
  6. Reverse the change with the matching action (restore a review, reactivate a user, set the status back); the reversal is audited as well.
curl -sS -i "$GATEWAY/admin/api/v1/audit?target=$USER_ID" -H "Authorization: Bearer $ADMIN_TOKEN"

Example answer: the three user.status events shown on the Audit log page (suspend, reactivate, delete) with the reasons the admin typed.
