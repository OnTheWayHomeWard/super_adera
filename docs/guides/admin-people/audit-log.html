Audit log

The append-only record of staff changes: how to query it with every filter, what each entry contains, and the catalogue of action names.

Overview

The audit log is the append-only record of every change staff make through the admin API: who (staff id, role, IP), what (an action name), on what (target type and id) and details. It answers "who changed this, when, and from where?". Each entry is written in the same database transaction as the change, so a change cannot exist without its entry: if the entry cannot be written the change is rolled back (503 audit_unavailable on user status changes). The API offers no way to edit or delete entries. In the backoffice it is the screen Audit log the card Audit for this user on a user's page and the tab Audit of an app; the Dashboard shows a Recent staff activity panel. Admins and super admins only.

Why it matters

Staff can suspend customers, hide reviews, grant partners the right to send SMS and add admins. The log is how the owner proves who did what, spots a misuse, and reconstructs a bad change.

Errors

  "error": "validation_failed",
  "fields": {
    "actor": "must be a staff id (uuid)",
    "from": "must be an ISO-8601 instant like 2026-10-01T00:00:00Z"

Plus the sign-in errors and 403 insufficient_role for a viewer. A filter that matches nothing is not an error: it returns [] with X-Total-Count: 0.

Use in a client

Read X-Total-Count to build the pager, and request limit=200 pages to export a period. To show a person's name instead of an id, join actorId with the staff list (super admins) or use actorEmail. Do not parse meta by position: key sets differ per action.

What is recorded

  • Every successful change made through the admin API listed in the catalogue, with the actor's staff id, the role at that moment, the client IP and a timestamp.
  • Rejected requests (validation errors, 403, 404, 409) write nothing: only changes that happened.
  • Asking for the status a user already has changes nothing and writes nothing; re-sending the same review or report status writes a new event each time.
  • The same table is open to other services: any service can post an event to registry-service's internal endpoint (POST /internal/audit, internal secret) with an action name of 2 to 61 lower-case characters (letters, digits, _ . -). Today only user-service does, for user.status.

What is not audited

  • Notification template changes (create and edit, notification-service): no audit entries exist for them today.
  • Sign-ins and sign-outs, and failed sign-ins (Kratos keeps its own records; they are not in this log).
  • Reads: looking at a user's full contact data is not recorded.
  • Changes made directly in the database or with the Kratos admin API (for example resetting an authenticator), and changes by the e2e and seeding scripts' direct SQL.

How to read it: examples

  • Who hid this review? /audit?target=<reviewId> shows each hide and restore with the actor and time.
  • What did Sara do last week? /audit?actor=<her staff id>&from=...&to=....
  • Who gave this app SMS rights? /audit?target=<appId>&action=capability.; meta.capability and meta.state tell which and what.
  • Why was this user suspended? /audit?target=<userId>: meta.reason is the text the admin wrote.

Errors

400 validation_failed (fields.actor, fields.from, fields.to), 403 insufficient_role for a viewer, plus the sign-in errors. See the error codes page.

Not built yet

  • No export file (CSV/JSON download); page through the API.
  • No free-text search in meta.
  • No alerting on risky actions (for example a new SUPER_ADMIN).
  • No retention policy or archive: entries are kept forever.
  • No audit of template changes, sign-ins or reads of personal data.
