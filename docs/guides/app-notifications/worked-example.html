Worked example

A partner sends an IN_APP notification; the user's client then reads the inbox. Every response below was captured from the running dev stack on 2026-10-26.

Overview

Cast: the user is the seeded demo user Demo Selam (language am, phone +2519*****02); the mini app is demo-food; the template is seed-order-update (kind IN_APP, texts in en, am, om). The user has one registered phone. Rows created for this example were deleted afterwards.

Step 0: the client's state before

curl -s "$GATEWAY/api/v1/me/notifications/unread-count" -H "Authorization: Bearer $TOKEN"
{
  "count": 0
}

The phone registered its FCM token earlier (PUT /api/v1/me/devices, see the Account guide). Without it everything below still works except the push.

Step 1: the partner's request (context only)

This is sent by the mini app's server, not by the app. It is signed (headers X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature; see the Partner API guide) and goes to the same gateway.

POST $GATEWAY/v1/notifications
Content-Type: application/json

{
  "externalId": "order-1042-eta",
  "userId": "u_p_3c5af220db58ca21a535e8dd0ce6474b",
  "templateId": "b94d53fa-c514-4371-9239-95db3fe1ed25",
  "params": { "name": "Selam", "eta": "7 min" },
  "data": { "screen": "order", "orderId": "1042" }
}
HTTP/1.1 202 Accepted

{
  "notificationId": "1a9aa88f-e23e-4ac4-8ffd-d54f22c3ccc7",
  "externalId": "order-1042-eta",
  "status": "QUEUED",
  "channel": "IN_APP",
  "environment": "DEV",
  "createdAt": "2026-10-26T10:51:14.507915Z",
  "expiresAt": "2026-10-27T10:51:14.497804Z"
}

(The example run used the external id doc-tmp-order-1042-eta; the prefix was only a marker for cleanup.) The partner chose no channel: the template kind IN_APP decided it.

Step 2: what happened in the background

About a second later the worker delivered it. The partner's own status call showed:

{
  "notificationId": "1a9aa88f-e23e-4ac4-8ffd-d54f22c3ccc7",
  "externalId": "order-1042-eta",
  "status": "SENT",
  "channel": "IN_APP",
  "environment": "DEV",
  "createdAt": "2026-10-26T10:51:14.507915Z",
  "expiresAt": "2026-10-27T10:51:14.497804Z",
  "completedAt": "2026-10-26T10:51:15.478008Z",
  "attempts": 1
}

The service rendered the Amharic text (the user's language), wrote the inbox row, and tried push. In dev the fake push provider only logs a line:

[PUSH fake] token=...abcdef title=ትዕዛዝዎ በመንገድ ላይ ነው

With real Firebase the phone would have shown a banner carrying the payload described in Push notifications.

Step 3: the client reads the inbox

On the push (or when the app is opened) the client refreshes the badge and the list.

curl -s "$GATEWAY/api/v1/me/notifications/unread-count" -H "Authorization: Bearer $TOKEN"
{
  "count": 1
}
curl -s "$GATEWAY/api/v1/me/notifications?unread=true" -H "Authorization: Bearer $TOKEN"
[
  {
    "id": "2d7e9b41-6ec3-41e1-8b49-b3701d0d8e38",
    "appId": "24daadb5-f356-416d-8b91-43f5e6be386b",
    "title": "ትዕዛዝዎ በመንገድ ላይ ነው",
    "body": "ሰላም Selam፣ በ7 min ውስጥ ይደርሳል።",
    "data": "{\"screen\": \"order\", \"orderId\": \"1042\"}",
    "createdAt": "2026-10-26T10:51:15.474Z",
    "readAt": null
  }
]
Look closely

data is a JSON string (note the escaped quotes), not an object: the client must decode it a second time. The item id differs from the partner's notificationId. The title and body are already in the user's language. The amharic text interpolates the values exactly as the partner sent them ("7 min" was not translated).

Step 4: the user taps the item

The client decodes data ({"screen":"order","orderId":"1042"}), opens the demo-food mini app (looked up by appId in the app catalog) at the order screen, and marks the item read:

curl -s -X PUT "$GATEWAY/api/v1/me/notifications/$ITEM_ID/read" -H "Authorization: Bearer $TOKEN"
{
  "read": true,
  "id": "2d7e9b41-6ec3-41e1-8b49-b3701d0d8e38"
}

The badge count becomes 0 on the next unread-count call.
