How delivery works

From a partner's signed request to something the user can see: what is decided immediately, what happens in the background, and which channel is used.

Overview

A partner (a mini app's server) asks Adera to notify one of its users by naming a pre-approved template and a few values. The partner never chooses a channel and never sees the user's phone, email or push tokens. Adera decides, delivers in the background, and (optionally) reports the final status back to the partner.

Step by step

  1. Request. The partner sends POST /v1/notifications with externalId, userId (the alias), templateId, params, and optionally data (a JSON object of at most 2048 bytes for the client to use), callbackUrl and ttlSeconds (60 to 604800, default 86400). The request is signed; the Partner API guide describes how.
  2. Immediate checks (synchronous). Valid request? Repeat of an earlier externalId? Does the template belong to this mini app and is it usable now? Can the user be reached at all? Which channel? Has the user muted this channel for this mini app? Is the mini app within its limits? Failures here are answered at once with an error and the user is never involved.
  3. Queued. If everything is fine the request is stored as QUEUED and answered 202. A background worker picks it up about once a second.
  4. Delivery (asynchronous). The worker re-checks the user (phone, email, mute, status may have changed since step 2), renders the template in the user's language, and sends through the chosen channel.
  5. Outcome. The status becomes SENT, or a final failure state (see Delivery states). If the partner gave a callbackUrl a signed status report is sent to it.

DIRECTSMS if the user has a phone number and the mini app has notify.sms; otherwise EMAIL if the user has an email and the mini app has notify.emailA text message, or an email (subject from the template, or the title, or the first 60 characters of the body). Neither appears in the inbox.
Why

Partners should not decide how to reach a person: the user chose how they sign up (phone or email), granted what each mini app may use, and may have muted channels. Keeping the decision in Adera lets the user's choices apply to every mini app the same way, and keeps phone numbers and tokens private.

Inbox versus push

For IN_APP the inbox row is written first. Then Adera tries push to each active device. A missing device, a dead token or a push outage never fails the notification: the status is still SENT and the item is in the inbox when the user opens the app. Treat the inbox as the source of truth and push as a nudge. The attempt log records SKIPPED / no_devices when the user has no registered device, PERMANENT / token_unregistered for a dead token, PERMANENT / push_rejected when Firebase refuses the message itself (configuration or payload; the token is kept) and TRANSIENT / push_unavailable for a Firebase hiccup; a transient push failure is not retried.

Timing

In the dev stack the example in this guide reached SENT and the inbox about one second after the 202. If the user directory (the user service) is down, delivery is retried with backoff (about 30 s, 1 min, 2 min, 4 min, up to 1 h, at most 8 attempts, never past the partner's ttlSeconds). So the client should never assume an item exists the instant the partner says it sent something.

What the user never sees

  • The partner's alias for them, the partner's externalId, callbackUrl, params or template id. The inbox item carries only rendered text, the mini app's id, and the partner's data.
  • Quotas and limits. If a mini app exceeds a limit the partner gets 429 quota_exceeded and nothing is stored, so the user sees nothing and cannot tell.
  • Failures. A user who muted a channel, a suspended user, or an expired message simply receives nothing; there is no "missed message" placeholder.
  • Other users' data, ever: every inbox call is scoped to the signed-in user by the gateway.

Unreachable and suspended users

A user whose account is suspended or deleted is unreachable: the partner request is refused with 422 user_unreachable (deleted, suspended and unknown aliases deliberately look identical), no push token of theirs is ever used, and no phone or email is revealed to the delivery code. If a user becomes unreachable after a request was queued, the status becomes UNREACHABLE at delivery time. Items already in the inbox stay stored, but a suspended user cannot sign in to read them.
