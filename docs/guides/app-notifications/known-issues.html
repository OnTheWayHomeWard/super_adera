Known issues

#IssueHow to see itAdvice
1The inbox data field is a JSON string, not an object (the service returns the database's text form).GET /api/v1/me/notifications: "data": "{\"screen\": \"order\"}"Decode twice. Key order is not preserved.
2A push carries notificationId but inbox items do not expose it, so a push cannot be matched to its inbox item by id.Compare the push payload with the list responseOn a push, re-fetch the list and the count instead of looking the item up.
3Fixed 2026-10-26: nested values in the partner's data are now serialised as JSON strings in the push (before, Java's text form such as {a=1}). A null value is left out of the push; the inbox copy always has the original JSON. Covered by a test of the payload builder; the live path uses the fake push provider.Send data with a nested object and read the push the fake provider logs or a test captures.Parse nested values with a JSON decoder.
4Fixed 2026-10-26: partner data keys named notificationId or appId (the two the server adds) are refused when the request arrives: 400 validation_failed, fields.data. The same applies to names Firebase reserves (from, message_type, anything starting with google or gcm).POST a notification with "data":{"appId":"x"}: 400.Choose other key names.
5Paging is offset based with no total and no cursor; items arriving during paging shift later pages.Compare two pages after a new item arrivesDe-duplicate by id.
6Items have no per-app count or filter on the server; the unread count is global.-Group on the client.
7Fixed 2026-10-26: a wrong HTTP method on an inbox path (for example DELETE /api/v1/me/notifications/{id}) now answers 405 {"error":"method_not_allowed"} (with an Allow header); before it was a framework default 404 body.DELETE /api/v1/me/notifications/<uuid>Do not call methods that are not documented.
8Firebase's INVALID_ARGUMENT and SENDER_ID_MISMATCH answers retire the token like UNREGISTERED does (code reading). A malformed push could therefore deactivate a good device.Code: FirebaseFcmProviderRe-register the token on every app start: it re-activates the device.
9The preference endpoints take any UUID as appId without checking that the mini app exists (not tested with an unknown id to avoid creating a stray row).-Send only catalog ids.

Not built yet

  • Push delivery with real Firebase. The sending code exists but is off (FCM_PROVIDER=fake), so no phone has ever received a push from this stack. iOS-specific settings (badge, sound) are not set.
  • Notification categories and per-type settings. Only three switches per mini app exist (in-app, SMS, email). No category filter, global switch, quiet hours, or separate push switch.
  • Inbox retention and deletion. Items are kept forever; there is no delete, archive, mark-unread, or expiry per item.
  • Rich content. Title and plain-text body only: no images, buttons or actions, no HTML, no per-notification deep-link field (use the partner's free-form data).
  • Real-time inbox updates (websocket or server push of the count) and a delivery receipt from the phone.
  • Per-app unread counts and an app filter on the inbox API.
