Building the bell screen

Recipes for the unread badge, the list, paging, empty states and deep links using the inbox data.

Overview

Everything below uses only the endpoints in Inbox API. There is no real-time channel (no websocket or server-sent events): the client learns about new items by a push, by polling, or when the app comes to the foreground.

The badge

  • Call GET /api/v1/me/notifications/unread-count when the app starts, when it returns to the foreground, when a push arrives, and after every mark-read. Show count on the bell; hide the badge at 0. Cap the display yourself (for example "99+"): the server does not cap.
  • The OS app-icon badge can use the same number. Remember it is per user and counts all mini apps together.
  • A fixed polling interval is a fallback only (the gateway allows 300 calls a minute per IP, shared by all users behind one IP: 60 seconds is plenty).

The list

  1. Open: GET /api/v1/me/notifications?size=20&page=0. Newest first.
  2. Scroll to the end: request page + 1; stop when fewer than size items come back. De-duplicate by id (new items shift pages).
  3. Pull to refresh: reload page 0 and merge by id.
  4. "Unread" tab: same call with unread=true. Remember an item marked read while on this tab drops out of later pages.
  5. Row: show the mini app's name and icon (look up appId in the app catalog you already hold; if the app is gone from the catalog, show a generic icon), title, body (as plain text), a relative time from createdAt, and an unread dot when readAt == null.
  6. Empty: 200 [] on page 0 is an empty state ("No notifications yet"). Nothing in the response tells you why (never received, or all muted).
  7. Group or filter by mini app on the client: the server has no per-app filter.

Marking read

  • Mark an item read when the user opens it: PUT /api/v1/me/notifications/{id}/read. Update the row optimistically and decrement the badge; if the call fails with 404 remove the row, otherwise retry later (it is idempotent).
  • "Mark all as read": PUT /api/v1/me/notifications/read-all, then set the badge to 0 and re-fetch the count (items that arrived meanwhile stay unread).
  • There is no "mark unread" and no delete: do not offer them.

Deep links from data

The partner decides the contents of data; Adera only guarantees it is a JSON object of at most 2048 bytes (stored in the inbox as a string). Adera defines no standard keys for it. In the seeded example the partner used screen and orderId.

// decode, then route
final data = jsonDecode(item["data"]) as Map<String, dynamic>;   // second decode: data is a JSON string
final miniApp = catalog.byId(item["appId"]);
if (miniApp != null) {
  openMiniApp(miniApp, screen: data["screen"], params: data);   // the mini app interprets its own keys
}
  • Always route through the mini app. Use appId to open the mini app and hand it the decoded data; let the mini app interpret screen, ids and so on. Do not build a universal router for partner keys.
  • Treat data as untrusted. It is partner-supplied text. Do not navigate to a URL found in it without checking it against the mini app's allowed origins, never execute it, and ignore keys you do not understand.
  • Handle data == "{}" (no deep link): opening the item should open the mini app's home, or just mark it read.
  • Handle a mini app that is no longer listed (paused, killed or removed): show the notification text, skip the deep link.
  • From a push, the same keys arrive in the push data (all values are strings; nested objects and arrays are JSON strings you parse) together with appId and notificationId.

Checklist

  • Register the FCM token on login and app start.
  • Badge from unread-count, not from counting a cached list.
  • jsonDecode the data string.
  • Handle 401 (login again), 429 (back off, HTML body) and 503 (retry).
  • Do not assume an item exists the moment a partner says it sent one.
