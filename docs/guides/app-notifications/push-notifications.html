Push notifications

What the client receives as a push, how it relates to the inbox, what fake versus real Firebase means today, and what happens to dead tokens.

Overview

For every delivered IN_APP notification Adera sends one push per active device of the user, through Firebase Cloud Messaging (FCM). Push is a nudge: it can be lost, delayed or switched off by the phone's settings, and it is never retried. The inbox is the source of truth.

What "fake" and "real" mean today

Fake provider (the default, and the dev stack)Firebase provider
Selected byFCM_PROVIDER=fake (default)FCM_PROVIDER=firebase plus a Firebase service account in the secret store; the service refuses to start without it
What happensThe service writes a log line [PUSH fake] token=...abcdef title=... and counts the push as OK. Nothing reaches a phone. The fake never reports a dead token.The service calls FCM, high priority on Android.

For client developers

Until real Firebase is switched on you cannot receive a push on a phone from the dev stack. Build and test against the inbox (poll unread-count on foreground), and use the payload below to write the push handler against FCM's own test console in the meantime.

The push payload

The message sent to FCM has a notification part (shown by the OS) and a data part (delivered to the app). This is read from the sending code; the dev fake does not expose it.

{
  "notification": {
    "title": "ትዕዛዝዎ በመንገድ ላይ ነው",
    "body": "ሰላም Selam፣ በ7 min ውስጥ ይደርሳል።"
  },
  "data": {
    "screen": "order",
    "orderId": "1042",
    "notificationId": "1a9aa88f-e23e-4ac4-8ffd-d54f22c3ccc7",
    "appId": "24daadb5-f356-416d-8b91-43f5e6be386b"
  },
  "android": { "priority": "HIGH" }
}
KeyWhereMeaning
title, bodynotificationThe same rendered text as the inbox item, in the user's language.
every key of the partner's datadataCopied as strings (FCM data values must be strings). Strings and numbers become their text. A nested object or array is flattened with Java's default text form (for example {a=1}), which is not JSON: tell partners to keep push-relevant data flat, or have the client read the full data from the inbox item instead.
notificationIddataThe partner-facing id of the request. Added by Adera; overrides a partner key of the same name.
appIddataThe mini app that sent it (same id as the app catalog and the inbox appId). Use it to open the right mini app on tap. Also overrides a partner key of the same name.

Notes:

  • The push does not contain the inbox item id, only notificationId, and inbox items do not expose notificationId. A client cannot match a push to its inbox row by id; on a push, refresh the list and badge instead (see Known issues).
  • There is no iOS-specific block (no explicit badge, sound or category); iOS delivery depends on the Firebase project's APNs setup, which is unverified here.
  • No push is sent for SMS or email notifications, and none for a muted channel.

Tokens: registering and dead tokens

Registering the FCM token is part of the account functions (PUT /api/v1/me/devices, GET to list, DELETE to remove, and logout, which removes the device's token): see the Account guide. What matters for notifications:

SituationWhat Adera doesWhat the client must do
Firebase answers that the token is dead (app uninstalled, token rotated, or the token/sender is invalid)Marks the device inactive (active: false) and stops using it; records PERMANENT / token_unregistered. The notification itself stays SENT.Nothing visible happens to the user. The device disappears from GET /api/v1/me/devices (only active devices are listed). The client recovers by calling PUT /api/v1/me/devices with its current token: that re-activates the device (or creates it).
The FCM SDK rotates the tokenNothing until the client says soCall PUT /api/v1/me/devices again. With a stable installationId the new token replaces the old one instead of piling up.
App start / login-Call PUT /api/v1/me/devices on every login and every app start (it is idempotent and refreshes lastSeenAt). This is the self-healing path for a token that was retired by mistake.
User logs outThe device's token is removedCall logout (Account guide) rather than just discarding the session, so the next person on the phone does not receive this user's pushes.
A temporary Firebase failureRecords TRANSIENT / push_unavailable; no retryNothing. The inbox item exists; the user sees it when the app is next opened.

The device locale is stored for information; it does not choose the language of notifications (see Languages).

Handling a push in the app

  1. Foreground: do not show a banner the OS would not; instead refresh unread-count (and the list if the bell screen is open).
  2. Background or killed, user taps the banner: read appId and the partner keys from the push data, open the mini app, and refresh the inbox.
  3. Treat every data value as untrusted input from a partner (see Building the bell screen).
