Known issues

Verified surprises and gaps in the catalog, review, report and mute features, with how to reproduce them and the "not built yet" list.

Overview

Things that behave in a surprising way or are missing, found while verifying this guide against the code and the running dev stack. Nothing here was changed. Items with a reproduction can be re-run with a normal user token; the dashboard actions (hide a review, pause an app) need staff.

Known issues and surprises

#IssueHow to reproduce (verified on the dev stack, 2026-10-26)Client workaround
1Fixed 2026-10-26: the author now sees that a review is hidden
A review hidden by staff disappears from the public list and from the rating. GET my-review and the PUT my-review response now carry status (VISIBLE or HIDDEN) and, while hidden, a message. Editing a hidden review does not unhide it (an admin decision) and the response says so.		Hide a review in the dashboard, then GET /api/v1/apps/{slug}/my-review as its author: "status":"HIDDEN". PUT a new rating: still HIDDEN, absent from GET .../reviews. Verified on a throwaway app.Show "removed by moderators" when status is HIDDEN.
2Fixed 2026-10-26: authors can read and delete their review of a PAUSED or KILLED app
GET and DELETE .../my-review now work for PAUSED and KILLED apps. PUT .../my-review (editing), the public catalog, the public review list and reporting stay 404 for apps that are not LIVE. The rating stored on the app is refreshed when the author deletes.		Pause an app (staff), then GET/DELETE .../my-review return 200 for the author and PUT returns 404 not_found. Verified.Offer "Delete my review" when the app cannot be loaded, if the product wants it.
3Fixed 2026-10-26: a second report is no longer silently dropped.
While the user's earlier report of that app is OPEN, a new report returns the existing report with "alreadyReported": true (status 200, same reportId, existing reason); the new content is still not stored. A first report answers "alreadyReported": false.		POST report BROKEN, then SCAM with details: same id, alreadyReported: true, reason still BROKEN. Verified.Show "You already reported this app" when the flag is true.
4Mute preferences accept any UUID
The preference endpoints do not check that the app exists or is LIVE; rows are created for random ids, and reads of unknown ids return all-false.		GET /api/v1/me/apps/00000000-0000-0000-0000-000000000000/preferences returns 200 with three false values; PUT with a body stores a row. Verified (GET); PUT behaviour from code and the seed notes.Only use ids from the catalog.
5Mute preferences take only the UUID, with a non-standard 400
Using the slug where appId is expected returns Spring's default error body instead of {"error":...}. Also: the same bad-JSON mistake is invalid_request on the registry endpoints and invalid_json on the preferences endpoint, and only the first invalid key is reported there.		GET /api/v1/me/apps/demo-ride/preferences gives {"timestamp":...,"status":400,"error":"Bad Request","path":...}. Verified.Keep the app id in your model; decode all three error shapes.
6PUT my-review replaces the review, including the comment
Sending only rating removes an existing comment. Documented behaviour but easy to trip on.		PUT {"rating":4,"comment":"Works well."} then PUT {"rating":5}: comment is null. Verified.Always send the full state.
7By design: admins hide reviews explicitly. Reviews of suspended or deleted users stay public and counted
No automatic hiding happens when an account is suspended or deleted; the review keeps counting until staff hide it with the existing hide action. This was decided on purpose (2026-10-26) and will not change.		Seed data: the deleted user u12's visible review is in the demo-food count of 10 (from the seed documentation; not re-checked).None for the client.
8Permission description is English only; reason may be missing in the user's language
description comes from a fixed English sentence per capability; reason is whatever staff entered per language.		See any permissions entry.Localise by capability key on the client; apply the language fallback to reason.
9Review and report endpoints differ on unknown fields
PUT my-review rejects unknown keys (400); POST report ignores them.		PUT {"rating":3,"lang":"en"}: 400 "lang": "unknown field". POST report with an extra key: 200.Send only documented fields.
10Cosmetic: timestamps have different precision between PUT and GET
The PUT response can carry nanoseconds (.249809178Z) while a later GET of the same review shows microseconds (.249809Z).		PUT then GET my-review.Compare as instants, not as strings.
11The logo URL host is the storage endpoint
logoUrl points at the object store, not the gateway. In dev this is http://127.0.0.1:9000, unreachable from a phone or an emulator unless that address is mapped. It is a server setting (STORAGE_PUBLIC_ENDPOINT).		Open a logoUrl on a device that is not the dev machine.Ask backend to set the public endpoint to an address the device can reach, or port-forward in dev.

Not built yet

Category, search, sort, paging parametersGET /api/v1/apps accepts only market; everything else is ignored. Filter, search and sort on the device.
Launching a mini app inside the super appNo web-view bridge, no session handover. The registry stores an entryUrl and allowedOrigins for it, but no user endpoint or client contract uses them.
Per-user consent and sharing user data with mini appsThe grant by staff exists and is shown to users; the user's own Allow/Deny step does not, and no data flows to apps. Only the notify.* capabilities are enforced (by the notification service).
A public way to mint the per-app pseudonymous idToday only an internal call creates it, so user.basic has no user-visible effect.
Paymentspay.request and payment settings are stored configuration; there is no payment service or endpoint.
Saved postal addressuser.address exists as a label; profiles have no address.
