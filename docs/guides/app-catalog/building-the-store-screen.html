Building the store screen

A worked end-to-end flow for the app-store and store-page screens, with the UI states to design, client code and caching rules.

Overview

This page puts the endpoints together into a working "app store" experience: a catalog grid with categories, search and sorting, and a store page with permissions, ratings, reviews, reporting and notification mute. It lists the calls in order, the screen states you must design, and ready-to-adapt client code (TypeScript-style pseudo code; the logic is the same in Dart or Kotlin).

Worked flow

StepWhat to do
1. Know the userRead language and market from the profile (GET /api/v1/me) once per session and keep them in app state. They drive text selection and the market filter.
2. Show the catalog fastOn start, render the cached list immediately (if any) and call GET /api/v1/apps?market=ET in the background. Replace the list when the answer arrives; keep scroll position. Build the category chips from the data. The order of the array is the default order.
3. Filter, search, sort on the deviceApply category chip, search box and sort on the cached array (code below). No network call.
4. Open a store pageRender at once from the list item (it contains everything), and in parallel call detail, my-review and the first page of reviews; then preferences with the app's id. A 404 from detail means the app is gone.
5. Show permissionsRender permissions as a read-only list grouped by sensitivity, with the localised reason under each row (how).
6. Let the user actRate or edit (PUT my-review, always sending the comment too), delete the review, report the app, mute channels. After each, update the screen from the response and refresh the detail for the new rating.
7. RefreshPull-to-refresh and a refresh when the app returns to the foreground after more than a few minutes; always refresh a store page when it opens.

Request sequence for one visit

1  GET /api/v1/me                                   -> language, market (once per session)
2  GET /api/v1/apps?market=ET                         -> catalog (cache it)
   --- user taps a tile ---
3  GET /api/v1/apps/demo-ride                         -> fresh detail (rating, permissions, new logo link)
4  GET /api/v1/apps/demo-ride/my-review               -> 200 own review | 404 none
5  GET /api/v1/apps/demo-ride/reviews?page=0&size=10  -> first reviews
6  GET /api/v1/me/apps/{{id}}/preferences               -> mute switches (id from step 3)
   --- user acts ---
7  PUT    /api/v1/apps/demo-ride/my-review            {{"rating":4,"comment":"..."}}
8  DELETE /api/v1/apps/demo-ride/my-review
9  POST   /api/v1/apps/demo-ride/report               {{"reason":"BROKEN","details":"..."}}
10 PUT    /api/v1/me/apps/{{id}}/preferences            {{"muteSms":true}}

Steps 3 to 5 are independent and can run in parallel. Mind the rate limit (300 per minute per IP): a visit like this uses about six calls, so a normal session is far below it.

Client code: language, categories, search, sort, images, reviews

// ---- types (mirror the JSON) ----
type Lang = "en" | "am" | "om";
type I18n = Partial<Record<Lang, string>>;
interface Permission { capability: string; description: string; reason: I18n }
interface MiniApp {
  id: string; slug: string; name: I18n; description: I18n;
  logoUrl: string | null; brandColor: string | null;
  categories: string[]; markets: string[];
  publisher: { name: string|null; legalName: string|null; supportEmail: string|null; supportPhone: string|null; website: string|null };
  entryUrl: string | null; ratingAvg: number; ratingCount: number; permissions: Permission[];
}

// ---- language: user language, then English, then anything ----
const ORDER: Lang[] = ["en", "am", "om"];
function pick(m: I18n | undefined, lang: Lang): string | null {
  if (!m) return null;
  return m[lang] ?? m.en ?? ORDER.map(l => m[l]).find(Boolean) ?? null;
}

// ---- categories chips from the data ----
function categoryCounts(apps: MiniApp[]): [string, number][] {
  const n = new Map<string, number>();
  for (const a of apps) for (const c of a.categories) n.set(c, (n.get(c) ?? 0) + 1);
  return [...n.entries()].sort((a, b) => b[1] - a[1] || a[0].localeCompare(b[0]));
}

// ---- search all languages, rank name > publisher > description ----
function search(apps: MiniApp[], q: string): MiniApp[] {
  const s = q.trim().toLocaleLowerCase();
  if (!s) return apps;
  const has = (t?: string | null) => !!t && t.toLocaleLowerCase().includes(s);
  const score = (a: MiniApp) =>
    Object.values(a.name).some(has) ? 3 :
    has(a.publisher.name) || a.categories.some(has) ? 2 :
    Object.values(a.description).some(has) ? 1 : 0;
  return apps.map(a => [a, score(a)] as const).filter(([, sc]) => sc > 0)
             .sort((x, y) => y[1] - x[1]).map(([a]) => a);   // sort is stable: server order kept inside a score
}

// ---- sort ----
function topRated(apps: MiniApp[]): MiniApp[] {
  const MIN = 3; // ignore averages built from fewer ratings
  const rank = (a: MiniApp) => a.ratingCount === 0 ? -2 : a.ratingCount < MIN ? -1 : a.ratingAvg;
  return [...apps].sort((a, b) => rank(b) - rank(a) || b.ratingCount - a.ratingCount);
}

// ---- images: cache key without the signature ----
const imageKey = (url: string) => url.split("?")[0];

// ---- reviews: PUT replaces, so always send the full state ----
async function saveReview(app: string, rating: number, comment: string | null) {
  return api("PUT", `/api/v1/apps/${app}/my-review`, { rating, comment: comment?.trim() || null });
}

Client code: opening a store page

async function openStorePage(slug: string, user: { language: Lang }) {
  show(skeleton());
  const [detail, mine, reviews, prefs] = await Promise.allSettled([
    api("GET", `/api/v1/apps/${slug}`),
    api("GET", `/api/v1/apps/${slug}/my-review`),
    api("GET", `/api/v1/apps/${slug}/reviews?page=0&size=10`),
    // preferences need the app id, so run this after detail resolves (shown here as a follow-up)
  ]);
  if (detail.status === "rejected") {
    if (detail.reason.status === 404) return showGone();      // paused/killed/removed: drop it from the cached list
    return showError(detail.reason);                           // offline, 5xx, 429: offer Retry, keep cached item visible
  }
  render(detail.value, {
    myReview: mine.status === "fulfilled" ? mine.value : null,   // 404 here means "no review yet"
    reviews: reviews.status === "fulfilled" ? reviews.value : [],
  });
  const prefsNow = await api("GET", `/api/v1/me/apps/${detail.value.id}/preferences`);
  renderNotificationToggles(detail.value.permissions, prefsNow);
}

Caching summary

  • Catalog: in-memory plus disk, show-then-refresh, refresh every 5 to 15 minutes while browsing and on pull-to-refresh.
  • Detail: fetch on every store-page open.
  • Images: cache by URL without query string; never persist logoUrl beyond about 50 minutes.
  • Reviews: do not persist; fetch on open.
  • Language and market: from the profile; re-read after the user changes them and re-filter.

Design notes

  • Treat every text from the API as untrusted plain text (names, descriptions, reasons, comments, publisher fields): no HTML or Markdown rendering, and handle very long strings and right-to-left or Ethiopic script.
  • Do not assume a tile has everything: brandColor, logoUrl, entryUrl, website and supportPhone may be null; description may be empty.
  • Use slug for deep links and routes, id where an API needs the UUID.
  • Do not offer "Open" as a launch inside the super app yet (see below). If you offer "Open website", use the system browser and entryUrl, and pass no user data.

Not built yet (affects this screen)

  • Server-side category filter, search, sort and paging parameters (do it on the device as shown).
  • Launching a mini app inside the super app: no web-view bridge and no session handover. The only data about where the app lives is entryUrl.
  • User consent and sharing user data with mini apps: no consent endpoint, no per-capability grant by the user; the permission list is informative only.
  • Payments (pay.request is a stored label; no payment service exists).
  • Featured/new flags, screenshots, versions, install or favourite lists, "recently used", per-app usage history.
  • Review language, titles, histogram, "my reviews" list.
