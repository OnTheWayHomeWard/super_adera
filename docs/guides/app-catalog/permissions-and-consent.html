Permissions and consent

What a user allowed each mini app to do, per capability: how the menu sheet, the permission dialog and the Disconnect button work, and the exact calls behind them.

Overview

Staff decide what a mini app may ask for (its granted capabilities, see "Capabilities and permissions"). This page is about the second gate: what the user allowed. Opening a mini app shows no dialog. When the mini app needs something (for example the user's precise location) it asks at that moment, one permission at a time; your super app shows the staff-approved text and the user answers. The server remembers the answer and decides everything: the app's bridge only drives the dialog, because a mini app is third-party code and cannot be trusted to enforce anything.

Why this existsA user must be able to say no to one permission and yes to another, change their mind later, and leave an app completely, without the app being able to nag or to fake an answer.

The four states

StateMeaningA request from the mini app
NOT_ASKEDNever askedA dialog is allowed.
GRANTEDThe user said yesAnswered at once, no dialog.
DENIEDThe user said no onceA dialog is allowed one more time (the mini app should explain why first).
BLOCKEDThe user said no twice in a rowAnswered at once, never a dialog. Only the menu switch changes it.

A permission the app was not granted by staff is reported as NOT_AVAILABLE (a request) or refused with 403 capability_not_granted (answer and menu). user.basic, the private id that is different in every app, needs no dialog: it is reported GRANTED while the app has it, until the user disconnects.

The flow in the super app

  1. The mini app asks (bridge call requestPermission). The super app calls request.
  2. If the answer has a prompt, show a dialog with prompt.label and prompt.purpose verbatim and Allow / Deny. If prompt is null, do not show anything: return the state to the mini app.
  3. Send the user's choice with answer and the promptId. Return the new state to the mini app.
  4. The mini app's top menu shows list: one switch per permission. A switch calls menu (the only way out of BLOCKED). A "Disconnect" button calls disconnect.
  5. The phone's own location dialog is separate and comes after ours (for location). Adera only records the user's consent.

How to use it

  • canAskAgain is true when a dialog would be shown on the next request (NOT_ASKED or DENIED), false for GRANTED and BLOCKED.
  • Capabilities staff removed are not listed; an earlier answer is kept but inert, and applies again if staff grant the capability again.

How to use it

  • Show the dialog only if prompt is not null, using label and purpose verbatim (they are staff-approved; the mini app cannot change them), then send the answer with the promptId.

Opening a mini app: the launch token

When the user taps a mini app, the super app calls launch (no dialog). It returns a five-minute token to give to the mini app, the URL to load (the registered URL with ?launch=<token>) and the user's state per permission, so the super app can show a "location is off" hint without asking anything. The mini app's backend verifies the token and then reads, with signed calls, only what the user allowed.

Who may call
the signed-in user's session (the super app, when the user opens a mini app)
Client path

Auth
Authorization: Bearer $TOKEN (Kratos session token), checked by the gateway's forward-auth.
Rate limit
60 per 60 s per client IP; over the limit the gateway answers 429

Purpose

Opening a mini app. No dialog. The server mints the user's pseudonymous id for this app (first time only), reconnects it if the user had disconnected (user.basic needs no dialog), asks for a five-minute RS256 launch token signed with the Adera key and returns it with the URL to load and the user's current state per permission. The mini app's backend verifies the token against /.well-known/jwks.json (the partner guide has runnable examples) and learns who is calling: sub is the pseudonymous id, never the real user id. scopes are only a hint; every data call re-checks consent.

How to use it

  • url is the app's registered entry URL with launch=<token> added (? or &); null when staff registered no URL.
  • consents lists every capability staff granted the app with this user's state (NOT_ASKED, GRANTED, DENIED, BLOCKED), in the registry's alphabetical order; it never shows a dialog.
  • The token lives 5 minutes (expiresInSeconds). Call launch again whenever the mini app is opened; do not cache a token.
  • Decoded token (see section 14): header {"alg":"RS256","typ":"JWT","kid":"..."}; claims iss adera, aud the app id, sub the pseudonymous id, env dev or prod, scopes, iat, exp, jti.
