Error codes

Every status and error code returned by the catalog, review, report and mute endpoints, who produces it and what the client should do.

Overview

Errors come from three places, with three shapes. Write one small error decoder in the client that handles all of them.

  1. Our services (registry-service for the catalog, user-service for preferences): {"error": "<code>"}, and "fields": {...} for validation. Branch on error, never on a message.
  2. The gateway: 401 with an empty body, 429 with an HTML page, 503 when it cannot verify the session. These have no JSON.
  3. The web framework for protocol mistakes: {"timestamp": "...", "status": 405, "error": "Method Not Allowed", "path": "..."}. Only a buggy client sees these.
Decoder rule

If the status is 401, 429 or 503 handle it by status alone and do not parse the body. Otherwise try to parse JSON; if the body has a string error and no status number it is ours; if it has a numeric status it is a framework error.

What a user sees when an app is paused, killed or missing

Nothing distinguishes them: the app disappears from the list and every per-app call answers 404 not_found (detail, reviews, my-review including delete, report). Only the mute endpoints keep working (they never look at the app). Show one neutral message ("This service is not available right now") and never say "paused" or "killed", because the client cannot know which it is and neither state is the user's concern. Existing notifications from a paused app already in the inbox stay there; a partner's new messages are a separate matter handled by the notification service.
