Super app: the mini-app catalog

How to list, show, rate, review, report and mute the partner mini apps from the Adera super app, for the client developers who build those screens.

Audience

You build the super-app screens that list mini apps, show one mini app (the "store page"), show what it is allowed to do, let the user rate, review and report it, and let the user mute its notifications. You do not create or configure mini apps: only staff do that (in the dashboard), and this guide only describes what staff settings look like from the user's side.

Everything here was checked against the running dev stack (gateway, registry-service, user-service) and the service code on 2026-10-26. Where something is stored but not acted on, or does not exist yet, the page says so plainly.

Base URL and authentication

ItemValue
Base URLThe gateway. In dev: http://127.0.0.1:9080 (written $GATEWAY in examples). Never call a service port directly.
AuthEvery endpoint in this guide needs a signed-in user session: Authorization: Bearer $TOKEN, where $TOKEN is the session token returned by the sign-up or login flow. (A Cookie header also works for browsers.) The gateway validates the token before the request reaches a service and injects the user id itself; a client can never choose whose data it reads.
Rate limits300 requests per 60 seconds per client IP on /api/v1/apps/** and 300 per 60 seconds on /api/v1/me/** (separate counters). Over the limit the gateway answers 429 with an HTML page, and every response carries X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset.
Content typeJSON in and out. Send Content-Type: application/json on PUT/POST bodies (without it the service answers 415).
No staff accessStaff use a different API (/admin/api/v1/**) that is not part of this guide.

The nine endpoints

Method and pathPurposePage
GET /api/v1/appsThe catalog: all LIVE apps, with permissions, ordered for displayList
GET /api/v1/apps/{idOrSlug}One app (same shape as a list item)Details
GET /api/v1/apps/{idOrSlug}/reviewsAnonymous reviews of the app, newest first, pagedReviews
GET /api/v1/apps/{idOrSlug}/my-reviewThe signed-in user's own reviewReviews
PUT /api/v1/apps/{idOrSlug}/my-reviewCreate or edit my review (rating 1 to 5, optional comment)Reviews
DELETE /api/v1/apps/{idOrSlug}/my-reviewDelete my reviewReviews
POST /api/v1/apps/{idOrSlug}/reportReport the app (the "report this app" menu item)Reporting
GET /api/v1/me/apps/{appId}/preferencesMy mute switches for one appMute
PUT /api/v1/me/apps/{appId}/preferencesChange my mute switches for one appMute

Note the two kinds of identifier: the first seven endpoints accept either the app's id (UUID) or its slug (for example demo-ride) in {idOrSlug}; the two preference endpoints accept only the UUID in {appId}.

Conventions

  • Error shape. Errors from our services are {"error": "<code>"}, plus "fields": {"fieldName": "message"} for 400 validation_failed (all problems are reported together). Errors produced by the gateway are different: an empty body for 401 and an HTML page for 429. A few framework-level errors (wrong HTTP method, missing Content-Type, unknown URL) come back in a third shape, {"timestamp", "status", "error": "Bad Request", "path"}. See Error codes.
  • Ids. UUIDs in lower-case canonical form. The slug is permanent (staff cannot change it), so it is safe to store in deep links.
  • Timestamps. ISO-8601 in UTC with a trailing Z and up to nanosecond precision (for example 2026-10-26T10:51:32.249809Z). Parse with a tolerant ISO parser; the number of fractional digits varies.
  • Languages. Three: en (English), am (Amharic), om (Afaan Oromoo). Texts that staff write per language (name, description, permission reason) come as an object keyed by language code; languages without a text are simply absent. The user's preferred language is language on their profile (GET /api/v1/me). How to pick and fall back.
  • Markets. ET (Ethiopia) and US. The user's market is market on their profile; an app lists the markets it is offered in.
  • Paging. Only the reviews list is paged (page from 0, size 1 to 100). The catalog itself is one unpaged response. There is no total count.
  • Only LIVE apps exist for users. DRAFT, PAUSED and KILLED apps behave exactly like an unknown app: 404 not_found.

Glossary

TermMeaning
Super appThe Adera app your team builds.
Mini appA partner service listed in the super app. Has a record in the registry (name, logo, publisher, permissions) and, later, an entry URL the super app opens.
SlugThe mini app's permanent short name used in links, for example demo-food. 2 to 40 characters: lower-case letters, digits and dashes.
StatusDRAFT (being prepared), LIVE (visible to users), PAUSED (temporarily hidden by staff), KILLED (switched off). Users only ever see LIVE apps, and never see the status field.
Capability / permissionA named thing a mini app is allowed to ask for or do, such as notify.sms or location.coarse. Staff grant them per app. The user-facing list is called "permissions". See Capabilities and permissions.
ReasonThe plain-language sentence, per language, that explains to the user why an app needs a capability ("To deliver to the address you pick").
MarketCountry grouping used to decide where an app is offered: ET or US.
Brand colourThe app's accent colour as #RRGGBB, for tiles and headers.
Partner notificationA message a mini app's backend sends to a user through Adera (in-app inbox plus push, SMS or email).
MuteA user switch that stops one channel of one app's partner notifications.
Pseudonymous id (alias)A per-app stand-in id for the user so a mini app never sees the real user id. Not yet handed out to apps by any public flow.

What is not built yet (summary)

Details and evidence are on Known issues. In short: no category, search, sort or paging parameters on the catalog; no way to launch a mini app inside the super app (the frontend bridge and the per-user consent step do not exist yet), so no user data actually flows to mini apps; no payments; no review language or titles; no list of "my reviews" or "my muted apps".
