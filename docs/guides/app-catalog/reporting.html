Reporting an app

The report-this-app endpoint: the five reasons, the one-open-report rule and what the client should show.

Overview

Users can report a mini app. This page documents the one endpoint, the five reasons, the duplicate rule and what the user sees. Only apps can be reported: there is no way to report an individual review, and no way to report an app that is not LIVE (it answers 404 not_found, as does any non-LIVE app; the app is already off the shelf).

Reasons and how to word them

ValueShow to the user asTypical use
SPAM"Spam or misleading"Unwanted promotion, fake listings
SCAM"Scam or fraud"Asks for money or secrets under false pretences. Staff look at these first.
INAPPROPRIATE"Offensive or inappropriate content"Abusive or adult content
BROKEN"Not working"Crashes, cannot open, wrong behaviour
OTHER"Something else"Anything else; encourage filling details

Send the upper-case values as above. Localise the labels yourself; the server only knows the codes.

What happens after a report

  • It is stored with status OPEN, the reporting user and time. The dashboard shows an "open reports" count and a list; staff set the status to REVIEWED or DISMISSED (or back to OPEN).
  • The user gets no notification and no status read-back; the report is private (not visible to the publisher or to other users).
  • Reporting does not hide or pause the app by itself. Staff decide.
  • Reports from suspended or deleted users stay as they are.

UI recommendations

  • Place "Report this app" in the three-dot menu of the store page and of the app window (when launching exists).
  • Sheet with the five reasons as radio rows and an optional multi-line field (counter to 2000).
  • On 200 show a confirmation and mark the app locally as reported by this user.
  • On 404 show "This app is no longer available" and drop it from lists.

Not built yet

  • Reporting a review or a publisher; a note or screenshot attachment; a way to read back the status of my reports; a way to withdraw a report; telling the user the outcome.
  • Reporting from outside the catalog (for example an app that is PAUSED).

Endpoint

POST/api/v1/apps/{idOrSlug}/reportReport an app
Who may call
Signed-in end user, any LIVE app.
Rate limit
300 requests per 60 s per client IP (route apps-catalog).
Headers
Authorization: Bearer $TOKEN, Content-Type: application/json
Implemented in
AppPublicController#report, ReviewService#report

Purpose

The "Report this app" item in the three-dot menu. It lets users flag a mini app that is a scam, spam, offensive or broken. Staff read the reports in the dashboard (Moderation, Reports) and mark them reviewed or dismissed, and may pause or kill the app. The user is not told the outcome.

Request body

NameTypeRequiredConstraintsWhy it exists
reasonstringyesOne of SPAM, SCAM, INAPPROPRIATE, BROKEN, OTHER. Case-insensitive (broken is accepted and stored as BROKEN).Lets staff triage: scams first.
detailsstring or nullnoUp to 2000 characters after trimming; blank is stored as none.The user's explanation.

Unlike the review endpoint, unknown extra keys are ignored here, not rejected.

Example request

curl -s -X POST "$GATEWAY/api/v1/apps/doc-tmp-store/report" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "broken", "details": "Does not open."}'

Example response (200)

HTTP/1.1 200 OK
Content-Type: application/json

{
  "status": "received",
  "received": true,
  "alreadyReported": false,
  "reportId": "7f450156-3652-442f-81be-c26610225c93",
  "reason": "BROKEN",
  "createdAt": "2026-10-26T17:30:36.332808709Z"
}

The success status is 200, not 201. reportId is an opaque id; there is no endpoint for the user to read it back, so you only need it for support conversations.

Duplicate rule

One open report per user per app. If the user reports the same app again while their earlier report is still OPEN (staff have not handled it), the server does not create a second one: it answers 200 with the same reportId and the explicit flag "alreadyReported": true (a first report has false); reason and createdAt are those of the existing report. The new reason and details are not stored. Verified: after BROKEN, sending {"reason":"SCAM"} returned alreadyReported: true, the same id and "reason": "BROKEN". Once staff mark the report REVIEWED or DISMISSED, the user can report the app again and a new report is created.

Client advice: after a successful report show "Thanks, we received your report" and keep the menu item enabled but remember locally (per app) that a report was sent, then show "You already reported this app" when you get alreadyReported: true (or earlier, from your local memory, instead of letting the user write a second message that is not stored). The server gives no way to ask "have I already reported this app?".

Example: invalid reason

curl -s -X POST "$GATEWAY/api/v1/apps/doc-tmp-store/report" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"reason": "NOPE"}'
HTTP/1.1 400 Bad Request

{
  "error": "validation_failed",
  "fields": {
    "reason": "must be one of SPAM, SCAM, INAPPROPRIATE, BROKEN, OTHER"
  }
}

A missing reason gives the same message. Details over 2000 characters: {"error":"validation_failed","fields":{"details":"max 2000 characters"}}.
