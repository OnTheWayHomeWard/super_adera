List the mini apps

Everything about GET /api/v1/apps: what is returned, in which order, how to filter, sort, search and cache it.

Overview

One endpoint returns everything the home grid and the store list need. It is deliberately simple: the server filters out everything that is not LIVE, optionally filters by market, orders the result, and returns it. Everything else (categories, search, sorting by rating, favourites) is the client's job today.

What is included and excluded

App statusIn the list?On the detail endpoint?Who sees it
LIVEYesYesEvery signed-in user
PAUSEDNo404 not_foundStaff only. A temporary hide: an app disappears from the catalog and comes back when staff resume it.
KILLEDNo404 not_foundStaff only. Switched off (only a super admin can revive it).
DRAFTNo404 not_foundStaff only. Not yet released: staff cannot make an app LIVE without a logo and a support email.

Verified on the stack: demo-paused, demo-killed and demo-flights (DRAFT) are absent from the list and answer 404 {"error":"not_found"} on GET /api/v1/apps/{slug}. The client cannot tell "paused" from "killed" from "never existed" and does not need to.

Ordering

The server sorts by the app's priority ascending (lower number first; set by staff, range 0 to 100000, default 100), then by slug alphabetically to make ties stable. The priority value is not included in the response: only the resulting order is. Treat the array order as the "recommended" order and keep it unless the user picks another sort. Do not re-sort by name by default, or you throw away staff's curation (the seeded catalog is not in alphabetical order).

The market filter

An app is returned when its markets array contains the value (upper-cased before comparing). Apps are created with ["ET"] unless staff choose otherwise, so today almost everything is ET. Recommendation: call GET /api/v1/apps?market=<profile.market> so a US user does not see Ethiopia-only services; fall back to the unfiltered call only if the user explicitly asks to "show all". If you omit market you get all LIVE apps whatever their markets.

Filter, sort and search on the client today

The server does not support category, text-search or sort parameters, and ignores unknown parameters silently. The catalog is small (a few dozen apps at most is the expected scale) and arrives in one response, so doing this on the device is cheap and is the supported approach.

  • Categories. Each app has categories: a list of up to 10 lower-case words such as food, delivery, travel, transport, shopping, classifieds, tools. They are free-form words chosen by staff, not a fixed list. Build the category chips from the data: collect the union of categories over the list, count apps per word, and show the most frequent first. Localise the chip label in the client with a lookup table (unknown words: show the word itself, capitalised). An app can appear under several chips.
  • Search. Match the query (trimmed, case-folded) against the localised name, then description, then publisher.name, then categories. Search all languages of name, not only the displayed one, so a user typing the English name still finds the app while the UI is in Amharic. Rank name matches above description matches.
  • Sort. "Recommended" = server order. "Top rated": by ratingAvg descending, but only rank apps with ratingCount of at least a few ratings above unrated ones (a single 5-star review should not beat an app with 200 reviews at 4.6); apps with ratingCount == 0 go last. "A to Z": by the displayed name using locale-aware comparison.
  • Do the work on the cached list; do not call the server for each keystroke. Code: Building the store screen.

Pick a language and fall back

name, description and each permission reason are maps such as {"en": "Food Delivery", "am": "ምግብ አቅርቦት"}. Rules verified in code and data:

  • name.en always exists (staff cannot save an app without an English name).
  • description has no such guarantee: it can be {} or lack en. A permission reason is {} for capabilities that need no explanation.
  • A missing language is absent, never an empty string.
  • Supported codes are exactly en, am, om. In the seeded data every app has en and am; om is rare.

Recommended selection function: use the user's profile language if the map has it; otherwise en; otherwise the first available value in a fixed order (en, am, om); otherwise nothing (hide the description block, do not show an empty paragraph). Do the choice per field, not per app: an app can have an Oromo name but only an English description. Optionally show a small "in English" hint when you fall back to a language other than the user's.

Caching advice

The responses carry no Cache-Control or ETag headers, so caching is a client decision. Recommended:

WhatHow longWhy
The catalog listKeep in memory and on disk. Show the cached copy immediately on app start, then refresh in the background (stale-while-revalidate). Refresh at most every 5 to 15 minutes while the user browses, and always on pull-to-refresh.Staff changes (a new app, a paused app, new texts, a new rating) are not pushed to clients, so a cached list is up to the refresh interval out of date. 300 requests per minute per IP is plenty, but mobile networks in the same carrier NAT can share an IP.
An app's detailRe-fetch when the user opens the store page (it is cheap), and render the cached list item while it loads.The list item and the detail are identical, but ratings and permissions are the data most likely to have changed, and an app can be paused between the list and the tap (then the detail is 404).
Logo image bytesCache by the URL without its query string (scheme, host and path). The path contains the image's id, so it changes exactly when staff upload a new logo.The query string (signature and timestamp) is different on every response, so a cache keyed on the full URL never hits.
logoUrl itselfNever store it for longer than 50 minutes. It expires 60 minutes after it was issued (X-Amz-Expires=3600).After expiry the storage refuses the request (an XML error page, not JSON). The fix is to re-fetch the list or detail to obtain a fresh URL; see the logo section.
Ratings and permissionsNever cache for long, and never trust them offline for a decision.They change whenever users review or staff change grants.

Edge cases

  • An app that is paused between list and tap returns 404 on detail, reviews, my-review and report. Handle it by removing the tile and showing "This service is not available right now".
  • The list is not paged. If it ever grows large the server will need a paging parameter first (not built).
  • ratingAvg is 0.0 when there are no ratings; use ratingCount == 0 to show "No ratings yet" instead of "0.0 stars".
  • Two apps can legitimately have the same name in a language. Use id or slug as the list key, not the name.

Not built yet on this page

  • Server-side category filter, text search, sorting and paging parameters on GET /api/v1/apps.
  • "Featured", "new" or "updated" flags, app version, size, screenshots, install counts.
  • A priority or position value in the response (only the order is given).

Endpoint

GET/api/v1/appsList the mini apps shown in the catalog
Who may call
Signed-in end user (session token in Authorization: Bearer $TOKEN).
Client path
/api/v1/apps through the gateway (route apps-catalog, forward-auth, 300 requests per 60 s per client IP).
Headers
Authorization: Bearer $TOKEN. Nothing else is required for a GET.
Implemented in
registry-service: AppPublicController#list, AppService#publicView

Purpose

Returns the whole catalog the user may open: every mini app whose status is LIVE, already in display order, each with the data needed for a tile and for a store page (names, descriptions, logo, colour, categories, markets, publisher, rating, permissions). Use it to fill the home grid, the app-store list and any "all services" screen. The same item shape comes back from the detail endpoint, so a tile can open the store page without another request.

Request parameters

NameInTypeRequiredConstraintsWhy it exists
marketquerystringnoCase-insensitive; compared against each app's markets (ET or US). Blank = no filter. An unknown value is not an error, it simply matches nothing and the answer is [].Show only apps offered in the user's market. Send the market from the user's profile.

There are no other parameters. Unknown query parameters are ignored silently (for example ?category=food or ?q=taxi do nothing; see filter, sort and search on the client).

Example request

curl -s "$GATEWAY/api/v1/apps?market=ET" \
  -H "Authorization: Bearer $TOKEN"

Errors

StatusError codeWhen it happensWhat the caller should do
401(empty body)Missing, expired or revoked session token; or the account is not allowed to sign in (for example suspended). Produced by the gateway.Send the user to sign-in. Do not retry with the same token.
429(HTML page)More than 300 requests in 60 s from this IP.Back off until X-RateLimit-Reset seconds have passed. Cache the list so this cannot happen from normal use.
503(empty or gateway body)The gateway could not reach user-service to verify the session (status_on_error: 503).Show a retry state; try again with a short back-off.

There is no 404 on this endpoint: an empty catalog is 200 [].
