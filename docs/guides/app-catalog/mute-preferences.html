Mute preferences

The three per-app mute switches (in-app, SMS, email): how to read and change them and what each one does to partner notifications.

Overview

Mini apps can send users messages through Adera (the partner notification API): in-app messages (inbox plus push), SMS and email. The user keeps control with three switches per app: mute in-app, mute SMS, mute email. This is the "mute" item behind the three-dot menu of an app, and the "Manage" row on the store page. The state is stored per user and per app id and is read by the notification service on every send.

What each switch does

SwitchWhich partner messages it stopsWhat the partner seesWhat stays unaffected
muteInAppMessages the partner sends with an in-app template: no inbox item and no push notification is created.The send request is answered 200 with status SUPPRESSED and reason recipient_opted_out (instead of 202 queued). It does not count against the app's limits.SMS and email from the same app; any in-app messages already in the inbox (muting does not delete them).
muteSmsDirect messages that Adera would deliver as an SMS.Same: SUPPRESSED / recipient_opted_out.In-app and email.
muteEmailDirect messages that Adera would deliver as an email.Same.In-app and SMS.
  • Scope: one app. Muting demo-food does not affect demo-ride. There is no global mute.
  • No fallback to another channel. For a direct message Adera first picks the channel (SMS if the user has a phone and the app has notify.sms; otherwise email if the user has an address and the app has notify.email) and only then applies the mute. If the user muted SMS, the message is suppressed; it is not re-sent as an email. To silence a chatty app completely, a user must switch off every channel the app uses. A good default for the UI is a single "Mute everything from this app" action that sets all three to true.
  • Checked twice. At the moment the partner asks (instant suppression) and again just before delivery, so muting right after a message was queued still stops it.
  • Mute applies to partner notifications only. Nothing else in the user API consults these switches. Muting does not remove the app's permissions from its public view.
  • Whether a user can be reached at all (suspended or deleted accounts, missing phone) is a different mechanism: the partner gets 422 user_unreachable then.

UI recommendations

  • On the store page, show "Notifications" only for the channels the app is granted: notify.inapp gives a "Notifications" toggle, notify.sms "Text messages", notify.email "Emails" (see Capabilities and permissions). The server accepts all three switches regardless, but a switch for a channel the app cannot use is confusing.
  • The toggle is "on = receive". Show it inverted from the field: muteSms == true means the toggle is off.
  • Load with GET when the sheet opens; PUT on every toggle change; keep the toggle in a loading state until the response arrives; on failure revert it.
  • There is no endpoint that lists all of the user's mute settings: you can only read an app at a time.

Not built yet

  • A global do-not-disturb or quiet hours; per-message-kind switches (only the three channels exist).
  • A list of all apps the user muted; a way to find out which apps ever messaged the user.
  • Validation that the app exists or is LIVE.

Endpoints

GET/api/v1/me/apps/{appId}/preferencesGet my mute switches for one app
Who may call
Signed-in end user. The user id comes from the session, so a user can only read and change their own switches.
Client path
/api/v1/me/apps/{appId}/preferences (gateway route me, 300 requests per 60 s per client IP, served by user-service).
Headers
Authorization: Bearer $TOKEN; Content-Type: application/json on PUT.
Implemented in
user-service: PreferenceController#get, PreferenceService#get

Purpose

Reads the three per-app mute switches so the "Notifications from this app" settings can show their current state. If the user never changed anything for this app, all three are false (nothing muted).

Request parameters

NameInTypeRequiredConstraintsWhy it exists
appIdpathstring (UUID)yesThe app's id. The slug is not accepted here. The app must exist and be LIVE, otherwise 404 not_found (checked with the registry; 503 service_unavailable if the registry cannot be reached; a status change is noticed within about a minute).Preferences are stored per user and app id.

Example request

curl -s "$GATEWAY/api/v1/me/apps/$APP_ID/preferences" -H "Authorization: Bearer $TOKEN"

Example response (200)

HTTP/1.1 200 OK
Content-Type: application/json

{
  "muteInApp": false,
  "muteSms": false,
  "muteEmail": false
}

PUT/api/v1/me/apps/{appId}/preferencesChange my mute switches for one app
Who may call
Signed-in end user. The user id comes from the session, so a user can only read and change their own switches.
Client path
/api/v1/me/apps/{appId}/preferences (gateway route me, 300 requests per 60 s per client IP, served by user-service).
Headers
Authorization: Bearer $TOKEN; Content-Type: application/json on PUT.
Implemented in
user-service: PreferenceController#update, PreferenceService#update

Purpose

Turns channels on or off for one app. It is a partial update: only the switches you send change, the others keep their stored value. The response is the full state after the change.

Request body

NameTypeRequiredConstraintsWhy it exists
muteInAppbooleannoLiteral true or false; strings and numbers are rejected.Stop in-app messages (inbox plus push) from this app.
muteSmsbooleannosameStop text messages from this app.
muteEmailbooleannosameStop emails from this app.

Unknown keys are rejected. An empty object {} is accepted and changes nothing (answers the current state).

Example request

curl -s -X PUT "$GATEWAY/api/v1/me/apps/$APP_ID/preferences" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"muteSms": true}'

Example responses

HTTP/1.1 200 OK

{
  "muteInApp": false,
  "muteSms": true,
  "muteEmail": false
}

Then {"muteInApp": true, "muteSms": false} gave (verified): muteInApp true, muteSms false, muteEmail false (the earlier SMS mute was lifted, the untouched email switch stayed).

# body: {"muteSms": "yes", "foo": 1}
HTTP/1.1 400 Bad Request

{
  "error": "validation_failed",
  "fields": {
    "muteSms": "must be true or false"
  }
}

Only the first problem is reported (here foo's "unknown field" was not listed), so fix one and resubmit.

How to use it

  • Bind each switch to one toggle; send only the toggled key.
  • Update the UI from the response, not from your guess.
  • An unknown, paused, killed or draft app answers 404 not_found and stores nothing; a registry outage answers 503 service_unavailable (retry later).
