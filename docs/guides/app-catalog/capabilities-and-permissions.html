Capabilities and permissions

What each permission a mini app can hold means, who enforces it today, and how to show the permission list to users.

Overview

A capability is a named permission a mini app needs for a feature (location.coarse, notify.sms...). Staff decide per app which capabilities it has. The catalog shows users the granted ones as permissions so they can see, before opening an app, what it is allowed to do and why. This is the transparency half of the privacy model: the admin gate (staff grant) exists and the list is visible to users today; the per-user consent gate (the user taps "Allow" before data flows) is not built, because the frontend bridge that would carry the data does not exist yet.

Read this first

Of the nine capabilities, only the three notify.* ones are enforced by any service today, and only against the partner's notification requests. The other six are stored and displayed but nothing checks them, and no user data is sent to any mini app. Show them truthfully as what the app is allowed to request, not as proof that data is being shared.

So the client only ever receives granted capabilities. There is no way to show a "denied" or "suspended" row, and you should not try: absence means "this app cannot do that". Because a suspension takes effect at the next fetch, refresh the detail when the user opens the store page so a stale cached list does not claim an ability that was removed.

The shape of a permission

{
  "capability": "location.fine",
  "description": "Precise location, foreground only",
  "reason": {
    "am": "ለእርስዎ ቅርብ የሆነውን አሽከርካሪ ለማግኘት",
    "en": "To find the closest driver to you"
  }
}
FieldNotes
capabilityThe key from the table below. The stable identifier: switch on it.
descriptionA short English-only sentence from the server. It is not translated. Use it only as a fallback for a capability key your app does not know yet; for known keys, use your own localised strings.
reasonWhat the partner said it needs this for, per language, shown to the user verbatim. Written by staff for the app, so treat it as untrusted text: render as plain text, never as HTML or Markdown, and tolerate long strings. {{}} for capabilities where no reason is required (user.basic, notify.*); optional there, so it can be present.

Order: alphabetical by key (location.*, notify.*, pay.request, user.*). Re-order on the client by sensitivity (below).

Notes on the table:

  • "Enforced today" is checked in one place: when a partner backend asks Adera to send a notification. The notification service reads the app's granted capabilities and refuses with 403 capability_not_granted if the right one is missing. For a direct message it prefers SMS when the user has a phone and notify.sms is granted, otherwise email when the user has an address and notify.email is granted. For an in-app message it requires notify.inapp.
  • Default limits are written when staff first grant the capability (existing limits are never overwritten), and staff can change them per app. If a limit is hit, the partner gets 429 quota_exceeded; the user sees nothing. Users never see limits in the API.
  • "Data a mini app can receive" is "nothing" for every capability today because the only channel between Adera and a mini app is the partner notification API, which carries no user data in either direction except the pseudonymous alias the partner already holds.
  • Whether the user's own mute (next section) applies: yes to all three notify.* channels (Mute preferences). Muting does not remove the permission from the list.

How to show permissions to users

On the store page, a section "This app can..." (or "Permissions"), built from permissions, grouped and ordered from most to least sensitive:

GroupCapabilitiesSuggested row text (localise it yourself)Notes
Paymentspay.request"Ask you to pay for things"Show first and visually distinct. Add the reason below.
Your identityuser.contact, user.address, user.full_name, user.basiccontact: "See your phone number and email"; address: "Use one address you choose"; full name: "See your name"; basic: "Recognise you with a private ID (not your real identity)"Sensitive first, user.basic last: it is the mildest.
Your locationlocation.fine, location.coarsefine: "See your exact location while you use it"; coarse: "See your city"If both are present show only fine (it covers coarse).
Messagesnotify.sms, notify.email, notify.inappsms: "Send you text messages"; email: "Send you emails"; inapp: "Send you notifications"Add a "Manage" link to the mute switches for this app.
  • Title from your localised string for the key (fallback: description); second line is reason chosen with the language fallback in List the mini apps (user language, then en, then any). If there is no reason, show only the title.
  • Unknown future key: do not hide it. Show the English description in a neutral row. A new capability that the user cannot see is a trust problem.
  • If permissions is empty: say "This app does not ask for any permissions."
  • Do not render these as toggles. The user cannot grant or revoke a capability today (the consent step is not built). Use a read-only list. When consent exists, this is where the toggles will go.
  • On the tile in the list, at most show a small summary ("Uses location, payments") derived from the same array. Do not show all rows there.

What is not shown, and why

Notification limits, payment settings and the denied/suspended states are internal. A user-facing "this app can send you at most 3 texts a day" would be a promise the client cannot back with data, because the limits are not in the user API.

Not built yet

  • The frontend bridge that lets a mini app request a capability at runtime, and the consent prompt with per-user, per-capability grant and revoke (no endpoint stores a user's consent).
  • Any service that enforces user.*, location.* or pay.request: no user data goes to apps; no payment service; no stored postal address for user.address.
  • A public flow that creates the per-app pseudonymous id (it can only be created by an internal call today).
  • Showing denied or suspended capabilities, or per-capability limits, to users.
