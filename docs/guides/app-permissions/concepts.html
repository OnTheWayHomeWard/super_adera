How it works

The three gates, the four permission states and their rules, the two data paths, location, notifications as consent, revocation and what is and is not protected.

Overview

Staff decide what an app may ever ask for (its granted capabilities). The user decides what it actually gets, capability by capability. This page explains the rules; the next ones show the calls.

The three gates

GateQuestionFails with
1. GrantedIs the capability granted to the app, and is the app LIVE (not DRAFT, PAUSED or KILLED)?403 capability_not_granted or 403 app_not_live
2. ConsentedDid this user say yes to this capability for this app, and is it still yes? Is the user ACTIVE?403 consent_required (the body says the state)
3. In scopeIs what is asked for exactly what the capability covers? (location.coarse gives a city, never coordinates; user.contact never gives the address.)the data endpoint itself

Gate 1 is read on every call, so pausing an app or removing a capability in the backoffice bites at once.

The four states

StateMeaningA request from the mini app
NOT_ASKEDNever asked (also: no row)A dialog is allowed.
GRANTEDThe user said yesAnswered at once, no dialog.
DENIEDThe user said no onceA dialog is allowed one more time (the mini app should explain why first).
BLOCKEDThe user said no twice in a rowAnswered at once, never a dialog. Only the menu switch changes it.

A capability staff did not grant to the app is NOT_AVAILABLE (a request) or refused with capability_not_granted (answer, menu). Rules: a yes sets GRANTED and the denial count to 0. The first no sets DENIED (count 1); the second no in a row sets BLOCKED (count 2). A switch in the menu always works: on sets GRANTED, count 0; off sets DENIED, count 0, so the mini app may ask again later. There is no timer that unblocks; only the menu does. Consent does not expire.

The server enforces it, not the bridge

A dialog is only allowed after the server issued a one-time prompt (valid 5 minutes, single use, tied to one user, one app and one capability). An answer without a valid prompt is refused unless it comes from the menu. A bridge that tries to answer "yes" on its own, replays an old prompt, or answers for another app is refused.

user.basic: the pseudonymous id

user.basic is the user's id for the mini app (not personal data; the app needs it to identify the user at all). It needs no dialog: it is reported GRANTED as soon as staff granted it to the app, until the user disconnects (then DENIED). Opening the app again reconnects it. The menu cannot switch it off alone (409 use_disconnect): leaving is the Disconnect action.

Two kinds of data, two paths

KindExamplesHeld byHow the mini app gets it
Server-helduser.basic, user.full_name, user.contact, user.addressAdera (user service)Path B (recommended): the mini app's backend calls GET /v1/users/{alias}/profile with a signed request. The data never travels through the browser, each read is logged on our side, and the partner's keys, address list and environment checks apply. Path A (through the bridge, for user.basic and device data only) exists for low-risk fields; anything in the page can be copied by the partner's scripts or by a bad library it loaded.
Device-heldlocation.coarse, location.fineThe phoneThe bridge asks the phone; Adera records consent only and never stores a position. If the mini app's backend needs the position, its frontend sends it.
Action, no datanotify.sms, notify.email, notify.inapp, pay.requestAdera servicesThe mini app's backend calls the partner API; the gate is applied there.

Location is different

The live position is read from the phone, so it needs the phone's own permission as well as ours. Our consent is a separate yes. The bridge returns a reading only if both are yes and otherwise says denied or blocked without telling which of the two refused.

Notifications are consent too

The permissions notify.inapp, notify.sms and notify.email are the user's consent to be messaged by the app on that channel. The old "mute" switches are the same data (muted means DENIED). A partner message is sent only while the answer is GRANTED; otherwise the partner's request is refused with 403 consent_required (capability and state in the body) and nothing is sent. The answer is checked again right before delivery, so a user who switches it off after a message was accepted still stops it.

Revocation and telling the partner

  • Revocation is immediate: the gate reads the consent row on every call, there is no cached "allowed".
  • When consent changes the partner gets a signed callback (user.consent_changed with alias, capability and the new state; user.disconnected on Disconnect) if staff set a callback address. A partner that kept the user's name is expected to delete it on user.disconnected; Adera cannot enforce that once the data has left.
  • A suspended or deleted user fails gate 2 for everything.

What this does and does not protect

ThreatHandled by
A mini app calls the bridge for data it was not grantedGate 1 in the backend; the bridge's own check is only a courtesy
A mini app asks for data the user said no toGate 2, on every call
A mini app asks for more than a capability coversGate 3: each capability has a fixed set of fields
The mini app page loads a different site and the bridge talks to itThe bridge is injected only for the registered origin and checks the origin on every message
A stolen launch tokenFive-minute life, one app, one pseudonymous id; data calls need the partner's private key as well
A partner keeps data after the user withdrew consentNot preventable by Adera: callbacks, terms and audit only
A partner shares data with a third partyNot preventable by Adera: same
