Super app: the bridge specification

The JavaScript bridge a mini app's page calls: the four methods, the message format, the origin rule, the rules and the error codes.

Overview

For the super app team. The bridge lets a mini app's page ask for permissions and a location reading. It is thin by design: every method ends in one of the user endpoints (see "Super app: the user API") and the backend decides. The text below is the specification to implement; no code in the Adera backend or in this repository implements the page side.

What the bridge is

The bridge is a thin layer in the super app (the Adera app, a Flutter WebView host) that lets the mini app's page ask for permissions and a location reading. It adds no authority of its own: a mini app is third-party code, so the backend decides everything (the three gates), and the bridge only drives the dialog and carries answers. Every bridge method ends in one of the user endpoints (the user API); a mini app that bypasses the bridge and calls them directly has no session of the user, and a mini app's backend can never trigger a dialog. This is a specification for the super app team: nothing in the Adera backend implements the page side.

The four methods

The super app injects window.adera into the mini app's page (only for the registered origin, see the origin rule). Every method returns a Promise.

CallResolves withWhat the super app does
adera.requestPermission(capability)"granted", "denied", "blocked" or "not_available"One permission per call; there is no batch call. Calls POST /api/v1/me/apps/{app}/permissions/{capability}/request. If the answer has a prompt, shows the dialog with prompt.label and prompt.purpose verbatim and Allow / Deny, then calls PUT .../answer with the promptId and resolves with the new state. If the state is GRANTED, BLOCKED or NOT_AVAILABLE there is no dialog and it resolves at once. A dialog dismissed without Allow or Deny (back button) answers nothing: the Promise rejects with dialog_dismissed and the prompt expires by itself.
adera.getPermission(capability)The same four values plus "not_asked"Never shows a dialog. Calls GET .../permissions and picks the capability (a capability that is not in the list resolves "not_available"). Use it to decide whether to explain first or to show a different screen.
adera.openPermissionSettings(){"permissions": {"location.fine": "granted", ...}} when the user closes the sheetOpens the app's permission sheet from the super app menu (one switch per permission, GET .../permissions, switches call PUT .../permissions/{capability}, the only way out of blocked) and resolves with the states at the moment the sheet closes.
adera.getLocation(options?)Success: {"state": "granted", "location": {"latitude": 9.0054, "longitude": 38.7636, "accuracyMeters": 12, "at": "2026-11-04T09:12:44Z"}}. Not allowed: {"state": "denied"}, "blocked", "not_asked" or "not_available"Never shows a dialog by itself. With {"precision": "fine"} (default) it needs the permission location.fine; with {"precision": "coarse"} it needs location.coarse and returns only {"place": {"countryCode": "ET", "region": "Addis Ababa", "city": "Addis Ababa"}}, never coordinates. It returns a reading only if both our consent and the phone's own location permission are yes, and otherwise says denied or blocked without telling which of the two refused (so the mini app cannot probe the phone). The reading comes from the phone; Adera never stores a position. The phone's own dialog is the system's and comes after ours (the first time).

State names on the bridge are the lower-case form of the API's states: NOT_ASKED becomes not_asked, and so on; NOT_AVAILABLE (staff did not grant the capability to the app) becomes not_available.

Message format

All messages are JSON objects with the marker "adera": 1 (the protocol version). A request has a unique id chosen by the mini app (a string of at most 64 characters), a method and params. The answer repeats the id and has ok true with a result, or ok false with an error object (code, message). A message that is not an object, has no "adera": 1, has an unknown method or a params over 1 KB is answered with an error and nothing else happens.

// mini app -> super app
{"adera": 1, "id": "m_17", "method": "requestPermission", "params": {"capability": "location.fine"}}

// super app -> mini app, success
{"adera": 1, "id": "m_17", "ok": true, "result": {"state": "granted"}}

// super app -> mini app, failure
{"adera": 1, "id": "m_17", "ok": false, "error": {"code": "busy", "message": "A permission dialog is already open."}}

Transport. In a native WebView (the Flutter app) the page posts the JSON string to a JavaScript channel named AderaBridge and the super app answers by calling window.adera._receive(json); window.adera wraps this in the four Promise methods so mini app code never touches the channel. In a web-hosted super app the page uses window.parent.postMessage(message, superAppOrigin) and the super app answers with event.source.postMessage(answer, miniAppOrigin), never with "*".

The origin rule

  • The bridge is injected only for pages whose origin (scheme, host and port) is the origin of the mini app's registered URL (entryUrl) or one of its allowedOrigins, both set by staff in the backoffice. Navigating to any other origin removes the bridge before the page loads; a page of another origin never sees window.adera.
  • Every message is checked again: in a WebView the host compares the origin of the frame that sent it, and a message from a frame whose origin is not in the list (for example an embedded advertisement) is ignored with no answer. Answers go only to the registered origin.
  • The super app sends the user's session to the backend itself. The mini app never receives the session token, the user's id or the launch scopes through the bridge.

Rules the super app must keep

  • One dialog at a time. A second requestPermission while a dialog is open is rejected with busy; there is no queue and no batch.
  • The text is ours. The dialog shows only label and purpose from the server, as plain text. The mini app cannot change it, add to it or style it.
  • The server decides. Never answer from a cached state: requestPermission always calls the server first (the state may have changed in the menu or been blocked), and getLocation checks the consent on the server before it reads the phone.
  • Show no dialog at launch. A mini app opening is POST .../launch only.
  • Limit calls: at most 30 requestPermission per minute per mini app (the gateway also limits that endpoint to 30 per minute per address). Beyond it the bridge rejects with too_many_requests.

Status

This specification is written, but the bridge is not built (the super app is a separate project). Everything behind it exists and is captured against the running stack: the endpoints it calls, the launch token and the backend profile call. The samples in this specification (the messages above) are protocol examples, not captures.
