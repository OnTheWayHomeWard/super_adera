Mini-app permissions and the bridge

How a mini app gets data about a user and from the device, how the user decides what it may have, and how Adera stops it from taking more: for super-app and mini-app developers.

Audience

Two groups. Super-app developers (the Adera app team and backend colleagues) who build the permission dialog, the menu sheet, the settings screen and the bridge. Mini-app developers (partners) who need to know how their page asks for a permission and how their backend reads what the user allowed. Staff configuration is covered in one short page. Nothing here links outside this folder: it can be zipped and shared on its own.

Overview

A mini app is third-party code running inside the Adera app. It must not be able to describe its own powers or take data the user did not allow. So there are three gates, all enforced by the Adera backend, in this order: (1) did Adera staff grant the capability to the mini app, and is the app live; (2) did this user say yes to this capability for this app, and is it still yes; (3) is the request for exactly what that capability covers. The user answers one permission at a time, at the moment of need (like Android), never all at launch, and a second refusal in a row blocks the permission until the user switches it on in the menu.

Why it is built this way

The user must be able to say no to one thing and yes to another, change their mind, and leave an app completely, without the app being able to nag, to fake an answer, or to read data through a script that a bad advertisement injected. So the server decides, the page only asks, and personal data goes to the mini app's backend with a signed request, not through the browser.

Conventions

  • Base URL. Everything goes through the gateway: $GATEWAY is http://127.0.0.1:9080 on the dev stack, the public API host later. Paths below are exactly what a client calls.
  • Authentication. User endpoints: Authorization: Bearer $TOKEN (the user's session token from sign-in). Staff endpoints: a staff session at assurance level aal2. The mini app's backend: signed requests (ADERA-SIG-1, with its private key) and Adera's public key from /.well-known/jwks.json to verify the launch token and callbacks.
  • Errors have the shape {"error": "<code>", ...details}; validation errors add fields ({"error": "validation_failed", "fields": {"state": "..."}}). Errors produced by the gateway itself (an empty 401, a 429 page) do not. See "Error codes".
  • Ids and timestamps. The mini app is {app}: its UUID or its slug. A capability is a key such as location.fine. Timestamps are ISO-8601 UTC. The user is known to a mini app only by a pseudonymous id u_p_... (different in every app), never by the real user id.
  • Languages. The purpose sentence is shown in the user's language (en, am, om), falling back to English and then to the capability's default sentence.

Glossary

TermMeaning
Super appThe Adera app that hosts mini apps.
Mini appA partner's service listed in the super app: a web page in a WebView plus the partner's own backend.
CapabilityOne thing a mini app can be allowed to ask for: user.basic, user.full_name, user.contact, user.address, location.coarse, location.fine, pay.request, notify.inapp, notify.sms, notify.email.
GrantStaff's decision that an app may ask for a capability (gate 1). Does not give the app anything by itself.
Consent / permissionThe user's answer for one capability of one app (gate 2): NOT_ASKED, GRANTED, DENIED, BLOCKED.
PurposeOne sentence staff approved per granted capability, shown to the user in the dialog ("Find a driver near you.").
PromptThe one-time ticket the server issues when a dialog is allowed; an answer needs it.
Launch tokenA five-minute signed token the super app gives a mini app when the user opens it.
AliasThe user's pseudonymous id for one mini app (u_p_...).
BridgeThe JavaScript the super app injects into the mini app's page to ask for permissions and a location reading.
