Mini app developers

Asking for a permission from the page, verifying the launch token, reading what the user allowed, sending notifications and handling the callbacks.

Overview

For mini-app developers (the partner's frontend and backend). When a user opens your mini app the Adera app loads your registered URL with a launch token. Your page asks for permissions through window.adera (the bridge), at the moment it needs them. Your backend verifies the token and then reads what the user allowed with a signed request. The backend can never open a dialog.

In the page: asking at the moment of need

Opening your mini app shows no dialog. Ask when the user does the thing that needs the permission, one permission per call.

// "Find a ride" was tapped
const state = await adera.getPermission("location.fine");      // no dialog ever
if (state === "blocked") {
  showText("Location is switched off for this app.");
  button("Open settings", () => adera.openPermissionSettings());   // the only way out of blocked
} else {
  if (state === "denied") await explainWhyYouNeedLocation();       // you get ONE more dialog: explain first
  const answer = await adera.requestPermission("location.fine");   // "granted" | "denied" | "blocked" | "not_available"
  if (answer === "granted") {
    const r = await adera.getLocation();                           // never shows a dialog by itself
    if (r.state === "granted") findDriversNear(r.location);
  } else {
    showText("We cannot find a driver without your location.");
    button("Allow", () => adera.requestPermission("location.fine"));   // asks again only while the state is "denied"
  }
}

Specification example: the bridge is not built yet, so this snippet is not captured or run; the endpoints behind it are real (next page).

What to do with each answer

ValueMeaningWhat your page does
grantedThe user allowed itUse it. It can be switched off later in the menu: check again before each use.
deniedThe user said no onceYou may ask once more. Explain why first (a screen of your own), then requestPermission.
blockedThe user said no twiceDo not ask again (you would get blocked with no dialog). Show what the user can still do, and a button calling openPermissionSettings().
not_asked (getPermission only)Never askedShow your own explanation, then ask.
not_availableAdera staff did not grant your app this capabilityIt will never work: contact Adera, do not show a feature that depends on it.

You decide what a refusal means for your product ("we cannot continue without your location"); the server does not know which permissions your app cannot live without, and there is no "required" flag.

In the backend: the launch token

The URL your page is loaded with ends in ?launch=<token>. Send it to your backend and verify it before you trust anything. It is an RS256 JWT signed with Adera's key; the public key is at /.well-known/jwks.json (the kid in the token header names the key). Decoded claims of a real token from the dev stack:

header  {"alg": "RS256", "typ": "JWT", "kid": "adera-sig-202610"}
claims
{
  "iss": "adera",
  "aud": "4e831b72-a33b-4d93-a7ba-65e19b9dbd0a",
  "sub": "u_p_d1efd341d635c27f071db27f347e5062",
  "env": "dev",
  "scopes": [
    "user.basic"
  ],
  "iat": 1793827924,
  "exp": 1793828224,
  "jti": "b9eee4f0-74c6-40ed-9ae6-d984a20635b1"
}
ClaimWhat to check
issAlways adera.
audYour app's id. Reject a token for another app.
subThe user's pseudonymous id for your app: use it in the profile call and in notification requests. Never the real user id.
envdev or prod: the environment that issued it.
scopesWhat the user allowed when the app opened. A hint only: consent is re-checked on every data call.
iat, expFive minutes. Reject an expired token; ask for a new launch instead of keeping tokens.
jtiA random id (you may refuse a replay).

Two runnable examples are in the examples/ folder next to these pages (Python needs pip install cryptography; Node.js 18 or newer needs nothing). They fetch the JWKS, check alg is RS256 (never accept none), verify the signature, then check iss, aud, exp and env:

ADERA_BASE=https://api.example ADERA_APP_ID=<your app id> python examples/verify_launch_token.py "$LAUNCH_TOKEN"
ADERA_BASE=https://api.example ADERA_APP_ID=<your app id> node examples/verify-launch-token.js "$LAUNCH_TOKEN"

In the backend: reading what the user allowed

GET /v1/users/{alias}/profile with a request signed with your private key (ADERA-SIG-1; the signature covers the path with its query string; the partner guide has the signing clients). It returns the pseudonymous id, granted (the permissions the user allowed) and only the fields of those permissions: fullName (user.full_name), phone and email (user.contact, each only if the user has one), address (user.address: countryCode, region, city, never coordinates). Fields the user did not allow are absent, never null. The optional query ?fields=user.full_name,... says what you need: if one of them is not allowed you get 403 consent_required naming it, so you know to send the user back to your page to ask. AnswerWhat your backend does
200 with granted and fieldsUse only those fields; keep only what you need; never log the values. An absent field is not allowed (or the user has none): not an error.
403 consent_required, state NOT_ASKEDThe user was never asked: tell your page to call requestPermission, then retry.
403 consent_required, state DENIEDThe user said no once: your page may explain and ask once more.
403 consent_required, state BLOCKEDDo not ask again; offer a way on without it or a button to the permission settings.
403 consent_required for user.basicThe user disconnected. Delete what you hold about them as agreed in your terms.
403 capability_not_grantedAdera staff did not grant that capability to your app: ask Adera.
422 user_unreachableUnknown id (or one of another app), deleted or suspended user. Do not retry.
403 wrong_environmentYour key belongs to the other environment than the deployment you called.

In DEV the synthetic user u_p_test_ok answers the profile with fake data, and u_p_test_noconsent, u_p_test_denied, u_p_test_blocked show the three refusal states; u_p_test_unreachable answers 422. In PROD they are refused.

Sending notifications

A notification goes out only while the user's consent for the channel (notify.sms, notify.email or notify.inapp) is GRANTED. Otherwise your request is refused and nothing is sent. Real answers:

POST /v1/notifications     (the user refused SMS once)

HTTP 403
{
  "error": "consent_required",
  "capability": "notify.sms",
  "state": "DENIED"
}

POST /v1/notifications     (after the user switched SMS on in the menu)

HTTP 202
{
  "notificationId": "96f9f099-99e4-4846-b30b-afbc561a61ee",
  "externalId": "e2e-perm-8de17d-sms-3",
  "status": "QUEUED",
  "channel": "SMS",
  "environment": "DEV",
  "createdAt": "2026-11-04T21:32:05.450406Z",
  "expiresAt": "2026-11-05T21:32:05.439496Z"
}

Do not retry in a loop: it answers the same until the user changes the permission. The channel is the one Adera picks from your template and the user's contact data; there is no fallback to another channel the user allowed. A user who switches the channel off after you were accepted but before delivery makes the message end SUPPRESSED (reason recipient_opted_out).

Callbacks: the user changed a permission or disconnected

If Adera staff set a callback address for your app and environment, Adera POSTs a signed callback when the user changes a permission or disconnects. They use the same headers and signature as notification status callbacks (X-Adera-Event, X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature, Idempotency-Key): verify the signature with Adera's public key over ADERA-SIG-1, the timestamp, POST, the path and query of your URL and the body hash joined with newlines. Answer any 2xx within 8 seconds; failures are retried for 24 hours.

X-Adera-EventBody fields
user.consent_changedevent, alias, capability, state, at, environment
user.disconnectedevent, alias, capabilities (everything taken back), at, environment

If you kept the user's name, contact or address, delete it when you get user.disconnected. Delivery is at least once and a late event can arrive after a newer one: de-duplicate on Idempotency-Key and order by at. Limits and good manners

  • Ask only for what the feature needs, at the moment it needs it, with a screen of your own that explains why before the second ask.
  • Never loop on a refusal (denied, blocked, 403 consent_required).
  • Treat everything from the profile as personal data: keep the minimum, delete on user.disconnected, never log values.
  • The dialog request is limited to 30 per minute per address; the profile call shares the partner API limit (600 per minute).
