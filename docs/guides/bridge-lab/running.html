Running and registering it

Start the Bridge Lab container next to the Adera dev stack and register the Bridge Lab mini app through the admin API.

Overview

Everything lives in the repository folder bridge-lab/: a plain HTML/CSS/JavaScript front end, a small Node.js backend with no dependencies, one container, its own compose file, and a registration script. It joins the network of the running Adera stack and never starts, stops or changes the Adera services.

Why localhost

The registry accepts an entryUrl only when it is https:// or http://localhost / http://127.0.0.1. A plain LAN address such as http://192.168.1.20:8095 is refused, so on the laptop the phone reaches Bridge Lab through adb reverse.

Start it

cd bridge-lab
python3 -I seed.py                 # once; safe to repeat
docker compose up -d --build       # the bridge-lab container, on the adera_default network
docker compose logs -f bridge-lab  # its own log
docker compose down                # stop it (only Bridge Lab)

After a new seed run, restart the container (docker compose restart) so it reads the new configuration.

What the seed script registers

seed.py signs in as a temporary ADMIN made for the run (a random tempstaff-...@adera.local account with its own authenticator, removed when the script ends; the bootstrap admin account is never used) and calls the real admin API through the gateway. Each step reads first and changes only what differs.

StepAdmin API callResult
The appPOST /admin/api/v1/apps (if missing), PATCH when fields differ, logo uploadMini app bridge-lab, "Bridge Lab", support e-mail and logo (both needed for LIVE).
Where it livesPATCH /admin/api/v1/apps/{id}entryUrl http://localhost:8095/?entry=1; allowedOrigins http://localhost:8095, http://localhost:8096.
CapabilitiesPUT .../capabilities/{capability} for every key of GET /admin/api/v1/capabilitiesAll ten granted, each with a one-sentence purpose.
DEV environmentPUT .../environments/DEVAllowed caller addresses (the docker ranges) and the callback URL.
Partner keyPOST .../keysAn RSA key pair is generated in bridge-lab/.local/; only the public half is registered.
TemplatesPOST /admin/api/v1/notification/templatesbridge-lab-inapp (IN_APP) and bridge-lab-direct (DIRECT: SMS or e-mail).
StatusPOST .../statusLIVE. A KILLED app needs --revive (a temporary SUPER_ADMIN for that one call).
Configuration(file)bridge-lab/.local/config.json: app id, key id, template ids, labels and purposes. Gitignored, with the private key.

Options (or environment): --gateway (ADERA_GATEWAY), --entry-url (BRIDGE_LAB_ENTRY_URL), --alt-origin (BRIDGE_LAB_ALT_ORIGIN), --callback-url (BRIDGE_LAB_CALLBACK_URL), --gateway-internal, --revive. The entry URL must be https (or localhost): the registry refuses anything else.

Staging server

On the staging server Bridge Lab is served over https by a reverse proxy: https://bridge-lab.157-245-133-250.sslip.io (port 8095, the entry origin), https://bridge-lab-alt.157-245-133-250.sslip.io (port 8096, the second allowed origin) and https://bridge-lab-foreign.157-245-133-250.sslip.io (port 8095 again, an origin that is deliberately not registered).

Register it on the server (the temporary ADMIN needs the stack's local ports):

python3 -I bridge-lab/seed.py   --entry-url "https://bridge-lab.157-245-133-250.sslip.io/?entry=1"   --alt-origin https://bridge-lab-alt.157-245-133-250.sslip.io

The container there needs BRIDGE_LAB_PUBLIC_URL, BRIDGE_LAB_ALT_URL and BRIDGE_LAB_FOREIGN_URL set to those three https addresses, ADERA_STORAGE_PREFIX=http://157.245.133.250:9000/adera-media/, ADERA_STORAGE_INTERNAL=http://rustfs:9000, and bridge-lab/.local mounted at /app/.local.

Callback address

http://bridge-lab:8095/adera/events is accepted: the registry allows http:// callback addresses on a DEV deployment, and the notification service delivers to a private address over http on port 8095 only while private callbacks are allowed (dev mode). Otherwise a callback must be https, on port 443 or 8443, on a public address: the public https://bridge-lab.157-245-133-250.sslip.io/adera/events would do.

Images on an https page

Banner and logo links are signed plain-http storage links. Bridge Lab loads them through its own /lab/img proxy, which serves only addresses under ADERA_STORAGE_PREFIX and keeps the link's Host header (the signature covers it), so the page has no mixed content.
