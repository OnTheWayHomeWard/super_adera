Running a test, verdicts and logs

The three screens (list, test, report), how a verdict is reached, and how to read the two logs.

The test list

Tests grouped by area, each with its status icon (○ not run, ✅ pass, ❌ fail, 🚧 not developed yet, ⏭️ skipped) and whether it needs a person. A progress bar and the counts are at the top; chips filter by status.

One test

  • Goal and Before you start; a link to the specification section.
  • Automatic steps (⚙️) have a Run step button. While a step waits for a person (a dialog to answer, a sheet to close) a yellow box says what to do and a countdown shows the time left: two minutes for a dialog, five for the settings sheet, seven for the expired-prompt test. Everything else must be answered within 10 seconds.
  • Instructions (👤) are for a person: "Tap Deny", "Staff: set Bridge Lab to PAUSED".
  • Questions (❓) take a Yes or No ("Did a dialog appear?").
  • At the end: Bridge Lab's suggestion, the four status buttons and a note.

How a step's verdict is reached

What happenedVerdictShown as
No window.adera on the pagenot developedThe bridge is not injected, with the injection and transport rules to build.
window.adera exists but the method does notnot developedThat method is not built, with its rules from the specification.
No answer within the limitnot developedThe super app did not answer, with the answer format to build.
An answer arrived but with an id no request hadfailId mismatch; the stray answer is shown.
An answer without "adera": 1, an unknown state or error code, a bad location shapefailThe broken rules are listed.
The method threw or returned no Promisefail
The expected valuepassExpected and actual side by side.
A precondition is not met, or the behaviour is not specifiedinfoWhat to do to get there, or what was recorded.

The test's suggestion is Fail if any step failed, else Not developed if any step was not developed, else Pass when every judged step passed. The person always decides.

The two logs

A drawer at the bottom of every screen; it opens with Logs.

TabWhat it shows
BridgeEvery message: page to super app (↑) as posted to AderaBridge, super app to page (↓) as passed to window.adera._receive, and each method call and its result at API level. Times, round trip in ms, pretty JSON, broken rules in red, unsolicited for answers that match no request. Filter by method, copy, download JSON.
BackendA live stream from Bridge Lab's server: every launch-token check (claims, each check, why it was refused), every signed partner call (method, path, signed headers without the signature, status, body with personal data masked, X-Request-Id, trace id, whether Adera's response signature verified, links to the trace and the logs in Grafana) and every callback received (headers, signature result, body). The last 500 entries per user are kept, so reopening shows the history.

The Banners screen

Banners in the top menu fetches the public banner list per placement (and optionally category and limit) through the Bridge Lab backend, so every request shows in the Backend log. Each banner shows its image (the size that fits the screen, loaded through the image proxy, with the size actually received), title and subtitle in the chosen language with an "en fallback" mark, placement, category, action type, target, the linked app with its logo, and any field that breaks the documented shape. Tapping a banner shows what the super app should do for its action type (MINI_APP: launch and open the route; INTERNAL: the deep-link router; EXTERNAL: a browser; NONE: nothing). The Banners test group uses the same data.

The report

Counts per status, What the super app still needs to build (every test or step marked not developed, with the rule to build and the specification link), then every group with each test's status and note. Download as Markdown or JSON, copy the Markdown, or Upload to the Bridge Lab server: phone WebViews often cannot save files, so the upload gives two addresses to open on the laptop.
