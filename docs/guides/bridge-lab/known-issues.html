Known issues and decisions

Limits of the tool, and the choices made where the brief or the specification left room.

Limits

  • Wrapping host objects. Bridge Lab wraps AderaBridge.postMessage and window.adera._receive to log the raw messages. If the super app's objects cannot be changed (a frozen object, a native host object) the Bridge log falls back to method calls and results, and says so.
  • Raw message tests (E01, E02, the last step of E03) need the AderaBridge channel to be reachable from the page; without it they are Not developed.
  • Origins. The foreign origin is the same server under 127.0.0.1; the second allowed origin is port 8096. With adb reverse both ports must be reversed.
  • No network test (SA05). Over USB with adb reverse the phone still reaches the laptop in airplane mode; use Wi-Fi to the laptop for that one.
  • Push (D06) cannot be tested on the dev stack (fake push provider).
  • Quota (N08) uses up the test user's three SMS for the day.
  • Too many requests (E07) also uses the gateway's 30 dialog requests per minute for your address: other dialog tests fail with too_many_requests for a minute afterwards.
  • Sessions live in the Bridge Lab server's memory: restarting the container forgets the backend log and the uploaded reports (results on the phone stay).
  • The list of sessions (/api/sessions) and the logs are not protected: Bridge Lab is a development tool. Personal data in the backend log is masked.

Decisions

  • Not an auto-runner. Each step runs only when a person taps Run step; a test is marked by a person.
  • Time limits. 10 seconds without an answer means "the super app did not answer". Steps where a person must act wait longer (two minutes for a dialog, five for the settings sheet, seven minutes for the expired-prompt test).
  • A replayed launch token is a warning, not a refusal, so reloading the page keeps working; test L09 checks that it is noticed.
  • Partner calls always use the alias of the verified launch token. Only the DEV synthetic users and one unknown-alias probe can be chosen freely.
  • Every partner call carries a W3C traceparent, so its trace id is known before the answer; it was checked that the trace shows up in Tempo with the gateway and notification-service spans.
  • Rejections: the specification does not say what object a rejected Promise carries. Bridge Lab accepts an Error with code, an object {code, message} or a string, and records the shape.
  • Not specified, but tested: getLocation with location services off (LO07) or unknown options (LO08), a notification's deep link (D05), what a reload does after the token expired (SA07), the Back button (SA08), language and theme (SA09), external links (O05), the web-hosted super app (B11), what happens after Disconnect (S07). Each records what happens and proposes what the super app should do.
