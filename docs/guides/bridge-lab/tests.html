The full test list

Launch (12)

IdTestKind
L01Opened with a launch token in the URL
The super app opens a mini app by calling POST /api/v1/me/apps/{app}/launch and loading the returned url, which ends in ?launch=<token>.		auto
L02The registered entry URL is kept (path and query)
The launch answer's url is the registered entryUrl with the token appended (& when the entryUrl already has a query). The super app must load it as is, not rebuild it.		auto
L03The backend verifies the token against the JWKS
The mini app's backend verifies the RS256 signature with Adera's public key (kid from /.well-known/jwks.json) and checks iss, aud, exp and env.		auto
L04The token is fresh: 5-minute life, right environment
exp - iat = 300 s, iat is the moment of opening, env is this deployment's (dev here).		auto
L05No permission dialog appears when the app opens
Opening a mini app is POST .../launch only. Permissions are asked at the moment of need, never at launch.		human
L06The scopes in the token match the permission states
scopes = the capabilities the user allowed at the moment of opening. A hint only, but right after opening they must match what getPermission says.		auto
L07Tampered and foreign tokens are rejected
The backend must refuse a changed signature, changed claims, alg none, an HMAC alg, an unknown kid, garbage, and a token for another app.		auto
L08An expired token is rejected
Tokens live 5 minutes; a mini app backend must refuse an expired one and ask for a new launch.		human + auto
L09A replayed token (same jti) is noticed
jti is a random id; a backend may refuse a replay. Bridge Lab flags it (a warning, so a reload still works).		auto
L10Every opening gets a new token
Each opening calls launch again: a new jti and a new iat.		human + auto
L11The page receives no session token, user id or scopes from the super app
The super app keeps the user's session to itself; the page gets only the launch token in the URL.		auto
L12Opening Bridge Lab while signed out not specified
A launch needs the user's session: a signed-out user signs in first, then the app opens with a token.		human

Bridge basics (11)

IdTestKind
B01window.adera is injected
The super app injects window.adera into the page of the registered origin.		auto
B02The four methods exist and return Promises
requestPermission, getPermission, openPermissionSettings and getLocation, each returning a Promise.		auto
B03Transport: the AderaBridge channel and window.adera._receive
In the Flutter WebView the page posts JSON strings to the JavaScript channel AderaBridge and the super app answers through window.adera._receive(json).		auto
B04Request messages follow the format
A request is {"adera":1,"id":"<at most 64>","method":"...","params":{...}} posted as a JSON string.		auto
B05Answer messages follow the format
An answer repeats the id and has "ok": true with "result", or "ok": false with "error": {code, message}; "adera": 1.		auto
B06Parallel calls are matched by id
Several calls in flight at once each get their own answer (the id ties them together).		auto
B07The bridge is still there after a reload
Reloading the page (same origin) gets window.adera again.		auto
B08The bridge is still there after same-origin navigation
Navigating to another page of the same origin keeps the bridge.		auto
B09Unsolicited messages from the super app are logged and checked
The spec defines answers only: every message from the super app answers a request. Anything else is listed here.		auto
B10getPermission never shows a dialog
getPermission only reads; it never opens a dialog, for any capability.		auto + human
B11Web-hosted super app (iframe + postMessage) not specified
In a web-hosted super app the page talks to window.parent with postMessage. Nothing says who provides window.adera inside a cross-origin iframe.		auto

Permissions (12)

IdTestKind
P01user.basic is granted with no dialog
The pseudonymous id needs no dialog: requestPermission("user.basic") resolves "granted" at once (unless the user disconnected).		auto + human
P02getPermission says not_asked before the first ask
A capability never asked is not_asked.		auto
P03Ask, Allow -> granted (user.full_name)
The full dialog round: request -> dialog with Adera's text -> Allow -> answer -> "granted"; the backend then reads the name and gets a callback.		auto + human
P04The dialog shows Adera's approved label and purpose verbatim
The dialog shows only prompt.label and prompt.purpose from the server, as plain text; the mini app cannot change or style it.		auto + human
P05Ask, Deny -> denied (user.contact)
The first no sets DENIED (count 1): the page gets "denied", the backend gets 403 consent_required DENIED, and a callback.		auto
P06Ask again after a denial, Deny -> blocked
After one no the dialog may be shown once more; the second no sets BLOCKED.		auto + human
P07blocked answers at once with no dialog
A blocked permission resolves "blocked" with no dialog; only the menu can unblock it.		auto + human
P08The server decides: a switch changed in the menu is seen at once
requestPermission always asks the server first (never a cached state).		auto + human
P09not_available for a capability the app was not granted
A capability staff did not grant never gets a dialog: requestPermission and getPermission resolve "not_available".		auto + human
P10Staff remove a grant while the app is open
Gate 1 is checked on every call: a capability staff remove becomes not_available at once (within about 15 s).		human + auto
P11The backend sees the same consent
What the page sees and what the backend's profile call returns agree (the same three gates).		auto
P12One permission per call (no batch)
There is no batch call: an array is not a capability.		auto

Settings sheet (9)

IdTestKind
S01openPermissionSettings() opens the sheet and resolves on close
The page can open its own permission sheet; the Promise resolves with the states when the sheet closes.		auto + human
S02The sheet lists exactly the app's granted capabilities
The sheet lists only what staff granted the app (all 10 for Bridge Lab), with Adera's labels.		auto + human
S03Unblock only from the menu
blocked cannot be asked again; the menu switch is the only way out, and it sets GRANTED with the count back to 0.		auto
S04Switch off in the sheet -> denied, and the dialog may be shown again
Switching off sets DENIED with count 0, so the mini app may ask again later (the dialog appears).		auto + human
S05user.basic has no switch of its own
The menu cannot switch user.basic off alone (the API answers 409 use_disconnect); Disconnect is the way.		human
S06The sheet opened from the super app's menu; the page re-checks
The menu sheet always works, also without the page asking. Nothing tells the page that a permission changed; the page must re-check (getPermission).		auto + human
S07Disconnect
Disconnect sets everything to DENIED (count 0), sends user.disconnected to the partner and the profile is refused.		human + auto
S08Reopening after Disconnect reconnects user.basic
A new launch after Disconnect turns user.basic back on (callback user.consent_changed user.basic GRANTED); the other permissions stay denied.		human + auto
S09The super app's settings screen lists Bridge Lab
GET /api/v1/me/permissions feeds a settings screen: every app that holds a permission, with what it can see.		human

Location (8)

IdTestKind
LO01getLocation() before consent -> not_asked, no dialog
getLocation never shows a dialog by itself; without consent it says the state.		auto + human
LO02Fine location after consent
After location.fine is granted, getLocation() returns {"state":"granted","location":{latitude,longitude,accuracyMeters,at}}; the phone's own dialog comes after ours the first time.		auto + human
LO03Coarse location gives a place, never coordinates
With {"precision":"coarse"} getLocation needs location.coarse and returns only {"place":{countryCode,region,city}}.		auto
LO04precision coarse without location.coarse consent -> not granted
Coarse needs location.coarse (location.fine does not count).		auto
LO05Phone permission off -> denied/blocked without saying which
A reading needs both our consent and the phone's permission; otherwise denied or blocked, without telling the mini app which of the two refused.		auto + human
LO06Our consent switched off -> no reading
getLocation checks the consent on the server before reading the phone (no cached yes).		auto + human
LO07Location services off on the phone not specified
Not specified: what getLocation answers when the phone's location services are off.		auto + human
LO08Unknown options not specified
Not specified: getLocation with an unknown precision. invalid_params would match the rest of the spec.		auto

Profile (backend) (8)

IdTestKind
PR01Profile with only user.basic
GET /v1/users/{alias}/profile, signed: 200 with the alias (= the token's sub) and granted.		auto
PR02Adera's response signature verifies
Every API answer is signed by Adera (ADERA-SIG-1-RESPONSE over status, body hash and the request's signature).		auto
PR03?fields= for a permission not allowed -> 403 consent_required
A backend that needs a field says so with ?fields=; if the user did not allow it the answer is 403 with the capability and the state the page sees.		auto
PR04Full name after the user allowed it
With user.full_name granted, the profile carries fullName.		auto
PR05Contact and address after the user allowed them
user.contact gives phone and email (each if the user has one); user.address gives the saved place (country, region, city).		auto
PR06DEV synthetic users
On DEV, u_p_test_ok answers fake data, u_p_test_noconsent/denied/blocked refuse with their state, u_p_test_unreachable answers 422.		auto
PR07Unknown alias -> 422 user_unreachable
An id never issued to this app is unreachable (never 404, never a hint whether the person exists).		auto
PR08Bad partner signatures are refused
Every partner call must be signed with the app's key: wrong key, old timestamp, unknown key id, missing headers are refused.		auto

Notifications (9)

IdTestKind
N01Bridge Lab's approved templates
A partner sends only staff-approved templates; GET /v1/templates lists them.		auto
N02Default deny before notify.inapp is allowed
A notification goes out only while the channel's consent is GRANTED; NOT_ASKED is refused too.		auto
N03In-app message after the page asked for notify.inapp
The page asks for notify.inapp; then the backend's message is accepted (202), delivered (SENT) and shows in the bell.		auto + human
N04SMS after notify.sms was allowed
A DIRECT template goes by SMS when the user has a phone and SMS is allowed (dev: console SMS, no real message).		auto + human
N05SMS refused -> 403, no fallback to email
If the user did not allow the chosen channel the request is refused; it is never re-sent by another channel.		human + auto
N06Muting SMS in the super app is a consent change
The app's mute switches are the notification consent: muting SMS sends user.consent_changed notify.sms DENIED and the next SMS is refused.		auto + human
N07Idempotency on externalId
The same request again answers 200 replayed:true (nothing sent twice); the same externalId with other content is 409.		auto
N08Daily SMS quota -> 429 quota_exceeded
Default SMS limit: 3 per user per day; the next is 429 quota_exceeded max_per_user_per_day. Uses up today's SMS for this user.		auto
N09Final status callback notification.status
With a callbackUrl Adera POSTs the final status, signed.		auto

Callbacks (6)

IdTestKind
C01The receiver refuses forged callbacks
Bridge Lab's receiver checks Adera's signature (JWKS) before trusting a callback; an unsigned or wrongly signed one is refused.		auto
C02user.consent_changed arrives after a change
Every real change (dialog answer, menu switch, mute) sends a signed user.consent_changed to the app's callback address.		human + auto
C03Every callback received verifies against the JWKS
All callbacks (consent and status) are signed with Adera's key.		auto
C04Duplicate deliveries are ignored
Delivery is at least once: de-duplicate on Idempotency-Key.		auto
C05user.disconnected lists everything taken back
One user.disconnected per Disconnect, with capabilities = everything taken back (user.basic included).		auto
C06Events are ordered by at
A late event can arrive after a newer one; a receiver orders by at. Bridge Lab reports the order it saw.		auto

A killed app behaves like a paused one for the user; only a SUPER_ADMIN can revive it.		human + auto

Bridge error codes (9)

IdTestKind
E01invalid_message
A message that is not a JSON object, has no "adera": 1, a missing or too long id, or params over 1 KB is answered with invalid_message and nothing else happens.		auto
E02unknown_method
A method other than the four is answered with unknown_method.		auto
E03invalid_params
A capability that is not a key like location.fine is invalid_params (the API's 400 validation_failed).		auto
E04busy: a second request while a dialog is open
One dialog at a time: a second requestPermission while a dialog is open is rejected with busy; no queue.		auto
E05dialog_dismissed: the dialog closed with Back
A dialog dismissed without Allow or Deny answers nothing: the Promise rejects with dialog_dismissed and the state does not change.		auto
E06prompt_expired: answered after 5 minutes
A prompt lives 5 minutes; answering later gives 409 prompt_expired -> the bridge rejects prompt_expired; the mini app may ask again.		auto
E07too_many_requests: 31 calls in a minute
At most 30 requestPermission per minute per mini app (the gateway also allows 30 per minute); beyond that too_many_requests.		auto
E08Every error has a known code and a message, and no personal data
Errors are {"code", "message"} with codes from the table; internal_error and the others never carry details of the user or the phone.		auto
E09internal_error
internal_error covers anything else (5xx); a mini app cannot provoke it. E08 checks that no error leaks details.		auto

Origin rule (5)

IdTestKind
O01The bridge is present on the registered origin
window.adera exists on the origin of the registered entryUrl.		auto
O02The bridge is present on another allowedOrigins origin
allowedOrigins lists more origins the mini app may use (Bridge Lab's second origin: port 8096 locally, the bridge-lab-alt host on the server); the bridge is injected there too.		human + auto
O03No bridge after navigating to a foreign origin
Navigating to any other origin removes the bridge before the page loads; a foreign page never sees window.adera and gets no answers.		auto
O04A foreign iframe gets no bridge and no answer
A frame of another origin (an ad, say) inside the mini app: no window.adera there, and its messages are ignored with no answer.		auto
O05External links open outside the mini app not specified
Not specified for mini apps (the banner guide says external pages never open inside a mini-app WebView with the bridge).		auto + human

Banners (12)

IdTestKind
BN01The banner list loads for every placement
GET /api/v1/banners?placement=... answers a list (no sign-in) with Cache-Control public, max-age=60, for each of the four placements.		auto + human
BN02Every banner has the documented fields
title with English, placement, category, actionType, a target that fits the action type, three image sizes.		auto
BN03Only live banners appear, highest priority first
The server leaves out drafts, paused, not-yet-started and ended banners and banners of apps that are not live, and sorts by priority.		auto + human
BN04Image sizes
Each banner has small (480), medium (960) and large (1600, longest side) JPEGs; the app picks the smallest that covers the slot.		auto + human
BN05Title in the user's language, English as fallback
title and subtitle are objects with en (always) and maybe am, om; show the user's language, else English.		auto + human
BN06Category filter, limit and bad values
category= narrows the list, limit= caps it (1 to 50, default 10), a bad placement or limit is 400 validation_failed.		auto
BN07Tap a MINI_APP banner: Bridge Lab opens at its route
A MINI_APP banner for Bridge Lab with route /deeplink/banner: the super app launches Bridge Lab and loads it at that route (same as D02, started from the banner list).		human + auto
BN08Tap an INTERNAL banner: a super-app screen opens
INTERNAL target adera://... goes to the super app's own deep-link router (e.g. adera://wallet); an unknown link does nothing or opens home.		human
BN09Tap an EXTERNAL banner: the page opens in a browser
EXTERNAL https:// target on an approved domain opens in the system browser or an in-app browser tab, never in a mini-app WebView with the bridge.		auto + human
BN10A NONE banner is not tappable
actionType NONE: an image-only announcement; no pressed state, nothing happens.		human
BN11Banners of a paused mini app disappear
A banner whose linked app is not live is left out by the server; the app does not need to check.		auto + human
BN12Images load without mixed content
Banner images are signed plain-http storage links; on an https page Bridge Lab loads them through its own /lab/img proxy, which serves only the storage prefix.		auto
