Forgot password

Recover an account: by email through Kratos recovery (returns a short privileged session), by phone through our reset endpoints, and what is and is not enforced about the channel.

Overview

A user who forgot the password asks for a code and chooses a new password. There are two routes, because Kratos' recovery flow accepts only an email address (its input is validated as an email; a phone number is refused with message 4000040):

Email route (Kratos recovery flow)Phone route (our endpoints)
Code sent tothe email address typed (by email)the phone typed (by SMS)
CallsGET /kratos/self-service/recovery/api, POST /kratos/self-service/recovery?flow=ID twice, then the settings flowPOST /public/v1/password-reset/start, POST /public/v1/password-reset/finish
After the right codeKratos hands over a short privileged session token and a settings flow id; the app sets the new password in the settings flowthe new password is sent in the same call as the code; the account is changed and signed out everywhere; no session is returned: the app signs the user in with the new password
Works foraccounts that have an emailaccounts that have a phone

Which channel is used when the account has both a phone and an email? What is and is not enforced. Kratos sends the recovery code to the address the user types; it has no setting that makes it prefer the phone. So nothing on the server forces the phone: if a user with both types the email in the email route, the code goes to the email. The preference is implemented only by the client: ask for the phone number first and use the phone route; offer "use email instead" only when the user says they have no phone or cannot receive SMS, and use the email route for accounts that have only an email. Recovery by email is therefore always available to anyone who knows the address, also for accounts that also have a phone.

Email route

  1. (optional) POST /public/v1/login-codes/check with the email (see Verification).
  2. GET /kratos/self-service/recovery/api: flow id.
  3. POST /kratos/self-service/recovery?flow=ID with {"method":"code","email":"..."}: the answer is the same whether or not the address has an account (no enumeration): state sent_email and message 1060003. Nothing is sent for an unknown address (the gateway-side config sets notify_unknown_recipients: false).
  4. The user types the code: POST /kratos/self-service/recovery?flow=ID with {"method":"code","code":"..."} on the same flow. Wrong code: 200 with message 4060006. Right code: 200 with continue_with holding set_ory_session_token and show_settings_ui.
  5. Store the token as the session (it is a real session, method code_recovery, and counts as a recent login). Open the settings flow by id and set the password (see Change password, request method: "password").

Kratos limits the wrong tries per code; after that the user must ask for a new code (post the email again).

Phone route

Why it exists: phone-only accounts (the main case in the target market) could not recover through Kratos at all. The code is generated, sent by SMS and checked by our notification service (stored hashed; 10 minutes; 5 wrong tries kill it; single use). The password is then set through Kratos' admin API and every session of the account is revoked.

POST/public/v1/password-reset/startSend the reset code by SMS
Who may call
anyone, no session
Auth
none
Rate limit
5 per 60 s per IP and 5 per 15 minutes per identifier (route password-reset-start)
Implemented by
notification-service

Purpose

Sends an SMS code if the phone belongs to an active app account. The answer is the same 202 for every well-formed phone (registered or not, staff or not), so it cannot be used to find accounts. It also counts against the per-number send limit (the same one the pre-flight check uses): over it the answer is 429 {"error":"too_many_codes","retryAfterSeconds":N}.

Parameters

identifierstringyesa phone like +251911234567; an email is refused with 400

  -H 'Content-Type: application/json' -d '{"identifier":"+251903050827"}'

POST/public/v1/password-reset/finishCheck the code and set the new password
Who may call
anyone, no session
Auth
none
Rate limit
10 per 60 s per IP and 10 per 15 minutes per identifier (route password-reset-finish)
Implemented by

Purpose

Verifies the code and sets the new password in one step, signs the account out everywhere. Unknown phone, wrong code, expired code, used code and "too many tries" all answer the same invalid_code. The password rule is checked before the code is touched, so a too-short password does not use up the code or a try.

Parameters

HTTP/1.1 200 OK

{"status": "password_changed"}

A second use of the same code returns 400 {"error":"invalid_code"}. After success, sign in with the new password (Login); every old session token answers 401. Staff accounts and suspended accounts get no SMS and cannot be reset here.

Does recovery reveal which accounts exist?

No, in both routes: the answers to "send a code" are identical for known and unknown addresses (email: same 200 and message; phone: same 202), and nothing is sent to unknown ones. The remaining signals are timing (a send takes longer than a no-op) and the registration form, which does reveal an existing identifier (message 4000007).
