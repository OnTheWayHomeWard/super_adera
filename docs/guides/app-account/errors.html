Error codes of these APIs

Every error a client can get from the sign-in and account APIs: the five shapes, the full status table, every validation message, the Kratos answers, and the limits.

Overview: five different error shapes

Errors in these APIs come from four places, and they do not look the same. Write one error handler that checks the HTTP status first, then the content type, then the body.

SourceLooks likeWhere
Adera services{"error": "<code>"}, with "fields": {"fieldName": "message"} added for validation_failedeverything under /api/v1/me* that reaches the user service
Gateway user check (forward-auth)401 with an empty body; 403 and 503 with the Adera JSON above (the content type is text/plain even though the text is JSON)before any /api/v1/me* call runs
Gateway rate limit and routing429 with an HTML page; unknown route 404 with {"error_msg":"404 Route Not Found"}any route
Spring framework defaults{"timestamp":"...","status":404,"error":"Not Found","path":"/api/v1/me/nothing"} (here error is a reason phrase, not a code)404, 405, 415 on /api/v1/me* paths
Kratosflow JSON with state and messages (400), or {"error":{"code":...,"status":...,"reason":...}} where error is an objecteverything under /kratos/*
Suggested client logic
  1. Status 429: back off and retry (the body is HTML: do not parse it).
  2. Status 401 from /api/v1/*: the session is gone; sign in again. A 401 from /kratos/* means the same for that token.
  3. Status 403 from /api/v1/* with account_suspended or account_deleted: blocking screen.
  4. Status 5xx or no connection: keep the session, retry with back-off.
  5. Otherwise if the body is JSON with a string error: switch on it; for validation_failed show each fields entry next to its input.
  6. Under /kratos/*: read state and the message ids, not only the status (a 400 may be a success step).
