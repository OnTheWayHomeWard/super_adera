Registration and login with a one-time code

How a person signs up and signs in: the Kratos native flows behind the gateway (/kratos/*), what they cost, what they answer, and what registration creates.

Overview

Adera has no passwords. A person proves they control a phone number or an email address by typing a one-time code, and that single act is both sign-up (first time) and login (every later time). The calls in this page are Ory Kratos' own native app self-service API; Adera wrote no code for them, but configured them (code method only, 30-day sessions, our own SMS/email delivery) and puts them behind the gateway under the prefix /kratos.

Every flow has the same shape: (1) create a flow with a GET, (2) POST the identifier (phone or email) to the flow: Kratos asks our notification service to send a code, (3) POST the same identifier plus the code: Kratos answers 200 with a session_token. The token is what the app stores and sends as Authorization: Bearer on every later call.

Base URL and headers

All paths are relative to the gateway ($GATEWAY, in dev http://127.0.0.1:9080). Submit bodies are JSON with Content-Type: application/json. No Authorization header is needed to sign in. Do not send cookies: the gateway strips Cookie (and Origin on submits) because native flows must not carry them.

Read the answer by state, not only by HTTP status

Kratos' API flows answer 400 when a step needs more input. After you submit the identifier, the normal, successful answer is 400 with "state": "sent_email" (the name says email but it is also used for SMS). Only a 200 carrying session_token means you are signed in.

New or returning user: which flow to start

The app has to choose between registration and login, and a person usually does not know which one applies to them. Recommended sequence (the cheapest in SMS and in rate limit):

  1. Ask for the phone number (or email) once.
  2. Start a login flow and submit the identifier. If Kratos answers state: sent_email (message id 1010014), the account exists: continue with the code step of the login flow.
  3. If it answers state: choose_method with message id 4000035 ("This account does not exist or has not setup sign in with code"), the person is new: no SMS was sent. Start a registration flow with the same identifier and continue there.

Why not registration first: registering an identifier that already has an account still answers "a code has been sent" (anti-enumeration) and really sends an SMS; the failure 4000007 ("An account with the same identifier ... exists already") only appears after the person typed the code. That costs an SMS, a code entry and a restart. Verified: registering a phone number that already had an account sent a registration SMS and answered 1040005.

After you have a session, you can tell a brand-new profile from a finished one with GET /api/v1/me: a new profile has firstName: null, termsAcceptedVersion: null and createdAt equal to updatedAt. Use firstName == null (and your own terms version) to decide whether to show onboarding; the profile endpoint has no separate "is new" flag. A registration response also carries continue_with (a set_ory_session_token action), a login response has continue_with: null.

Login is not anti-enumeration

A login attempt for an unknown identifier tells the caller the account does not exist (4000035), so anyone can test whether a number is registered. This is accepted for now (see Known issues). Do not build UI that exposes it beyond what you need.

The IP limit is shared

The gateway counts per source IP address. Many phones on one mobile-carrier NAT or one office Wi-Fi share the same 10 submits per minute. Handle 429 with a calm "too many attempts, try again in a minute" message and an automatic retry, never an error screen. A single sign-in costs 2 submits (3 for a new user who first tried login).

The real answer when the limit is reached (captured, the body is not JSON):

Pre-flight check: may I ask for a code?

Because the per-recipient limit drops codes silently (Kratos cannot be told), a sign-in screen that says "we sent a code" can be lying. Since 2026-10-26 there is a public check to call before the send-code step:

curl -s -X POST "$GATEWAY/public/v1/login-codes/check" -H "Content-Type: application/json" -d '{"identifier": "+251911900169"}'
HTTP/1.1 200 OK

{"allowed":true,"limitPerHour":5,"limitPerDay":10,"remainingThisHour":4,"remainingToday":9}

When the address has used up its allowance (the sixth request for a phone in the example), the answer is a JSON 429 with the time to wait, also in the Retry-After header (seconds). Do not start the Kratos flow then; show "Too many codes were requested for this address, try again in N minutes":

HTTP/1.1 429 Too Many Requests
Retry-After: 3600

{"error":"too_many_codes","allowed":false,"retryAfterSeconds":3600,"limitPerHour":5,"limitPerDay":10,"remainingThisHour":0,"remainingToday":5}
  • It does not reveal whether an account exists. Every request for an address is counted, registered or not, and the answer has the same shape; an unknown address gets exactly the same numbers as a known one. (Kratos' own "account does not exist" message at login is a separate, known leak.)
  • Each call uses one request of the allowance. Call it once per "send me a code" press, not on every keystroke. Same limits as the real ones (SMS 5/hour and 10/day, email 10/hour and 20/day; the response carries the numbers, so show them instead of hard-coding).
  • Write the identifier the way the user signs in: a phone as +251... (spaces and dashes are ignored), an email in any letter case. Anything else is 400 validation_failed with fields.identifier.
  • Advisory, not a lock. A client that calls Kratos directly skips it, and the notification service still drops the code silently. If the check itself cannot be answered (network, 5xx), carry on and keep the "wait and retry" hint.
  • The gateway limits the check to 10 calls per minute per IP (HTML 429, as on the Kratos submit route).
  • Recommended wording after a successful request: "If this address is registered, we sent a code. It is valid for 5 minutes. If nothing arrives within a minute, wait a little and request a new one (at most N per hour)." The backoffice login page does exactly this.

Identifiers: phone and email

IdentifierField in registrationField in loginRules
Phonetraits.phone_numberidentifierInternational E.164 format with the country code, e.g. +2519XXXXXXXX. National format such as 0911223344 is refused (4000041 "Enter a valid phone number"). Kratos normalises spaces: +251 91 122 3344 was accepted. The code is sent by SMS.
Emailtraits.emailidentifierA valid address; an invalid one gives 4000040 "Enter a valid email address". The code is sent by email (subject "Use code NNNNNN to complete your account registration" or "... to log in").

Send one identifier per registration. The account is identified by whichever you used; a person who registered with a phone and later signs in with an email address gets a different account (there is no account linking, see Known issues). The profile's phone or email is filled from the identifier used at registration; the other stays null.

The SMS text in dev is Your registration code is: 542546 (login: Your login code is: ...) followed by "It expires in 5 minutes." Messages are produced by the notification service, which also sends the email variant; the 6-digit code is the only thing the app has to understand.

What registration creates

  • An identity in Kratos (the account) with the phone or email as its only trait. Its id is the user id.
  • A profile row in the user service: a web hook that Kratos calls right after the identity is created (POST /internal/kratos/after-registration with identityId, email, phone). Defaults: id = the Kratos identity id (so identity.id = X-User-Id = app_user.id = the id field of GET /api/v1/me), status ACTIVE, verificationTier CONTACT, language en, timezone Africa/Addis_Ababa, market ET (US if the phone starts with +1), empty extra.
  • The hook is non-blocking: a slow or stopped user service never prevents a sign-up. If the call is lost, the profile is created on the person's first call to any /api/v1/me endpoint from Kratos' own record (verified: after deleting the row, GET /api/v1/me returned a fresh profile with the phone filled in). So a valid session always ends up with a profile, and the app needs no special handling.
  • A session (hook: session): you do not need a separate login after registering.

Reading codes in the dev stack

In dev (ADERA_ENV=dev) nothing is really sent. The SMS provider is the console and the email provider is Mailpit. Two ways to get the code while testing:

  • GET http://127.0.0.1:8085/dev/messages?to=<url-encoded phone or email> returns a JSON list [{"at","channel","to","subject","body"}] of recent messages to that recipient; take the entry with the greatest at (do not rely on its position in the list: it was newest-first when checked) and read the six digits from body. This endpoint exists only when the notification service runs with dev endpoints on.
  • Emails also show up in Mailpit's inbox at http://127.0.0.1:8025.
  • Messages arrive a fraction of a second after the step-1 answer: poll for up to a few seconds instead of reading once. Make sure the entry you pick is newer than your step-1 request, so you do not pick up an old code.
  • Use a number or address of your own for sign-in tests rather than the seeded "Demo ..." accounts: every code sent counts against that recipient's hourly limit, and other people share those accounts.
