Registration

Create an account with a phone number (email optional) and a password: the Kratos native flow, the rules, what is created, and every error.

Overview

A person creates an account with a phone number (an email is optional, or the only identifier if they have no phone) and a password. Registration does not sign them in: the account must first prove it owns the phone or email by typing a code (see Verification), and only then can they sign in with the password (see Login). Staff of the dashboard use a different account type and cannot register here: the gateway refuses identity_schema=default with 403.

The calls are Ory Kratos' native app self-service flow behind the gateway at /kratos/*: (1) GET a flow, (2) POST the form to the flow id. The flow JSON also carries a ui object (the form description: ui.nodes, ui.messages). It is trimmed in the examples below to what matters; field-level errors are in ui.nodes[].messages, flow-level ones in ui.messages.

Identifiers and password rules

FieldRule
traits.phone_numberinternational format, e.g. +251911234567. At least one of phone or email is required. It is the sign-in name.
traits.emailoptional when a phone is given, otherwise required. Also a sign-in name.
passwordat least 6 characters (message 4000032). Nothing else is checked: no digit or symbol rule, no check against lists of leaked passwords, no similarity check against the phone or email. A password like 123456 is accepted; the client may add its own advice.
methodalways "password"

A phone or email that already has an account is refused with a flow-level message (ui.messages, id 4000007, "An account with the same identifier ... exists already"). This reveals that the address is registered: registration cannot hide that, by design of every sign-up form.

Call sequence

  1. (optional) POST /public/v1/login-codes/check with the phone: may a code be sent? See the pre-flight check.
  2. GET /kratos/self-service/registration/api returns a flow with an id.
  3. POST /kratos/self-service/registration?flow=ID with the phone, optional email and password. 400 = fix the fields and post again to the same flow; 200 = account created.
  4. Read continue_with[0].flow.id and .verifiable_address: the verification flow already exists and a code was sent to that address. Go to Verification.
  5. After verification, sign in (Login). The registration response has no session_token.

What registration creates

  • A Kratos identity with schema user. Its id is the user id everywhere in the API.
  • A profile row in the user service, created right away by a non-blocking web hook (if that call were lost, it is created on the first authenticated call). See Profile.
  • A verification code sent by SMS (phone) or email.

Phone and email together

Both become verifiable addresses. Kratos sends the first code to one of them, named by continue_with[0].flow.verifiable_address (here the phone), and not to both. Read that field instead of assuming. The other address stays unverified until the user signs in with it (see Login and Verification).

What protects registration

  • Gateway: 5 submits per minute per IP.
  • Every verification code goes through the per-recipient send limit (SMS 5 per hour and 10 per day per number; email 10 per hour and 20 per day per address). Over it the message is dropped silently by the notification service (Kratos still answers success): this is why the app should call the pre-flight check first.
  • Accounts are unusable until verified, so typing someone else's number creates an account nobody can sign in to, and the owner receives one SMS per request, within the limit above.
