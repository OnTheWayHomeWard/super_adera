Verification

Prove that the phone or email belongs to the person: the code, the flow, the pre-flight check, and how to get a new code.

Overview

Verification proves that the person controls the phone number (code by SMS) or email address (code by email) of the account. An account cannot sign in until the address it signs in with is verified. The code is 6 digits, valid 10 minutes, and is checked through Kratos' verification flow (method: "code").

Where the flow comes from: registration returns it in continue_with. If the user closes the app before typing the code, the next login attempt is refused with session_verified_address_required, and that error carries a new verification flow and sends a fresh code (see below).

Call sequence

  1. Get the verification flow id: from the registration response (continue_with[0].flow.id) or from the refused login (error.details.continue_with[0].flow.id). Both also say which address got the code: verifiable_address.
  2. The code arrives by SMS or email (text below). Show a code field.
  3. POST /kratos/self-service/verification?flow=ID with {"method":"code","code":"123456"}.
  4. state: "passed_challenge" in the answer = verified. Then the user signs in with the password (Login).

With a phone and an email on one account each address must be verified separately, and the address typed at sign-in must be a verified one. Verifying the phone does not verify the email: signing in with the email afterwards is refused (session_verified_address_required) and starts a verification flow for the email. Kratos picks which address gets the code: read verifiable_address from the flow reference, do not assume it is the one the user typed. The native flow offers no field to choose the address.

The code messages

SMS: Adera: your verification code is 563901. Do not share it with anyone. It expires in 10 minutes. Email subject: Your Adera verification code: 563901, body in English with the same warning. The messages are sent by our notification service (Kratos courier), so the per-recipient send limits apply.

Pre-flight check: may I ask for a code?

Kratos cannot tell the app that a code was not sent because the number hit its send limit (the notification service drops it and answers success, so Kratos retries nothing). To avoid a screen that says "code sent" when nothing was, the app calls this public endpoint before every action that sends a code: registration, asking for a new verification code, email recovery, and phone password reset (that one calls it by itself). It counts the request against the same hourly and daily limit as the real send.

Purpose

Answers whether one more code to this address would be delivered, and how many are left. It answers the same way for every well-formed address, registered or not, so it reveals nothing about which accounts exist. It is advisory: a client that skips it still hits the real limit (silently).

Parameters

FieldTypeRequiredNotes
identifierstringyesphone (+251911234567, spaces and dashes are ignored) or email

Example request

curl -s -X POST "$GATEWAY/public/v1/login-codes/check" \
  -H 'Content-Type: application/json' -d '{"identifier":"+251903050827"}'

Example response

HTTP/1.1 200 OK

{"allowed": true, "limitPerHour": 5, "limitPerDay": 10, "remainingThisHour": 4, "remainingToday": 9}

Over the limit

Status 429 with a Retry-After header and {"error":"too_many_codes","allowed":false,"retryAfterSeconds":3590,"limitPerHour":5,"limitPerDay":10,"remainingThisHour":0,"remainingToday":9} (field values depend on the address; the keys are exactly these). A malformed identifier gives 400 {"error":"validation_failed","fields":{"identifier":"..."}}. The gateway can also answer 429 as an HTML page when one IP calls it more than 10 times a minute. The path keeps the name login-codes for historical reasons; it now guards every code.

Getting a new code

Trigger a login with the password (Login): while the address is unverified Kratos answers the error below and sends a new code (the answer is 403 at the gateway while the body says "code": 400; test the error.id, not the status).

HTTP/1.1 403 Forbidden

{
  "error": {
    "id": "session_verified_address_required",
    "code": 400,
    "status": "Bad Request",
    "reason": "Your account's email or phone address are not verified yet. Please check your email or phone inbox or re-request verification.",
    "details": {
      "continue_with": [
        {"action": "show_verification_ui",
         "flow": {"id": "4fa6a848-0ed6-44b2-b615-116f66406050",
                  "verifiable_address": "+251903050827",
                  "url": "http://localhost:3000/verification?flow=4fa6a848-0ed6-44b2-b615-116f66406050"}}
      ]
    },
    "message": "your email or phone address is not yet verified"
  }
}

The native verification flow has no working "resend" button for phones (its resend form only accepts an email address field), so the app uses this route for phones. For an email-only account the same route applies. The new code is sent to the address named in verifiable_address.

Reading codes in the dev stack

In dev nothing real is sent: SMS go to the console, email to Mailpit (http://127.0.0.1:8025). The notification service also lists them:

GET http://127.0.0.1:8085/dev/messages?to=%2B251903050827      (dev stack only)

[{"at": "2026-10-26T21:41:29.234862277Z", "channel": "sms", "to": "+251903050827", "subject": null,
  "body": "Adera: your verification code is 563901. Do not share it with anyone. It expires in 10 minutes.\n"}]

The list is newest first. Codes are sent a moment after the request, so poll for a message newer than the one you saw before. The endpoint does not exist in production.
