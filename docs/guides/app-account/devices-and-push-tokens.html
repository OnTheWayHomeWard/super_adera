Devices and push tokens (FCM)

Register the phone's FCM token so the platform can push to it: registration, rotation, listing, removal, and what logout does.

Overview

For Adera to push a notification to a phone, it must know that phone's Firebase Cloud Messaging (FCM) token and which user it belongs to. The app tells the server with PUT /api/v1/me/devices. A "device" here means one installation of the app that can receive push. When a mini app sends a notification to a user, the platform delivers it to all of that user's active devices.

Method and pathPurpose
PUT /api/v1/me/devicesregister this installation, or refresh its token and details (idempotent)
GET /api/v1/me/deviceslist my active devices
DELETE /api/v1/me/devicesremove a device (by token or installation id)
POST /api/v1/me/logoutsign out and remove this device's token in one call (see Session and logout)

All need Authorization: Bearer $TOKEN and share the 300 per minute gateway limit. In the dev stack push is a fake provider: nothing reaches a phone and the server does not check the format of the token (any non-blank string up to 4096 characters is accepted), so you can test the whole API without Firebase.

How registration behaves

  • The FCM token is unique across the platform. Registering a token that already exists moves it to the current user and re-activates it (the case of one phone used by two accounts over time: the new account gets the pushes). It is never delivered to two users.
  • The installation id makes rotation clean. If you send a stable installationId and later register a new token for it, the server replaces the old token on the same device row (verified: the device id stayed the same, and only one device was listed). Without an installation id every new token creates a new row, and the old rows stay until Firebase reports them dead.
  • Idempotent. Calling PUT with the same data again only refreshes lastSeenAt and the descriptive fields (verified: appVersion changed from 1.0.3 to 1.0.4 on the same row).
  • Dead tokens are retired by the server. When Firebase tells the notification service a token no longer works, the row is marked inactive: it disappears from GET /api/v1/me/devices and gets no more pushes. The row is kept for history. If the app registers that token again it becomes active again. The app has no endpoint to deactivate (only to remove).
  • Blocked accounts get no push. A suspended or deleted account is treated as unreachable for delivery.

When the app should call it

MomentCall
Right after sign-in or registrationPUT /api/v1/me/devices with the current FCM token
App start (signed in)PUT again: cheap, refreshes lastSeenAt, app version, OS version and locale
Firebase rotates the token (onTokenRefresh / onNewToken)PUT with the new token and the same installation id
Notification permission granted later (iOS, Android 13+)PUT as soon as you get a token
LogoutPOST /api/v1/me/logout with fcmToken and installationId (removes the device and the session)
"Stop notifications on this device" switchDELETE /api/v1/me/devices with the token or installation id; register again when the person turns it on
Installation id

Generate a random UUID the first time the app runs, store it in app storage and send it with every registration. It survives token rotations but not a reinstall (a new install is a new device). Do not use hardware identifiers (IMEI, advertising id): the server only needs something stable and unique, max 64 characters.

Purpose

Tells the platform "this installation can receive push at this token". Call it after login and whenever the token changes.

Request body

FieldTypeRequiredConstraintsWhy
fcmTokenstringyesnot blank, max 4096where to send the push
platformstring enumyesexactly ANDROID, IOS or WEB; send it upper-case. An unknown value (verified with SYMBIAN) is answered 400 invalid_jsonwhich push channel and format the platform uses
installationIdstringrecommendedmax 64stable id of this install, makes token rotation replace instead of add
appVersionstringoptionalmax 32support and staff diagnostics
osVersionstringoptionalmax 32same
deviceNamestringoptionalmax 100shown in a future "my devices" screen (for example "Pixel 8")
localestringoptionalmax 16device language tag such as am-ET

Blank optional strings are stored as null; values are trimmed.

Example request

curl -s -X PUT "$GATEWAY/api/v1/me/devices" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"fcmToken":"<fcm token>","platform":"ANDROID","installationId":"a1b2c3d4-0000-4000-8000-doc000000001","appVersion":"1.0.3","osVersion":"Android 15","deviceName":"Pixel 8","locale":"am-ET"}'

Purpose

Deletes the user's device row that matches the token and/or the installation id, so it receives no more pushes. Only your own devices can be removed (the match includes your user id). Removing something that is not there is not an error.

Gotcha

Some HTTP libraries refuse to send a body with DELETE. If yours does, use POST /api/v1/me/logout (which accepts the same two fields) when signing out, or configure the client to allow a DELETE body.

What logout does to devices

  • POST /api/v1/me/logout with fcmToken and/or installationId deletes the matching device row and revokes the session. This is how the next person using the phone is prevented from receiving the previous user's notifications (verified: after logout the device row was gone and the token was rejected).
  • If you call logout without those fields, the session ends but the device row stays: the phone would still receive the previous user's pushes until it is registered by someone else or Firebase retires the token. Always send them.
  • After logout, delete the local FCM token and ask Firebase for a new one before the next user signs in, so a token is never shared between accounts.
  • "Sign out everywhere else" (DELETE /kratos/sessions) and a staff suspension do not remove other devices' push tokens. Staff suspension makes the account unreachable for delivery, so nothing is sent anyway.
