The free-form extra object

The free-form extra JSON of the profile: merge rules, the 16 KiB size limit, examples and advice.

Overview

extra is a free-form JSON object stored with the profile. It exists so the client team can keep small per-user settings (theme, font size, onboarding steps seen, home-screen order, last chosen city...) without a backend change for every new setting. The server does not interpret it, validate its content, or use it for anything: it only stores it, merges updates into it, and returns it in every profile response.

Not a place for secrets or shared data

extra is plain JSON in the database. No other Adera service (mini apps, partners, notifications) reads it today and staff screens do not show it, but do not store passwords, tokens or other people's data there, and do not use it for anything a mini app must see. It is the user's data and goes where the profile goes.

Rules

RuleDetail
Shapethe top level of extra must be a JSON object. A string, array, number or null as the whole value is rejected: "must be a JSON object (use null values inside it to remove keys)"
Keys and valuesany keys; values may be strings, numbers, booleans, arrays, objects. There is no schema, no depth limit and no limit on the number of keys: only the size limit below. Key order in the answer is not guaranteed (the database does not keep it)
Update semanticsJSON Merge Patch (RFC 7386): the object you send is merged into the stored one. A key with a value sets or replaces it; a nested object merges recursively; a key set to null removes that key; keys you do not mention are kept
Arraysan array is a plain value: it replaces the stored array as a whole (there is no per-element merge)
Removing a subtree{"prefs": null} removes the whole prefs object
Size limit16384 bytes (16 KiB) of serialised JSON, checked twice: on the object you send, and on the merged result. Either failing rejects the whole PATCH and saves nothing. The limit is a server setting (EXTRA_MAX_BYTES, default 16384); ask the backend team before relying on a different value
Where it is sentinside PATCH /api/v1/me, together with other fields if you like: {"language":"am","extra":{...}}. There is no separate endpoint
Readingalways present in the profile as extra; {} when empty
Concurrencyno version check. Keys merge independently, so two devices changing different keys both win; the same key is last-write-wins. Reading, changing and writing the whole object back would erase other devices' keys: send only the keys you changed

Examples (captured)

1. Set values (also changes other profile fields in the same call):

curl -s -X PATCH "$GATEWAY/api/v1/me" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"extra":{"occupation":"nurse","prefs":{"theme":"dark"}}}'
HTTP/1.1 200 OK
{ "...": "profile fields",
  "extra": { "occupation": "nurse", "prefs": { "theme": "dark" } } }

2. Merge: remove one key, add a nested key, keep the sibling:

curl -s -X PATCH "$GATEWAY/api/v1/me" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"extra":{"occupation":null,"prefs":{"font":16}}}'
HTTP/1.1 200 OK
{ "...": "profile fields",
  "extra": { "prefs": { "theme": "dark", "font": 16 } } }

3. Arrays replace: after {"extra":{"tags":["a","b"]}} the stored value is exactly ["a","b"]; sending {"tags":["c"]} later leaves ["c"].

4. Remove several at once: {"extra":{"a":null,"tags":null,"prefs":null}} answered "extra": {}.

5. Not an object:

HTTP/1.1 400 Bad Request

{ "error": "validation_failed",
  "fields": { "extra": "must be a JSON object (use null values inside it to remove keys)" } }

6. Too large in one request (a single 17000-character string):

HTTP/1.1 400 Bad Request

{ "error": "validation_failed", "fields": { "extra": "too large (max 16384 bytes)" } }

7. Each request fits, the result does not: after storing a 9000-character value under a, adding another 9000-character value under b is refused:

HTTP/1.1 400 Bad Request

{ "error": "validation_failed", "fields": { "extra": "too large after merge (max 16384 bytes)" } }

Free the space by removing keys ({"extra":{"a":null}}) and retry.

Design advice for the client

  • Namespace your own keys (ui, onboarding, feature_flags) so independent features do not collide, and keep each value small.
  • Treat unknown keys as data you must preserve: never write back the whole object you read, only the keys you changed.
  • Store a schema version inside it ({"v":1}) if the shape of a value may change.
  • Do not store large blobs (images, long lists): the 16 KiB cap is shared by everything under extra.
  • To drop all your data on a user's request, send null for each top-level key you own.
