Super app: sign-in and account

Everything the super-app client calls to sign a person in and manage their own account, verified against the running dev stack.

Who this is for and what it covers

This guide is for the developers who build the super app (the Adera mobile or web client) and the backend colleagues who support them. It covers everything an end-user client calls to sign in and manage the user's own account: registration and login with a one-time code, the session token, the profile, the free-form extra JSON, the optional location, the avatar, push-notification devices, and logout, plus what the client sees when an account is suspended or deleted. You should be able to build all of it from this guide without reading the code.

It does not cover the mini-app catalog and ratings, the in-app notification inbox, per-app preferences, or anything staff or partners do; those have their own guides. They use the same session token described here.

Base URL, authentication, conventions

TopicDetail
Base URLOne address for everything: the gateway. In the dev stack http://127.0.0.1:9080, written $GATEWAY in all examples. The app never talks to a service directly. Two path prefixes matter here: /kratos/* (sign-in, sessions) and /api/v1/me* (the user's own data)
AuthenticationSign-in calls need no credentials. All /api/v1/me* calls need Authorization: Bearer $TOKEN, where $TOKEN is the session_token returned by the code step. The gateway verifies it on every call and tells the service who the user is; a user id you send is ignored
Content typesJSON requests use Content-Type: application/json; the avatar upload is multipart/form-data. Responses are JSON (except the empty 204s and the HTML 429 page)
NamesAdera's own APIs use camelCase JSON (firstName, avatarUrl); Kratos uses snake_case (session_token, expires_at) and dotted field names in submits (traits.phone_number)
Error shapeAdera services: {"error": "<code>"}, and for validation {"error":"validation_failed","fields":{"<field>":"<message>"}} listing every problem at once. The gateway and Kratos answer differently in some cases: see the Error table
IdsUUIDs (lower-case, hyphenated). The user id equals the Kratos identity id
TimestampsISO-8601 in UTC with a Z, 6 to 9 fractional digits (2026-10-26T10:49:43.643301Z); dates of birth are plain YYYY-MM-DD
Languagesen, am (Amharic), om (Oromo). The profile language decides the language of notifications sent to the user
MarketsET (Ethiopia), US
Paginationnone in these APIs (the device list is small and complete)
Rate limitsper client IP and route at the gateway: submits 10/min, other Kratos calls 120/min, avatar upload 20/min, other profile calls 300/min; over the limit the answer is 429 with an HTML body. Per-recipient code limits: SMS 5/hour, email 10/hour
Request idgateway responses carry X-Request-Id; include it in bug reports
Dev modein the dev stack nothing real is sent: read one-time codes from http://127.0.0.1:8085/dev/messages?to=... (or Mailpit at http://127.0.0.1:8025 for email)

How the pieces fit

  1. The app asks the gateway (APISIX) for a Kratos flow; Kratos asks Adera's notification service to deliver the code by SMS (Twilio) or email (Resend); dev uses a console log and Mailpit.
  2. When the code is right, Kratos creates the identity (the account) and calls a web hook so the user service creates the profile row with the same id, then returns a session_token.
  3. For every /api/v1/me* call the gateway asks the user service to check the token with Kratos and to check the account status, then forwards the call with the verified user id. A suspended or deleted account is refused here.
  4. Avatar images live in private object storage (RustFS, S3 API); the profile hands out short-lived signed links. Device (FCM) tokens are stored by the user service and used by the notification service when a mini app sends a push.
