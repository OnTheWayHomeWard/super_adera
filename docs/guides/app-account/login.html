Login

Sign in with phone or email and password: the flow, the session token, what a wrong password and an unverified account look like, and the guessing protections.

Overview

A returning user signs in with the phone number or email and the password. No code is involved. The answer carries a session_token valid 30 days; the app sends it as Authorization: Bearer ... on every call. Signing in with a code is not available to app users (a code login attempt answers 4000035, "does not exist or has not setup sign in with code").

Call sequence

  1. GET /kratos/self-service/login/api returns a flow id (valid 10 minutes).
  2. POST /kratos/self-service/login?flow=ID with {"method":"password","identifier":"+251903050827","password":"..."}.
  3. 200: store session_token in the platform's secure storage. 400: show the message and let the user retry on the same flow. 403 session_verified_address_required: go to Verification.
  4. Call the API with the token (below).

Wrong password, or unknown phone/email (400)

The two cases answer identically (same message id 4000006, same text), so the answer does not reveal whether an account exists. Real answer for a wrong password; the one for a never-registered number differs only in the ids and timestamps.

Address not verified yet

See Verification: status 403, error.id session_verified_address_required, with a fresh verification flow and code. Note that the check is on the address you signed in with: an account with a verified email and an unverified phone can sign in with the email but not with the phone.

Guessing passwords: what protects an account

Kratos has no account lockout. The brakes are at the gateway only: (a) 10 sign-in submits per minute per IP, and (b) 10 submits per 15 minutes for the same phone/email whatever the IP (the identifier is read from the request body), so rotating IPs does not help against one target. With a 6-character minimum and no complexity rule, a determined attacker can still try about 40 passwords per target per hour, and the limit also lets an attacker block a victim's sign-in for 15 minutes by spamming wrong tries (a denial of service on one account). Not built: lockout with notification, CAPTCHA, device trust, second factor for customers. Behind a real proxy the gateway must see the real client IP (a production checklist item).
