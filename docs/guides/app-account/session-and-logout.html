Session, token storage and logout

The session token: what to store, how to send it, how long it lives, how to renew it, how to sign out, and what the app sees when an account is blocked.

Overview

A successful sign-in returns a session_token. It is an opaque string that stands for one session (one login on one device). The gateway turns it into the user's id on every call, so the app never sends a user id: it sends the token and the server decides who you are.

FactValue
Who issues itOry Kratos, after the code step of registration or login
Lifetime30 days from the moment the code was entered (session.lifespan: 720h); session.expires_at tells the exact instant
Sliding?No. Using the API does not extend it. Only a refresh login (below) or a new login does.
Assurance levelcustomers are always aal1 (one factor: the code)
One per logineach sign-in on each phone is its own session; they are independent and can be listed and revoked

What to store and what to send

  • Store the session_token in the platform's secure storage (iOS Keychain, Android Keystore-backed encrypted storage), never in plain preferences or logs. Also keep session.expires_at and the user id (session.identity.id) if you want to show them without a call.
  • Send Authorization: Bearer <session_token> on every call to /api/v1/.... The scheme word is case-insensitive (bearer worked); a token without the word Bearer gets 401.
  • The alternative header X-Session-Token is accepted by Kratos' own endpoints (/kratos/sessions/whoami answered 200 with it) but not by /api/v1/* (401). Use Authorization: Bearer everywhere to keep it simple.
  • Do not send cookies and do not send an X-User-Id header: the gateway replaces it with the verified id (a forged one was ignored: the call still returned the caller's own profile).
  • Never put the token in a URL or a log line. Signed avatar URLs (see Avatar) are separate and carry no session.
How the gateway checks the token

For every /api/v1/me* call the gateway first asks the user service (GET /internal/auth/verify) who owns the token. The user service asks Kratos whoami, checks the account status, and answers with the user id or a refusal. This is why a stopped Kratos shows up as 503, and why a suspended account is refused even though its Kratos session is still valid.

App start-up and the three answers that matter

On launch, read the stored token and call GET /api/v1/me (it doubles as the session check and loads the profile). React to the status:

StatusBodyMeaningApp action
200profile JSONsession valid, account activecontinue into the app
401empty (Content-Type: text/plain)token missing, malformed, expired, revoked (logout, "sign out everywhere", staff action)delete the stored token, local profile caches and the FCM registration for this user; show the sign-in screen
403{"error":"account_suspended"} or {"error":"account_deleted"}session valid but the account is blocked by staffshow a blocking "account suspended / closed, contact support" screen; offer sign out (see below)
503{"error":"identity_service_unavailable"}the identity service could not be reached; not a statement about your tokenkeep the token, show "try again" and retry with back-off; do not log the user out
429HTML pagetoo many requests from this IP (300 per minute on /api/v1/me*)back off, retry

Never treat a network failure or a 5xx as "logged out". Only a 401 from the gateway means the token is dead.

Session lifetime and renewing a session

A session ends 30 days after login. The app can simply send the person through sign-in again when a call returns 401. To renew without creating a new session, Kratos supports a refresh login: start a login flow with ?refresh=true and the current token, then do the normal code steps. Verified result:

  1. GET /kratos/self-service/login/api?refresh=true with header X-Session-Token: $TOKEN answers 200, flow with "refresh": true.
  2. POST /kratos/self-service/login?flow=ID with the identifier (step 1: code sent) and then with the code (step 2), both with the same X-Session-Token header.
  3. Step 2 answers 200 with the same session_token and the same session id, but authenticated_at and expires_at are now moved 30 days forward (captured: expires_at went from 2026-11-25T10:54:50Z to 2026-11-25T10:55:40Z, authenticated_at to the new time). The old token value keeps working (it is the same token).

Because it costs a code (an SMS), use it sparingly: for instance when the person opens the app inside the last days of the 30 and you want to avoid a surprise logout; otherwise just let a 401 lead to a normal sign-in. Starting a normal login while sending a valid token fails with 400 session_already_available ("you are already logged in ... forget to set ?refresh=true"). A flow created with refresh=true and no session simply behaves like a normal login flow.

Endpoints

POST/api/v1/me/logoutLog out this device (the call the app should use)
Who may call
a signed-in user whose account is not blocked
Auth
Authorization: Bearer $TOKEN (the same token is the one revoked)
Headers
Content-Type: application/json if you send a body
Rate limit
300 per 60 s per IP (route me)
Implemented by
services/user-service/.../auth/LogoutController.java

Purpose

One call that fully signs this phone out: (1) removes this device's push token so the next person who uses the phone does not receive this user's notifications, and (2) revokes the session behind the token. Kratos has no logout hook for native apps, which is why this combined call exists. Prefer it over Kratos' own logout.

Parameters (JSON body, optional)

FieldTypeRequiredConstraintsWhy
fcmTokenstringoptionalmax 4096the FCM token of this device; the matching device row of this user is deleted
installationIdstringoptionalmax 64the app's installation id; the matching device row of this user is deleted. Give at least one of the two to remove a device; both may be given

An empty body, no body, or a body with both fields blank skips the device step and only revokes the session.

Example request

curl -s -X POST "$GATEWAY/api/v1/me/logout" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"fcmToken":"<this device FCM token>","installationId":"a1b2c3d4-0000-4000-8000-doc000000001"}'

Example response

HTTP/1.1 204 No Content

Using it in the app

  • Call it, then in all cases delete the stored token, cached profile and avatar, and the local FCM token (ask Firebase for a fresh one for the next user).
  • Verified: after logout the old token answers 401 on /api/v1/me and on Kratos' whoami; the user's other sessions are unaffected.
  • A device row that is not matched by the given token or installation id stays (for instance one registered without an installation id and logged out without its token).

Gotcha

It signs the other device out of the API but does not remove that device's push token (the other phone does that when it logs out; otherwise the token is retired when FCM reports it dead).

When the account is suspended or deleted

Staff can set an account to SUSPENDED or DELETED in the dashboard (the status is also visible as status in the profile). What the app sees:

SituationWhat the client sees
Staff changes the statusThe dashboard action also revokes all the user's Kratos sessions (code: AdminUserService.setStatus calls revokeSessions), so existing tokens turn into 401 on the next call. Push messages stop: the account is no longer reachable for delivery.
The person signs in againKratos still lets them in (the identity is not deleted) and returns a session. But every call that goes through the gateway's user check is answered 403 with {"error":"account_suspended"} or {"error":"account_deleted"} (the body has Content-Type: text/plain, parse it as JSON anyway). This applies to all /api/v1/me* routes including POST /api/v1/me/logout and the device, avatar and location calls (verified for profile read and update and for logout).
Same session, status changed in the database only403 immediately, while Kratos' own whoami still answers 200 (verified). Always trust the 403 from the API over whoami.
Back to ACTIVEA suspended account can be re-activated by staff; the next sign-in works normally. DELETED is final (staff get 409 user_deleted when they try to change it).

What the app should do on 403: show a blocking screen ("Your account is suspended. Contact support."), stop all background calls, and let the person sign out with DELETE /kratos/self-service/logout/api (the combined logout is refused). Do not retry. The two codes are stable and safe to switch on.
