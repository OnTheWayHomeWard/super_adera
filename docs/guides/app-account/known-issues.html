Known issues and not built yet

Behaviours that can surprise a client developer today, with how to reproduce them, and the list of features that are not built yet.

Overview

Two lists. Known issues are behaviours that exist today and can surprise a client developer; each has a short repro and the advised workaround. Not built yet lists features a client might expect that do not exist; the app must not offer them. Both were checked against the code and the running dev stack on 2026-10-26.

Known issues

#IssueReproWorkaround / effect
1Login reveals whether an account exists. An unknown identifier gets 4000035 "This account does not exist...", a known one gets "code sent". The same text is returned for a malformed identifier.Start a login flow, submit {"method":"code","identifier":"+251977000000"} for a number never registered.Planned fix: one "continue" endpoint that always answers "code sent" (not built). Until then, use the answer only to switch to registration, never to display "this number is (not) registered" text.
2Registering an existing identifier sends a real code, and fails only after the code is typed (4000007).Start a registration flow for a number that already has an account and submit it: answer 1040005 "code sent" and an SMS goes out (verified in the send log).Try login first, then registration (see Registration and login).
3Error shapes are not uniform. Gateway 401 has an empty body; 403 account_* and 503 JSON arrive with Content-Type: text/plain; 429 is HTML; 404, 405 and 415 on /api/v1/me* use the Spring default shape (error is a reason phrase); Kratos has its own shape.curl -i $GATEWAY/api/v1/me (empty 401); curl -i -X DELETE $GATEWAY/api/v1/me -H "Authorization: Bearer $TOKEN" (405 Spring JSON).Branch on the status first (see the Error table).
4The submit rate limit is per source IP. 10 submits per minute shared by every phone behind one carrier NAT or office network; in the dev stack by every developer and test script.Run two sign-ins within a minute from the same machine while others also sign in: the 11th submit gets 429 (HTML).Back off and retry; do not show an error screen. Production needs the real client IP configured at the edge.
5The per-recipient SMS/email limit is silent. After 5 SMS per hour (10 per day) to one number, Kratos still answers "code sent" but nothing is delivered.Request more than 5 login codes for the same number within an hour. Limits come from the notification service settings (LIMIT_SMS_PER_HOUR=5, LIMIT_SMS_PER_DAY=10, LIMIT_EMAIL_PER_HOUR=10, LIMIT_EMAIL_PER_DAY=20); the sixth request was not exercised here.Throttle "resend" in the app (about once a minute) and tell people to wait if the code does not arrive.
6Logout is refused for blocked accounts. A suspended or deleted account gets 403 on POST /api/v1/me/logout, so the push token cannot be removed that way.Suspend a test account, call POST /api/v1/me/logout: 403 account_suspended.Sign out with DELETE /kratos/self-service/logout/api. Push stops anyway because blocked accounts are unreachable for delivery.
7Revoking an unknown session id answers 204. DELETE /kratos/sessions/{id} does not report "not found"; DELETE /kratos/sessions returned count: 1 in a test where no other session was live.DELETE /kratos/sessions/<random uuid> with a valid token gives 204.Do not use the answers as proof of what existed; re-list with GET /kratos/sessions.
8A bad platform value is reported as invalid_json instead of a field message.PUT /api/v1/me/devices with "platform":"SYMBIAN" gives {"error":"invalid_json"}.Send exactly ANDROID, IOS or WEB.
9DELETE /api/v1/me/devices needs a JSON body and answers invalid_json without one; some HTTP libraries cannot send a body with DELETE.curl -X DELETE $GATEWAY/api/v1/me/devices -H "Authorization: Bearer $TOKEN".Allow a body on DELETE, or use POST /api/v1/me/logout when signing out.
10Devices registered without an installation id pile up on every token rotation (one row per token) until Firebase reports the old tokens dead.PUT /devices twice with different tokens and no installationId: GET /devices lists two.Always send a stable installationId.
11Avatar: HEIC and WebP are refused (400 not a supported image); EXIF orientation is not applied and is dropped (not tested with a rotated sample); animated GIF keeps one frame.Upload a WebP file to POST /api/v1/me/avatar.Convert to an upright JPEG on the device before upload.
12market, language and termsAcceptedVersion are self-declared. The user can set market to ET or US regardless of the phone; sending termsAcceptedVersion again refreshes termsAcceptedAt; the server does not know which terms version is current.PATCH /api/v1/me {"market":"US"} succeeds for a +251 phone.Treat them as preferences, not as proof.
13Unsupported Kratos self-service features are reachable. The gateway exposes all of /kratos/self-service/*, including the settings flow (authenticator-app enrolment, changing the email/phone trait). The app does not support them: a customer who enrolled an authenticator app would, per Kratos' behaviour for staff, need a second step the customer app does not implement, and a changed identifier is not copied to the profile. The consequences of enrolling or changing were not tested here.GET /kratos/self-service/settings/api with a customer token returns a settings flow (verified for a throwaway email account).Do not call the settings flow from the app. Backend follow-up: block or wire it.
14Real delivery is not proven. The dev stack uses a console SMS provider, Mailpit and a fake push provider. The Twilio and Resend providers are built but no real message has been sent from this platform yet; Ethiopian SMS routing is unresolved.n/a (dev only)Plan a real-device test with the live allow-list before launch.
15The registration web hook is unauthenticated (internal network only, not routed by the gateway); if it is lost the profile is created on first use. No client impact.n/aNone needed.

Not built yet

Nothing below exists in the APIs or in the apps' reach; do not design screens that assume it.

FeatureState today
Account deletion by the userNo endpoint. Staff can mark an account DELETED (it then refuses all calls and is final), but that does not delete the Kratos identity, anonymise the profile, or remove avatar and device rows. A store-compliant "delete my account" flow (identity, profile, avatar files, device tokens) is planned.
Account linking / changing the phone or emailNo endpoint. A phone account and an email account are two different accounts; a person who signs in with the other identifier gets a new, empty account. Merging two profiles is not built.
"Continue with phone or email" single entry pointNot built (the anti-enumeration endpoint that always answers "code sent"). The client chooses between login and registration itself.
TOTP / second factor for customersNot offered. Authenticator-app codes exist only for dashboard staff; customers are always aal1.
Passwords, social sign-in (Apple, Google), magic linksDisabled/not built: the code method is the only one enabled.
Refresh tokens / silent renewalThere is one opaque token with a fixed 30-day life. The only renewal is a refresh login that needs a new code.
Other users' profiles and avatarsNo endpoint: each user can only read and change their own.
Profile fields beyond the listNo username, bio, address book, multiple locations, location history, or avatar size variants (one 512 px picture).
Data exportNo endpoint to download a user's data.
Marking a device inactive from the clientOnly removal exists; deactivation happens on the server when Firebase reports a token dead.
Per-device notification settings and topicsNot in the device API.
Content moderation of avatarsNot built (re-encoding removes active content, not inappropriate images).
