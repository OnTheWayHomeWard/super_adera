Launch token and user profile

How your mini app learns who opened it, and how your backend reads what that user allowed: the launch token the Adera app gives your page, and the signed profile call.

Overview

When a user opens your mini app, the Adera app loads your registered URL with a short-lived launch token (?launch=<token>). Your backend verifies the token with Adera's public key and learns the user's pseudonymous id for your app. To read anything about the user (name, contact, address) your backend then calls GET /v1/users/{alias}/profile with a signed request. Adera answers with only the fields the user allowed. Nothing personal travels through the browser.

Why this existsA mini app is third-party code. It must not be able to describe its own powers or read data the user did not allow, and a leaked page script must not be able to copy the user's name. The launch token proves who is calling (and only for five minutes); the signed profile call proves it is really your server; and the user's own permission decides what comes back.

The flow

  1. The user taps your mini app. The Adera app calls its backend and gets a launch token (no dialog is shown).
  2. The Adera app opens your URL with ?launch=<token>. Your page sends the token to your own backend.
  3. Your backend verifies the token (below) and now knows sub, the user's id for your app.
  4. If you need the user's name, contact or address, your page asks for the permission through the Adera app's bridge (requestPermission); the user sees the staff-approved sentence and answers.
  5. Your backend calls GET /v1/users/{sub}/profile (signed). If the user allowed the field it is in the answer; if not, you get 403 consent_required and tell your page to ask.

The launch token

An RS256 JWT signed with the same Adera key as every response and callback; the public key is at /.well-known/jwks.json (the kid in the token header names the key). Decoded claims of a real token (DEV):

header   {"alg": "RS256", "typ": "JWT", "kid": "adera-sig-202610"}
claims
{
  "iss": "adera",
  "aud": "4e831b72-a33b-4d93-a7ba-65e19b9dbd0a",
  "sub": "u_p_5496f0de1378750142d148c9ea19b2c9",
  "env": "dev",
  "scopes": [
    "notify.inapp",
    "notify.sms",
    "user.basic"
  ],
  "iat": 1793824051,
  "exp": 1793824351,
  "jti": "d73f34b8-021e-420f-9f57-4fe89757e898"
}
ClaimMeaning and what to check
issAlways adera. Reject anything else.
audYour app's id. Reject a token whose aud is not yours: it was issued for another mini app.
subThe user's pseudonymous id for your app (u_p_...): the id to put in /v1/users/{sub}/profile and in notification requests. Never the real user id.
envdev or prod: the environment that issued it. Reject a token of an environment you are not running in.
scopesThe permissions the user allowed when the app was opened. A hint only: Adera re-checks consent on every data call, so a permission revoked a minute later stops working even with a live token.
iat, expIssued at and expiry, seconds since 1970. The life is five minutes. Reject an expired token; do not keep tokens, ask the Adera app for a new launch.
jtiA random id of this token (you may remember used ones to refuse a replay).

Verify it: runnable examples

Both files are in the examples/ folder. They fetch the JWKS, check alg is RS256 (never accept none or a different algorithm the sender chooses), verify the signature, then check iss, aud, exp and env. Cache the JWKS for an hour in a real service and refetch once when you meet an unknown kid.

# Python (pip install cryptography)
ADERA_BASE=https://api.example ADERA_APP_ID=<your app id> python examples/verify_launch_token.py "$LAUNCH_TOKEN"

# Node.js 18+, no dependencies
ADERA_BASE=https://api.example ADERA_APP_ID=<your app id> node examples/verify-launch-token.js "$LAUNCH_TOKEN"

The profile call

GET/v1/users/{alias}/profileRead what the user allowed (name, contact, address)
Who may call
A mini app's server (partner)
Client path
/v1/users/{alias}/profile through the gateway
Auth
No login. Headers X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature (ADERA-SIG-1, see the Signing page); the signature covers the path with the query string. The caller's IP must be on the app's allowed list and the key must belong to this deployment's environment.
Rate limit
600 per 60 s per client IP
Answers are signed
Yes, like every /v1 answer (errors included).

Purpose

The only way a mini app's backend learns anything about the user. Returns the user's pseudonymous id, the list granted of permissions the user allowed, and ONLY the fields of those permissions: fullName (user.full_name), phone and email (user.contact, each only when the user has one), address (user.address: countryCode, region, city as saved in the profile, never coordinates). Fields the user did not allow are absent, never null, so you cannot tell "no data" from "not allowed" except through granted. Three gates run on every call: your app was granted the capability (403 capability_not_granted), the user said yes (403 consent_required), and the field belongs to that capability. The data never travels through the browser, and each read is logged on our side (who asked, which permissions were released, no values). Your backend can never open a dialog: if a permission is missing, your frontend must ask through the super app.

Request parameters

NameInTypeRequiredConstraintsWhy it exists
aliaspathstringyesu_p_ + 1 to 60 letters, digits or _The user's id for your app: the sub of the launch token.
fieldsquerystringnocomma-separated among user.basic, user.full_name, user.contact, user.addressWhat you NEED. If the user did not allow one of them the answer is 403 consent_required naming it, so your backend knows to send the user back to the frontend permission request. Without it you get whatever is allowed (an empty profile is a normal 200).

Errors

StatusError codeWhen it happens
403consent_requiredThe user did not allow user.basic (for example after Disconnect), or one of the fields you asked for. Body: capability, state (NOT_ASKED, DENIED, BLOCKED).
403capability_not_grantedStaff did not grant your app user.basic or a capability named in fields. Body: capability.
422user_unreachableUnknown alias (or one of another app), deleted or suspended user.
422synthetic_user_not_allowedA u_p_test_* id on a PROD deployment.
400validation_failedBad alias, or fields with a key that is not a profile capability.
403wrong_environment, ip_not_allowed, app_paused...As for every partner call (see the common errors).
401missing_signature and the other signature errorsSee the common errors.

How to use it

  • user.basic is the connection itself: it is reported granted without a dialog until the user disconnects (then 403 consent_required for the whole profile). Opening the app again (launch) reconnects it.
  • In DEV the synthetic users answer too: u_p_test_ok (all allowed, fake data), u_p_test_noconsent / _denied / _blocked (state NOT_ASKED / DENIED / BLOCKED for the non-basic permissions), u_p_test_unreachable (422).
  • Treat the values as personal data: keep only what you need, delete a user's data when you get the user.disconnected callback (Adera will send it; see "Not built yet"), and never log the values.
  • Runnable examples: get_profile.py and get-profile.js in the partner guide's examples/ folder.

Run it: examples

# Python
python examples/get_profile.py "$ALIAS"                       # whatever the user allowed
python examples/get_profile.py "$ALIAS" user.full_name        # I NEED the name: 403 consent_required if it is not allowed

# Node.js
node examples/get-profile.js "$ALIAS" user.full_name

Both use the signing client in the same folder (adera_client.py / adera-client.js), which also verifies Adera's signature on the answer. A real run (seeded app demo-ride, the alias from the token above):

$ python examples/get_profile.py u_p_5496...b2c9
200 {
  "alias": "u_p_5496f0de1378750142d148c9ea19b2c9",
  "granted": [
    "user.basic"
  ]
}

What to do with each answer

AnswerWhat your backend does
200 with granted and fieldsUse only those fields; keep only what you need; never log the values. Absent fields are not allowed (or the user has none): do not treat absence as an error.
403 consent_required, state NOT_ASKEDThe user was never asked. Tell your page to call requestPermission for that capability, then retry.
403 consent_required, state DENIEDThe user said no once. Your page may explain why you need it and ask once more.
403 consent_required, state BLOCKEDThe user said no twice. Do not ask again; show a way to continue without it, or a button that opens the permission settings of the Adera app. Only the user can undo it.
403 consent_required for user.basicThe user disconnected from your app. Delete what you hold about them as agreed in your terms; the user can open the app again.
403 capability_not_grantedAdera staff did not grant your app that capability. Ask Adera; it is not a user problem.
422 user_unreachableUnknown id (or an id of another app), deleted or suspended user. Do not retry.

Not built yet

  • The callbacks user.consent_changed and user.disconnected that tell your server when a user changes a permission or disconnects (until they exist, learn it from the next profile call).
  • The bridge (requestPermission, getPermission, openPermissionSettings, getLocation) is a separate specification for the Adera app team; until it exists, your page cannot trigger the dialog.
