Limits and quotas

How many messages your app may send, how the four limits work, what null and 0 mean, the exact quota_exceeded answer, and the two "soft refusals" a partner must understand: muted users and unreachable users.

Overview

Staff set limits per app and per channel (SMS, EMAIL, IN_APP). They exist to protect users from spam and Adera from cost (SMS costs money), and to cap the damage if a partner's key is stolen or a bug loops. Limits are checked when you send; a request over a limit is refused with 429 quota_exceeded and uses nothing.

The four limits

Limit (as in limit)What it countsResets
max_per_user_per_dayMessages on this channel to one userevery UTC day (00:00 UTC)
max_per_dayMessages on this channel to everybodyevery UTC day
max_distinct_users_per_dayHow many different users received a message on this channel today. A user already messaged today does not count again, so this limit only refuses messages to a user who has not been messaged yet today.every UTC day
max_totalAll messages on this channel, ever (per environment)never (staff must raise it)
  • null means unlimited, 0 means none. A limit set to 0 refuses every message (verified: maxPerDay: 0 gave quota_exceeded with limit: max_per_day on the first request). A limit that is not set (null) is not checked. A channel without any limits row at all is unlimited. Staff turn a limit off by setting it to null or omitting it.
  • Evaluation order when several limits are used up: max_total, then max_per_user_per_day, then max_per_day, then max_distinct_users_per_day. The answer names the first one that would be exceeded.
  • Counted per channel: the SMS limits do not affect email. Which channel a message uses is decided by Adera (channel selection), so an SMS limit can be reached by DIRECT templates only while SMS is the chosen channel.
  • Counted per environment: DEV and PROD have independent counters (the limit values are the same for the app).
  • What counts: every accepted request (202) counts when it is accepted, whatever happens later. A message that ends FAILED or EXPIRED still counted. What does not count: replays, requests refused with any error, and muted-user requests (200 SUPPRESSED). In DEV, synthetic u_p_test_* users do count (observed).
  • Counting is atomic: concurrent requests cannot overshoot a limit.
  • Limits are about your app; the separate gateway rate limit (600 requests per minute per IP) is about requests of any kind.

A refused request is rolled back completely: nothing is stored (GET /v1/notifications/{externalId} gives 404 not_found) and the quota is not used, so you may send the same externalId again later.

What your server should do

  • max_per_user_per_day, max_per_day, max_distinct_users_per_day: do not retry in a loop. Queue the message and try again after 00:00 UTC, or drop it if it is no longer useful. Consider combining several events into one message per user per day: that is the point of the per-user limit.
  • max_total: never resolves by waiting. Ask Adera staff to raise the limit.
  • If you see 429 without the {"error":"quota_exceeded"} body, it is the gateway's per-IP rate limit (600 per minute): slow down.
  • Partners cannot read their limits or their remaining quota through the API; staff can see usage per channel (GET /admin/api/v1/notification/usage?appId=..., fields lifetime, today, distinct_users_today) and set limits (PUT /admin/api/v1/apps/{id}/notification-limits/{channel}, role ADMIN, audit action limit.set, effective within about 15 seconds). Ask staff for your numbers.

Muted users: 200 SUPPRESSED

A user can switch off a channel for your app (in-app, SMS or email) in the Adera app. Respecting that is a product rule, not an error, so Adera does not answer with an error status:

HTTP 200
{
  "notificationId": "f7dad0c0-d9db-4ed6-90a5-ccef62448016",
  "externalId": "doc-x6",
  "status": "SUPPRESSED",
  "channel": "SMS",
  "reason": "recipient_opted_out",
  "environment": "DEV",
  "createdAt": "2026-10-26T10:58:25.167863Z",
  "expiresAt": "2026-10-27T10:58:25.158642Z",
  "completedAt": "2026-10-26T10:58:25.167863Z"
}
  • It is final and already complete: nothing is sent, ever. A callback (if you gave a callbackUrl) follows with "status": "SUPPRESSED".
  • It uses no quota.
  • The channel is the one Adera would have used. A user with a phone and an email who muted SMS for your app is SUPPRESSED for DIRECT templates even though email is not muted: there is no fallback to another channel (verified). Muting in-app does not affect SMS (verified).
  • The mute is also checked at delivery time, so a user who mutes your app after you sent gets a final SUPPRESSED via callback or poll.
  • You cannot read the user's settings, only observe the result. Do not nag around it (for example by resending as another template kind): the user chose this.
  • The same request again is a normal replay (200, "replayed": true, status SUPPRESSED).

Where the user sets it: PUT /api/v1/me/apps/{appId}/preferences with for example {"muteSms": true}, an endpoint of the Adera app's user API (not part of the partner API).

Unreachable users: 422 user_unreachable

HTTP 422
{"error": "user_unreachable"}

Returned when Adera cannot reach the person for any of these reasons, which are deliberately indistinguishable:

  • the id was never issued to your app (never minted, mistyped, or an id from another app),
  • the user deleted their Adera account,
  • the user is suspended by Adera staff,
  • a DIRECT notification for a user with neither a phone number nor an email address,
  • in DEV, the synthetic user u_p_test_unreachable.
Why generic

If the API said "no such user" for one and "deleted" for another, a partner could probe ids to learn who is on Adera, who left, or who was suspended. One answer for all of them leaks nothing. Real demo cases, all 422 {"error":"user_unreachable"}: a suspended user, an id that was never issued, an id issued for another app.

What to do: stop sending to that id, mark the user as "not reachable by Adera" in your records, and do not retry. Never show the user an error that implies a reason.

The same situation appearing after acceptance is the final status UNREACHABLE (statuses), with a reason that is visible to you: user_unreachable, no_phone or no_email.

Not built yet

  • No partner endpoint for reading your own limits or remaining quota; no Retry-After or reset time in the 429 quota_exceeded answer (the reset is always 00:00 UTC for the daily limits).
  • No per-template or per-category limits (the PROMOTIONAL category has no special limit yet).
  • No quota for callbacks.
