Environments, allowed IPs and keys

Which deployment a key works on, which of your servers may call, what has to be set up by Adera staff before your first call, and how to rotate or revoke a key.

Overview

Three things must all be true before a request is accepted, in addition to a valid signature: (1) the key belongs to the environment of the deployment you call, (2) the mini app's status allows calls in that environment, (3) the call comes from a server address registered for that environment. This page explains each, and what you receive from staff.

DEV and PROD

Every Adera deployment is exactly one environment, fixed by its configuration (ADERA_ENV=dev or prod; the notification service and the registry service must agree, otherwise the API answers 503 service_unavailable and logs the mismatch). One deployment never serves both. You therefore have, per mini app, up to two independent sets of setup:

Every notification answer contains "environment": "DEV" or "PROD", so you can assert in your tests which world you are talking to.

403 wrong_environment

Raised when your signature is valid but the key's environment is not the deployment's environment: a ak_prod_... key sent to the dev deployment, or a ak_dev_... key sent to production. It is checked after the signature (so an attacker cannot learn which environment a key belongs to without holding the private key). Fix: use the key id and base URL of the same environment (typically two sets of configuration in your service: ADERA_BASE and ADERA_KEY_ID per environment).

Real example: a PROD key id (registered with the same public key) sent to the DEV deployment:

HTTP 403
{"error": "wrong_environment"}

App status and 403 app_*

The DEV column was verified on the dev stack (DRAFT, PAUSED and KILLED); the PROD column is from the code and could not be exercised there.

PAUSED is a temporary stop staff use while they investigate; KILLED is an emergency stop that only a super admin can undo. The change is effective within about 15 seconds (Adera caches the app configuration). 403 app_not_active is a fallback code that should not occur. The app status is set by staff; you cannot see or change it through this API (the answer codes are the only signal).

Real example on the dev deployment, after staff set the throwaway app to KILLED:

POST /v1/notifications (any request)   -> HTTP 403 {"error": "app_killed"}
GET  /v1/templates                      -> HTTP 403 {"error": "app_killed"}
(the same app set to PAUSED on the dev deployment still answered 202: DEV only refuses KILLED)

Allowed server addresses

Staff register, per environment, a list of IP addresses or ranges (CIDR) from which your server may call (up to 50 entries, IPv4 or IPv6, for example 203.0.113.10, 198.51.100.0/24, 2001:db8::/32). A single address is stored as a /32 (or /128). A request from any other address, or any request while the list is empty, is refused after the signature and status checks with:

HTTP 403
{"error": "ip_not_allowed"}
  • Why: a stolen private key is useless from an attacker's machine. The address list is the second factor.
  • Give staff your egress address: the public IP your requests leave from, not your server's private address. Behind a NAT gateway or a cloud load balancer give the NAT/egress address; for several servers give all of them or the range. Serverless platforms with changing egress addresses need a fixed-egress add-on before they can use this API.
  • How Adera sees your address: the Adera gateway records the TCP peer address of your connection ($remote_addr) and passes it to the service, together with a secret that proves the gateway wrote it. A client-supplied X-Forwarded-For or X-Client-IP is ignored, so you cannot (and need not) set it. In Adera's own dev stack a call from the developer machine arrives from the docker bridge address (for example 172.18.0.1); that is the address staff must register for local tests.
  • Changing the list takes effect within about 15 seconds.
  • Private or loopback addresses are accepted in DEV lists (needed for local testing) and are meaningless in PROD unless your traffic really arrives from such an address.

Real example captured while the throwaway app's DEV list contained only the documentation address 203.0.113.77:

$ python send.py doc-first $ABEBE $JOB
403 {
  "error": "ip_not_allowed"
}

Key lifecycle, seen from the partner side

StepWhoWhat happens
1. GenerateYouopenssl genrsa -out partner.pem 2048, then extract the public key (see Signing). Use a separate key pair per environment. Keep the private key in your secret store.
2. RegisterYou send the public key; staff register itSend the PEM that begins -----BEGIN PUBLIC KEY----- (SPKI, which is what openssl rsa -pubout writes; the older BEGIN RSA PUBLIC KEY format is refused). RSA only, at least 2048 bits. A private key is refused outright. Staff choose the environment and may set an optional expiry date and a label (up to 100 characters). Adera answers with the key id (ak_dev_... or ak_prod_...) and a fingerprint.
3. Verify the fingerprintYouThe fingerprint is the SHA-256 of your public key in DER form, in hex. Check that Adera registered your key and not another one: openssl rsa -pubin -in partner.pub -outform DER | openssl dgst -sha256 must print the same value (verified for the key used on these pages).
4. UseYouSend the key id in X-Adera-Key-Id and sign with the private key.
5. RotateYou and staffAn app can have up to 5 active keys per environment at the same time, so rotation has no downtime: generate a new pair, staff register the new public key, you deploy and switch to the new key id, then staff revoke the old key.
6. Expire or revokeStaff (or the expiry date)An expired or revoked key is refused with 401 key_revoked_or_expired. Revocation is permanent; there is no un-revoke (register a new key). It takes effect within about 15 seconds, because Adera caches key lookups: a revoked key may still work for a few seconds (verified: a request signed with a key revoked a moment earlier was still accepted, and refused 40 seconds later).
Lost or leaked private keyYou tell staff immediatelyStaff revoke it (action key.revoke); register a replacement. Until revoked, an attacker also needs one of your allowed server addresses.

You cannot list, create or revoke keys yourself: there is no partner endpoint for it. Everything in the table that says "staff" is a request to Adera.

Key ids are not secret, but do not publish them either. Errors you may see: 401 unknown_key (typo, or a key id from another deployment's database), 401 key_revoked_or_expired.

What staff set up before your first call Adera staff

A mini app can send nothing until staff have done all of the following in the admin dashboard (admin API /admin/api/v1, role ADMIN or above, staff signed in with the authenticator step). Each action is written to the audit log under the name shown.

Granting also creates default limits for that channel if none exist (see Limits). DENIED or SUSPENDED gives 403 capability_not_granted.

Order for a new partner

Create the app, grant capabilities, register the DEV address list and the DEV key, create templates: the partner can now integrate against DEV while the app is still DRAFT. When the partner is ready, repeat for PROD (PROD address list, PROD key), then set the app LIVE. After each change wait 15 seconds before testing.
