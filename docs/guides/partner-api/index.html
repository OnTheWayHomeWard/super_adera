Mini-app backend API (partner API)

Everything a mini app's server can call on Adera, and everything Adera sends back to it: signed requests, templates, notifications to users, delivery status, signed callbacks, limits and every error code.

Who this is for

  • A mini-app developer (partner engineer): start with the Quick start, then read Signing and Sending notifications. This section is written so that you can be handed the whole folder.
  • Adera developers and the owner: the same pages tell you exactly what a partner sees and what happens behind each answer. Boxes marked Adera staff describe what staff must configure for a partner (keys, addresses, capabilities, limits, templates) and what that changes.
What this API is for

A mini app is a partner service listed inside the Adera app. Its backend can reach an Adera user by SMS, email, or the in-app inbox plus a push notification, using only pseudonymous ids and message templates that Adera staff approved. The partner never sees a phone number or an email address, never writes free text to users, and never picks the channel. That is the whole API today: it is a notification pipe with delivery reports. See what data a mini app gets from Adera today.

AnyoneGET /.well-known/jwks.jsonAdera's public key, to verify responses and callbacksSigning

There are no other partner endpoints. In particular there is no endpoint to create templates, look up users, read user data, or take payments (see not built yet).

Base URLs

DeploymentBase URLKeys that work there
Adera's local dev stackhttp://127.0.0.1:9080 (the gateway)DEV keys (ak_dev_...)
Productionthe public API host Adera tells you when your app goes livePROD keys (ak_prod_...)

Every example in this section uses $ADERA_BASE for the base URL (on Adera's dev stack it equals http://127.0.0.1:9080, written $GATEWAY in Adera's internal notes). Each deployment is exactly one environment: one deployment never serves DEV and PROD at the same time. Details: Environments.

HTTPS

Production traffic must use HTTPS. The dev stack speaks plain HTTP only because it runs on a developer machine. The signature protects integrity and authenticity, not secrecy: the body travels in clear text without TLS.

Authentication in one paragraph

There is no login, no API token and no OAuth. Every request carries three headers (X-Adera-Key-Id, X-Adera-Timestamp, X-Adera-Signature) where the signature is an RS256 signature, made with your private key, over a canonical string that covers the method, path, query, timestamp and a hash of the body. Adera stores only your public key. In addition, the request must come from a server address staff registered for your app in that environment. Adera signs every answer and every callback with its key, published at /.well-known/jwks.json. Full details: Signing.

Conventions

  • Content type: JSON in and out (Content-Type: application/json), UTF-8. Body limit: 64 KiB.
  • Error shape: {"error": "<code>"}, plus details for some codes: fields (validation_failed, param_invalid: an object {"fieldName": "what is wrong"}), limit and channel (quota_exceeded), capability (capability_not_granted). Always branch on the HTTP status and the error code, never on the text of a fields message. The full list is in Error codes.
  • Timestamps in answers: ISO-8601 in UTC with fractional seconds, for example 2026-10-26T10:52:46.960692Z. The X-Adera-Timestamp header is different: whole unix seconds.
  • Ids: notificationId and template id are UUIDs generated by Adera. externalId is yours (1 to 100 characters from A-Z a-z 0-9 . _ : -). User ids are u_p_... strings.
  • Languages: en, am (Amharic), om (Afaan Oromo). The user's language is chosen by the user in the Adera app; you never send a language.
  • Pagination: none. GET /v1/templates returns the whole array (an app has a handful of templates). There is no list-notifications endpoint: you look a notification up by your own externalId.
  • Gateway rate limit: 600 requests per 60 seconds per client IP on /v1/* (and 120 per 60 seconds on the JWKS route). Answers carry X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset. Over the limit the gateway answers 429 with its own body, not signed and not in the {"error": ...} shape. This is separate from the per-app quotas, whose 429 is quota_exceeded.
  • Every answer of the API is signed, its {"error": code} errors included. Not signed: gateway answers (rate limit, outage) and the framework's own 404 (unknown path), 405 (wrong method) and 415 (wrong content type).
  • Caching on Adera's side: Adera caches your key and your app configuration (status, capabilities, limits, allowed addresses) for about 15 seconds. After staff change something, or after a key is revoked, allow up to 15 seconds before the API reflects it.

Glossary

TermMeaning
Super appThe Adera mobile/web app that end users install.
Mini appA partner service listed inside the super app. Its server is "you" in this section.
PartnerThe company or team behind a mini app.
StaffAdera employees using the admin dashboard. Only staff create mini apps, register keys and addresses, grant capabilities, set limits and write templates.
Environment (DEV / PROD)Which world a deployment and a key belong to. A DEV key works only on a DEV deployment, a PROD key only on a PROD deployment.
Key idThe public identifier staff give you for a registered public key, for example ak_dev_b05f96cc4740e2a118a55282. Sent as X-Adera-Key-Id.
ADERA-SIG-1The name and version of the request signing scheme (RS256 over a canonical string).
JWKSJSON Web Key Set: Adera's public signing key in a standard format, at /.well-known/jwks.json.
Pseudonymous user idThe u_p_... id that stands for one Adera user inside one mini app. See User ids.
TemplateAn approved message with named placeholders, owned by one app. You send a template id and the placeholder values, never free text.
ParamA declared placeholder value of a template (name, maximum length, required, whether links are allowed).
CapabilityA permission staff grant to an app, for example notify.sms, notify.email, notify.inapp. Without it the matching channel is refused.
ChannelHow a message reaches the user: SMS, EMAIL, IN_APP (inbox plus push). Chosen by Adera, not by you.
KindA template's delivery family: DIRECT (SMS, else email) or IN_APP.
externalIdYour own unique id for one notification request. Makes sending idempotent and is the key for polling.
CallbackA signed HTTP POST from Adera to your callbackUrl when a notification reaches a final status.
QuotaA per-app, per-channel cap staff set (per user per day, per day, distinct users per day, lifetime total).
Muted / suppressedThe user switched off a channel for your app in the Adera app. The request is answered 200 with status SUPPRESSED.
Synthetic userA fake user id starting with u_p_test_ that exists only in DEV, for testing without real people.

How this section was verified

Every request and response shown was captured on 2026-10-26 from Adera's running dev stack, through the gateway, using a throwaway mini app (created and deleted for this guide), real seeded demo users, and the three signing implementations printed in Signing (Python, Node.js 22, curl with openssl). Personal data is masked. Behaviour that could not be reproduced on the dev stack is marked from the code, not reproduced.
