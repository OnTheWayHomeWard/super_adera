Behaviour that surprised us while verifying this guide (with how to reproduce it), design limits you should know about, and the list of things that do not exist yet.

Known issues and sharp edges

All were observed on the dev stack on 2026-10-26 unless marked "from the code".

#WhatReproduceImpact and advice
1Fixed 2026-10-26: a bad callbackUrl is now refused when you send the request. The shape is checked at once (scheme must be https, no credentials, port 443 or 8443 only, and an IP-address host must be public) and a bad value answers 400 validation_failed with fields.callbackUrl. The host name is still resolved only when the callback is sent, so a name that points at a private address is refused then: the callback is marked failed on Adera's side and not retried.Send "callbackUrl": "https://user:pw@example.com/hook": 400 (verified live). A host name that resolves to a private address cannot be shown on the dev stack, which allows private callbacks; from the code.Check the 400 answer when you register your callback URL. Poll the status endpoint if you cannot receive callbacks.
2Callback retry window is about 2 hours, not "about a day". Eight attempts with delays of 1, 2, 4, 8, 16, 32 and 64 minutes (127 minutes in total, before +-10% jitter); the 6-hour cap is never reached. The Javadoc of the callback worker and the older internal partner notes say "about a day".Observed delays 57 s and 132 s for the first two retries; the arithmetic follows from the code (RetryPolicy.callbackDelay, 8 attempts).A partner endpoint that is down for more than about two hours loses the callback for good. Poll as a safety net. Either correct the comment or lengthen the schedule.
3The framework's 404, 405 and 415 answers under /v1/ are not signed and not in the {"error": code} shape (Spring's default body with timestamp, status, error, path).GET /v1/nothing (404), DELETE /v1/notifications/x (405), POST /v1/notifications without Content-Type (415): no X-Adera-Signature header.A client that insists on a verified signature for every answer will reject these. They only happen on caller bugs. Suggested fix: make the signing filter cover the error dispatch and give these a JSON error code.
4A revoked key still works for up to ~15 seconds (accepted trade-off, decided 2026-10-26: the 15 s cache stays) (caches of 15 s for key and app configuration). The same delay applies to changes of status, capabilities, limits and allowed addresses.Revoke a key, immediately send a request signed with it: 202; 40 s later: 401 key_revoked_or_expired.Design trade-off. Do not rely on instant revocation; for a leaked key also rely on the address list.
5No replay protection inside the 5-minute window. There is no nonce. A captured signed request can be sent again until its timestamp is 5 minutes old.Send the same signed GET twice: both 200. For POST /v1/notifications a second copy is a harmless 200 replay (same externalId).Low impact because of the idempotency key and the address check. Use HTTPS.
6Fixed 2026-10-26: template changes are now audited. Creating a template writes template.create and editing, activating, deactivating or expiring one writes template.update (target type template, target id the template id; the entry records the staff id, role, client address and, for edits, which fields changed). If the audit entry cannot be written the change is undone and the call answers 503 audit_unavailable.Create or edit a template, then read the audit log (verified live).None needed.
7Template text changes apply to messages already queued. The text is rendered at delivery time from the current template, not from the version current at acceptance.From the code (DeliveryService.deliver reads the template by id).An edit in the middle of a campaign changes the text of the messages still waiting. Create a new template for a different message.
8Quota detail field channel is not in the older partner notes. quota_exceeded carries limit and channel; the internal partner notes list only limit.Any 429 quota_exceeded answer.Documentation drift only; this guide is correct.
9The "links not allowed in params" check is a heuristic and over-blocks. A value such as Hana.co (a name that ends like a domain) is refused.Template job-accepted, {"name": "Hana.co"}: 422 param_invalid, "links are not allowed in this value"; Dr. Smith and 12.5 pass.Ask staff to allow links for such a param or sanitize values before sending.
10externalIds never expire. Notification rows (and therefore the idempotency record) are kept; there is no clean-up job.From the code (no purge job).Reusing an externalId months later gives 200 replayed or 409. Make ids unique over time. Table growth is Adera's problem.
11Muted-user callbacks can arrive before the 200. The callback for SUPPRESSED is queued in the same transaction as the answer.Send to a muted user with a callbackUrl: the notification's createdAt and completedAt are identical, because it was completed at the door, and the callback is queued at that moment (it arrives within a couple of seconds).Design for callbacks arriving before you stored the response.
12Fixed 2026-10-26: the alias-minting endpoint now checks that the app exists. POST /internal/aliases asks registry-service; an unknown app id is 404 not_found, a registry outage is 503 service_unavailable. Any status counts (DRAFT, PAUSED too) so DEV integration works before an app is LIVE.Mint with a random appId: 404, no row created.Fixed (internal endpoint, secret-protected).

Limits by design

  • One notification goes to one user. There is no batch endpoint and no "send to everyone who opened my app".
  • No channel choice, no free text, no attachments, no per-message language: all by design (templates).
  • SENT means "accepted by the provider", not "read" (statuses).
  • Delivery is at-least-once; very rarely a message may be sent twice after a crash at the wrong moment.
  • Callbacks are best effort for about two hours (issue 2); the status endpoint is the source of truth.

Not built yet

These do not exist today. Nothing in this section describes them as working.

  • Frontend bridge: the Adera app opening a mini app, per-user consent, and handing the mini app a user id and data. Consequence: a partner cannot obtain real user ids by itself (User ids).
  • Any user data for partners: name, phone, email, address, location, avatar, language, payments (data available). The capabilities user.*, location.*, pay.request exist in the catalog but have no effect.
  • Partner self-service: creating or editing templates, registering or revoking keys, setting addresses or reading limits and usage. All of these are staff actions.
  • Listing endpoints: no list of your notifications, no search, no cancel or retry endpoint, no endpoint to replay a callback.
  • Batch sending and broadcast to all users of an app.
  • Delivery receipts from handsets, email open or click tracking.
  • Quota reporting to the partner (remaining quota, reset time, Retry-After).
  • A published rotation procedure for Adera's own signing key and a JWKS with more than one key (today one key; select by kid and refetch on an unknown kid).
  • Simulating provider failures in DEV (RETRYING, FAILED) with a synthetic user, synthetic users that go by email or speak Amharic.
  • Webhooks other than notification.status (for example user mute changes, account deletion).
  • Per-category rules: PROMOTIONAL templates have no special limits, quiet hours or opt-in yet.
