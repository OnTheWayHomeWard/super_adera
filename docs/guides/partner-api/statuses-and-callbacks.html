Statuses, retries and callbacks

What happens to a notification after 202: the statuses and what each means, how retries and expiry work, how to poll, and the signed callback Adera sends you when the notification is finished.

Overview

Delivery is done by background workers. A notification starts as QUEUED, is picked up within about a second, and ends in exactly one final status. You learn the final status in two ways: Adera calls your callbackUrl, or you poll GET /v1/notifications/{externalId}. Use the callback as the main path and polling as a safety net.

What SENT means

SENT means the provider accepted the message (the SMS gateway, the mail server, or for IN_APP the inbox entry was written and pushes were attempted). Adera does not track handset delivery receipts, email opens, or whether the user read the inbox entry. Do not tell your own user "delivered"; say "sent".

Final statuses carry completedAt. FAILED, UNREACHABLE, SUPPRESSED and EXPIRED never change again. Treat any status string you do not know as non-final until it is one you do (the list may grow).

How the rarer statuses were reproduced

The dev providers (console SMS, local mail catcher, fake push) never fail, so EXPIRED and UNREACHABLE were produced by editing the throwaway notification rows in the dev database (moving the deadline into the past, pointing a row at a suspended user, pointing an email notification at a phone-only user) and letting the real worker process them; the answers and callbacks below are what the real worker produced. RETRYING and FAILED need a failing provider and are described from the code.

Errors

StatuserrorWhen

How to poll

  • Poll only when you must: after the callback is overdue. A sensible schedule is 5 s, 15 s, 1 min, then every few minutes until a final status or until expiresAt has passed.
  • An externalId that contains characters outside A-Z a-z 0-9 . _ : - cannot have been accepted; the path uses it as is, so no encoding is needed for valid ids.
  • The createdAt/expiresAt/completedAt values are UTC.

Retries, backoff and expiry

WhatRule
Permanent errorsIf the provider rejects the request itself (HTTP 4xx except 408 and 429: an invalid number, an invalid address, a rejected sender) the notification is FAILED at once and never retried.
Temporary errorsTimeouts, 5xx, 429, network errors, or Adera's own user directory being down: status RETRYING and a new attempt later.
BackoffAfter attempt n fails, wait 30 s x 2^(n-1): 30 s, 1 min, 2 min, 4 min, 8 min, 16 min, 32 min, capped at 1 hour, each randomly shifted by +-10% so a burst of failures does not retry in lockstep.
Maximum attempts8. After the 8th failure: FAILED with reason max_attempts:<last error>. The seven waits add up to about 64 minutes, so a notification that keeps failing ends within roughly an hour regardless of ttlSeconds.
ExpiryWhen the next retry would fall after expiresAt (or a notification is picked up after it), it becomes EXPIRED instead. A short ttlSeconds therefore means fewer retries: with ttlSeconds: 60, one retry after 30 s and then EXPIRED. Pick it to match how long the message is still useful.
Re-checks at deliveryBefore every attempt Adera re-reads the user (still active? phone/email still present? still not muted?). A user who muted your app after you sent gets SUPPRESSED; a deleted user gets UNREACHABLE.
At least onceDelivery is at-least-once: if an Adera worker crashes after the provider accepted a message but before it was recorded, the claim expires after 60 seconds and the message may be sent a second time. This is rare; the alternative (never retrying after a crash) would lose messages.
PushFor IN_APP the inbox entry is written first and is idempotent per notification (a retry never shows it twice). Push is best effort: a token that Firebase reports as unregistered is retired, a transient push failure is recorded but does not fail the notification. A user with no registered device still gets the inbox entry, and the notification is SENT.

Callbacks: Adera calls you

Why callbacks

Delivery takes seconds to hours. A callback tells your server the moment a notification is finished, so you can update your own records (for example, offer the user another way to reach them if it ended FAILED or UNREACHABLE) without polling.

When: once per notification, when it reaches a final status (SENT, FAILED, UNREACHABLE, SUPPRESSED, EXPIRED), if you gave a callbackUrl. There are no callbacks for QUEUED, PROCESSING or RETRYING. A request answered 200 SUPPRESSED (muted user) also produces a callback, and it can reach your server before you have processed the 200. Not sent for: replays, requests refused with an error, notifications without callbackUrl.

  • The order of keys in the JSON is not fixed and spaces may appear after : and ,. Never re-serialize before verifying: verify the raw bytes, then parse. Ignore fields you do not know (more may be added).
  • The signed path is the path plus query of your callback URL exactly as Adera sent it (/adera/hook?src=capture above). If a proxy in front of your app rewrites the path, verify with the path as Adera sent it.
  • Timestamps are fresh (signed when sent, also on retries), so apply the same 5-minute tolerance you apply to your own clock.

What your endpoint must do

  1. Read the raw body. Verify the signature (reject with 401 if it is wrong: Adera retries, so a wrong rejection only delays, but never accept an unverified callback).
  2. De-duplicate on Idempotency-Key (and apply updates in a way that is harmless if repeated, e.g. "set status to SENT" rather than "add one").
  3. Answer any 2xx quickly (Adera waits at most 8 seconds, connecting 5 seconds). Do slow work after answering. The response body is ignored.

Callback retries

SituationWhat Adera does
You answer 2xxDone.
Anything else (non-2xx, redirect, timeout, connection error)Retries with backoff: after a failed attempt wait 1 min, 2 min, 4 min, 8 min, 16 min, 32 min, 1 h, 2 h, then every 4 h, each wait up to 10 % shorter (jitter), for 24 hours after the callback was queued (the last retry falls exactly at the 24 h mark; at most 15 attempts, 14 in practice), then it is FAILED. Nominal retry times after the first attempt: +1 min, +3, +7, +15, +31, +1 h 03, +2 h 03, +4 h 03, +8 h 03, +12 h 03, +16 h 03, +20 h 03, +24 h. No failure is retried sooner than 30 seconds. A Retry-After header (seconds or an HTTP date) on a failing answer can make a wait longer, never shorter, and at most 4 h. Answer 2xx as soon as you have stored the event; use the Idempotency-Key to de-duplicate.
URL refused by Adera's address rulesFailed at once, no retry (see callback URL rules).
All attempts failedThe callback is given up on. The notification itself is unaffected: poll GET /v1/notifications/{externalId} to learn its status. Adera has no replay endpoint for callbacks.

Ready-to-run callback receivers

Both verify the signature with Adera's public key, de-duplicate on Idempotency-Key and answer 204. They use the client files from Signing. Python (examples/callback_receiver.py):

"""A callback endpoint: verifies Adera's signature, de-duplicates on Idempotency-Key, answers 2xx.
Run: ADERA_BASE=... ADERA_KEY_ID=x ADERA_PRIVATE_KEY_FILE=... python callback_receiver.py 8099"""
import json, sys
from http.server import BaseHTTPRequestHandler, HTTPServer
from adera_client import verify_callback

seen = set()          # use a database or cache with expiry in production


class Hook(BaseHTTPRequestHandler):
    def do_POST(self):
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        try:
            verify_callback(self.path, raw, self.headers)       # self.path = path + query exactly as received
        except Exception as e:
            print("REJECTED:", e); self.send_response(401); self.end_headers(); return
        key = self.headers["Idempotency-Key"]
        if key in seen:
            print("duplicate delivery ignored", key)
        else:
            seen.add(key)
            event = json.loads(raw)
            print("callback", self.headers["X-Adera-Event"], json.dumps(event))
        self.send_response(204); self.end_headers()          # any 2xx means "received"

    def log_message(self, *a):
        pass


HTTPServer(("0.0.0.0", int(sys.argv[1])), Hook).serve_forever()

Node.js (examples/callback-receiver.js):

// A callback endpoint: verifies Adera's signature, de-duplicates on Idempotency-Key, answers 2xx.
// Run: ADERA_BASE=... ADERA_KEY_ID=x ADERA_PRIVATE_KEY_FILE=... node callback-receiver.js 8098
const http = require("node:http");
const { verifyCallback } = require("./adera-client");

const seen = new Set(); // use a database or cache with expiry in production

http.createServer((req, res) => {
  const chunks = [];
  req.on("data", (c) => chunks.push(c));
  req.on("end", async () => {
    const raw = Buffer.concat(chunks);                       // the raw bytes: verify BEFORE parsing
    try {
      await verifyCallback(req.url, raw, req.headers);       // req.url = path + query exactly as received
    } catch (e) {
      console.log("REJECTED:", e.message);
      res.writeHead(401).end();
      return;
    }
    const key = req.headers["idempotency-key"];
    if (seen.has(key)) console.log("duplicate delivery ignored", key);
    else { seen.add(key); console.log("callback", req.headers["x-adera-event"], raw.toString()); }
    res.writeHead(204).end();                                // any 2xx means "received"
  });
}).listen(Number(process.argv[2]), "0.0.0.0");

Test locally

On Adera's dev stack the receiver can run on your laptop: pass callbackUrl: "http://<your-lan-or-docker-bridge-ip>:8099/adera/hook". Production requires public https; to test that path, expose your receiver through a TLS tunnel or a staging host.
