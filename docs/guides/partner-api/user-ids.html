Pseudonymous user ids

How Adera identifies a user to your mini app without telling you who they are: what the u_p_... id is, why it is different in every mini app, and how a partner obtains one today (it cannot yet).

Overview

You never address a person by phone number, email address or Adera account id. You address them by their pseudonymous id for your app, a string like u_p_639f130c5885168c50d6eecf129cf633. You send it as userId in POST /v1/notifications. Adera looks up which person it stands for, reads their phone, email, language and mute settings on its side, and delivers.

Why it exists

Privacy and blast-radius control. If a partner's database leaks, the ids in it cannot be linked to a person, to the same person's id in another mini app, or to Adera's own records. A partner also cannot build a contact list: it can only reach users who opened its app, one template at a time.

What it looks like

  • u_p_ followed by 32 lowercase hexadecimal characters (the first 128 bits of an HMAC-SHA256 computed with a secret only Adera holds over the user id and the app id).
  • When you send an id, Adera accepts the pattern u_p_ plus 1 to 60 letters, digits or underscores (so that the synthetic test ids u_p_test_... fit). Anything else is 400 validation_failed on field userId.
  • Treat it as an opaque string: do not parse it, do not assume the length, store it as text.

Properties

PropertyWhat it means for you
Per appThe same user has a different id in every mini app, because the app id goes into the computation. The id from one mini app does not work in another: Adera looks ids up per app, so another app's id is unknown to yours (422 user_unreachable). Verified on the dev stack: one demo user got u_p_639f130c... for the throwaway app and u_p_fe2b3855... for another app id.
StableIt is deterministic: the same user in the same app always has the same id, minting it twice returns the same value (verified). Store it as your user key for that person.
Not reversible by youOnly Adera's table maps it back to a person. You cannot derive an id from a phone number, and you cannot find a phone number from an id.
Exists only after it was issuedAn id that was never issued is indistinguishable from a deleted user: 422 user_unreachable (verified with u_p_00000000000000000000000000000000).
Active users onlyIf the person is later suspended or deletes their Adera account, the id still exists but every request answers 422 user_unreachable, and notifications already accepted end as UNREACHABLE. The API deliberately does not say which of "unknown", "suspended" or "deleted" it is, so it cannot be used to find out who is on Adera.
Personal data on your sideIt does not identify a person to outsiders, but together with your own records it identifies a person to you. Protect it like any user id.

How a partner obtains an id today

Internal only today

There is no partner-facing way to obtain a u_p_... id yet. The mechanism that is meant to give you one, the frontend bridge (the Adera app telling your mini app who opened it, with the user's consent), is not built. Today an id is created only by an internal Adera call that is not reachable through the gateway. Until the bridge exists, ids reach a partner only because Adera staff or developers hand them over for test users.

What exists today, verified:

  • Issuing (internal): POST /internal/aliases on the user service with header X-Internal-Secret and body {"appId": "<app uuid>", "userId": "<adera user uuid>"} answers {"alias": "u_p_..."}. It is idempotent. It answers 401 {"error":"unauthorized"} without the secret and 404 {"error":"not_found"} when the user does not exist. Called through the public gateway it is not routed at all (404 {"error_msg":"404 Route Not Found"}), so a partner cannot reach it. The appId is not checked against the registry.
  • Resolving (internal): the notification service resolves an id back to a user with GET /internal/aliases/resolve, for each notification you send.
  • Real exchange on the dev stack (secret not shown): 
    POST http://127.0.0.1:8086/internal/aliases      (user service, dev port, X-Internal-Secret: ***)
{"appId": "e50fd74c-8d27-4e2b-bc34-02678e06d243", "userId": "c3b1c779-3459-480a-a0c9-b34f37b8fb61"}

200 {"alias": "u_p_639f130c5885168c50d6eecf129cf633"}
(second call, same inputs)    200 {"alias": "u_p_639f130c5885168c50d6eecf129cf633"}
(other appId, same user)      200 {"alias": "u_p_fe2b38554ec0ffde1ae5203adf6e6c8f"}
(no secret)                   401 {"error": "unauthorized"}
(through the gateway)         404 {"error_msg": "404 Route Not Found"}
(user id that does not exist) 404 {"error": "not_found"}

Adera staff To test a partner integration against DEV with real (seeded) users, a developer mints the ids for chosen test users with the call above and gives them to the partner; or the partner uses the synthetic ids u_p_test_* that need no minting (Sandbox). There is no endpoint in the dashboard API to mint or look up aliases.

What the user controls

A user can mute your app per channel in the Adera app (mute in-app, mute SMS, mute email, stored per user and per app). A muted channel makes your request answer 200 SUPPRESSED; see muted users. You cannot read the setting; you only see its effect.

Not built yet

  • The frontend bridge that hands a mini app the user's id when they open it (with consent). Until then partners have no way to learn ids on their own.
  • A partner-facing lookup of any kind (id to profile, phone to id). By design there is no phone-to-id lookup; whether a consented profile lookup will exist is not decided here.
  • A way to learn that an id's user has been deleted other than the generic 422 user_unreachable or a final UNREACHABLE status.
